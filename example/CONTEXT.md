# example/ — runnable demos + paper experiment scripts

## Intent
Ten flat, standalone scripts that show how to assemble an EvoGP run end-to-end: build a `Problem`, build a `GenerateDescriptor`, build a `GeneticProgramming` algorithm, hand both to `StandardPipeline`, call `.run()`.
Four of them (`uci_sr.py`, `custom_sr.py`, `uci_classifier.py`, `brax_task.py`) are the exact scripts the EvoGP paper (arXiv 2501.17168) used for its experiments (see README → "Experiments in Paper"); the other six are demos / task integrations.
This directory is documentation-by-example: it is the reference for wiring the public API, and the place to copy from when writing new experiments.
There are no subdirectories, no `__init__.py` (not a package), no shared helpers, and no test harness.
Each file carries a module docstring stating what it demonstrates, the exact run command, its external requirements and its expected runtime / outcome.

## How to run
There is no build step: evaluation runs through the external `evoxc` package (`evogp.tree.evoxc_engine`), so `import evogp` works from a plain checkout — no CUDA/HIP toolchain, no compiled extension.
Run from the **repo root** (`./imgs/...` and `data/...` paths in the scripts are CWD-relative) with the project venv and the `evoxc` sibling checkout on the path; no `python`/`python3` on `PATH` has torch:
`PYTHONPATH=src:/root/evoxc <venv>/bin/python example/<file>.py`
Every file still runs its whole experiment at import time — there are no `if __name__ == "__main__"` guards and no `def main()`, so importing a file executes the full run.
Every run still needs a **CUDA-visible device**: everything above the engine hard-codes `device="cuda"` (`check_tensor` relocates CPU tensors to cuda, descriptor tensors, `randint`, the algorithm operators, the problem data). The engine itself is device-agnostic, so only it can be exercised CPU-only.
Recommended environment for every run:
- `EVOXC_DISABLE_LOCATIONS=1` — evoxc's tracing-only speed knob (locations are debug metadata, never part of the compiled program or the cache key, so the fitness trajectory is unchanged); it speeds tracing up ~4x and is the recommended setting for real runs.
- `EVOGP_EVAL_MODE=auto|dense|specialized` — route override; the default `auto` is dense+iree from pop 64 on a device box and specialized+numpy below that, on CPU or on any fallback.
- `EVOGP_EVOXC_BACKEND=iree` (+ `EVOGP_EVOXC_DEVICE=<visible gpu index>`, `EVOGP_EVOXC_OPT_LEVEL=O0|O1`) — opt-in accelerated execution instead of the default `"numpy"` reference interpreter; the compile target follows the evoxc `Device` kind (`cuda` on CUDA boxes, `rocm` on ROCm boxes).
- `EVOGP_EVOXC_CACHE_SIZE=<n>` — size of the in-memory per-structure compile cache (default 4096 entries).
- `EVOGP_EVOXC_ARTIFACT_DIR=<dir>` — opt-in on-disk artifact cache, default off: a repeated structure reloads in ~0.16 s instead of paying a ~3.1–6.5 s compile, which is what makes a repeated whole run fast.

- `transformer.py` → `Transformation(dataset="diabetes")` feature-construction task; the only file that drives evolution manually (`algorithm.step(fitness)` / `problem.evaluate(forest)` in a loop) instead of `StandardPipeline`, then scores the augmented data with a Ridge regressor.
- `mjx_task.py` → `MujocoProblem("SwimmerSwimmer6", max_episode_length=1000)`, the MuJoCo-Playground counterpart of `brax_task.py`; stopped by the same environment boundary (see the status table and Known Issues).

## Hard-coded settings a re-runner must know
RNG: seeding happens at the top of the file, before the `evogp` imports; `custom_sr.py` / `uci_sr.py` / `uci_classifier.py` use `seed = 1`, `regressor.py` / `classifier.py` / `transformer.py` / `brax_task.py` / `mjx_task.py` / `combined_sr.py` use `0`, and `basic.py` sets no seed at all (its final fitness varies within ≈ -0.23…-0.25).
Budget / population: `generation_limit=100` everywhere and 100 manual steps in `transformer.py`; `pop_size` is 50 (`basic.py`), 100 (`custom_sr.py`, `uci_sr.py`, `uci_classifier.py`, `combined_sr.py`), 200 (`regressor.py`) and 1000 (`classifier.py`, `transformer.py`, `brax_task.py`, `mjx_task.py`).
`regressor.py` is the only demo whose GP settings were cut for the per-structure engine — its original numbers (pop 1000 × 300 generations, `max_tree_len=128`, `max_layer_cnt=7`) measured 35–44 s **per generation**, i.e. ≈3 h, so it runs pop 200 × 100 generations with `max_tree_len=64` in ≈16 s on the default route (≈5 min measured previously on the specialized numpy backend). The other demos keep their original populations, which only partly fit a smoke budget at pop 1000 × 100 generations: ≈9 min for `transformer.py`, beyond 15 min for `classifier.py`. The paper scripts (`uci_*`, `custom_sr.py`, `brax_task.py`, `mjx_task.py`) keep their published settings.
`GenerateDescriptor`: `max_tree_len` 32–512, `max_layer_cnt` 4–9 (mutation always uses `descriptor.update(max_layer_cnt=3or4)`; note `max_tree_len >= 2**max_layer_cnt - 1` is asserted for the binary function sets, which is why `regressor.py` uses `max_layer_cnt=6` with `max_tree_len=64`), `using_funcs=["+","-","*","/"]` in the demos and the RL scripts and `["+","-","*","/","sin","cos","tan"]` in the three UCI/custom scripts, `const_samples=[-1,0,1]` for demos vs `const_range=[-5,5], sample_cnt=10000` for the UCI/custom scripts (`brax_task.py` / `mjx_task.py` use `const_range=[-1,1], sample_cnt=100`), `layer_leaf_prob=0.3` (UCI/custom) / `0` (`regressor.py`) / the `0.2` default elsewhere.
Operators: `DefaultCrossover()` in all ten; `DefaultMutation(mutation_rate=0.2, descriptor=descriptor.update(max_layer_cnt=3))` alone in `basic.py` / `transformer.py`, wrapped in `CombinedMutation([..., DeleteMutation(mutation_rate=0.8)])` in `regressor.py` / `classifier.py` / `brax_task.py` / `mjx_task.py`, with `DefaultSelection(survival_rate=0.3, elite_rate=0.01)` as selection in all six; the UCI/custom scripts use `DefaultMutation(0.1)` + `TournamentSelection(tournament_size=20, survivor_rate=0.5, elite_rate=0.1)`; `combined_sr.py` uses `CombinedDefaultCrossover()` + `CombinedDefaultMutation(0.2, descriptors=descriptor.update(max_layer_cnt=3))` + `DefaultSelection`; `enable_pareto_front=True` only in `basic.py` and `classifier.py` (a Pareto front needs `algorithm.forest.max_tree_len`/`input_len`/`output_len`, which only a plain `Forest` has).
`StandardPipeline(..., is_show_details=True)` (also the default) is passed explicitly by the experiment scripts and prints per-generation fitness stats to stdout.
`SymbolicRegression.execute_mode` is left at the `"auto"` default everywhere; all five accepted strings now route to the same engine path (see "Engine-induced, user-visible changes").
The `func` callable contract for `SymbolicRegression(func=...)`: it is `torch.vmap`-ed over the data dimension, so it receives a 1-D `Tensor[num_inputs]` and must return a Tensor reshapeable to `(1,)` (see `func` in `regressor.py`).

## The multi-part (`CombinedForest`) path — `combined_sr.py`
`CombinedForest` models a multi-part program instead of a multi-output tree: every named variable of the model gets its own sub-forest over its own named inputs, described by `data_info = {"out_name": ["in_name", ...]}`, and the model itself is a plain Python loss function.
Supported call shape (what `combined_sr.py` uses):
- `CombinedForest.random_generate(pop_size=, data_info=, descriptors=)` — one `GenerateDescriptor` per output name (a single one is replicated); asserted `descriptor.input_len == len(data_info[name])` and `descriptor.output_len == 1`.
- The problem is `CustomLoss(existing_data: dict, loss_func)`, re-exported from `evogp.problem` (its definition lives in `evogp.problem.custom_loss`; `combined_sr.py` uses `from evogp.problem import CustomLoss`). `loss_func`'s signature is split by `inspect_function`: the first `len(existing_data)` parameters must be exactly the keys of `existing_data` (shared data), the rest receive the sub-forest outputs, so the signature is `loss(<existing keys in any order>, <output names in data_info order>)`; `torch.vmap` maps over the forest outputs (`in_dims` `None`×len(existing_data) + `0`×rest) and the function must reduce to one scalar per individual (`.mean()` / `.sum()`), otherwise the returned fitness is not `(pop_size,)`.
- `pipeline.run()` returns a `CombinedTree`; `best.A.to_sympy_expr()` works per component (the components are set as attributes named after the `data_info` keys), and the composed expression is written by hand from those sympy expressions.
- Prediction in `combined_sr.py`: `best.to_combined_forest().batch_forward(data)` with **1-D** per-name tensors (one value per XOR row) returns `{output_name: (pop, N, 1)}`, so the first individual's predictions are `res[0, :, 0]`.
- `SymbolicRegression.evaluate` deliberately raises `NotImplementedError` for a `CombinedForest`; `CustomLoss` is the only supported route.
- Dict-input contract of the three entry points (`CombinedTree.forward`, `CombinedForest.forward`, `CombinedForest.batch_forward`): every name required by `data_info` may be a Python/NumPy scalar number, a 0-D tensor, a 1-D `(K,)` tensor or a 2-D `(K, 1)` column (the two column forms are equivalent); all required names must agree on `K`; values are never broadcast; keys that `data_info` does not require are ignored completely — which is how `CustomLoss` hands its `existing_data` (data + target) to the same containers. A missing name, `ndim > 2`, a 2-D second dimension other than 1, an empty value, a `K` disagreement, or a `K > 1` value reaching `CombinedForest.forward` (its single-point mode) raise `ValueError` naming the offending key, its shape and the sub-forest that needs it. Return shapes: `CombinedTree.forward` → `{out: (out_len,)}` for `K == 1` and `{out: (K, out_len)}` for `K > 1`; `CombinedForest.forward` → `{out: (pop, out_len)}` (that one point replicated across the population); `CombinedForest.batch_forward` → `{out: (pop, K, out_len)}`.

## Public API contract exercised (all 10 scripts)
Skeleton: `problem = <Problem>(...)` → `GenerateDescriptor(...)` → `Forest.random_generate(pop_size=, descriptor=)` → `GeneticProgramming(initial_forest=, crossover=, mutation=, selection=, enable_pareto_front=)` → `StandardPipeline(algorithm, problem, generation_limit=, is_show_details=)` → `pipeline.run()`.
Load-bearing symbols and call shapes:
- `Forest.random_generate(pop_size=, descriptor=)` in 9 scripts (all but `combined_sr.py`); `CombinedForest.random_generate(pop_size=, data_info=, descriptors=)` in `combined_sr.py`.
- `GenerateDescriptor(...)` params used: `max_tree_len`, `input_len=problem.problem_dim`, `output_len=problem.solution_dim`, `using_funcs`, `max_layer_cnt`, `const_samples` | `const_range`+`sample_cnt`, `layer_leaf_prob`; `descriptor.update(max_layer_cnt=...)` returns a new descriptor and also mutates the receiver's stored params.
- Operators: `DefaultCrossover()`, `DefaultMutation(mutation_rate=, descriptor=)`, `DeleteMutation(mutation_rate=)`, `CombinedMutation([...])`, `TournamentSelection(tournament_size=, survivor_rate=, elite_rate=)`, `DefaultSelection(survival_rate=, elite_rate=)`, `CombinedDefaultCrossover()`, `CombinedDefaultMutation(mutation_rate=, descriptors=)`; `DiversityCrossover` is only imported (commented-out ablation knob).
- Algorithm/pipeline: `algorithm.forest`, `algorithm.step(fitness)` (`transformer.py` only), `algorithm.pareto_front` (only when `enable_pareto_front=True`, i.e. `basic.py` / `classifier.py`), `pipeline.run()` → best-ever `Tree`/`CombinedTree`, `pipeline.fitness` (final-generation CPU snapshot, `custom_sr.py` / `uci_sr.py`), `pipeline.algorithm.forest.batch_subtree_size[:, 0]` (per-tree node count, same two scripts).
- Returned `Tree`: `best.forward(x)` (`basic.py`), `best.to_sympy_expr()` (`basic.py`, `regressor.py`, `classifier.py`, `combined_sr.py`), `best.to_png(path)` (`classifier.py`, needs the optional `pygraphviz` plus the graphviz `dot` binary).
- `Classification(datapoints=..., labels=...)` (1-D contiguous class indices starting at 0) vs `Classification(dataset="iris", multi_output=True)` (sklearn loader, labels built from `labels.max() + 1`); `Transformation` implements neither `problem_dim` nor `solution_dim`, so `transformer.py` passes `input_len=10` / `output_len=1` by hand.
- Multi-output (`output_len > 1`): reached by `classifier.py` (iris → 3 classes) and `uci_classifier.py` (one output per class; the forest is a plain `Forest`, not a `CombinedForest`, and accuracy is softmax+argmax over `output_len`), and by `brax_task.py` / `mjx_task.py` (`env.action_size`).
No example references `tree/evoxc_engine.py` or `tree/dense_engine.py` directly; the engine coupling visible in this directory is limited to `device="cuda"` tensor creation, `torch.cuda.manual_seed` / `torch.cuda.synchronize` (`transformer.py`), the `execute_mode` string, and the `EVOGP_EVOXC_*` / `EVOXC_DISABLE_LOCATIONS` environment variables documented above.

## Engine-induced, user-visible changes
- **No compiled extension, no build step**: the four `.cu` kernels are gone; `import evogp.tree` works from a checkout (the only engine requirement is that `evoxc` is importable). `pip install . --no-build-isolation` still installs the package, but nothing needs a CUDA/HIP toolchain.
- **Evaluation is a true jit over evoxc, with two selectable routes**: `auto` (the default) takes the dense all-ops graph + iree from pop 64 on a device box, and the per-structure route (every distinct tree structure decoded and compiled once, `EVOGP_EVOXC_CACHE_SIZE` default 4096) on numpy below that threshold, on a CPU box, or on any fallback. `EVOGP_EVAL_MODE=dense|specialized` forces one route; a fresh random population on the per-structure route is a cold compile per individual, which is why the demos' populations were right-sized.
- **Backend is env-selectable**: default `"numpy"` (CPU reference interpreter, bit-exact model of the old kernels' semantics); `EVOGP_EVOXC_BACKEND=iree` (with `EVOGP_EVOXC_DEVICE`, `EVOGP_EVOXC_OPT_LEVEL=O0|O1`, target following the evoxc `Device` kind: `cuda` or `rocm`) is the accelerated path.
- **`EVOXC_DISABLE_LOCATIONS=1`** drops evoxc's per-op call-site capture: ~4x faster tracing, no effect on the computed fitness.
- **An opt-in disk layer exists for repeat runs**: `EVOGP_EVOXC_ARTIFACT_DIR=<dir>` (default off) stores compiled artifacts so a later process reloads a structure in ~0.16 s instead of paying a ~3.1–6.5 s compile.
- **`execute_mode` is API-compatibility only**: `"torch"`, `"hybrid parallel"`, `"data parallel"`, `"tree parallel"`, `"auto"` are still validated and accepted by `SymbolicRegression` (and `Tree`/`Forest.SR_fitness`), but all five now produce bit-identical fitness — the old `kernel_type` dispatch no longer exists, so scripts must not use it to select a code path.
- **`SymbolicRegression` no longer accepts a `CombinedForest`** (`NotImplementedError`): the multi-part route is `evogp.problem.CustomLoss` + the `data_info` dict protocol (see above).
- Sympy rendering, `to_infix` and `to_png` behave as before; `to_png` still needs `pygraphviz` + graphviz `dot`.

## Files written
`classifier.py` writes `./imgs/classifier_tree.png` via `best.to_png(...)` (overwrites a committed asset in `imgs/`; needs the optional `pygraphviz` plus `dot`).

## Constraints for code in this directory
Keep the scripts self-contained and copy-pasteable — no imports from sibling example files, no shared helper module, one script = one complete runnable story.
Keep the module-level convention: seeds and knobs as plain top-level constants set *before* the `evogp`/`torch` imports, because seeding must precede them.
Match the existing public-API surface and keep the file runnable from the repo root; if a script needs a new runtime dependency, document it in the module docstring *and* here (several are optional/undeclared, see below).
External-dependency failures must be self-explanatory: the pattern used here is a module docstring stating the exact requirement plus, where the raw traceback would be opaque, a guarded import / explicit start-up message (`SystemExit`) — `custom_sr.py` (pandas + CSVs), `uci_sr.py` / `uci_classifier.py` (ucimlrepo/pandas + network), `brax_task.py` / `mjx_task.py` (jax + brax/mujoco_playground). Do not mask real library bugs with such guards.

## Known Issues
- **`classifier.py` is slow at its shipped size**: pop 1000 × 100 generations exceeded a 900 s cap on the validation box (it was still inside its generation loop, so this is a budget matter, not a failure). `transformer.py` runs the same population scale through 100 manual steps in ≈536 s; halve `pop_size` or `generation_limit` for a smoke run.
- **`mjx_task.py` was not attempted in the current campaign; measured previously it stopped inside the third-party stack**: `MujocoProblem.__init__` reaches `registry.load(env_name=...)`, which descends `mujoco_playground/_src/registry.py` → `dm_control_suite/__init__.py` → `swimmer.py` → `mujoco/mjx/_src/io.py:575` and raises `AttributeError: type object 'int' has no attribute 'WARP'` (`getattr(mjxw.types.GraphMode, 'WARP')`, because mujoco-warp is not installed). Logged just before it: `Failed to create stream executor for device CUDA:7: CUDA error: : CUDA_ERROR_ECC_UNCORRECTABLE` and `Loaded runtime CuDNN library: 9.1.0 but source was compiled with: 9.8.0` — the same environment problem as `brax_task.py`. Verbatim repro from the repo root: `EVOXC_DISABLE_LOCATIONS=1 PYTHONPATH=src:<evoxc checkout> <venv>/bin/python -c "from evogp.problem import MujocoProblem; MujocoProblem('SwimmerSwimmer6', 1000)"`. Note the example's `except ImportError` guard (`mjx_task.py:40`, catching the jax/mujoco_playground import errors) does not catch this `AttributeError`, so `mjx_task.py` itself surfaces the raw traceback.
- **`brax_task.py` was not attempted in the current campaign; measured previously it failed because jax's CUDA backend is broken in that venv**: `BraxProblem.__init__` → `brax.envs.get_environment("swimmer")` → `brax/io/mjcf.py:528` → jax JIT → `JaxRuntimeError: INTERNAL: RET_CHECK failure (external/xla/xla/service/gpu/gpu_compiler.cc:2798) dnn_support != nullptr`, logged after `Loaded runtime CuDNN library: 9.1.0 but source was compiled with: 9.8.0` and `Failed to create stream executor for device CUDA:7: CUDA_ERROR_ECC_UNCORRECTABLE`. Forcing `JAX_PLATFORMS=cpu` gets past that but then `jax.dlpack.from_dlpack` refuses the CUDA torch tensor (`RuntimeError: Unknown backend cuda`), so the torch↔jax bridge cannot work CPU-only either. Needs a working jax CUDA install; the script's own wiring matches `BraxProblem`'s documented contract.
- **The combined containers differ in return rank by design**: `CombinedTree.forward` strips the population dimension (`{out: (out_len,)}` for a single point, `{out: (K, out_len)}` for a batch) while `CombinedForest.forward` / `batch_forward` keep it (`{out: (pop, out_len)}` / `{out: (pop, K, out_len)}`). `CustomLoss.evaluate` depends on that: it calls `forest.batch_forward(self.existing_data)` and squeezes the trailing axis of each `(pop, K, 1)` output before `torch.vmap` maps over the population. `combined_sr.py` likewise predicts through `best.to_combined_forest().batch_forward(...)[0, :, 0]`; `best.forward(x)` is the pop-free equivalent for one combined individual.
- `combined_sr.py` imports `CustomLoss` from `evogp.problem` (the package re-exports it from `evogp.problem.custom_loss`), and `CustomLoss.inspect_function` requires the loss signature to list the `existing_data` keys first (`inspect_function` also rejects default arguments).
- `classifier.py:60` writes with `best.to_png(...)`, which needs the optional `pygraphviz` plus the graphviz `dot` binary; nothing in `setup.py`/`requirements.txt` installs them (only a commented line in `requirements.txt`).
- `custom_sr.py` / `uci_sr.py` report `mse = -torch.max(pipeline.fitness)` and node statistics from `pipeline.algorithm.forest.batch_subtree_size[:, 0]`, i.e. from the *final* generation's population, not from the best-ever individual (`pipeline.best_fitness` / `pipeline.best_tree`). Treat those printed numbers as end-of-run population snapshots.
- `uci_sr.py` re-reads an int `problem_id` from the top of the file and only special-cases UCI ids 1 (Abalone: `Sex` mapped `M/F/I → 0/1/2`) and 9 (Auto MPG: rows with NaN `horsepower` dropped); any other id with string columns fails at `to_numpy(dtype=np.float32)` — `uci_classifier.py` holds the generic `convert_categoricals_to_int` helper. Both UCI scripts need network access at run time. Neither `ucimlrepo` nor `pandas` is installed in the validation venv, and that venv has no `pip`, so enabling `uci_sr.py` there means bootstrapping pip or otherwise editing the venv, not just `pip install ucimlrepo` (which itself pulls `pandas`).
- Right-sizing note for re-runners: `regressor.py`'s population (200, `max_tree_len=64`, `max_layer_cnt=6`, 100 generations) was cut for the per-structure engine, *not* its CUDA-scale original (pop 1000 × 300 generations × `max_tree_len=128` × `max_layer_cnt=7` ≈ 3 h); `combined_sr.py` was likewise reduced from pop 5000 (hours at 3 sub-forests × 100 generations) to pop 100. With the current default route both run in well under 20 s, so these are conservative settings rather than limits of the engine (see the status table for the measured numbers). The other demos and the paper scripts keep their original populations (see "Hard-coded settings"), and `brax_task.py` / `mjx_task.py` remain pop 1000 × 100 generations of 1000-step episodes, i.e. multi-hour runs even on a working jax install.
- `Transformation` still uses `.squeeze()` with no dimension, never implements `problem_dim`/`solution_dim`, and demeans with the population-wide mean (one NaN/constant tree turns every row's correlation into NaN) — `transformer.py` therefore keeps its hand-written `input_len`/`output_len` and expects some `max_fitness: nan` lines.
- Near-duplicates: `custom_sr.py` ≈ `uci_sr.py` (identical descriptor/algorithm configuration, only the data-loading block differs) and `brax_task.py` ≈ `mjx_task.py`. Editing one of a pair usually means editing the other.
- `uci_sr.py` and `uci_classifier.py` import `CombinedMutation`, `DeleteMutation`, `DiversityCrossover` without using them (the commented-out blocks next to the operator arguments are the paper's ablation knobs, so keep them if you touch those lines).
- Undeclared optional dependencies: `pandas` (`custom_sr.py`, `uci_classifier.py`) and `ucimlrepo` (`uci_sr.py`, `uci_classifier.py`) are in neither `requirements.txt` nor `setup.py`; `pygraphviz` is only a commented line in `requirements.txt` yet `classifier.py` requires it; jax/brax are `extras_require["brax"]` but `mjx_task.py` needs the additional `mujoco_playground` (no extra exists); the engine dependency `evoxc` is not declared in `setup.py` either (it is a sibling-project checkout install).
- `SymbolicRegression.generate_data` has a copy/paste bug in its scalar-bound checks (`if isinstance(upper_bounds, int) or isinstance(lower_bounds, float)`), so a float `upper_bounds` (e.g. `upper_bounds=5.0`) skips the tensor conversion and fails later on `5.0[None, :]`; `regressor.py` deliberately passes ints.
- Timing instrumentation is only whole-run wall clock: `uci_sr.py:113` / `custom_sr.py:125` bracket `pipeline.run()` with `time.time()` and print `During time`, with no `torch.cuda.synchronize()`; `transformer.py:88`/`92` computes per-step `tic`/`toc` under `torch.cuda.synchronize()` but never uses or prints them (the `print` shows only `step` and `max_fitness`). No script uses `time.perf_counter`, `torch.profiler` or a throughput print, and no per-generation timing exists.

## Test Strategy
There is no CI (no `.github/`, no pytest collection) and no test imports these scripts; the pytest suite that guards the engine lives at `../src/evogp/tests/` (see its CONTEXT.md) and the de-facto validation for this directory is running the scripts.
Cheapest checks, in order: (1) `PYTHONPATH=src:<evoxc checkout> <venv>/bin/python -m py_compile example/*.py` (syntax only, no GPU); (2) `PYTHONPATH=src:<evoxc checkout> <venv>/bin/python -m evogp.sr_test` (the README's install validator, ~15.6 s, best fitness ≈ -0.2259, with `EVOXC_DISABLE_LOCATIONS=1`); (3) `EVOXC_DISABLE_LOCATIONS=1 PYTHONPATH=src:<evoxc checkout> <venv>/bin/python example/basic.py` (≈17 s, prints a per-generation fitness line, the tree's predictions and a sympy expression); (4) the same for `example/regressor.py` (≈16 s, the `func=`-generated-data path) and `example/combined_sr.py` (≈19 s, the `CustomLoss` + `CombinedForest` path); (5) `example/transformer.py` (≈536 s) as the slowest run that still fits a smoke budget. Everything else either needs a package/data/download that is absent (see the status table) or exceeds the budget (`classifier.py` at pop 1000) — do not smoke-test pop-1000 runs or the robotics scripts.
Ground truth for "is an example still valid" is the library itself: read the signatures in `../src/evogp/tree/forest.py`, `../src/evogp/tree/combined_forest.py`, `../src/evogp/problem/*.py` (including `custom_loss.py`) and `../src/evogp/pipeline/standard.py` rather than trusting these scripts.
Runtimes in this file were measured with the project venv (python 3.11 + torch, `evoxc` imported from its sibling checkout, scikit-learn present, jax/brax/mujoco_playground importable, **no pandas, no ucimlrepo, no pygraphviz, no genesis**), from the repo root with `PYTHONPATH=src:/root/evoxc` and `EVOXC_DISABLE_LOCATIONS=1`.

## Notes for benchmark-style use
These scripts are demos, not microbenchmarks of `problem.evaluate()`:
- `StandardPipeline` runs with `is_show_details=True` (its default), so every generation prints a fitness block and does a GPU→CPU sync in `step()` (`fitnesses.cpu()`, then argmax/max on CPU); `run()` also prints `Generation limit reached!` at the end. The printed/measured per-generation time wraps the whole generation (`problem.evaluate` + `algorithm.step`), not the raw evaluate call.
- `uci_sr.py` / `custom_sr.py` wrap `pipeline.run()` in `time.time()` (their `During time` covers the full GP loop incl. printing); `basic.py` / `combined_sr.py` / `regressor.py` render sympy only after the run, and `basic.py` additionally prints the Pareto front — none of them isolates evaluation.
- `transformer.py` is the only example that calls `problem.evaluate(forest)` directly (manual `algorithm.step` loop), but it needs `scikit-learn`.
- Datasets inside the demos are tiny (8 XOR rows in `basic.py` / `combined_sr.py`, 100 synthetic points in `regressor.py`, 60 rows in `uci_sr.py` via id 409), so compile cost dominates any data-size effect: a fresh population on the per-structure route is cold cache misses (in-process `EVOGP_EVOXC_CACHE_SIZE`, default 4096) and later generations partly hit, while the default dense route pays one graph per population shape.
