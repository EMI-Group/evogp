# `test/benchmark/evoxc/` — evoxc engine vs plain-PyTorch controlled harness

## Intent
Answer one question with evidence: what does the evoxc-based EvoGP engine cost per evaluation compared with the plain-PyTorch implementation of the same tree evaluation, on identical populations, in the same session, warm/steady-state.
The final campaign widens that question to the post-optimization tree: HEAD against the pre-optimization snapshot `530518e` measured in one window, plus a cold-start column and whole-training-run columns; `FINAL.md` is the report of record.
A second round prices the opt-in `batch` route (`EVOGP_EVAL_MODE=batch`, one merged graph per population structure multiset) against the same arms, on a fixed population and inside a real `StandardPipeline.step()` loop; `BATCH.md` is its report of record.
It is the "new engine vs old torch version" counterpart to `../r4/`/`../r5/`/`../r6/`, which compare the evoxc engine against the deleted legacy CUDA engine; those rounds are frozen history and are never edited from here.
Every arm is validated numerically against `src/evogp/tests/reference_eval.py` before its timings are trusted (`VALIDATION.md`), and every record states the environment, the route that actually resolved, and the cold compile it paid.
A batch-route record also splits one evaluation into ten stages (`stages.py`), so it states where the time went — host decode/dedupe/trace/merge versus lower/compile/load versus upload/run/gather — and not only how much of it there was.

## Contents
- `common.py` — ONE definition of every workload: the cell grid (`main_cells()`/`n64_cells()`/`long_tree_cells()`/`parse_cell`, the long-tree column being `LONG_TREE_LENS = (128, 256)` at `N` = 1024), deterministic `build_workload` (`torch.manual_seed(0)` + `Forest.random_generate`), the `+ - * /` descriptor, `env_block` (git SHA, versions, GPU, knobs), `time_call` (cold call separated from warmup+reps medians), `digest`, `population_signature` (sorted structure-multiset sha256 = the stand-in for the merged-graph cache key), `route_decision` (asks the policy's own `resolve_eval_mode`/`resolve_backend_name`/`should_use_dense`, so a record reports the real decision instead of a re-derivation), `src_root()`/`checkout_root()`. A cell is `cell(pop, tree_len, input_len, rows, max_layer_cnt=5)`: the dict carries the per-cell generation depth cap `max_layer_cnt` and the id gains a `-d<k>` suffix only when it is not 5 (`p256-L128-i32-N1024-d7`), so every pre-existing cell id stays byte-identical; `parse_cell` reads that suffix back (`-d7` → `{"d": "7"}` → `max_layer_cnt=7`, a non-int `d` is a usage `SystemExit`) and `build_workload` defaults its own `max_layer_cnt` argument from the cell (an explicit caller argument still wins). It also single-sources the route knobs: `BATCH_KNOBS`/`BATCH_ENV_VARS` (the seven `EVOGP_BATCH_*` names with their documented defaults), `DENSE_ENV_VARS` (the dense trace cap `EVOGP_DENSE_MAX_TREE_LEN`) and `ROUTE_ENV_VARS = BATCH_ENV_VARS + DENSE_ENV_VARS` (every env var the arms clear before applying their own knob spec), `is_batch_arm`, `batch_engine_present`, `batch_policy` (module present, `mode_supported` from `dense_engine.EVAL_MODES`, per-knob provenance `arm`/`env`/`module`/`harness-default`, never raises) and `batch_route_decision` — `route_decision` dispatches to it for `EVOGP_EVAL_MODE=batch`, which is what keeps `resolve_eval_mode` (it raises on a tree whose `EVAL_MODES` has no `batch`) out of the path. The registry's `evoxc-dense-iree-raised` entry carries a `{tree_len}`-templated knob, so one route covers both the default-cap and the raised-cap cell.
  It also owns the band/merge report of one merged plan: `BAND_REPORT_KEYS` (`bands`, `band_sizes`, `band_strategy`, `cost_estimate`, `flat_estimate`, `n_functions`, `emitted_ops`, `band_count`) and `band_report(plan_or_described, described=None)` — torch-free and getattr-probed, it reads the `describe_plan` mapping AND the plan's own `report` (`merged.batch_report.as_dict()`, the only place `cost_estimate`/`flat_cost_estimate` live, which is why those read `null` unless `EVOGP_BATCH_BANDS=auto` ran the static cost model; `flat_estimate` is the report's `flat_cost_estimate`), keeps a chunked plan's aggregate nulls (`bands`/`band_sizes`/`band_strategy` = `null`) as recorded, and reports `available`/`source`/`note`/`chunk_count`/`report_keys` with every field `null` when neither source carries it — never `0`, never a raise.
- `counter_blocks.py` — the ONE owner of the strict number/block helpers every optional batch-route counter surface shares, torch-free and evogp-free: `number`/`integer`/`rounded`/`delta`/`delta_int`/`median`/`maximum` (a missing or non-numeric value reads `None`, never `0`, and `maximum` skips a `None` instead of fabricating a floor), `has_any(snapshot, keys)`, `accessor(module, name)` (the getattr probe behind every optional accessor, `None` when absent, never a raise), `block(available, stats_fn, note, keys, values)` (one block's `available`/`stats_fn`/`note` envelope around its counter values) and `keys_of(*snapshots)` (the sorted counter names a set of snapshots actually carries, so a record states which counters its tree exposed instead of assuming a schema).
- `stages.py` — the ONE owner of the per-stage cost vocabulary, torch-free and evogp-free: `STAGES` (decode, dedup, trace, merge, lower, compile, load, upload, run, gather, in pipeline order), the counter keys `batch_<stage>_calls` / `_total_ms` / `_max_ms` plus `batch_compile_wall_ms` / `batch_compile_jobs` (the compile pool's own wall time and job count), the optional route contract (`stage_stats_fn`/`stage_reset_fn` getattr-probe `evogp.tree.batch_engine.batch_stage_stats()` / `batch_stage_reset()`, `None` when absent, never a raise), and every derived block: `unavailable_block` (every counter `null` + a note), `snapshot_block` (one post-reset per-call snapshot), `delta_block` (a before -> after window: `calls`/`total_ms`/compile wall+jobs are after-minus-before, `max_ms` stays the AFTER snapshot's process-lifetime maximum because a max is not delta-able), `median_block` (per-call medians over the timed samples + `samples`), `StageStatsProbe` (wraps a callable so each call is reset+snapshot bracketed; `blocks[0]`/`.first` is the untimed call), `plan_fields`/`plan_block` (`describe_plan`'s `compile_workers`/`chunk_count`/`chunk_sizes`) and `stage_totals` (`{stage: total_ms}` off one block) / `summary_block` (`cold_stage_ms`/`warm_stage_ms`/`compile_share`) / `compile_share` (the compile stage's own time over the loop's wall time, `null` when a row cannot tell whether it compiled; that block also STATES what the share divides (`numerator_kind` = `parallel-stage-counter-sum`, `denominator_kind` = `loop-wall-ms`) and whether it exceeded 1 (`share_gt_one`, `None` when there is no share to judge), plus a note when it does, because the numerator SUMS the compile stage's PER-CHUNK timers while the compiled-graph pool runs those chunks CONCURRENTLY — a share above 1 is a concurrency-weighted stage-counter ratio (`p256-L32-i8-N1024` reads 2.3743 = 12440.8 ms over 5239.9 ms at the shipped pool of 4, chunks [57, 56, 56, 56]), not wall-clock attribution). Null, never zero everywhere: an absent accessor, a missing key, a half-read window or a non-numeric value reads `None` (or `available: false`) plus a note, because "this stage took no time" and "this stage was not measured" must never look alike.
- `content.py` — the ONE owner of the content-addressed plan-key vocabulary and of every block derived from it, torch-free and evogp-free: `STATS_FN_PATH` (`evogp.tree.batch_engine.batch_content_stats`) and its five counters `batch_content_hits` / `_misses` / `_rejects` / `_entries` / `_maxsize` (`DELTA_KEYS` are the running totals, `ENTRIES_KEY`/`MAXSIZE_KEY` are table gauges that a block carries as the AFTER snapshot's value because a gauge is not delta-able), `stats_fn` (the getattr probe, `None` when absent) and the blocks `unavailable_block` / `snapshot_block` / `delta_block` (hits/misses/rejects after-minus-before, `entries`/`maxsize` as the AFTER gauge), `derived` / `window_block` (`attempts` = hits + misses — how often the content key was consulted at all — and `hit_rate` = hits/attempts, both `None` when there was no attempt, because a `0` rate would claim a miss the identity fast path never made), `row_state` (`hit` / `miss` / `no_attempt` / `unknown`, read off the RECORDED row) and `summary_block` (the window plus `generations` outcome counts `rows` / `with_content_hit` / `with_content_miss` / `no_attempt` / `unknown`). An absent accessor records `available: false` with every counter `null` and a note naming the missing function, never a fabricated `0`, because "the content table served nothing" and "there is no content table" must not look alike.
- `arms_torch.py` — the two pure-torch baselines: `PerTreeEvaluator` (Python tree walk, torch ops per node) and `BatchedEvaluator` (one vectorized pass over the population, per-position masked `torch.where`, per-row child gather). Op semantics are copied from the oracle.
- `arms.py` — the arm namespace: `TorchArm`/`EvoxcArm`, `resolve_knob_value` (`{tree_len}`/`{pop}`/`{input_len}`/`{rows}` substituted from a cell dict; literal values returned unchanged; `ValueError` naming the arm and the placeholder when a template has no cell or an unknown placeholder), `apply_arm_env(arm, cell=None)` (`EVOGP_EVAL_MODE`/`EVOGP_EVOXC_BACKEND` per arm, plus the optional `knobs` mapping a spec may carry, applied RESOLVED into `env.applied_knobs`; it clears every `common.ROUTE_ENV_VARS` entry first for EVERY arm so a route knob — `EVOGP_BATCH_*` or `EVOGP_DENSE_MAX_TREE_LEN` — can never leak between arms), `make_arm`, `SRLossProblem` + `make_pipeline` for the GP generation step; `evoxc-auto` leaves both knobs unset so it times the shipped policy itself, and `evoxc-auto-iree` only differs from it below the dense threshold (specialized+iree instead of specialized+numpy).
- `worker.py` — ONE process, ONE `(cell, arm)`: cold call, warmup, reps, cache deltas, value digests, `gp_step` split into eval/operator, per-workload `first_call_ms`, `structures.structure_signature`. Honors `--tree-root`. It passes the cell dict into `apply_arm_env` (so a templated knob resolves) and records `dense_policy.max_tree_len_cap` (the cap this process ran with, from `dense_engine.MAX_TREE_LEN_ENV` else `DEFAULT_MAX_TREE_LEN`) next to `auto_min_pop`/`auto_max_rows`; for an explicit-`EVOGP_EVAL_MODE=dense` non-batch arm it adds `dense_route` (`max_tree_len_cap`, `tree_len_max`, `supported`, `reason`, `probe_ms` — a direct `dense_engine.sr_fitness_dense` probe run AFTER all timed workloads, so it is a memo hit when dense served the cell and an immediate `DenseUnsupported` raise when the cap declined it). For a batch arm it adds `batch_policy` and `batch_cache` (merged-graph cache counters, `stats_keys` naming the counters the route exposes, `available: false` + nulls when the tree exposes no `batch_cache_stats`; the compile deltas are read off `batch_exec_misses` — the exec table, a hit never reaches `evoxc.lower`/`compile`/`load` — via `batch_miss_key`, with `batch_plan_misses` recorded alongside through `batch_plan_miss_key`), extra per-workload `cache.batch_*` deltas and per-`gp_step` `batch_compile_misses` / `batch_plan_misses`, `batch_plans` (`batch_engine.describe_plan` of each `BATCH_PLAN_MEMO` entry, deduped by `(variant, per_row)`) and `batch_plan_summary` (per variant: `emitted_ops`, `band_count`, `band_sizes`, `band_strategy`, `n_functions`, `functions`, `row_index_collisions`, `pop_size`, `input_len`, `output_len`, `per_row`, `backend`, `device` plus the merge-shape fields `compile_workers`/`chunk_count`/`chunk_sizes` from `stages.plan_fields` — a report that predates them reads `null`, never `0`; `available: false` + a note when the memo or `describe_plan` is missing — compile-free introspection, never raises; each variant entry now also carries `band_report` from `common.band_report(plan_object, described_plan)`, an ADDITIVE sub-block, so `band_count`/`band_sizes`/`band_strategy` stay byte-compatible and an older record simply has no `band_report` key). The same batch arm also carries the per-stage split through `stages.py`: `batch_cache.stage_before_workloads` / `stage_after` (the stage snapshots bracketing the whole config, taken where `stats_before_workloads` / `stats_after` are taken), `batch_cache.stage_keys` (the sorted counter names those snapshots actually carry, `[]` when none), `batch_cache.stage_totals` (`stages.delta_block` of that window — per-stage `calls`/`total_ms`/`max_ms` plus `batch_compile_wall_ms`/`batch_compile_jobs` — with its compact `stage_ms` = `{stage: total_ms}` table) and, per `gp_step` step, `gp_step.steps[i].stage_ms` (that step's own before -> after delta, so a recompiling generation says WHERE its compile went). All of it is null-never-zero: a tree without `batch_engine.batch_stage_stats()` records `stage_totals.available: false` with every counter `null` plus a note, never a fabricated `0`. The same batch arm records the content-addressed third counter contract over exactly the span the stage window covers: `batch_cache.content_before_workloads` / `content_after` (the snapshots bracketing the whole config, taken where the stage snapshots are), `batch_cache.content_keys` (the counter names those snapshots actually carry, `[]` when the tree has no content table) and `batch_cache.content_totals` (the `content.py` window block with its `attempts`/`hit_rate` — HEAD reads `{hits 0, misses 3, attempts 3}` because a first call for a new plan shape is an identity miss, one content probe per workload plan, while the warmup+reps calls behind it leave the table untouched at `attempts` 0, not a miss). It refuses to write a record when the imported tree cannot run the route (clear `SystemExit`, campaign status `failed`).
- `campaign.py` — the sequential driver: one subprocess per config, idle-device guard (`rocm-smi --showpids`, excluding the driver's own ancestor chain), `--tree-root`/`--resume`/scope policy, `--cells main|n64|long|<list>`, `--arms all|torch|evoxc|batch|<list>`, per-config `.log` + `campaign.json` with the guard verdict per config and the batch arms' specs (`protocol.batch_arms`, `batch_engine_present`, `batch_route_note`); `--dry-run` is torch-free, prints one `batch policy …` line per selected batch route and one `dense knob <arm> <cell> EVOGP_DENSE_MAX_TREE_LEN=<n>` line per templated knob and cell (plain string formatting from the cell dict, which is why it does not import `arms`). `EVOGP_BATCH_*` reaches the child from the caller's environment, `EVOGP_DENSE_MAX_TREE_LEN` deliberately does not (per-arm provenance, cleared and set by `apply_arm_env`).
- `validate.py` — every arm vs the oracle and vs the engine, three function sets (`arith` bitwise-mandatory, `rich` transcendental spread, `ternary` for the `if` operand order), 12 cases over the four scheduled cells. It does not know the batch route (see Known Issues).
- `decompose.py` — per-call phase breakdown of one cell on both routes (inclusive `perf_counter_ns` timers on the engine's own functions, residual row for host glue, seam counters for dispatches/uploads/readbacks, cold compile separate).
- `summarize.py` — stdlib-only renderer: environment block, per-workload tables (median with min in parentheses), `auto` route per cell, speedup vs both torch arms, the `gp_step` section (total, eval/ops split with the operator share, speedup vs both torch arms, `best_fitness`), cold-compile table, digest agreement, caveats; `gp_step` cells fall back to the upper median of `steps[].total_ms` / `steps[].eval_ms` (marked `*`) when a record lacks the aggregate keys, and `--compare-results DIR --compare-label NAME` adds one before/after ratio table per workload plus one for the `gp_step` total. A route's own `kind` wins over `would_use_dense` (so a batch cell reads `batch/iree → batch (bands=flat, …)`), a `Batch route arms: …` caption appears only when a batch arm is recorded, and a render of a batch-free directory is byte-identical to the pre-batch renderer.
- `check.py` — stdlib-only gate over ONE campaign result directory (`<dir>/<cell>/<arm>.json`): record presence/schema, `len(samples_ms) == reps >= 5`, medians re-derived from samples and `gp_step`'s `median_total_ms` from `steps[].total_ms`, `first_call_ms > 0`, evoxc route + compile-miss fields, `check_batch` for a batch arm (FAIL when `batch_policy.mode_supported` is not true / the recorded route is not `batch` / `batch_cache` has no boolean `available`; WARN-only when the merged-graph compile is not attributed to any counter, or when `batch_cache.stats_keys` carries no `batch_exec_misses`), `check_stages` for a batch arm (WARN-only, silent on every record without stage keys: a block claiming `available: true` over all-null counters, claiming `available: false` over numeric counters, or a `compile_share` without its boolean `available`), `check_content` for a batch arm (WARN-only and deliberately check-count-free, modelled on `check_stages` and silent on every record without content keys: a content block claiming `available: true` over all-null counters, or `available: false` over numeric ones), cross-arm digest agreement, `gp_step` sanity, guard honesty, plus `--allow-snapshot` (a null `env.tree_root_sha` warns instead of failing when the recorded tree root has no `.git`), `--allow-missing` (the 10 unscheduled pop ≥ 256 `evoxc-specialized-iree` cells) and `--allow-digest-mismatch` (the numpy-vs-iree sha256 split); exits 1 on failure. Expected-arm coverage comes from the campaign's OWN scheduled arms, so appending an arm to the registry never breaks a previously recorded campaign.
- `cold_start.py` — the cold-start column: ONE cell and ONE population per process (the in-memory compile cache is per process) from module import to the first synchronized `Forest.SR_fitness` value on the DEFAULT route, with `import_ms`/`workload_build_ms`/`first_call_ms`, `cache_stats()` compile misses before/after the first call and `--repeat` warm-cache repeats; `--cell`, `--pop` (replaces a loop: one process per population), `--tree-root`, `--artifact-dir` drives the opt-in disk layer (`EVOGP_EVOXC_ARTIFACT_DIR`) as two child processes (populate, then reload), `--phase populate|reload` is the internal half selector those children run as, and a tree without `artifact_cache.py` records `artifact_cache: "absent"`.
- `training_run.py` — the end-to-end training-run column: one complete `StandardPipeline`/`GeneticProgramming` run on the in-process `sr_test` symbolic-regression problem (no dataset, no network) with `--arm engine|torch-per-tree|preopt`, `--pop`/`--generations`/`--seed`/`--tree-len`/`--input-len`/`--num-data`/`--report-gens`, per-generation sync-bracketed wall ms plus the full best-fitness trajectory, `best_fitness_at` (gens 10/25/50), the trajectory digest and `final_pop_size` — driven through `pipeline.step()`, i.e. the library's own loop, so the fitness callable is called exactly as the library calls it.
- `batch_economics.py` — the batch route's compile-economics column (stdlib-only driver, one child process per `(cell, route)`): default cells `p256-L32-i8-N1024,p1000-L32-i8-N1024,p1000-L64-i32-N1024`, routes `batch,dense` (`batch-flat` is the third base token; round 2 adds the named composition tokens `batch-banded`, `batch-flat-chunked`, `batch-auto-chunked`, each carrying its own `{"arm", "knobs"}` spec in `ROUTE_SPECS` — `ROUTES` is derived from it, so token → arm cannot drift), `--generations` iterations of a real `StandardPipeline.step()` loop recording per generation the population's `structure_signature` (sampled BEFORE the step, i.e. the population that generation evaluates), `signature_seen_before`, total/eval/ops ms, the compile misses of BOTH caches and `compile_hit`, plus a derived `summary` (`generation_hit_rate`, `generations_with_compile`, `distinct_population_signatures`, `median_warm_eval_ms`/`median_cold_eval_ms`, `first_call_ms`, `warm_median_ms`, `compile_ms_share`); records go to `results/batch/<cell>/<route>.json` + `economics.json`, `--dry-run` is torch-free and warns when the tree has no `evogp/tree/batch_engine.py`, and the driver applies `EVOXC_DISABLE_LOCATIONS=1` by default and records that it did. A batch child also records the per-stage split (`stages.py`): `first_call.stage_ms` (the cold call's before -> after window over decode/dedup/trace/merge/lower/compile/load/upload/run/gather plus the compile pool's wall time and jobs) with `first_call.stage_ms.plan` (`compile_workers`/`chunk_count`/`chunk_sizes`), `sr_fitness.stage_ms` (per-call medians over the timed samples, reset-bracketed when the route ships `batch_stage_reset`, plus `.first_call` and `.plan`), `generations[i].stage_ms` (that generation's delta), and `summary.cold_stage_ms` / `warm_stage_ms` (the `{stage: total_ms}` tables) / `compile_share` (the compile stage's own share of the loop's wall time); `protocol.batch_compile_workers` is the resolved pool width and its `source` (a `harness-default` source means no resolver / unset, never a fabricated value). Every stage read is getattr-probed, so a tree without `batch_stage_stats()` records `available: false`, EVERY counter `null` and a note — never `0`. `--knob NAME=VALUE` (repeatable) is the way to sweep a route knob without registering a new arm: it is validated against `common.ROUTE_ENV_VARS`, applied AFTER `arms.apply_arm_env` cleared and wrote the arm's own spec and BEFORE the policy is resolved, so `batch_policy`, `env.applied_knobs` and the record's own `knobs_override` all carry the value the engine really read — `--knob EVOGP_BATCH_COMPILE_WORKERS=1` and a companion `=4` run (one config each, the knob is per process) is the compiled-graph-pool sweep; an exported `EVOGP_BATCH_COMPILE_WORKERS` is cleared by the arm spec like every other route knob. The content-addressed plan key gets its own blocks on the same rows (`content.py`): `first_call.content`, `sr_fitness.content`, `generations[i].content` and `summary.content` (the five counters plus `attempts`/`hit_rate`, and in the summary the `generations` outcome counts), null-never-zero on a tree without `batch_content_stats()`, next to `generations[i].batch_plan_misses` and the summary's `merged_graph_cache.plan_misses_generations` so a row states the plan table as well as the exec table; `summary.compile_share` states its kinds (`numerator_kind` `parallel-stage-counter-sum`, `denominator_kind` `loop-wall-ms`, `share_gt_one`) and, when the share exceeds 1, the note that it is a concurrency-weighted stage-counter ratio rather than wall-clock attribution. The content-table evidence is `results/batch_opt_round1/content-blocks/{after,base,chunked-p256,worker-after,worker-base}/` (the generation loop on both trees, the cell whose pool really chunks, and the two `worker.py` records). A named route's own env layer is applied by ONE helper the dry run and the child share (`apply_route_env`: `arms.apply_arm_env` clears every `common.ROUTE_ENV_VARS` entry — `EVOGP_BATCH_CHUNK_BANDS` and `EVOGP_DENSE_MAX_TREE_LEN` included — and writes the arm's spec, then the route's spec, then an explicit `--knob`, which therefore wins for the same variable), and `protocol.route_knobs` states per variable the value, the raw `env_value` (`null` = really unset) and the layer that won (`harness-knob` > `route` > `arm` > `env`, else the engine's `module` resolver / `harness-default` / `unset`); `protocol.batch_compile_workers` is its compile-pool row and `protocol.route_spec` names the token's `{"token", "arm", "knobs"}`. Each batch record also carries `common.band_report`'s block for the plan(s) that served it (`band_report.sr_fitness` + every distinct plan under `band_reports` + `band_report_note`): `bands`/`band_sizes`/`band_strategy`, `cost_estimate`/`flat_estimate`, the clamp verdict (`band_requested`, `band_requested_bands`, `band_clamped`, `band_note`, `band_policy`) and a chunked plan's per-body `chunk_bands`, null-never-zero (`available: false` + nulls + a note when no plan can be described), so a composition record states whether the clamp fired and what band counts the banded+chunked merge produced.
- `econ_child.py` — the child-side measurement internals of the economics column, torch-free at import (the caller imports `torch`/`evogp` and passes the engine modules in a `econ_child.Measurement`): `CounterSurfaces` (the route's three optional counter contracts — `batch_cache_stats`, `batch_stage_stats`/`batch_stage_reset`, `batch_content_stats` — resolved once, with the one tolerant delta helper each), `generation_entry` (one row: signature + `signature_seen_before` + total/eval/ops ms + both caches' misses + `compile_hit`), `merged_cache_block`, `band_reports`, `generation_summary` (the unchanged summary formulas) and `measure` (cold call → warm medians → the `StandardPipeline.step()` loop → the record). Splitting it out left `batch_economics.py` the driver (CLI, cell/route resolution, env construction, subprocess launching, `economics.json`); no recorded key or formula changed.
- `reuse_probe.py` — the plan-key reuse workload, one child process per column: a fixed four-call `SEQUENCE` on one cheap cell (`p64-L64-i32-N64`, seed 0, `evoxc-batch-iree`, band 32, pool 4) — A cold, A identity, B rebuilt-but-equal, B identity — where B is a second `Forest` built from the same seed and verified `identical_content` in `no_shared_storage` by `forests.same_content`, evaluated against one shared `x`/`labels` object. Every call records `calls[i].{call_ms, digest, cache.batch.*, content.*, stage_ms.*}` (both counter surfaces before -> after, the value digest, the sync-bracketed wall time and, where the tree ships them, the ten stage CALL counts, so "it skipped trace/merge/compile" is measured rather than inferred) plus `cache_keys` (the counter names each surface exposes, `[]` when absent) and a `verification` block whose every expectation is `true`/`false`/`null` — `null` whenever no counter on that tree could decide it (`rebuilt_call_skips_trace_merge_compile`, `identity_call_leaves_content_untouched`, …). `--tree-root` runs the same sequence against any checkout (the pre-round tree has no content table and records `available: false` with null counters), `--out-dir` defaults to `results/batch_opt_round1/reuse` and refuses `results/final|baseline|batch`, and `--dry-run` prints the planned sequence without importing torch.
- `band_sweep.py` — the WARM band-size sweep of the opt-in batch route (stdlib-only driver, one child process per `(cell, config)`, `--child` is the internal half): default cells `p256-L32-i8-N1024,p256-L64-i32-N1024,p64-L64-i32-N64`, configs `b8,b16,b32,b64,flat` (`b<N>` pins `EVOGP_BATCH_BAND_SIZE=N` and leaves `EVOGP_BATCH_BANDS` unset; `flat` pins `EVOGP_BATCH_BANDS=none` and leaves the band size unset), workloads `sr_fitness,batch_forward,forward` in that FIXED order, `--warmup 1 --reps 5 --seed 0`, `--tree-root src`, `--evoxc-root /tmp/evoxc_r2`, `--out-dir results/batch_opt_round2/warm`, `--timeout`, `--note`, `--resume`, `--dry-run` (torch-free: one line per (cell, config, workload) with the exact env it would set and the resolved band policy).
  Every config also pins `EVOGP_EVAL_MODE=batch`, `EVOGP_EVOXC_BACKEND=iree` and `EVOGP_BATCH_COMPILE_WORKERS=1` — the SINGLE-BODY path, because chunking changes the merge `SHAPE` (one compiled body per chunk with its own band partition) and would confound the band knob with the pool width — and clears every other `common.ROUTE_ENV_VARS` entry, `EVOGP_DENSE_MAX_TREE_LEN` included; `--workers` is therefore asserted to be 1.
  `EVOGP_BATCH_MIN_POP` stays unset (64: `p64-L64-i32-N64` sits exactly ON the floor and must be served, not declined), and the child `PYTHONPATH` is exactly `[<src>, <evoxc-root>, <this node dir>]` — never `/root/evoxc` — with `EVOXC_DISABLE_LOCATIONS=1` defaulted on and its provenance recorded (`batch_economics.disable_locations_provenance`).
  The driver runs ONE child at a time, calls `campaign.guard(--guard-wait)` before each config and records its verdict in the child record and in `<out>/sweep.json` (schema `evogp-bench-evoxc-v1-band-sweep-driver`; per record `evogp-bench-evoxc-v1-band-sweep` at `<out>/<cell>/<config>.json` + a `.log`), so a busy box delays the sweep instead of contaminating it (`--guard-wait 0` only for a deliberate smoke).
  Per workload it records `first_call_ms` (the cold merged-graph compile of that workload's plan), `warmup`/`reps`/`samples_ms`/`median_ms`/`min_ms`/`max_ms`/`mean_ms`, the value `digest`, the merged-graph `cache` deltas (exec + plan table, `stats_keys`, null-never-zero), `stage_ms` (the reset-bracketed per-call median through `stages.StageStatsProbe` + `stages.median_block`, with `.plan` = `stages.plan_block`), `stage_first_call` (the probe's cold block) and `band_report` from `common.band_report` off the plan memo (compile-free; `available: false` + a note when the memo or `describe_plan` is unreachable, never a raise), next to `batch_policy` (the engine's own resolvers, no re-derivation), `cell` (parsed cell dict + `population_signature` + the deduped `n_functions`) and `validation` (keyed by workload: `validate.compare` against `src/evogp/tests/reference_eval.py`, i.e. `max_abs`/`max_rel`/`bitwise_equal`/`nan_mismatch`/`inf_mismatch`/`finite_points` + the oracle digest, so cross-config agreement is checkable).
  A config the route cannot run still writes a record — `status: "failed"` plus `error`/`error_type`/`traceback` and a non-zero exit — and `results/final|baseline|batch|batch_opt_round1` are refused as `--out-dir` (the refusal also covers `--dry-run`).
- `results/` — the evidence: `baseline/` (the earlier round's committed records, frozen and untouched, rendered by `SUMMARY.md`), `final/after/` (130 records at HEAD: the two torch arms plus `evoxc-auto`, `evoxc-auto-iree`, `evoxc-dense-iree`, `evoxc-specialized-numpy` and `evoxc-specialized-iree` on the pop ∈ {16, 64} cells only), `final/before/` (90 records, the same harness against the snapshot `/tmp/evogp_preopt` = commit `530518e` via `--tree-root`, evoxc arms only), `final/{decompose,decompose-before}/` and `final/{cold,training}/` (one-cell / one-run records, their own schema), `final/validation.json` (the 12-case sweep) and `final/RENDERED.md` (the three `summarize.py` renders as plain text).
  `batch/` is the batch-route round: `batch/{warm-r5,small-r5,flat-r5,flat1000-r5,flat1000-3w-r5}/` are the campaign records at the protocol sample count (`--reps 5`, gateable), `batch/{warm,small,flat,flat1000}/` are the same grid measured as the `--reps 3` pilot (kept verbatim, structurally ungateable by `MIN_SAMPLES`), `batch/long-trees/{l128,l256,p1000,gp}/` is the long-tree round (pop 256 at `tree_len` 128 with the generation depth pinned at d5/d6/d7, pop 256 at `tree_len` 256 at d5/d8, pop 1000 at d5, plus the two `gp_step` cells; five arms each, four in `gp`), `batch/<cell>/<route>.json` + `batch/economics.json` are the `batch_economics.py` compile-economics records, `batch/validation-{batch,dense}.json` are the oracle sweeps, and `batch/RENDERED-*.md` + `batch/long-trees/RENDERED-*.md` are the per-directory `summarize.py` renders; the report of record for that round is `BATCH.md`.
  `batch_opt_round1/` is the round-1 chunked-compile / per-stage / reuse round: `base/` is the pre-round tree `619cbf7` via `--tree-root`, `after_{default,w1,w8}/` are the `EVOGP_BATCH_COMPILE_WORKERS` sweep at HEAD, `after_dense/` is the dense comparison column, `campaign/` is the campaign-format gate record, `reuse/{after,after-replay,base}/` are the `reuse_probe.py` sequences (HEAD, the reproducibility column, the pre-round tree), `content-blocks/{after,base,chunked-p256,worker-after,worker-base}/` are the content-table blocks of the economics loop on both trees, of the cell whose pool really chunks, and of two `worker.py` records, `content-blocks/campaign-content/` is the campaign-format gate unit whose batch record carries `batch_cache.content_*` (1 record / 40 checks / 0 failures), and `SUMMARY.md` is the round report (digest in `BATCH.md` §13).
- `FINAL.md` — the report of record for the post-optimization campaign: the arm redefinition, the headline/compare/decomposition tables, cold-start economics, the 50- and 200-generation training runs, numeric validation, the noise audit, the gate and the reproduce block.

- `VALIDATION.md` — numeric validation of the final sweep plus the cross-arm digest-agreement finding and its practical relevance.

## Constraints
- One process per timed config (the engine's compile cache, executable memo and input memo are per-process), and never two timed configs concurrently.
- `cold_start.py` measures one population per process for the same reason: a `pop` loop inside one process would be cold only for its first population (use `--pop` and one process per value).
- `training_run.py` drives `StandardPipeline.step()` instead of `run()` (which is the same loop plus the stopping rules) so each generation is a timed unit; the fitness callable still goes through `problem.evaluate`. Arms share one seed and one problem construction, and speed is only read next to `best_fitness_by_generation`.
- `auto` resolves to dense+iree at `pop >= 64` on a device box and to specialized+numpy below that, on a CPU box, or on any fallback (`EVOGP_DENSE_AUTO_MIN_POP` moves the threshold, `EVOGP_DENSE_AUTO_MAX_ROWS` the rows ceiling), so the `evoxc-auto` arm measures the dense path at pop ≥ 64 and the specialized path at pop 16.
- `before` carries no torch arms by design: the torch baselines are tree-root-independent, so their after values are the reference for both sides.
- The gate of record is per side — `python3 check.py --results results/final/after --allow-snapshot --allow-missing --allow-digest-mismatch` (130 records / 3602 checks) or `--results results/final/before` (90 records / 2642 checks) — because `results/final/cold/` and `results/final/training/` hold a different schema so the container directory is not gateable in one run, and because the 10 unscheduled `evoxc-specialized-iree` cells and the numpy-vs-iree digest split are declared expectations rather than defects.
- Never run anything else that imports torch while a campaign is in flight — the box has one usable device and the numbers are the deliverable.
- Cold compile never sits in the warm numbers: `worker.py` times the first call separately (`first_call_ms`, `cache.compile_misses_first_call`) before the warmup loop.
- `specialized`-iree costs ~272-284 ms of compile per distinct tree structure on this box, so that arm is scoped to `pop ∈ {16, 64}`; the dropped cells are listed in `campaign.json` (`protocol.scope_dropped`) instead of being silently omitted.
- `EVOGP_EVAL_MODE=batch` is the third evaluation route (`evogp/tree/batch_engine.py`): ONE merged graph per population (structure multiset) built on `evoxc.batch_functions`, iree with a numpy fallback like dense, and `auto` never resolves to it. Its knobs are `EVOGP_BATCH_BAND_SIZE` (32 programs per band), `EVOGP_BATCH_BANDS` (an explicit band count K, or `none`/`flat`), `EVOGP_BATCH_SWITCH_OPS` (off), `EVOGP_BATCH_ALIGNMENT` (`variant`), `EVOGP_BATCH_CACHE_SIZE`, `EVOGP_BATCH_MIN_POP` (64 — below it the route declines to `specialized`) and `EVOGP_BATCH_COMPILE_WORKERS` (the compiled-graph pool width, i.e. how many chunk compiles the merge may run at once; it moves the COLD cost, so it is swept with `batch_economics.py --knob EVOGP_BATCH_COMPILE_WORKERS=N` rather than with one arm per value).
- The per-stage split is a SECOND, optional counter contract on the same module (`batch_engine.batch_stage_stats()` / `batch_stage_reset()`), resolved through `stages.stage_stats_fn`/`stage_reset_fn` and recorded as windows (`batch_cache.stage_*` in `worker.py`, `first_call`/`sr_fitness`/`generations[i]`/`summary` stage blocks in `batch_economics.py`). Null, never zero: an absent accessor, a missing key or a half-read window is `None` (or `available: false`) plus a note, and `batch_<stage>_max_ms` is the after snapshot's PROCESS-LIFETIME maximum, not a delta. Without `batch_stage_reset()` every block stays cumulative, which is why the records read before -> after deltas instead of per-call blocks.
- A route knob is swept by `batch_economics.py --knob NAME=VALUE` (validated against `common.ROUTE_ENV_VARS`, applied after `apply_arm_env` and before the policy is resolved, recorded in `knobs_override`), never by exporting the variable — `apply_arm_env` clears every `ROUTE_ENV_VARS` entry first.
- The BAND knob is swept by `band_sweep.py` (one child process per `(cell, config)`, configs `b8|b16|b32|b64|flat`), which is a different question from the pool-width sweep: every config pins `EVOGP_BATCH_COMPILE_WORKERS=1`, so a difference between two configs of a cell is the band partition alone.
The population, the data and the seed are identical across configs, so what two records of one cell must share is the ORACLE deviation (`validation.<workload>.max_abs/max_rel/bitwise_equal`), which is config-independent — measured exactly equal in all five configs of every cell/workload.
Value digests are a weaker witness and split by design: `sr_fitness` is bitwise identical across the banded configs and differs only on the flat merge (1 ulp at `p256-L32`), while `batch_forward`/`forward` form per-config digest groups at ≤5e-11 relative `abs_sum` — the same order as the route's documented non-bitwise `batch_forward` caveat, not a band-size accuracy effect.
- The dense route's trace cap is `EVOGP_DENSE_MAX_TREE_LEN` (`dense_engine.MAX_TREE_LEN_ENV`, default `dense_engine.DEFAULT_MAX_TREE_LEN` = 64): when `tree_len_max > min(EVOGP_DENSE_MAX_TREE_LEN, forest.max_tree_len)` the dense evaluator raises `DenseUnsupported` and the public API falls back to the per-tree `specialized` route — silently. `evoxc-dense-iree` measures that fallback on a long-tree cell, `evoxc-dense-iree-raised` pins the cap to the cell's `{tree_len}` and measures dense itself, and the explicit-dense record's `dense_route` says which happened; the long-tree cells (`--cells long`, `max_tree_len` 128/256) exist to price that fallback against the batch route, whose per-program cost scales with the merge rather than with the cap.
  Tree length has two axes on those cells: the actual node count of the population is `max_layer_cnt`-driven (a full tree is `2 ** d − 1` nodes: seed 0 / pop 64 gives mean/max 15.8/29 at `d=5`, 27.1/57 at `d=6`, 35.5/101 at `d=7`, 69.9/187 at `d=8`), while the dense trace length is `tree_len`-driven (the row stride, and the value the cap is compared against), so a long-tree cell pins both and the `-d<k>` sibling cells separate the two axes.
- A batch arm's large `first_call_ms` and large `compile_misses_first_call` are the measurement, not a defect: the merged graph covers the whole population, so the cold call pays one multi-second-to-minutes compile, which the existing one-untimed-first-call protocol keeps out of the warm medians; `check.py` therefore has no upper bound on either number and only WARNs when the compile is not attributed to any counter.
- The batch arms carry no `campaign.SCOPE` rule: the round measured them on every cell it scheduled, with `--timeout` bounding a runaway config (an overrun is recorded as `status: "timeout"` with its worker log as evidence).
  On the single-executable compile path (`EVOGP_BATCH_COMPILE_WORKERS=1`, the control arm) the measured merged compile is 10.9–12.2 s per workload at pop 256 and 91.0–162.0 s at pop 1000 (91.1 s at p1000-L32-i8-N1024 and 162.0 s at p1000-L64-i32-N1024 in the gateable `results/batch/warm-r5` records, 166.9 s in the `--reps 3` pilot `results/batch/warm`), plus 102.7 s for a flat (K=1) merge at pop 1000.
  The shipped default of 4 chunk compiles (`EVOGP_BATCH_COMPILE_WORKERS`) compiles pop 256 cold in 4.44 s (3.78 s at 7 chunks) against 1.80× the warm call (2.011 → 3.628 ms), and chunking is inert below 32 deduped functions, so the pop-64 cells stay at 2.2–2.9 s per workload.
  `BATCH.md` §13 and `results/batch_opt_round1/SUMMARY.md` carry that round's numbers.
- A timed workload needs `--reps >= 5`: `check.py` enforces `len(samples_ms) == reps >= MIN_SAMPLES` (5), so a `--reps 3` campaign is structurally ungateable and must be reported as a pilot, not as evidence.
- Records are written verbatim: a contaminated or re-run cell is annotated (`--note`, guard block), never smoothed.
- `results/baseline/` and `results/final/**` are frozen evidence; a re-run writes into a fresh result directory, and `../r2/`, `../r4/`, `../r5/`, `../r6/` are never touched from here.
- This subtree is not collected by pytest and is not part of the `src/evogp/tests/` suite.

## Adding a new arm (an additional evaluation route)
Registration is data, not code: an evoxc-style route is one entry in `common.EVOXC_ARMS` carrying `{"eval_mode", "backend", "family"}` plus an optional `"knobs"` mapping (env name -> value, e.g. `evoxc-batch-iree-flat`'s `EVOGP_BATCH_BANDS=flat`, or a per-cell template such as `evoxc-dense-iree-raised`'s `EVOGP_DENSE_MAX_TREE_LEN={tree_len}`), `None` meaning "leave the env var unset".
`common.ALL_ARMS` is derived, so `--arms all|evoxc` and `check.py`'s expected-arm coverage pick it up with no further edit; append new arms LAST, because registry order is the render order used by `summarize.order_arms` and the `auto route` column's fallback.
`arms.apply_arm_env(arm, cell=None)` writes `EVOGP_EVAL_MODE`/`EVOGP_EVOXC_BACKEND` from that spec and then the spec's `knobs`, resolved through `arms.resolve_knob_value` against the cell dict (it clears every `common.ROUTE_ENV_VARS` entry first for every arm, and `KeyError`s on an unregistered name).
Arm methods take no arguments (`getattr(arm_obj, name)()` in `worker.py`), and the object must expose `setup_ms`, `family` and `fitness(forest, report=None)`; a route that needs a different call path needs its own class in `arms.py` (the batch arms do not: they go through the same public `Forest.SR_fitness`/`batch_forward`/`forward`).
`worker.py` reads compile economics through `evoxc_engine.cache_stats()` and, additionally for a batch arm, through `evogp.tree.batch_engine.batch_cache_stats` when that module exposes it — a new route whose counters live elsewhere must be pointed at its own stats callable (null, never 0, when it is missing). The same holds for the per-stage split: a new route's stage accessors are registered in `stages.py` (`STATS_FN_NAME`/`RESET_FN_NAME`, the one owner of the ten-stage vocabulary and of every derived block), and its costs then render as the null-or-measured blocks `worker.py` and `batch_economics.py` already write.
`check.py` treats any arm absent from `TORCH_ARMS` as an evoxc arm, so a new arm is required to record `routes` plus a non-`None` `cache.compile_misses_first_call`, and its `batch_forward`/`forward` sha256 and every workload's `nan`/`finite` counts must match the other arms of the cell (or be declared with `--allow-digest-mismatch`); `campaign.SCOPE` is the only per-arm coverage rule, and the batch arms have none because their round scheduled them explicitly on the cells that matter (`BATCH.md` §6 has the compile numbers a scoping rule would be built from).
A route with extra knobs should route them through `common.BATCH_*`-style single-sourced tables and record its own resolved policy block, the way a batch arm records `batch_policy`; `check_batch` is the model for the checks such a route deserves (mode support + route identity as FAIL, counter attribution as WARN).
A route that only differences its ENV (a band policy, a pool width, the banded+chunked opt-in) needs no new registry arm at all: it is one `ROUTE_SPECS` entry in `batch_economics.py` (`{"arm", "knobs"}` — the spec is validated against `common.ROUTE_ENV_VARS` when the token is resolved, and an explicit `--knob` overrides it for the same variable), and `protocol.route_knobs` then states which layer won.
`summarize.py` renders any record it finds (`order_arms` puts an unregistered arm last), derives the route kind from the record's own `routes[...]kind` when present, and sources the `auto route` column from `evoxc-auto`/`evoxc-auto-iree` first.
`cold_start.py` (default route only, `apply_arm_env("evoxc-auto")`), `training_run.py` (its own `ARMS = ("engine", "torch-per-tree", "preopt")`), `decompose.py` (its own `ROUTES` table, keyed on route name + instrumented phase lists) and `batch_economics.py` (its own `ROUTE_SPECS` table: `batch`/`batch-flat`/`dense` plus round 2's `batch-banded`/`batch-flat-chunked`/`batch-auto-chunked`) do NOT read the arm registry, so a new route needs a separate edit in each to be measured there.

## Known Issues
- The batch route's band size is a first-order knob only through flat-vs-banded: at `EVOGP_BATCH_COMPILE_WORKERS=1` (`results/batch_opt_round2/warm/SUMMARY.md`) a single unbanded merge (K = 1) is 15 % slower on warm `sr_fitness`, 8 % on `batch_forward` and 34 % on the per-row `forward` at the two pop-256 cells (worst column +53 %), and the whole spread among the banded configs (`b8/b16/b32/b64` → K = 29–31/15–16/8/4) is 3–6 %, i.e. at this box's cross-config noise floor (the same-shape `p64` twin b64-vs-flat reads 2.6 %).
  Band size 16 is the minimax setting on both the median- and the min-based estimator (pooled geomean 1.0185 of the per-column argmin, worst column 1.061, against 1.0223/1.137 for the shipped 32 and 1.0415/1.167 for 8), and it is where a `K ≤ 15` policy clamp lands anyway; the shipped 32 gives up 12–14 % on the band-sensitive `forward` at `p256-L32-i8-N1024`.
  The effect lives entirely in the `run` stage (`forward` `run` 0.232 ms at K = 16 vs 0.589 at K = 1) — `upload` and `gather` are band-count-insensitive, and the flat merge's `sr_fitness` `upload` alone doubles at `p256-L64-i32-N1024`; the `p64-L64-i32-N64` cell is inert (all five configs within 6 %).
  The `b16` argmin is a power-of-two grid result on three cells: nothing here bounds `p1000`, `bands=auto` or the banded+chunked composition.
- The batch route is not uniformly dominated: warm `sr_fitness` at pop ≥ 64 on trees that fit the shipped dense cap is 0.37–0.995× of `dense+iree` at pop 256–1000 (need-capped dense wins by 1.05–1.41× at long strides too), its merged compile there is 10.9–12.2 s at pop 256 and 91.0–162.0 s at pop 1000 on the single-executable path (`EVOGP_BATCH_COMPILE_WORKERS=1`) and 4.44 s cold at pop 256 on the shipped 4-worker default, against dense's 3.4–6.5 s, and a generation loop rebuilds the merged graph almost every generation (1 hit in 8, 99.4–99.7 % compile share), so `gp_step` is 193–2355× slower than dense; once the population's longest tree exceeds the default cap of 64 the ordering flips — batch is 1.5–4.2× faster than dense with `EVOGP_DENSE_MAX_TREE_LEN` raised to cover the population and 23.5–25× faster than the cap-64 decline fallback (per-tree `specialized`), but still 190–460× behind dense in a generation loop. Its other win is a fixed population of ~64 trees at N=64 (0.979 ms vs dense 1.41 ms, cold 2.17 s vs 6.18 s), and even there a generation loop loses. `BATCH.md` is the report of record (§11 for the long-tree round), `results/batch/**` the evidence.
- The content-addressed plan key wins only for a rebuilt-but-equal population: at `p64-L64-i32-N64` a second `Forest` built from the same seed evaluates in 2.724 ms against the pre-round tree's 79.109 ms (29.0×, 76.4 ms of host decode + trace + merge removed), with `batch_content_hits` 1 / 0 misses / `hit_rate` 1.0, trace/merge/compile stage calls 0 and a bit-identical answer (sha256 `b6584500…`), while the pre-round tree pays a plan miss and re-decodes + re-traces + re-merges (its exec table already shares the compiled body, so the 76.4 ms is host-side work, never a recompile). In a generation loop it buys nothing — 6 generations at the same cell read 6 attempts / 0 hits, `{rows 6, with_content_hit 0, with_content_miss 5, no_attempt 1}` — because a generation presents new programs every step, so the rebuilt-object regime `reuse_probe.py` measures stays the only one it helps. `BATCH.md` §13.10 is its report of record.
- The long-tree d7/d8 cells split into four sha256 groups per value workload and need `--allow-digest-mismatch`: `specialized`+iree contracts a `mul` into the following `add`/`sub` (FMA, ≤2.2e-3 relative at d7 and ≤6.1e-3 at d8 after deep-tree cancellation, minimal 5-node repro `add(mul(x0,x1), x0)`), while dense differs from numpy only in the NaN payload bit on `sub` and is value-identical to `specialized`-numpy and `torch-per-tree`; the pop-1000 cell splits into three groups (both dense caps share one).
- `EVOGP_DENSE_MAX_TREE_LEN` is a cost knob, not only a safety valve: pinning it above what the population needs multiplies dense's per-call cost (2.030 → 5.277 ms at 31-node trees for cap 64 → 128, 2.126 → 19.497 ms for 64 → 256), so the `evoxc-dense-iree-raised` arm may only be compared inside its own cell and the shipped default of 64 stays.
- The batch `batch_forward` value path is non-bitwise on the `arith` set where dense is exact (1.5625e-02 abs / 1.13e-03 rel at p256-L32-i8-N1024, 7.81e-02 abs at p256-L64-i32-N1024; the loss and per-row paths agree to ~1e-7 rel), which is why the batch arm forms its own sha256 digest group; `results/batch/validation-batch.json` vs `validation-dense.json` is the comparison.
- Explicit `EVOGP_EVAL_MODE=dense` at pop 16 recompiles when the population's used-function-set changes (2 compiles in 3 generations, ~3.0 s each, `gp_step` 3015.8 ms vs 8.0 ms on `auto`, which routes pop < 64 to specialized) — engine behaviour, recorded in `results/batch/small-r5/p16-L32-i8-N1024/evoxc-dense-iree.json`.
- Asking for the batch route below the population floor costs ≈1.6 ms per call more than asking `specialized` directly (3.94 ms vs 2.31 ms at pop 16), so the decline path is not free.
- `batch_economics.py` and `validate.py` have now both been exercised on the box (economics on 4 cells × 2 routes, validation on 2 cells × 3 function sets with `EVOGP_EVAL_MODE=batch`), but `validate.py` still has no batch entry of its own — the batch sweep is produced by exporting the route, not by a named set.
- `results/batch/flat1000-r5` cannot reach 0 failures under its own `--workloads sr_fitness` schedule (`check.py` wants a digest for every value workload in the cell); the 3-workload sibling `flat1000-3w-r5` is the gateable record of that cell.
- The guard's `python` hint field lists the harness's own `systemd-run` launcher chain, not a foreign tenant; `contaminated` stays false and the gate reads `ok`/`idle` on all 220 records (130/130 after, 90/90 before), with empty `gpu_pids`.

## Routing Table
- `BATCH.md` → the report of record for the `batch` evaluation route (`EVOGP_EVAL_MODE=batch`): what the route is, the `EVOGP_BATCH_*` knob table, the warm per-call and `gp_step` tables at every measured cell, the compile-economics/break-even table, the regimes where it wins (a fixed population of ~64 trees, and long trees past the dense trace cap), numeric validation, gates and the exact reproduce commands; §11 is the long-tree round and its scaling crossover (batch's cost tracks the population's node count, dense's the trace length, with the fixed-population win past `EVOGP_DENSE_MAX_TREE_LEN` and its limits), and §13.10 is the content-addressed plan-key follow-up (the four-call reuse sequence with its replay column, the content blocks in the economics/worker records, and the over-1 compile share).
- `FINAL.md` → the report of record for the post-optimization dense/specialized campaign; its §11 holds the exact reproduce commands and §12 the caveats worth carrying forward.
- `SUMMARY.md` → the rendered baseline round (protocol statement, per-workload tables, `gp_step`, cold compile, digest agreement, caveats) with a header pointing at `FINAL.md`.
- `VALIDATION.md` → the 12-case oracle validation and the cross-arm digest-group finding.
- `README.md` → the entry point: the question, the arms, the grid/protocol, the final-campaign section (measured grid, commands, verdicts), the report/gate rules and the rules for this subtree.
- `content.py` → the content-addressed plan-key vocabulary of the batch route and every derived content block (read it before touching a `content` block in any record).
- `counter_blocks.py` → the strict number/block helpers every optional batch counter surface shares (null never zero: a missing key or a non-numeric value reads `None`).
- `reuse_probe.py` → the plan-key reuse workload and its records in `results/batch_opt_round1/reuse/` (§13.10 of `BATCH.md` interprets them).
- `band_sweep.py` → the warm band-size sweep of the batch route (writes `results/batch_opt_round2/warm/` by default): one record per `(cell, config)` carrying the warm per-call medians, the ten-stage split, `band_report` and the per-workload oracle validation; `--dry-run` prints the exact route env of every (cell, config, workload).
- `batch_economics.py` → the batch route's compile-economics column (writes to `results/batch/`); README's "Batch route: compile economics" section is its human-facing description, and the `EVOGP_BATCH_*` knob table is single-sourced in `common.BATCH_KNOBS` (README's `## Arms` renders it).
- `econ_child.py` → the child-side loop internals `batch_economics.py` calls (counter surfaces, per-generation record assembly, the summary derivation, the band-report block); read it before touching a `first_call` / `sr_fitness` / `generations[i]` / `summary` / `band_report` block in an economics record.
- `results/` → data only (`baseline/`, `final/`, `batch/`, `batch_opt_round1/` and `batch_opt_round2/`, each with its renders); the reports of record are `FINAL.md`, `BATCH.md` and `VALIDATION.md` at this node.
- `results/batch_opt_round2/warm/SUMMARY.md` → round 2 work item 1: the warm band-size sweep at `EVOGP_BATCH_COMPILE_WORKERS=1` (`b8/b16/b32/b64/flat` × `sr_fitness`/`batch_forward`/`forward` on `p256-L32-i8-N1024`, `p256-L64-i32-N1024`, `p64-L64-i32-N64`), with the per-cell tables, the ten-stage split, the cross-config validation, the noise/contention audit and the band-size verdict; records are the 15 `<cell>/<config>.json` + `sweep.json` beside it.
- `../r4/`, `../r5/`, `../r6/` → the historical legacy-CUDA-engine comparison; read-only from here.
- `../../../src/evogp/tests/reference_eval.py` → the oracle every arm is validated against.
