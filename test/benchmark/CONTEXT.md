# `test/benchmark/` — old-vs-new performance benchmark: legacy CUDA engine vs evoxc "true jit" engine

## Intent
Quantitative comparison of EvoGP's two evaluation engines, measured on the same shared box through the
identical public API (time-only; the round-1 methodology is frozen in `SPEC.md`).
Two measurement types since R4: **type 1** = the end-to-end public-API evaluation quoted in R1–R3, **type 2** = the pure internal compiled-forward pass (`--task eval-pure` in `bench_gp.py`; precise definitions in `r4/README.md` and `r4/SUMMARY.md` §B).
- **OLD** = the legacy custom-CUDA engine at commit `b613503` (last pre-rewrite revision; hand-written
  `src/evogp/cuda/*.cu` + `evogp.evogp_cuda`), materialized and built outside the repo at
  `/tmp/evogp_legacy_bench` — the only side that needs a CUDA build.
- **NEW** = the evoxc "true jit" engine (`src/evogp/tree/evoxc_engine.py`: host-side decode + per-structure
  `evoxc.build_cached` graphs) on its two backends: the default `numpy` (CPU reference interpreter) and the
  opt-in `iree` (IREE-cuda GPU), plus the dense one-graph evaluator (`src/evogp/tree/dense_engine.py`)
  that the `iree` backend takes under the default `EVOGP_EVAL_MODE=auto` for short-trace populations.
Those two sides are what the six rounds below measure; the separate `evoxc/` subtree answers the *other*
engine question — evoxc engine vs plain-PyTorch on identical populations — and is the harness new
measurements go into (routing entry below).
The `etl` names inside the R1–R6 records, payload keys and reports are the pre-rename name of `evoxc`
(`bench_gp.py`'s `etl_version()` returns the `evoxc` package version under that frozen payload key); the
committed records are quoted verbatim and never re-keyed.
Six measurement rounds are executed and committed (R4 adds the second measurement type; R5 is an analysis-only RCA round; R6 adds the Triton fused-kernel prototype):
- **Round 1** — `SPEC.md` methodology, matrix C0–C7, records in `new/results/` + `legacy/results/`,
  write-up `SUMMARY.md`: legacy ~34×–7,670× faster per generation, the new side needing no build step.
- **Round 2 (R2)** — protocol `r2/README.md`, records in `new/results/r2/` + `legacy/results/r2/`,
  baseline analysis in the R2 sections of `REPORT.md`, operator log `r2/RUNLOG.md`. Warm/steady-state
  per-call medians as the headline, per-structure compilation reported separately; R2-era gap: the legacy
  engine is ≈33–148× faster than the numpy backend and ≈110–363× faster than iree on the fixture evals.
- **Round 3 (R3, previous round's verdict)** — `r2/round3/` (protocol `r2/round3/README.md`): the R2 headline
  configs re-measured after two engine waves, in two arms — **Arm A** (merged evogp + stock ETL: records
  `r2/round3/results/{new,legacy,backend_agreement}/`, write-up `r2/round3/SUMMARY.md`) and **Arm B**
  (the same nine new-side configs under a patched-ETL checkout shadow: `r2/round3/results/armB/`,
  write-up `r2/round3/SUMMARY_armB.md`).
  Verdict (the "Round 3" section of `REPORT.md`): the dense route compressed the
  old-vs-new gap on the fixture evals to **≈16–23×** (iree, default) / **≈36–142×** (numpy) / **≈94–372×**
  (forced specialized); warm medians Arm A 10.64 / 10.50 ms vs legacy 0.6323 / 0.6357 ms per call, Arm B
  14.84 / 10.03 ms; the patched ETL measured ≈neutral on warm cost but flat iree fds (91 vs
  2 395–17 243) and R2's `iree_sr_b2` SIGSEGV did not reproduce (both routes exit 0).
- **Round 4 (R4, current verdict)** — `r4/` (protocol `r4/README.md`, analysis of record `r4/SUMMARY.md`,
  operator log `r4/RUNLOG.md`): adds the type-2 task (`bench_gp.py --task eval-pure` — times only the
  compiled graph call(s) of a fixed population in a tight loop: device-resident inputs, no readback, no
  host assembly, no per-call key derivation; cold/compile reported separately) and records **both halves of
  the round**: the pre-code-round **before**-baselines for 8 configs (fixture64/200 × dense/specialized ×
  numpy/iree) at evogp `e272714` / etl `51a7141`, every record `local-fallback:*` (`r4/results/`), and the
  **after**-round re-running the identical protocol at evogp `6e8bf6f` on a read-only shadow export of etl
  `87c7562`, every record `frozen-api:*` (`r4/results/after/`), plus a 14-cell type-1 E2E matrix.
  Verdict (the "Round 4" section at the head of `REPORT.md`): every pure route improved (**−8.8 % to
  −91.3 %**; the specialized-iree cells 53.214 → 5.922 and 214.655 → 18.570 ms), the provenance flip is
  numerically inert (A/B `max|diff| = 0`), and on the type-1 side the default iree route reads
  **≈6.1–6.7 ms** warm against the frozen legacy anchor (0.6323 / 0.6357 ms) ⇒ an old-vs-new gap of
  **≈9.5–10.5×** (R3: ≈16.5–16.8×), the patched ETL measuring warm-neutral. No old-vs-new pure row: the
  legacy engine has no separable pure forward.
- **Round 5 (R5, RCA round — diagnosis, not a new verdict)** — `r5/` (analysis of record `r5/RCA.md`,
  protocol `r5/README.md`, gate `r5/check_r5.py`): analysis-only round that removes the cross-window doubt
  (one serialized same-window run: legacy 0.6461 / 0.6372 ms, dense-iree e2e 5.3823 / 5.7912 ms, pure
  1.2142 / 1.4612 ms ⇒ **8.33× / 9.09×** e2e, **1.88× / 2.29×** pure, honest band **≈8–11× centred ~9.5×**)
  and decomposes one warm call into ≥8 measured components (uploads 3.51 / 1.53 ms dominant, `etl.run`
  2.13 / 2.37 ms, decode+unique 0.70 / 1.38 ms, host loss assembly 0.51 ms, D2H 0.14 / 0.17 ms, readback
  0.11 ms; reconciliation 99.94–99.95 %), pinning the GPU mechanism (dense graph = 310 device ops = 249
  dispatches + 61 DtoD copies on a 125-deep serial chain vs the legacy engine's 3 ops; ~103× fewer needed).
  Removal floors: host glue 3.3752 / 2.8064 ms, pure-only 2.3849 / 2.4497 ms. Compile churn, readback
  volume and harness artifacts are falsified as contributors; legacy parity requires collapsing the op
  count plus removing the host glue (`RCA.md` §8/§9).
- **Round 6 (R6, Triton prototype round — feasibility + measurement)** — `r6/` (analysis of record `r6/SUMMARY.md`, protocol `r6/README.md`, stdlib gate `r6/check_r6.py`): a Triton fused evaluator for single-output SR (build-once `prepare_dense` staging, one fused interpreter kernel per call — the legacy reversed-prefix design — driven through the unmodified public API via a runtime-rebound dense seam). Verdict: the r5 hypothesis is **confirmed and exceeded** — same-window 10-cell campaign (GPU 6): triton e2e **0.1314 / 0.1379 ms** vs legacy **0.6364 / 0.6269** vs dense-iree **4.7860 / 6.3179** (f64/f200) ⇒ **4.8× / 4.6× faster than legacy** and 36.4× / 45.8× faster than the dense route; pure 0.05470 / 0.05472 vs dense pure 1.3339 / 1.4796 ms; 1 launch/call (device 5.8 / 9.1 µs, ≈50 µs host residual — launch-bound; legacy itself is ≈97 % host-side). Fixture validation green vs the oracle + goldens (four declared fixture-irrelevant deviation classes); one per-shape compile ≈0.73 s warm / 1.79 s cold cache; benchmark-only prototype (no `src/` change, no landed selection path).
Everything here is hand-run tooling + frozen data: nothing imports it and the repo has no CI.

## Known Issues
- **Historical (`etl`-era): stock ETL leaked iree file descriptors; the patched checkout fixed it.** Stock `etl` (`main` @ `a863545`) leaked ~32–35 fds per compiled structure plus ~0.6–3/build call, so any iree config needed `ulimit -n 65536` and was watched via `payload.fds.end`; the patched commit `51a7141` (in flight upstream — not on `main`) kept iree flat at 91 fds at 170 / 517 / 1181 builds.
- **R2's `iree_sr_b2` SIGSEGV did not reproduce on the patched checkout.** R2: exit 139 after ~800–900 builds (skeleton kept in `new/results/r2/`). R3 re-attempt, both routes: exit 0 (dense 431/1500 misses in 213 s; pinned-specialized 1181/1500 in 595 s), fds flat 39 → 91 → 91, identical fitness trajectory — a "did not reproduce", not proof of the original cause; the b2 ids stay out of the frozen manifests.
- **IREE per-structure compile time is not reproducible on this shared box**: 342–2 162 ms per build (~6.3× spread for identical build counts), so read `first_call_ms`/`cold_build_ms` as "± a factor of a few", never as a hardware constant; only the fd curve and the warm numbers are stable.
- **Two-window contention (R3) — cross-window warm deltas are not resolvable.** W1 ran on GPU 6 with a foreign tenant (bursting 0→100 %); W2, the committed Arm B records of record, ran on GPU 0 with a mid-window tenant takeover. Within-window ratios, build traffic, exit codes, fd curves and fitness vectors are the robust metrics; single warm cells run both ways inside the band. The numpy rows ride the shared-host noise band in both rounds (no engine shift attributed).
- **Stage probe: dense-route degeneracy + unresolved tax.** The probe wraps the specialized call sites only, so dense-routing records (iree `auto`) report their cost in the uninstrumented `misc` bucket (`build_calls=0`), and the `stages` marker in manifests means "the config passes `--stage-probe`", not "the stages block is meaningful". The probe tax stays ≲1 ms on `eval64` and inside box noise on `sr`.
- **`--stage-probe` does not apply to `eval-pure`** (it wraps `evoxc.run`, i.e. exactly the loop being measured): the flag is accepted but warns and `stages` stays `null` in every `eval-pure` record; cold/warm separation comes from the `compile` / `pure` blocks instead.
- **R4's two pure record sets are separate, equivalent, and never mixed.** The before-records (`r4/results/`, evogp `e272714`) are `local-fallback:{dense|specialized}` / `compile.path="fallback"` and stay immutable; the after-records (`r4/results/after/`, evogp `6e8bf6f` on the etl `87c7562` shadow) are `frozen-api:*` / `"frozen"`. The two constructors are A/B-bit-identical (`r4/results/after/ab/ab_equivalence_report.txt`: equal `output_checksum` digests, byte-identical `.npz` captures, `max|diff| = 0` over all 53 arrays with identical NaN placement), so any table spanning both sets must carry the `runner_source` column. The frozen construction records **no** decode/build split: `compile.build_ms` and `compile.decode_plan_ms` are `null` there (only `construct_total_ms`), and its `cache_hits` is 0 where the fallback records counted 5 / 16 hits on the specialized numpy routes.
- **Historical: `etl`-shadow identity is not recorded in the JSONs.** `etl_version` is `"0.1.0"` for both the stock and the patched checkout; the evidence is the per-config `etl:` header line in every `run_all_armB.sh` / `run_pure.sh` log (read `file=` / `pythonpath=`, never `rev=` / `etl_version`) plus the dated fresh-process probes in `r2/round3/results/armB/etl_import_probe.txt` (R3 shadow `51a7141`) and `r4/results/after/etl_import_probe.txt` (R4 shadow `87c7562`, with its sha256 pins and the `find_spec("etl.jit")` discriminator). Both `/tmp` exports are session-scoped and the R4 source branch no longer exists (no ref contains `87c7562`), so those committed probes and per-log lines are the surviving evidence. Today the same payload key holds the installed `evoxc` package version (`bench_gp.py` `etl_version()`).
- **`r5/probe_lib.py` no longer runs on the current engine.** `install_etl_proxy()` proxies `dense_module.etl` and raises `RuntimeError` when that global is absent, which it now is (the engine module imports `evoxc`); the r5/r6 probe measurements are therefore historical, while the stdlib gates over the committed records (`check_r5.py`, `check_r6.py`) still run.
- **IREE `O2`/`O3` miscompile CUDA silently** — the rounds only ever use `O0`/`O1`, and any IREE timing is gated on the `O1` agreement pre-flight.
- **The R2 directory-scan validation always reports 2 failures**: `legacy/results/r2/C5.json` and `C5b.json` are prior-round artifacts of round 1's `legacy/run_matrix.py` driver (they predate the R2 key schema and are not manifest ids). The scan skips `new/results/r2/backend_agreement/` because those are pre-flight records, not config results.
- **CPU/GPU profilers are blocked on this box; kineto is the working fallback.** nsys 2022.4.2.1 collection succeeds but QDSTRM import/analysis fails against driver 535.247.01 (`Unknown runtime API function index: 440`, empty kernel tables); ncu 2022.3 fails with `API call is not supported in the installed CUDA driver`; `torch.profiler` (kineto) DOES see IREE kernels + DtoD copies, so a kernel timeline exists while per-launch host-vs-device splits stay inferred.
