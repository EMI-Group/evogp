# `test/benchmark/` — performance measurement: the current evoxc-vs-torch harness plus the frozen legacy-engine rounds

## Intent
This directory measures EvoGP's evaluation cost through the same public API on the same box; nothing here is imported by `evogp`, by the examples or by the pytest suite, and no CI collects it.
**Current** — `evoxc/` answers "what does the evoxc-based engine cost per evaluation compared with the plain-PyTorch implementation of the same tree evaluation", on identical populations, in one session, warm/steady-state; its reports of record are `evoxc/FINAL.md` (the shipped `specialized`/`dense` routes) and `evoxc/BATCH.md` (the opt-in `batch` route).
**Historical** — `r2/`, `r4/`, `r5/`, `r6/` and the reports `REPORT.md` / `SUMMARY.md` compare the evoxc engine with the **deleted legacy CUDA engine** at commit `b613503` (hand-written `src/evogp/cuda/*.cu` bound as `evogp.evogp_cuda`); their committed records, numbers and gates stay valid as history and are immutable evidence.
Two measurement types, defined once and used by every round and by the current harness:
- **type 1** = the end-to-end public-API call (`problem.evaluate(forest)` / `Forest.SR_fitness` / `Forest.forward`): decode + cache lookup + graph run + device→host readback + host loss assembly.
- **type 2** = the pure compiled-graph forward only (`bench_gp.py --task eval-pure`, runner core `pure_forward.py`): device-resident inputs, no readback, no host assembly, outputs dropped; the legacy engine has no separable pure forward and the task exits 3 on it.
The `evoxc/` harness reports type-1 numbers per workload (`sr_fitness`, `batch_forward`, `forward`, `gp_step`), keeps the cold call out of the warm medians, and prices the host glue separately in `evoxc/decompose.py`.
The engine under measurement is `src/evogp/tree/evoxc_engine.py` (per-structure `evoxc.build_cached` graphs) plus the dense all-ops route in `src/evogp/tree/dense_engine.py` and the opt-in merged-population route in `src/evogp/tree/batch_engine.py`.
Its knobs are `EVOGP_EVAL_MODE` (`dense`/`specialized`/`batch`/`auto`), `EVOGP_EVOXC_BACKEND`, `EVOGP_EVOXC_DEVICE`, `EVOGP_EVOXC_OPT_LEVEL`, `EVOGP_EVOXC_CACHE_SIZE` and the opt-in on-disk artifact cache `EVOGP_EVOXC_ARTIFACT_DIR`; `EVOXC_DISABLE_LOCATIONS=1` speeds tracing up.
The batch route adds its own `EVOGP_BATCH_*` knobs (band size/bands/switch ops/alignment/cache size/pop floor, table in `evoxc/BATCH.md`), and `auto` never resolves to `batch`.
The shipped `auto` policy routes to dense+iree from pop 64 on a device box and to specialized+numpy below that, on a CPU box or on any fallback (`EVOGP_DENSE_AUTO_MIN_POP` / `EVOGP_DENSE_AUTO_MAX_ROWS` move the thresholds), so every record must state the route that actually resolved.

## Current subtree — `evoxc/` (also the only place new timing records go)
- `common.py` → the single workload/cell definition (`main_cells()`/`n64_cells()`/`parse_cell`), deterministic `build_workload`, `env_block`, `time_call` (cold call split from warmup+reps medians), `digest`, `route_decision` (asks the engine's own `resolve_eval_mode`/`resolve_backend_name`/`should_use_dense`).
- `arms_torch.py` → the two plain-PyTorch baselines (`torch-per-tree` Python tree walk, `torch-batched` one vectorized pass), op semantics copied from the oracle.
- `arms.py` → the arm namespace (`torch-per-tree`, `torch-batched`, `evoxc-auto`, `evoxc-auto-iree`, `evoxc-dense-iree`, `evoxc-specialized-numpy`, `evoxc-specialized-iree`, `evoxc-batch-iree`, `evoxc-batch-iree-flat`), per-arm env application, the GP pipeline for `gp_step`; `evoxc-auto` leaves both knobs unset so it times the shipped policy, and the two batch arms clear every `EVOGP_BATCH_*` variable first (`-flat` is the same route with unbanded merging).
- `worker.py` → one process, one `(cell, arm)`: the measured unit (cold call, warmup, reps, cache deltas, value digests, `first_call_ms`).
- `campaign.py` → the sequential driver: one subprocess per config, idle-device guard, `--tree-root` to time another checkout, `--resume`, per-config logs + `campaign.json`.
- `validate.py` → every arm against `../../src/evogp/tests/reference_eval.py` (three function sets, 12 cases) before any timing is trusted.
- `decompose.py` → per-call phase breakdown of one cell on both routes, with a residual row for host glue.
- `cold_start.py` → cold-start column: import → first synchronized fitness on the default route, one process per population, `--artifact-dir` drives `EVOGP_EVOXC_ARTIFACT_DIR` as a populate/reload pair.
- `training_run.py` → whole-training-run column: `StandardPipeline.step()` on the in-process `src/evogp/sr_test.py` problem for the `engine`, `torch-per-tree` and `preopt` (`--tree-root`) arms, with the best-fitness trajectory next to the per-generation timings.
- `batch_economics.py` → compile economics of one merged graph per population: cold first call, warm `sr_fitness`, and a real `StandardPipeline.step()` loop recording the structure-multiset hit rate, recompile count and compile-attributed share, for `batch` against `dense` in the same process layout.
- `summarize.py` / `check.py` → stdlib-only renderer (`--compare-results` adds before/after ratio tables) and the gate over one result directory.
- `results/` → frozen evidence: `baseline/` (the earlier round, rendered by `SUMMARY.md`), `final/{after,before,decompose,decompose-before,cold,training}/` + `final/validation.json` + `final/RENDERED.md`, and `batch/` (the batch route: pilot `warm`/`small`/`flat`/`flat1000`, the gateable `warm-r5`/`small-r5`/`flat-r5`/`flat1000-3w-r5` rounds with their `RENDERED-*.md`, `economics.json`, `validation-batch.json` and `validation-dense.json`), and the batch optimization rounds `batch_opt_round1/`, `batch_opt_round2/` and `batch_opt_round3/` (each with its own `SUMMARY.md` and its per-cell records).
- `FINAL.md` → the report of record for the shipped routes (headline/before-after/decomposition tables, cold-start economics, 50- and 200-generation training runs, noise audit, gate, reproduce commands).
- `BATCH.md` → the report of record for the opt-in batch route (route description, `EVOGP_BATCH_*` knob table, warm/`gp_step`/compile-economics tables, the one winning regime, numeric validation, gate, reproduce commands), plus its round sections: §13 round 1 (chunked parallel compile, the stage split and reuse), §14 round 2 (the band policy, the shipped default's chunked shape and the composition) and §15 round 3 (the per-cell warm/cold/loop table, the compile-pool break-even, the band-size policy and what would have to change).
- `VALIDATION.md` → the oracle validation and the cross-arm digest-agreement finding; `README.md` → methodology, arms, grid, the campaign commands of record.
- Gate of record is per side: `python3 test/benchmark/evoxc/check.py --results test/benchmark/evoxc/results/final/after --allow-snapshot --allow-missing --allow-digest-mismatch` (130 records / 3602 checks), the same over `results/final/before` (90 records / 2642 checks), and per campaign directory over `results/batch/{warm-r5,small-r5,flat-r5,flat1000-3w-r5}` (24/682, 36/1022, 4/126, 1/36 checks, 0 failures).
- Headline: warm `sr_fitness` at pop ≥ 64 is 4.9–75× faster than `torch-per-tree` and 2.1–3.9× faster than `torch-batched`; the shipped default is 0.73–0.81× the `torch-per-tree` arm at pop 16 (specialized route, a compile-cost decision); a cold 50-generation training run is compile-dominated at 7.8× the torch evaluator, and 1.14× faster than it with a warm `EVOGP_EVOXC_ARTIFACT_DIR`.
- Batch route verdict (do not re-litigate without new evidence): `batch` is dominated by the shipped `dense+iree` route in a GP loop — the pre-round N=1024 grid measured it at 0.37–0.995× of dense's warm `sr_fitness` speed, and round 3 re-prices the shipped default at 3.38× / 1.84× dense's warm `sr_fitness` at the two pop-256 cells (3.7250 / 3.7720 ms against 1.1015 / 2.0560 ms) with an 8-generation `StandardPipeline.step()` loop 64.9× / 71.5× / 17.8× slower (19 626.71 / 22 346.79 / 5 587.44 ms against 302.48 / 312.48 / 313.26 ms; eval-only 868× / 680× / 229×).
  The loop loses to the per-generation merged-graph recompile: `generation_hit_rate` 0.125, i.e. 7 of 8 generations build a new structure multiset (8 distinct structure signatures).
  The one warm win is a fixed population over few data rows (`p64-L64-i32-N64`: 1.1141 ms against dense 1.4378 ms, i.e. 1.29× faster) and it keeps a cheaper cold start as well: cold first calls are 4 064.48 / 4 071.43 / 2 274.46 ms against dense's 3 355.83 / 6 526.78 / 6 554.88 ms.
  Both knobs stay at their round-2 settings: `EVOGP_BATCH_COMPILE_WORKERS` stays 4 (pop-256 cold compile 10.73 / 11.96 s → 4.06 / 4.07 s for 1.69–1.87× the warm call, break-even 3 849 / 5 103 warm calls of one population and 18 702 at 111-node trees, inert at `p64` where `chunk_count` is 1) and `EVOGP_BATCH_BAND_SIZE` stays 16 (the `EVOGP_BATCH_BANDS=15` rocm-cap pin is the same merge at pop 256 — identical `band_sizes` and `emitted_ops` — and the `p64` K = 7 pin stays inside ±5 % box noise).
  `auto` never selects the route, so nothing on the default path changes; round 1 added the chunked compile, the content-addressed plan key and the per-stage records (`evoxc/BATCH.md` §13, `evoxc/results/batch_opt_round1/`) and round 3 closes the line (`evoxc/BATCH.md` §15, `evoxc/results/batch_opt_round3/`).
- Reproduce: `export PYTHONPATH=src:/root/evoxc:test/benchmark/evoxc EVOXC_DISABLE_LOCATIONS=1`, then from `test/benchmark/evoxc` `$PY campaign.py --out results/final/after --cells main,n64 --arms all` (and the before/decompose/cold/training commands in `README.md`, the batch campaign/economics/validation/gate commands in `BATCH.md`).

## Historical subtree — legacy CUDA engine vs evoxc engine

- `r2/` → R2 protocol, runner, manifest and `check_r2.py`, plus the executed round 3 in `r2/round3/` (Arm A on the merged tree, Arm B on a patched-checkout shadow).
- `r4/` → the round that introduced measurement type 2: pure-forward before/after records, the 14-cell type-1 E2E matrix, the frozen-vs-fallback A/B, `check_r4.py` / `check_e2e_r4.py` gates, analysis of record `r4/SUMMARY.md`.
- `r5/` → analysis-only RCA round (`r5/RCA.md`): same-window anchors, per-call decomposition, GPU mechanism, removal floors, `check_r5.py` gate over the committed records.
- `r6/` → Triton fused-kernel prototype round (`r6/SUMMARY.md`, stdlib gate `check_r6.py`): test-only prototype, never integrated into `src/`.
- `REPORT.md` → round-1/R2 round analysis plus the Round-3 and Round-4 verdicts; `SUMMARY.md` → the round-1 headline report.
- `new/` (round-1 new side: `run_matrix.sh`, `check_smoke.py`, `NOTES.md`, `results/`) and `legacy/` (round-1 old side: `setup_legacy.sh`, `run_matrix.py`, `check_results.py`, `BUILD_NOTES.md`, `results/`) → the two sides of round 1, including the only path that needs a CUDA build.
- `xval/` → round-1 cross-validation of the old side through `bench_gp.py`; `fixtures/` + `make_r2_fixtures.py` → the 200-tree cross-side fixture and its generator.
- `bench_gp.py` → the side-agnostic driver of the historical rounds: one JSON + one log per run, `--task sr|xor|eval64|evalfresh|eval-pure`, `--backend`, `--iree-device`/`--iree-opt-level`, `--data-rows`, `--mem-guard-mb`, cold-build bounds, `--stage-probe`; its `detect_side()` labels the engine family by the presence of `tree/evoxc_engine.py` in the resolved package directory (import-free).
- `pure_forward.py` (type-2 runner core) and `stage_probe.py` (runtime-monkeypatch stage split) belong to the frozen R4/R5 rounds and are history-only — the current measurement path is `evoxc/`.
- The `etl` names inside the R1–R6 records, payload keys and logs are the pre-rename name of `evoxc` (`bench_gp.py`'s `etl_version()` now returns the `evoxc` package version under that frozen payload key); the committed records are quoted verbatim and never re-keyed.

## Notes for agents
- Interpreter is the project venv — no `python`/`python3` on `PATH` has torch — and a CUDA-visible device is required; `evoxc` comes from its sibling checkout on `PYTHONPATH` (`/root/evoxc`).
- One process per timed config (the compile cache, executable memo and input memo are per-process), never two timed configs concurrently, and never another torch process while a campaign is in flight.
- Records are written verbatim: every JSON carries its own engine identity (`evogp_commit`, `evogp_file`, `etl_version`, `env`, `gpu`); a contaminated or re-run config is annotated, never smoothed, and frozen result directories are never rewritten in place.
- `results/final/**`, `results/batch/**`, `results/baseline/**`, `results/batch_opt_round1/**`, `results/batch_opt_round2/**`, `results/batch_opt_round3/**`, `r2/results/**`, `r4/results/**`, `r5/results/**`, `r6/results/**` are immutable evidence; a new round writes into a fresh directory.
- Warm medians are ±10 % on this shared box and a contended window inflates them 2–3×; read cold/first-call numbers as "± a factor of a few".
- `--max-cold-builds N` bounds cumulative cache misses on the new side (IREE only); IREE `O2`/`O3` miscompile CUDA silently, so only `O0`/`O1` are ever timed.
- The legacy rounds pinned GPU 6 and never used GPU 7 (hardware ECC fault on that box), serialized every heavy phase with `flock`, and kept `timeout` inside the lock; the current harness enforces the one-process-one-config rule with an idle-device guard instead of pinning a device.
- The built legacy checkout (`/tmp/evogp_legacy_bench`) and the patched-`evoxc` shadow exports of R2/R3/R4 are session-scoped and gone, so those halves are evidence, not steps; `legacy/setup_legacy.sh` + `legacy/BUILD_NOTES.md` hold the build recipe.

## Validation
- Current: `python3 test/benchmark/evoxc/check.py --results <dir> [--allow-snapshot] [--allow-missing] [--allow-digest-mismatch]` (stdlib-only, one side at a time, exit 1 on failure) and `python3 test/benchmark/evoxc/summarize.py --results <dir> --out <md>`; the timed records themselves need the GPU plus `validate.py` first.
- Historical gates over committed records (stdlib, no GPU): `check_r2.py` (126 checks), `r2/round3/check_r3.py` (45 + 34 checks) with `check_agreement_r3.py`/`check_agreement_armB.py`, `r4/check_r4.py` (369 checks per side), `r4/check_e2e_r4.py` (328 checks), `r4/check_agreement_r4.py`, `r5/check_r5.py` (1426 checks), `r6/check_r6.py` (1440 checks).
- `r5/probe_lib.py` proxies `getattr(dense_module, "etl")` and raises on the current engine, so the R5/R6 probe scripts are not re-runnable while their gates over the committed records are.
