# `test/benchmark/fixtures/` — R2 cross-side evaluation fixtures

## Intent

The R2 round of this benchmark evaluates **one fixed forest on both engines** (OLD = the legacy
custom-CUDA checkout at `b613503`, NEW = this repo at HEAD with the ETL "true jit" engine) so the
per-call numbers are comparable without any generator difference. The committed
`test/goldens/forest_random.npz` capture only holds 64 trees, so this directory adds a **200-tree**
version of the same workload, in the same npz schema, generated on the NEW side:

```bash
# eval-only microbench on the fixed 200-tree forest, either side, from the checkout root
PYTHONPATH=src <venv>/bin/python test/benchmark/bench_gp.py --task eval64 \
    --fixture test/benchmark/fixtures/forest200_tree64_random.npz --eval-reps 5 \
    --tag R2 --json-out <results>/R2.json
```

The OLD checkout has no `test/goldens/`, hence the explicit `--fixture <absolute path>`. The
fixture is *only* data for the eval tasks: `bench_gp.py` rebuilds a `Forest` from the three
`forest__*` arrays through the class constructor (identical at `b613503` and HEAD) and runs
`problem.evaluate(forest)` on it, so nothing here is RNG-dependent at measurement time.

## `forest200_tree64_random.npz`

Generated by `make_r2_fixtures.py` (this directory) with `--pop 200 --tree-len 64 --seed 0`, the
SPEC.md §W1 descriptor (`bench_gp.py::w1_descriptor`: `input_len=2, output_len=1, const_prob=0.5,
out_prob=0.5, using_funcs=['+','-','*','/'], layer_leaf_prob=0.2, const_range=(-5,5), sample_cnt=8,
max_layer_cnt=5`) and `Forest.random_generate`, i.e. torch's global RNG
(`torch.manual_seed(0)` + `torch.cuda.manual_seed(0)`) — the same construction the NEW side uses in
C1/C5-style configs.

The `forest__*` arrays are plain `Forest` constructor inputs — `batch_node_value` (float32),
`batch_node_type` (int16), `batch_subtree_size` (int16) — each row being the documented pre-order
prefix encoding of length `subtree_size[:, 0]` with zeros after it. `x`/`labels` are **copied
bitwise** from `test/goldens/forest_random.npz` (64 data rows), so the eval workload is exactly the
one in the legacy capture and `bench_gp.py --data-rows` tiling can grow the row count instead of
swapping the data set.

| key | shape | dtype | note |
|---|---|---|---|
| `forest__node_value` | (200, 64) | float32 | tree node values (constants / function ids) |
| `forest__node_type` | (200, 64) | int16 | `NType` + optional `OUT_NODE` bit |
| `forest__subtree_size` | (200, 64) | int16 | column 0 = tree length, 1 for leaves |
| `x` | (64, 2) | float32 | copied from `test/goldens/forest_random.npz` |
| `labels` | (64, 1) | float32 | copied from `test/goldens/forest_random.npz` |

Provenance record (values printed by the generator): file sha256
`6789ef61ecf8898b9b2a00774ee655e20b0b5be7c72eb861afc8d6b8799741b9` (104 474 bytes, five zip
members, fixed 1980 timestamps), array digest (sorted keys, canonical bytes)
`872e793f87eb6c775458783805376a954c3f2ab0b554496fcfcc1d19235edbdb`;
written on 2026-09-12 from evogp commit `5178a7cf0fb0122a39126cf6b8d36c9c5dd3c8d2` (`git rev-parse HEAD`
at generation time; `test/benchmark/legacy: R2 same-box legacy sanity re-runs ...`, i.e. on the
lineage of the subtree-restore commit `7a67e87`) with
`/mnt/local-ssd/bchuang/evox/.venv/bin/python` (torch 2.6.0+cu124, CUDA 12.4,
`CUDA_VISIBLE_DEVICES=6`, NVIDIA RTX A6000). `np.savez` (uncompressed) writes fixed zip
timestamps, so the file is byte-for-byte reproducible: two independent scratch runs to `$TMPDIR`
hash to the same sha256 (`cmp` identical, `np.array_equal` true for every key) and the committed
file equals them.

Regeneration command (from the checkout root, GPU required — the descriptor builds its tables on
`"cuda"`, `ETL_DISABLE_LOCATIONS=1` is set by the script itself):

```bash
PYTHONPATH=src <venv>/bin/python test/benchmark/make_r2_fixtures.py \
    --pop 200 --tree-len 64 --seed 0 \
    --out test/benchmark/fixtures/forest200_tree64_random.npz --verify
```

`--data-from` (default `test/goldens/forest_random.npz`) selects where `x`/`labels` come from. The
script self-checks shape/dtype/contiguity, tree lengths (`1 <= subtree_size[:, 0] <= width`), the
all-zero dead tail, valid `NType` ids and finite node values, and prints the file's sha256.

Structure reported for this population: 200 rows, width 64, tree lengths 1…31 (median 17, 15
distinct lengths, `31 = 2**5 - 1` = complete tree for `max_layer_cnt=5`), 165 distinct rows, node
kinds `var 764 / const 828 / bfunc 1392` (no unary/ternary and no `OUT_NODE` bit — the same profile
as the legacy 64-tree capture, which also has `var/const/bfunc` only and 22 % single-node trees).

## `sanity_eval.json` / `sanity_eval.log`

NEW-side load-and-run proof for the fixture (not part of the frozen SPEC matrix; a by-product of
building it):

```bash
PYTHONPATH=src <venv>/bin/python test/benchmark/bench_gp.py --task eval64 \
    --fixture test/benchmark/fixtures/forest200_tree64_random.npz --eval-reps 2 \
    --tag R2FIX-SANITY --json-out test/benchmark/fixtures/sanity_eval.json \
    > test/benchmark/fixtures/sanity_eval.log
```

Result: `side=new`, `eval_kind=fixture`, `config.pop=200`, `config.tree_len=64` (i.e. the harness
reads pop/tree-len off the fixture, as intended), `per_call_ms = [1166.6, 111.0]` —
`first_call_ms = 1166.6 ms` is the cold call (200 distinct structures ⇒ one ETL
`etl.build_cached` graph each, ≈ 5.8 ms/structure with `ETL_DISABLE_LOCATIONS=1`, numpy backend),
the second call (all-cache-hit, decode + 200 graph runs) is **111.0 ms**. As with the other eval
JSONs, `median_warm_ms` is `null` because `--eval-reps 2` leaves only one warm call (the harness
needs ≥ 2); the warm ballpark is `per_call_ms[1]`. The `--verify` run of the generator additionally
confirms the file round-trips: `Forest(pop_size=200, max_tree_len=64)` + one `SR_fitness(x, labels)`
call succeeds, with 12/200 trees NaN/±inf (division by an expression that vanishes on a data row —
the legacy capture shows the same effect, 3/64) and finite losses 2.72 … 650 003 (mean 6 969).

## Constraints / notes for agents

- **Read-only fixture data**: regenerating overwrites the committed file; the R2 matrix must record
  the sha256 above, so do not re-run the generator with a different seed/pop/tree-len into this path
  unless the matrix is re-run too (use `--out $TMPDIR/...` for scratch variants).
- The fixture contains structures only; it says nothing about which engine evaluates them. Any
  cross-side numeric comparison must use `x`/`labels` from this file unchanged (or tiled with
  `--data-rows`), on the same GPU and with the same `EVOGP_ETL_*` environment.
- The legacy side never sees `x`/`labels` from this file by accident: `bench_gp.py` requires an
  explicit `--fixture` there because the old checkout has no `test/goldens/`.
- Scope: no library code, no `src/**`, and nothing under `test/benchmark/{new,legacy,xval,r2}/` is
  touched from here.
