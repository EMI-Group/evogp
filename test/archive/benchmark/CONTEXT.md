# `test/benchmark/` — performance measurement: the current evoxc-vs-torch harness plus the frozen legacy-engine rounds

## Intent
This directory measures EvoGP's evaluation cost through the same public API on the same box; nothing here is imported by `evogp`, by the examples or by the pytest suite, and there is no CI (the only files a runner collects are the two torch-free pytest modules in `evoxc/`).
**Current** — `evoxc/` answers "what does the evoxc-based engine cost per evaluation compared with the plain-PyTorch implementation of the same tree evaluation", on identical populations, in one session, warm/steady-state, over the engine's FOUR routes: the shipped `auto` policy over `fused`/`dense`/`specialized`, the explicit `fused` (Triton) request, and the opt-in `batch` merge that `auto` never resolves.
Its reports of record are `evoxc/FINAL.md` (the shipped `specialized`/`dense` routes against both torch baselines), `evoxc/BATCH.md` (the opt-in `batch` route plus its three optimization rounds), `evoxc/LARGE_SCALE.md` / `evoxc/LARGE_SCALE_ROUND2.md` (the large-scale column), and the `t1a1` directories — `evoxc/results/t1a1_auto_r3/README.md` (the SHIPPED default's campaign of record, `auto` → fused on the release tree), `evoxc/results/t1a1_auto/README.md` (its one-screen verdict page, which quotes r3, keeping the pre-host-glue JSON as the A/B baseline), `evoxc/results/t1a1_auto_r2/` (the previous round's window), `evoxc/results/t1a1_fused/README.md` (the explicit `EVOGP_EVAL_MODE=fused` column) and `evoxc/results/t1a1_baseline/BASELINE.md` (the pre-fused default, where `auto` resolved dense+iree).
**Historical** — `r2/`, `r4/`, `r5/`, `r6/` and the reports `REPORT.md` / `SUMMARY.md` compare the evoxc engine with the **deleted legacy CUDA engine** at commit `b613503` (hand-written `src/evogp/cuda/*.cu` bound as `evogp.evogp_cuda`); their committed records, numbers and gates stay valid as history and are immutable evidence.
Two measurement types, defined once and used by every round and by the current harness:
- **type 1** = the end-to-end public-API call (`problem.evaluate(forest)` / `Forest.SR_fitness` / `Forest.forward`): decode + cache lookup + graph run + device→host readback + host loss assembly.
- **type 2** = the pure compiled-graph forward only (`bench_gp.py --task eval-pure`, runner core `pure_forward.py`): device-resident inputs, no readback, no host assembly, outputs dropped; the legacy engine has no separable pure forward and the task exits 3 on it.
The `evoxc/` harness reports type-1 numbers per workload (`sr_fitness`, `batch_forward`, `forward`, `gp_step`), keeps the cold call out of the warm medians, and prices the host glue separately in `evoxc/decompose.py`.
The engine under measurement is `src/evogp/tree/dense_engine.py` (which owns the ONE route policy, `resolve_route`), the per-structure `evoxc.build_cached` graphs in `src/evogp/tree/evoxc_engine.py`, the dense all-ops route, the opt-in merged-population route in `src/evogp/tree/batch_engine.py`, and the fourth route `src/evogp/tree/fused_engine.py` + `fused_kernels.py` (ONE Triton launch for the whole population, no evoxc graph and no per-generation compile).
Its knobs are `EVOGP_EVAL_MODE` (`fused`/`dense`/`specialized`/`batch`/`auto`), `EVOGP_EVOXC_BACKEND`, `EVOGP_EVOXC_DEVICE`, `EVOGP_EVOXC_OPT_LEVEL`, `EVOGP_EVOXC_CACHE_SIZE`, the fused route's `EVOGP_FUSED_*` set (`_MIN_POP` 16, `_BLOCK_ROWS` 256, `_NUM_WARPS` 1, `_MAX_SCRATCH_MB` 8192, `_HOST_MEMO` 16, `_DISPATCH` `bound`, with `jit` restoring Triton's `JITFunction.run`) and the opt-in on-disk artifact cache `EVOGP_EVOXC_ARTIFACT_DIR`; `EVOXC_DISABLE_LOCATIONS=1` speeds tracing up, and a fused run needs a writable `TRITON_CACHE_DIR`.
The batch route adds its own `EVOGP_BATCH_*` knobs (band size/bands/switch ops/alignment/cache size/pop floor, table in `evoxc/BATCH.md`), and `auto` never resolves to `batch`.
The shipped `auto` policy owns engine AND backend whenever no backend is named: it takes the `fused` (Triton) route FIRST from `EVOGP_FUSED_MIN_POP` (16) up while `triton` is importable, a torch device is usable and the fused memory envelope holds, else dense on `iree` from `EVOGP_DENSE_AUTO_MIN_POP` (64) up under dense's memory envelope (`EVOGP_DENSE_AUTO_BUDGET_MB` 8192, with the trace cap raised by power of two up to `EVOGP_DENSE_AUTO_MAX_TREE_LEN` 256), else specialized+numpy — below the thresholds, on a CPU box, and on every fallback.
An explicitly named backend never reaches the fused route under `auto` (`EVOGP_EVAL_MODE=fused` is how a caller asks for it), so every record must state the route that actually resolved.

## Notes for agents
- Interpreter is the project venv — no `python`/`python3` on `PATH` has torch — and a CUDA-visible device is required; `evoxc` comes from its sibling checkout on `PYTHONPATH` (`/root/evoxc`).
- The two `evoxc/` pytest modules are collected by the project gate AFTER `src/evogp/tests` (whose `conftest.py` leaves `EVOGP_EVOXC_BACKEND=numpy` in the process): harness stubs go through `sys.modules`, so no harness module may cache an `evogp` module handle — resolve it with `common.installed_module(...)` per call and clear the route environment in the fixture, or the test passes alone and fails in the gate.
- One process per timed config (the compile cache, executable memo and input memo are per-process), never two timed configs concurrently, and never another torch process while a campaign is in flight.
- Records are written verbatim: every JSON carries its own engine identity (`evogp_commit`, `evogp_file`, `etl_version`, `env`, `gpu`); a contaminated or re-run config is annotated, never smoothed, and frozen result directories are never rewritten in place.
- `results/final/**`, `results/batch/**`, `results/baseline/**`, `results/batch_opt_round1/**`, `results/batch_opt_round2/**`, `results/batch_opt_round3/**`, `results/largescale/**`, `results/largescale2/**`, `results/largascale/**`, `results/largascale2/**`, `results/t1a1_baseline/**`, `results/t1a1_fused/**`, `results/t1a1_auto/**`, `results/t1a1_auto_r2/**`, `results/t1a1_auto_r3/**`, `results/minpop_r3/**`, `r2/results/**`, `r4/results/**`, `r5/results/**`, `r6/results/**` are immutable evidence; a new round writes into a fresh directory.
- Warm medians are ±10 % on this shared box and a contended window inflates them 2–3×; read cold/first-call numbers as "± a factor of a few".
- A fused arm needs a writable `TRITON_CACHE_DIR` (this box's `$HOME` is read-only) and its first launch JIT-compiles the kernel: a declined call and a served one look identical in wall time, so read `cache.fused_served` (a `fused_kernel_launches`/`fused_kernel_compiles` delta from `fused_engine.fused_cache_stats()`), never the timing.
- Records from before the harness grew the fused counter surface carry `routes.*.eval_mode = "fused"` but no `engine` and no `fused_cache` block (`results/t1a1_fused/`), so the gate WARNs instead of proving a launch; `results/t1a1_auto_r3/` is the directory that does prove it (`results/t1a1_auto/`, its verdict page, proves the same launch on the pre-host-glue tree).
- `decompose.py`'s `ROUTES` table has no `fused` entry and `cold_start.py` hardcodes the `evoxc-auto` arm (which reaches fused, but only through the policy), so a per-phase column or an explicitly-fused cold-start column needs an edit in each.
- `--max-cold-builds N` bounds cumulative cache misses on the new side (IREE only); IREE `O2`/`O3` miscompile CUDA silently, so only `O0`/`O1` are ever timed.
- The legacy rounds pinned GPU 6 and never used GPU 7 (hardware ECC fault on that box), serialized every heavy phase with `flock`, and kept `timeout` inside the lock; the current harness enforces the one-process-one-config rule with an idle-device guard instead of pinning a device.
- The built legacy checkout (`/tmp/evogp_legacy_bench`) and the patched-`evoxc` shadow exports of R2/R3/R4 are session-scoped and gone, so those halves are evidence, not steps; `legacy/setup_legacy.sh` + `legacy/BUILD_NOTES.md` hold the build recipe.

- Current: `python3 test/benchmark/evoxc/check.py --results <dir> [--allow-snapshot] [--allow-missing] [--allow-digest-mismatch]` (stdlib-only, one side at a time, exit 1 on failure) and `python3 test/benchmark/evoxc/summarize.py --results <dir> --out <md>`; the timed records themselves need the GPU plus `validate.py` first, and every `t1a1` directory is gated with the same form (`results/t1a1_auto_r3`, `results/t1a1_auto_r2`, `results/t1a1_auto`, `results/t1a1_fused`, `results/t1a1_baseline/main`).
