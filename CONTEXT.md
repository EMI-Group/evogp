# EvoGP — Tree-based Genetic Programming on PyTorch + evoxc (repository root)
## Intent
EvoGP is a Tree-based Genetic Programming (TGP) framework for symbolic regression, classification, feature transformation and robotics-control benchmarks (Brax / MuJoCo-Playground / Genesis), with multi-output trees for classification and policy optimization.
Evaluation is a "true jit" over evoxc (EvoX Compiler) with three selectable routes (`EVOGP_EVAL_MODE`): a dense all-ops graph per population shape (default), the original per-tree-structure specialization into a cached `evoxc.build_cached` graph, and an opt-in merged-population graph built with evoxc's `batch_functions` transform; there is NO custom CUDA/HIP kernel and no compiled extension to build.
It is a sister project of EvoX and is described in the paper at https://arxiv.org/abs/2501.17168.
This repository is the development root (source tree + examples + paper experiment scripts + notebooks), not a docs site.
It is ORIGINAL upstream code from EMI-Group; see `git log` for its public history (the CUDA-kernel era stays visible in history and is documented in `test/goldens/README.md`).

## Global invariants & constraints
- No build step: `import evogp.<submodule>` works from a plain checkout; the only engine requirement is an importable `evoxc` (installed editable from the sibling checkout in the dev venv).
- Device policy: the evoxc engine itself is device-agnostic, but everything above it hard-codes `device="cuda"` (the same string selects AMD GPUs under ROCm); a full training run needs a CUDA-visible device.
- `src/evogp/__init__.py` is empty by design — all imports go through submodules (`from evogp.tree import ...`, `from evogp.algorithm import ...`, `from evogp.pipeline import StandardPipeline`, `from evogp.problem import ...`).
- Fitness contract used repo-wide: `evaluate(forest)` returns a `(pop_size,)` float32 CUDA tensor that is MAXIMIZED (losses negated) and mutated in place by the pipeline.
- Most entry points run at import time (no `if __name__ == "__main__"` guard): the `example/` scripts, `test/fix_bug.py` and `src/evogp/sr_test.py` start work when imported.
- The package DAG is strict: `tree/` is the foundation (`algorithm/`, `problem/` depend on it; `pipeline/` depends on both and is imported by nothing); preserve the direction when adding modules.
- Engine economics: evaluation routes are selectable via `EVOGP_EVAL_MODE` — `dense` (alias `dynamic`): one compiled all-ops graph per population shape, no per-tree dispatch/readback; `specialized`: one cached `evoxc.build_cached` graph per tree structure; `batch` (opt-in, never chosen by `auto`): ONE merged graph per population structure multiset, built with evoxc's `batch_functions` transform and cached by that multiset; `auto` (default) picks by backend and scale: on a device box with `pop ≥ 64` it takes dense+iree (a compiled graph cannot amortize below that), otherwise specialized+numpy (always specialized on a CPU box and on every fallback).
  Per-structure compilation is memoized in one in-memory `evoxc.CompileCache` (`EVOGP_EVOXC_CACHE_SIZE`, default 4096; nothing persists across processes); on the specialized route a fresh population is a cold miss per distinct tree structure, duplicates/elites hit.
  The `batch` route has its own knobs (`EVOGP_BATCH_BAND_SIZE` 16, `EVOGP_BATCH_BANDS` — an explicit `K`, one of the flat spellings, or `auto`, `EVOGP_BATCH_CHUNK_BANDS` off, `EVOGP_BATCH_SWITCH_OPS`, `EVOGP_BATCH_ALIGNMENT`, `EVOGP_BATCH_CACHE_SIZE` 8, `EVOGP_BATCH_MIN_POP` 64, `EVOGP_BATCH_COMPILE_WORKERS` 4 — split the merge into contiguous chunks compiled concurrently, `0`/`1` = the single-executable path), a device binding-cap band policy (`K ≤ 15` bands with ≥ 8 merged functions per band on rocm/cuda), its own tables (`batch_cache_stats()` + `batch_content_stats()`), the per-stage timers `batch_stage_stats()`/`batch_stage_reset()` and a content-addressed plan key; design of record `src/evogp/tree/BATCH_EVAL.md`.
  IREE knobs: `EVOGP_EVOXC_BACKEND=iree`, `EVOGP_EVOXC_DEVICE`, `EVOGP_EVOXC_OPT_LEVEL` (only O0/O1); the compile target follows the evoxc `Device` kind (`cuda` on CUDA boxes, `rocm` on ROCm boxes).
  `EVOXC_DISABLE_LOCATIONS=1` speeds tracing up ~4x and is recommended for real runs (not part of the cache key).
- `MAX_STACK` / `MAX_FULL_DEPTH` / `NType` / `Func` are single-sourced in `src/evogp/tree/utils.py` (the old Python/C++ duplication is gone).
- Optional heavy dependencies (jax/brax, mujoco_playground, genesis, scikit-learn, pygraphviz) are imported lazily inside constructors; only brax is declared as a `setup.py` extra.
- Legacy numeric parity: the engine reproduces the deleted CUDA kernels' semantics (semantics of record: `src/evogp/tree/ENGINE_SPEC.md`) and is cross-validated against frozen goldens; generation RNG is distribution-equivalent to the legacy taus88 stream, not bit-identical.
## Known Issues
Cross-cutting problems only; the owning node documents the details.
- No CI. The pytest suite lives at `src/evogp/tests/` (1081 passed / 5 skipped on the validation box, ~121 s, the extra 7 coming from the harness's torch-free `test/benchmark/evoxc/test_large_cells.py`); the rest of the repo-root `test/` directory remains scratch tooling and is not part of the suite.
- At large scale the two compiled routes change order and the shipped `auto` policy picks the wrong one on the row axis: on the large-scale column (`test/benchmark/evoxc/LARGE_SCALE.md`) the `batch` merge is 1.1–6.2× faster than `dense` warm on 7 of 8 measured cells (6.2× at `p256-L64-i32-N16384`, 3.1× at `p1000-L64-i32-N16384`, 4.2× vs raised-cap dense on 123-node trees at pop 2 048) while it still loses at pop 2 048 / `N` 1024 (0.86×), and its compile envelope ends at pop 4 096 (78 k emitted ops / 191 s) — pop 8 192 and 187-node trees × pop 2 048 never finish a 900 s compile.
- Two library-side limits decide who wins at large scale and both are un-addressed: `EVOGP_DENSE_AUTO_MAX_ROWS` (2 048) makes `auto` decline dense on every `N ≥ 4 096` cell where dense is 1.4–8.7× faster than the `specialized`+numpy fallback it picks, and an explicit `EVOGP_EVAL_MODE=dense` on a large-population cell whose trees exceed `EVOGP_DENSE_MAX_TREE_LEN` declines into per-structure `specialized`+iree with unbounded artifact growth (measured cgroup OOM kill at pop 2 048 / 123-node trees). Details in `src/evogp/tree/CONTEXT.md` and `LARGE_SCALE.md` §7.
- Performance against the plain-PyTorch baselines (warm medians, one process per config, MI300X; report of record `test/benchmark/evoxc/FINAL.md`): the default `auto` route is 4.9–75× faster than a per-tree torch eval loop at pop ≥ 64 on `Forest.SR_fitness` and 2.1–3.9× faster than the batched whole-population torch implementation, with one honest loss — at pop 1000 × tree length 64 `torch-batched` wins by 1.16× (the engine reads 0.86–0.88×).
- At pop 16 the shipped default is 1.22–1.37× slower than plain torch-per-tree because a compiled graph cannot amortize there; forcing `EVOGP_EVAL_MODE=dense` wins both baselines in that cell (1.26–2.08× / 2.17–3.03×) at the price of a compile.
- A full GP generation (`gp_step`) is at parity at pop 16–64 and 2.9–7.9× faster than torch-per-tree / 1.4–7.8× faster than torch-batched from pop 256; the operator layer alone costs 2.2–2.7 ms per generation and is 21–53% of it.
- The opt-in `batch` route (report of record `test/benchmark/evoxc/BATCH.md` §15, round-3 evidence `test/benchmark/evoxc/results/batch_opt_round3/`, round 2 in `…/batch_opt_round2/`, round 1 in `…/batch_opt_round1/`, earlier grid `…/results/batch/`) is DOMINATED by the shipped `dense+iree` route in a GP loop and is settled unless new evidence appears: at pop 256 the shipped default shape (band size 16, 4 compile chunks) is 3.38× (L32) / 1.84× (L64) slower warm than dense and its cold call is 4 064.48 / 4 071.43 ms against dense's 3 355.83 / 6 526.78 ms measured in the same window, an 8-generation `gp_step` loop is 64.9× / 71.5× / 17.8× slower (eval-only 868× / 680× / 229×), and a fresh generation is a new structure multiset (7 of 8 generations recompile) so the merge is always rebuilt; the round-1 single-executable 0.37–0.995× grid at N=1024 still holds.
- The batch band policy is settled by measurement: `EVOGP_BATCH_BAND_SIZE` defaults to 16 (the minimax setting, never >6% off any measured warm column) and the first-order decision is flat vs banded (flat is 8–53% slower by workload); `EVOGP_BATCH_BANDS=auto` stays opt-in because evoxc's static cost model overshoots the device binding cap ~14× (213 bands against 15) and won 0/9 warm columns.
Pinning the band COUNT at the device cap (`EVOGP_BATCH_BANDS=15`) is a same-merge control at pop 256 — identical `band_sizes` and `emitted_ops` to band size 16, because the size model is already clamped to K = 15 there — and the `p64` K = 7 pin does change the plan (`[9]×7` vs `[16,16,16,15]`) but stays inside the ±5% box noise, so 16 stands and no pin beat it anywhere.
- One exported dispatch per band and 16 bindings per ROCm-HIP dispatch cap a banded merge at `K ≤ 15` bands with ≥ 8 merged functions per band (llvm-cpu `K ≤ 31`, numpy uncapped): the band-size model and `auto` are clamped to that set and record `band_clamped`/`band_note`, while an explicit illegal `EVOGP_BATCH_BANDS=K` raises `ValueError` naming the cap and the remedy.
- Chunked parallel compile (`EVOGP_BATCH_COMPILE_WORKERS`, default 4) cuts the pop-256 cold compile from 10.73 / 11.96 s to 4.06 / 4.07 s (band size 16; the compile pool is 89–96% of the cold call and `lower` only 0.8–11.6% of it) but costs 1.69–1.87× the warm call because each chunk uploads, runs and reads back separately, so break-even is 3 849 / 5 103 warm calls of one population (18 702 at 111-node trees, where the trade is 4.58× cold for 1.46× warm) and `=1` is the warm-oriented setting; chunking is inert (one chunk) below 32 deduped functions — including the `p64` fixed-population niche, whose value plans compile as `chunk_sizes [63]` — and refused for an explicit `EVOGP_BATCH_BANDS` spelling (flat included) or `switch_ops=True` — `EVOGP_BATCH_CHUNK_BANDS=1` (default off) is the only way to combine banding with chunking, and it is 2.6–2.9× faster cold / 1.69–1.87× slower warm than the single-body banded build, so it stays a fixed-population lever.
  Its wins are real but narrow: a FIXED population of ~64 trees over few data rows (round-1 p64-L64-i32-N64: batch warm 1.127 ms vs dense 1.385 ms, cold 2.24 s vs 6.44 s), and — because dense's cost tracks the `max_tree_len` trace cap while the merge tracks actual node count — 1.5–4.2× faster than a raised-cap dense and 23–25× faster than the per-tree `specialized` fallback once the population's longest tree exceeds `EVOGP_DENSE_MAX_TREE_LEN` (111/187-node trees); it still loses at the generation level there (190–460×).
- `EVOGP_DENSE_MAX_TREE_LEN` is a cost knob as well as a safety valve: on identical 31-node trees, raising the cap 64 → 128 → 256 costs 2.0 → 5.3 → 19.5 ms per call, and past the cap dense declines into the specialized fallback — so raise it only to the depth actually generated rather than switching routes.
- Where a warm dense call's time goes now (`test/benchmark/evoxc/results/final/decompose/`): `evoxc.run` is 84.7% of a 2.40 ms call at pop 256 / L=64 / N=1024 and host glue is the remaining 15.3% — the two blocks have swapped roles since `test/benchmark/r5/RCA.md` measured host glue at 75–77%.
- What remains is the dispatch-bound graph (~310 chained device ops versus the legacy CUDA engine's 3) and only a fused device-side evaluator removes it: the r6 Triton prototype (test-only, not integrated into `src/`) measures 4.8×/4.6× faster than the deleted CUDA engine (`test/benchmark/r6/SUMMARY.md`).
- Cold start is the remaining practical weakness: a dense graph compiles in ~3.1–3.4 s (L=32) / ~6.1 s (L=64) per shape × used-function-set, so a cold 50-generation run at pop 256 is 7.8× slower end to end than the plain-torch loop and break-even is ≈1250 generations; the opt-in artifact cache (`EVOGP_EVOXC_ARTIFACT_DIR`, default off) reloads an artifact in ~0.16 s and flips that run to 1.14× faster than torch.
- Benchmarking keeps two measurement types: type-1 end-to-end and type-2 pure graph-forward (`test/benchmark/pure_forward.py`); the R1–R6 rounds and `test/benchmark/REPORT.md` are historical records.
- Numeric parity by route is measured in `test/benchmark/evoxc/VALIDATION.md`: value paths are bitwise exact for the arithmetic and ternary function sets and ~1e-6 relative elsewhere, but the transcendental (`rich`) set deviates up to 4.4e-01 absolute from the plain-torch oracle at large output magnitudes on the dense/iree route, and no pytest covers `rich`-set parity per route — treat the iree transcendental lowering as approximate.
- `specialized` + iree is a bit-level outlier (11/64 trees, abs ≤1.6e-2) but sits off the default path, since `auto` routes pop ≥ 64 to dense+iree; its cause is now identified — iree contracts `mul` into a following `add`/`sub` (FMA), leaving ≤1 ulp per op but up to 2.2e-3 / 6.1e-3 relative after deep-tree cancellation at generation depth 7/8, so it is also what the shipped cap-64 dense degrades to on deep trees (repro in `test/benchmark/evoxc/BATCH.md` §11.5).
- The `batch` route's loss path matches the oracle to ~1e-7 relative but its `batch_forward` is non-bitwise on the arithmetic and ternary sets (≤1.1e-3 relative, ~1e-8 of the value scale) where dense is exact, so its records form their own digest group; dense differs from numpy only in the NaN payload bit on `sub` (value-neutral, also digest-splitting).
- The merged-graph compile grows superlinearly in the population's TOTAL node count: pop 1000 × (L=128, generation depth 7) and pop 1000 × L=256 exceeded a 20-minute compile and were recorded as dropped, while pop 1000 at depth 5 costs 178.5 s on the single-body path — the batch route's scale envelope stops well below dense's; on the shipped chunked default `p1000-L32-i8-N1024` (817 functions) compiles in 15 517.88 ms and its warm `sr_fitness` is 6.9384 ms.
- Robotics problems cannot be verified on the validation box (third-party environment boundary, not library defects): dm_control-suite MuJoCo envs need `mujoco-warp` and jax's CUDA backend hits the CuDNN 9.1-vs-9.8 mismatch; `GenesisProblem.evaluate` is a stub returning `None`; only the lazy-import binding of `MujocoProblem` is covered by tests.
- Multi-output `CombinedForest` path: the engine and the single/batched `forward`/`batch_forward` contract are implemented and tested, but the containers still lack `SR_fitness`/`to_sympy_expr`, `CombinedForest.__next__` never advances, and `SymbolicRegression.evaluate` rejects a `CombinedForest` — the supported route is `evogp.problem.CustomLoss` (`example/combined_sr.py` runs end to end).
- No dimension validation exists between `GenerateDescriptor.input_len/output_len` and `problem.problem_dim/solution_dim` (the pipeline's asserts are commented out), so mismatches fail inside the tree layer/engine instead of at wiring time.
- `test/goldens/*.npz` are frozen outputs of the deleted CUDA engine (bitwise-reproducible captures, no longer re-capturable) — treat as read-only fixtures; comparisons use 1e-4 rtol/atol because the old kernels used fast-math.
## Test Strategy
Supported sequence on the validation box (repo root as CWD, `PYTHONPATH=src:<evoxc checkout>`, the project venv's `bin/python` — never the `python` on PATH, which lacks torch; `EVOXC_DISABLE_LOCATIONS=1` recommended):
1. Import check (no build needed): `PYTHONPATH=src <venv>/bin/python -c "import evogp.tree"`.
2. `PYTHONPATH=src <venv>/bin/python -m evogp.sr_test` — synthetic SR convergence smoke (~16 s; best fitness ≈ −0.23).
3. `PYTHONPATH=src <venv>/bin/python -m pytest src/evogp/tests -q` — full suite (~114 s; 1074 passed / 5 skipped); `--ignore=src/evogp/tests/test_equivalence.py` for the fast subset, `-k golden` for the legacy-golden cross-checks, `-k batch` for the batch route.
4. Run the relevant `example/*.py` from the repository root (relative asset paths such as `imgs/` are CWD-dependent); `test/fix_bug.py` is a script (`python test/fix_bug.py`), not pytest.
5. Performance work: the current harness is `test/benchmark/evoxc/` (reproduce commands in its `README.md`, verdicts in `FINAL.md` for the shipped routes and `BATCH.md` for the opt-in `batch` route, gate `python test/benchmark/evoxc/check.py` per side with `--allow-missing --allow-digest-mismatch`, one process per config, warm medians, idle-GPU guard; `--tree-root` times any checkout, e.g. the pre-optimization snapshot at commit `530518e`; `batch_economics.py` measures per-generation compile economics and `--cells long`/`--arms batch` scope the long-tree rounds; `band_sweep.py` runs the batch band-size/auto grid (including the `k15`/`k7` band-COUNT pins, gated by the device cap) and `--cold-only` re-prices the cold column in ~1.5 min per cell; `BATCH.md` §15 is the round-3 closing section (per-cell warm/cold/loop table, compile-pool break-even, band-size policy, what would have to change) with its numbers in `results/batch_opt_round3/SUMMARY.md`). The R1–R6 rounds under `test/benchmark/{r2,r4,r5,r6}/` plus `REPORT.md` are historical records with their own still-valid gates, and the r6 Triton prototype keeps `SUMMARY.md` + `check_r6.py` as its analysis of record.
Known coverage gaps: dense/iree parity on the transcendental (`rich`) set, `specialized`-iree parity bounds, robotics rollouts, `CustomLoss` end to end, multi-output `CombinedForest` training route, cold-compile economics (no test covers it), and bitwise `batch_forward` parity on the arithmetic set (measured non-bitwise, deliberately tolerated at ~1e-3 relative).
## Notes for Agents
- Read `src/evogp/CONTEXT.md` first; it is the entry point to the library (API surface, dependency DAG, engine constraints).
- Never reintroduce a compiled extension or hand-written kernels; legacy op semantics are preserved as documentation only (`src/evogp/tree/ENGINE_SPEC.md` appendices, `test/goldens/README.md`).
- The most valuable single place to look for a numeric bug is the boundary between `tree/` (tensor schema, host-side decode) and the evoxc engine (`tree/evoxc_engine.py`); the independent plain-torch oracle `src/evogp/tests/reference_eval.py` is the reference to diff against.
- `python`/`python3` on PATH lack torch — always use the project venv; that venv has no `pip` and no jupyter/nbconvert (notebook re-execution uses the stdlib-json runner recipe in `tutorial/CONTEXT.md`).
- Determinism comes from torch's global RNG: `torch.manual_seed(0)` makes generation reproducible (distribution-equivalent to the legacy stream, not bit-identical).
