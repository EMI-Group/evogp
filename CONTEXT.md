# EvoGP — tree-based genetic programming on EvoX Compiler (`evoxc`), 1.0-alpha release `1.0.0a1` (repository root)
## Intent
EvoGP is a Tree-based Genetic Programming (TGP) framework for symbolic regression, the GP layer of the EvoX family and the subject of the paper at https://arxiv.org/abs/2501.17168.
`1.0.0a1` (1.0-alpha) is the first public pre-release of a SINGLE-STACK engine: the pre-1.0 torch-native stack (`evogp.tree` / `algorithm` / `problem` / `pipeline` / `sr_test`) is gone, and the engine the package ships is `evogp.gp` — a torch-free functional GP engine built on `evoxc` graphs plus numpy host glue, in the EvoX 2.0 idiom (frozen config dataclasses, tensor-only state, plain `init_gp` / `step` / `run` functions, key-based determinism via `run(..., key=0)`).
Two optional satellites sit beside the engine and neither is imported by it: `evogp.fused`, the device-native Triton evaluator, and `evogp.evox_ext`, which presents the stack as `evox.core.StdWorkflow` algorithm + problem components.
There is NO compiled extension and no build step: every route emits `evoxc` graphs, and the only JIT outside `evoxc` is Triton's, paid once at the fused route's first call.
Evaluation is three routes over one population encoding — the host numpy evaluator (the correctness route, no device), the in-graph `iree` route (`GraphEvaluator`, device-resident, one compiled graph per shape) and the fused Triton route (`FusedDeviceEvaluator`, one kernel launch per (tree, row block)).
The repository is the development root (source tree + examples + tutorial + dev tooling + the archived records of the pre-1.0 torch-native stack), not a docs site; the upstream project is EMI-Group's, and the CUDA-kernel era stays visible in `git log`.

## Global invariants & constraints
- No build step: `import evogp.gp` works from a plain checkout with `PYTHONPATH=src` alone, pulls in neither torch, `evox`, nor `evoxc` at module scope, and needs numpy only; `import evoxc` happens at call time (`encoding._evoxc()`, `_runtime.evoxc()`, `problem._require_evoxc`), each raising a `RuntimeError` that names the fix.
- `src/evogp/__init__.py` is EMPTY by design: `import evogp` has no side effects and exposes nothing; every import goes through a submodule.
- `evogp.fused` is the ONE subtree that imports torch at module scope (so it needs the `fused` extra); `triton` stays lazy inside `fused/kernels.py`; `evogp.gp` reaches `fused` only through an in-function `importlib` in `gp/fused_eval.py`.
- `evogp.evox_ext` is the only subtree that imports `evox`, at call time, and it is the only consumer of the `evox` extra.
- Dependency DAG: `gp/ → _tables.py, _multi_output.py`; `fused/ → _tables.py, _multi_output.py` (imports nothing from `gp/`); `evox_ext/ → gp/`; nothing imports `evox_ext/`, and nothing imports `evogp.fused` at import time.
- Population encoding: three prefix-order `[pop_size, max_nodes]` channels — `opcode` int32 (a `Func` id on a function node, an `NType` marker on a leaf), `payload` float32 (constant or variable index), `size` int32 (subtree size); node 0 is the root, only `[0, size[:, 0])` is live, and children are addressed `c1 = i + 1`, `c2 = c1 + size[c1]`, `c3 = c2 + size[c2]`.
- Fitness contract, repo-wide: the objective returns a `(pop_size,)` float32 vector that is MAXIMIZED (losses negated) and every non-finite entry is mapped to `-inf`; the driver never mutates the array a caller returned.
- Determinism is key-based: the RNG is an `evoxc` splitmix64 key carried in `GPState` and advanced there, `run(..., key=0)` reproduces a whole run from one integer, and there is no global seed and no `torch.manual_seed` anywhere in the reachable stack.
- Single-output only: `init_population` raises `NotImplementedError` for `output_len > 1`, every evaluator refuses an `OUT_NODE`-tagged population (`evogp._multi_output.MultiOutputError`), and `CustomLoss` is the documented escape hatch (including for a multi-output fitness); the fused route itself serves `output_len` 1..`MAX_OUT_LEN` (8).
- Device policy: numpy is the default, the correctness backend and the only one needing no device; `backend="iree"` with an `evoxc.Device` is the device route and rejects host input (no implicit transfer; a download goes through `.to(evoxc.Device("cpu", 0))`); the fused route needs a CUDA/HIP-visible device, a writable `TRITON_CACHE_DIR` (defaulted to `$TMPDIR/evogp-triton-cache` when unset) and the `fused` extra.
- Surviving environment knobs, all defaulted: `EVOGP_GP_COMPILE_CACHE_SIZE` (64), `EVOGP_GP_GRAPH_CACHE_SIZE` (32), `EVOGP_GP_EVAL_BUDGET_MB` (256), and the fused geometry `EVOGP_FUSED_BLOCK_ROWS` (256), `EVOGP_FUSED_NUM_WARPS` (1), `EVOGP_FUSED_MAX_SCRATCH_MB` (8192), `EVOGP_FUSED_HOST_MEMO` (16), `EVOGP_FUSED_DISPATCH` (`bound`). `EVOXC_DISABLE_LOCATIONS=1` speeds tracing up and is recommended for real runs.
- There is NO route policy and NO evaluation-mode variable: the route IS the `evaluate=` argument. `EVOGP_EVAL_MODE`, `EVOGP_DENSE_*`, `EVOGP_BATCH_*`, `EVOGP_EVOXC_*` and `EVOGP_FUSED_MIN_POP` are gone with the pre-1.0 torch-native stack.
- Never reintroduce a compiled extension or a hand-written CUDA/HIP kernel; the fused route's kernels are Triton source JIT-compiled on the fly.
- Never reintroduce the torch stack; if a deleted behaviour is needed, port it onto the channels (`test/archive/` documents the semantics, `git show 6720723:<path>` the code).
- Optional heavy dependencies are imported lazily or behind extras; the hard requirements are `evoxc` + numpy.
## Known Issues
Cross-cutting problems only; the owning node documents the details.
- CI is release-only: `.github/workflows/release.yml` runs on a published GitHub Release (plus a `workflow_dispatch` dry run) and its gate is `src/evogp/gp/tests` on a GitHub-hosted runner, so nothing runs on a pull request or a push and the fused/device suites still run by hand on the reference box.
  The manual gate is quoted per path — `pytest src/evogp/gp/tests` (349 passed), `pytest src/evogp/fused/tests` (45 passed), `pytest src/evogp/evox_ext/tests` (13 passed) = 407 passed / 0 failed, never reported as a bare sum — and the release's PyPI Trusted Publishing must be configured for project `evogp`, owner `EMI-Group`, repository `evogp`, workflow `release.yml` and environment `pypi`.
- `import evogp.fused` needs torch installed (module scope, by design) and `import evogp.evox_ext` is fine but its `make_stdworkflow` raises without `evox`; only `evogp.gp` is guaranteed on a numpy-only box. A `pip install evogp` without extras therefore yields the engine only.
- Neither archive carries the pytest suites — `[tool.uv.build-backend].source-exclude = ["tests"]` enforces it, because they need the dev-only `test/oracle/` tooling — so a packager can install and run the engine but cannot run the tests from the tarball; the suites live in the repository.
- `GraphEvaluator(backend="iree")` cannot compile at `max_nodes=64` on this box (`iree-compile` cannot distribute the channel graph's `stablehlo.reduce` on gfx942) while `max_nodes=32` compiles — the in-graph route is capped at small trees here, and its records are at 32 nodes.
- Single-output only, and the missing container surface is real: there is no population/forest object, no classification / feature-transformation / robotics problem, no sympy or infix exporter in the public API (`GPResult.best_channels` is the three 1-D rows of the winner, a population of one) and no PNG rendering; the examples compose an expression with the private `evogp.gp._constants` tables, so an expression exporter is the top paper-facing gap.
- `evogp.gp` channel validation is a ~50 ms Python loop per 256 × 300-node population (`validate=False` is the only mitigation), and the stack owns two `CompileCache`s (the operator layer's and the problem layer's).
- The device crossing is the open per-call item: `FusedDeviceEvaluator` exports three evoxc channels, converts them into torch channels and fences once per call, which measured 9.0×–19.8× dearer per call than the pre-1.0 torch-native stack's pre-bound `Forest` kernel on the same trees; the fix is structural (a kernel that reads the gp channel layout directly), not a faster conversion.
- The fused route's own limits (`src/evogp/fused/CONTEXT.md`, `fused/FUSED.md` §7): the multi-output path materialises the `(pop, rows, out_len)` prediction buffer, `rows ≤ 64` at 8–32-node trees is unmeasured, there is no per-stage timer surface (`cases.time_call` in the battery is the only timer), the envelope is a budget rather than a guarantee, the route is single-device by construction, and `clear_fused_cache()` deliberately keeps the compiled kernel handles (pinned by a test).
- `evox` 2.0 is a PyPI pre-release (needs `--pre`) and is GPL-3.0-or-later while EvoGP is Apache-2.0; `evogp.evox_ext` is an optional adapter, not a dependency of the engine, and `StdWorkflow(cache_dir=...)` is feature-detected so an older `evox` still runs.
- Performance numbers of record were measured on the pre-1.0 torch-native tree (commit `6720723`), whose torch-stack arms no longer exist: the surviving, reproducible columns are the gp lanes plus a plain-torch baseline, driven by `python -m evogp.gp.measure_popscale` / `measure_generation` / `measure_fused` with evidence under `src/evogp/gp/evidence/`.
  Per call, `gp-fused` reads 0.626 → 0.729 ms across pop 64 → 8 192 (1.16× for 128× population, floor ≈0.62 ms + 1.3e-05 ms/tree) against plain-torch batched 3.20× → 10.68×, torch-per-tree 29.8× → 481.9× and numpy 4.53× → 725.9×; the in-graph route is linear (0.574 → 10.99 ms) and crosses plain-torch batched between pop 1 024 and 2 048.
  A whole generation is 1.32 → 1.45 ms, i.e. 1.83×–2.31× the pre-1.0 torch-native stack and 1.69×–2.34× its fused route, because the operator layer is 3.2×–3.9× cheaper (0.50–0.92 ms against 2.19–2.95 ms) even where the evaluation slice loses.
  Cold start: `gp` 2.42–2.54 s (the IREE graph), `gp-fused` 0.87–0.91 s (one Triton JIT), the pre-1.0 torch-native stack ~0.60 s, so `gp-fused` needs ≈1 769–2 643 generations to amortize against it.
- `test/archive/` is read-only evidence: its producing code was deleted, its paths moved (`test/archive/benchmark/...`) and its numbers are not reproducible from this tree; the library's own reports (`gp/POPSCALE.md`, `gp/DEVICE_LOOP.md`, `fused/FUSED.md`) carry a banner saying so.
## Test Strategy
Reference box: the project venv `/tmp/rocvenv/bin/python` (py3.12, torch 2.13+rocm7.1 and triton installed, iree 3.11; NEVER `python`/`python3` on `PATH`, which lack torch and iree), with `evoxc` from the sibling checkout `/root/evoxc` and `evox` from `/root/evox/src`. CWD is the repo root.
1. Import checks (no build needed): `PYTHONPATH=src <py> -c "import evogp.gp"` (must also pass with neither `evoxc`, `evox`, torch nor triton importable) and `PYTHONPATH=src:/root/evoxc <py> -c "import evogp.fused, evogp.evox_ext"`.
2. Convergence smoke, the documented install validation: `PYTHONPATH=src:/root/evoxc EVOXC_DISABLE_LOCATIONS=1 <py> -m evogp.gp.smoke` → 100 generations, `-0.27225 → -0.10690`, 57-node winner, 3.7–4.4 s on the box (faster is normal on a quiet card).
3. The gate, quoted per path: `PYTHONPATH=src:/root/evoxc:/root/evox/src EVOXC_DISABLE_LOCATIONS=1 TRITON_CACHE_DIR=/tmp/triton_cache_root <py> -m pytest src/evogp/gp/tests src/evogp/fused/tests src/evogp/evox_ext/tests -q` → 349 / 45 / 13 passed, 0 failed (`-k fused` scopes the kernel net; `-k purity` the torch-free contract test).
4. `python -m evogp.fused.check --stage {parity,multi,goldens,declines,timing,tuning}` (or `--stage all`) is the in-library battery: 56/56 parity, 65/65 multi-output, 6/6 goldens, 58/58 declines, six timing cells (~55 s), the 4×3 tuning grid (~12 min); it needs a device and imports the oracle from `test/oracle`.
5. Examples: run each of the five `example/*.py` from the repo root with `PYTHONPATH=src:/root/evoxc:/root/evox/src EVOXC_DISABLE_LOCATIONS=1 TRITON_CACHE_DIR=<writable>` and compare against the measured table in `example/CONTEXT.md` — every deterministic number must match, timings may drift ±20 %.
6. Tutorial: `PYTHONPATH=src:/root/evoxc:/root/evox/src EVOXC_DISABLE_LOCATIONS=1 TRITON_CACHE_DIR=<writable> <py> tutorial/run_notebook.py` → `7/7 code cells MATCH, 0 lines differing`, ~15 s; `--write` refreshes the stored outputs deliberately.
7. Performance work: the reports of record are `src/evogp/gp/POPSCALE.md`, `src/evogp/gp/DEVICE_LOOP.md` and `src/evogp/fused/FUSED.md`, reproduced with `python -m evogp.gp.measure_popscale` (`--pops`, `--lanes numpy|gp|gp-fused|torch-batched|torch-per-tree`, `--reps`, `--warmup`), `measure_generation.py` and `measure_fused.py`, plus `python -m evogp.fused.check --stage timing|tuning`; one process per timed config, warm medians, an idle card.
8. Packaging, the `uv_build` path: `uv` is NOT preinstalled in the reference venv, so create a scratch venv under `$TMPDIR`, `pip install uv` and run `uv build`; assert both artefacts exist — `dist/evogp-1.0.0a1-py3-none-any.whl` and `dist/evogp-1.0.0a1.tar.gz` — then unpack the wheel under `$TMPDIR`, install it with `evoxc` + `numpy` into a clean venv and re-run step 2 (the smoke) from outside the checkout, so the src layout cannot shadow the installed module.
Coverage gaps: no test drives the pre-1.0 torch-native stack's behaviours by design; the `rich` transcendental parity on the in-graph `iree` route, the fused route's `rows ≤ 64` corner, a gf x942 `max_nodes=64` in-graph compile, and an expression/`sympy` exporter do not exist yet.
## Notes for Agents
- Read `src/evogp/CONTEXT.md` first, then the child `CONTEXT.md` of whichever subpackage you touch (`gp/`, `fused/`, `evox_ext/`) — each owns its API surface, invariants and known issues.
- The library is torch-free by contract except `fused/`: `src/evogp/gp/tests/` greps every `gp/` module for `import torch` / `from torch` / `import evox` / `from evox`, and a clean-subprocess case asserts `import evogp.gp` with `PYTHONPATH=src` alone pulls neither torch, `evox`, nor `evoxc`.
- The single source of truth for node types, function ids and arities is `src/evogp/_tables.py`; the single `OUT_NODE` refusal rule is `src/evogp/_multi_output.py`. Do not re-derive either.
- When touching `gp/fused_eval.py` (the one torch boundary of the engine) keep torch, triton and `evogp.fused` resolved with `importlib` INSIDE functions — a literal `import torch` there is a test failure.
- Every fused call needs `TRITON_CACHE_DIR` writable, and its first call costs a one-time Triton JIT (~1.6 s for the value kernel from an empty cache, ~2 ms from a warm disk cache).
- Deleted-stack code is recoverable read-only: `git show 6720723:<path>`; the archived benchmark harness/reports are under `test/archive/` and are evidence, not tooling.
- Notebook output is pinned: use `tutorial/run_notebook.py` rather than hand-editing stored outputs, and `--write` only when the change is intended.
- Bump both places when the version moves: `[project].version` in `pyproject.toml` and the README / CHANGELOG headers (the release workflow refuses a tag that does not match).
## Joint effort across EvoGP, evoxc and evox
The EvoX 2.0 line is one effort across three repositories; the contracts live with the code that uses them (`src/evogp/gp/EVOXC_API.md`, `src/evogp/evox_ext/CONTEXT.md`, `src/evogp/fused/FUSED.md`).
### From `evoxc` (EvoX Compiler, `/root/evoxc`)
- Required: `evoxc.build` / `evoxc.run` / `evoxc.build_cached`, the `CompileCache`, `evoxc.Device`, the `iree` adapter, and the native DLPack device export (`evoxc.core.Tensor.__dlpack__` / `__dlpack_device__`, `evoxc.from_dlpack`, `register_external_kernel(..., device_resident=True)`).
- The DLPack export is a merged contribution (commit `474bf72` on `/root/evoxc`'s main line); on an older `evoxc` whose `Tensor.__dlpack__` raises `DeviceError` for a device payload, `evogp.gp.interop_available()` answers `False` and the fused objective declines onto the host hand-off — correct but slower (one upload and one readback per call).
- `evoxc` is the package's one hard dependency (`evoxc>=0.1.0`); the dev venv takes it from the sibling checkout.
### From `evox` (EvoX 2.0.0a1+, `/root/evox`, importable as `/root/evox/src`)
- Required only by `src/evogp/evox_ext/`: `evox.core.StdWorkflow` and its component contract (a module holding a frozen config dataclass plus `init(config, key)` / `step(config, state, evaluate)` / `evaluate(config, state, pop)`), from the revision that also carries `StdWorkflow(cache_dir=...)`.
- `make_stdworkflow(cache_dir=...)` forwards that opt-in compiled-step artifact cache, feature-detected with `accepts_cache_dir` (an `inspect.signature` probe); an `evox` without the keyword drops the request with a `RuntimeWarning` instead of raising, and a repeated iree workflow cold start falls from 1.30 s to 0.07 s where it is available.
- `evox` 2.0 ships no tree / GP / symbolic-regression component, so `evogp.gp` — plus this adapter — is the family's GP layer, not a port; the idiom (frozen configs, tensor-only state, key-based RNG) is borrowed, not the code.
