# EvoGP — Tree-based Genetic Programming on EvoX Compiler (evoxc), EvoX-2.0-aligned (repository root)
## Intent
EvoGP is a Tree-based Genetic Programming (TGP) framework for symbolic regression, classification, feature transformation and robotics-control benchmarks (Brax / MuJoCo-Playground / Genesis), with multi-output trees for classification and policy optimization.
Release line 2.0.0a1 ships two stacks over that one engine: the torch-native stack (`tree/`, `algorithm/`, `problem/`, `pipeline/`, `sr_test.py` — also the numerics oracle and the benchmark baseline) and the torch-free functional stack `gp/`, which follows the idiom of EvoX 2.0 (`evox` 2.0.0a1, the from-scratch functional rewrite of EvoX on `evoxc`).
There is NO custom CUDA/HIP kernel and no compiled extension to build: the fused route's Triton kernels are JIT-compiled at the first call, and every other route emits graphs through evoxc.
Evaluation is a "true jit" over evoxc (EvoX Compiler, the compiler the EvoX 2.0 line is built on) with four selectable routes (`EVOGP_EVAL_MODE`): `fused` (one fused Triton kernel launch for the whole population — `auto`'s FIRST choice on a device box, 41×–157× the plain-torch batched evaluator and 8.6×–663× the `dense` default, and the route to use on any CUDA-visible device), `dense` (one all-ops graph per population shape — `auto`'s device choice when the fused route is unavailable or below its floor), `specialized` (the original per-tree-structure specialization into a cached `evoxc.build_cached` graph) and `batch` (opt-in merged population built with evoxc's `batch_functions` transform).
It is a sister project of EvoX and is described in the paper at https://arxiv.org/abs/2501.17168; EvoX 2.0 has no tree/GP/symbolic-regression component, so the GP layer is EvoGP's contribution to the family.
This repository is the development root (source tree + examples + paper experiment scripts + notebooks), not a docs site.
It is ORIGINAL upstream code from EMI-Group; see `git log` for its public history (the CUDA-kernel era stays visible in history and is documented in `test/goldens/README.md`).

## Global invariants & constraints
- No build step: `import evogp.<submodule>` works from a plain checkout; `evoxc` is the one runtime engine dependency (a declared PyPI dependency now, or the sibling checkout in the dev venv), `evogp.gp` needs neither torch nor a device, and the only run-time JIT outside evoxc is Triton's on the fused route's first call.
- Device policy: the evoxc engine itself is device-agnostic, the functional stack runs numpy/CPU by default and device-resident (`backend="iree"` + the fused Triton objective) on a ROCm/CUDA box, and everything in the torch stack hard-codes `device="cuda"` (the same string selects AMD GPUs under ROCm) — so a full torch-stack training run needs a CUDA-visible device, while the fused route turns that device into the speed (and needs a writable `TRITON_CACHE_DIR`).
- `src/evogp/__init__.py` is empty by design — all imports go through submodules (`from evogp.tree import ...`, `from evogp.algorithm import ...`, `from evogp.pipeline import StandardPipeline`, `from evogp.problem import ...`).
- Fitness contract used repo-wide: `evaluate(forest)` returns a `(pop_size,)` float32 CUDA tensor that is MAXIMIZED (losses negated) and mutated in place by the pipeline.
- Most entry points run at import time (no `if __name__ == "__main__"` guard): the `example/` scripts, `test/fix_bug.py` and `src/evogp/sr_test.py` start work when imported.
- The package DAG is strict: `tree/` is the foundation (`algorithm/`, `problem/` depend on it; `pipeline/` depends on both and is imported by nothing); preserve the direction when adding modules.
- Engine economics: evaluation routes are selectable via `EVOGP_EVAL_MODE` — `fused`: ONE fused Triton kernel launch for the whole population on the torch device, tree channels read directly, no evoxc graph, no per-node dispatch, no readback; `dense` (alias `dynamic`): one compiled all-ops graph per population shape; `specialized`: one cached `evoxc.build_cached` graph per tree structure; `batch` (opt-in): ONE merged graph per population structure multiset, built with evoxc's `batch_functions` transform and cached by that multiset; `auto` (default) picks by backend and scale: on a device box it takes `fused` FIRST from `EVOGP_FUSED_MIN_POP` (16) up while `triton` is importable and the call fits the fused memory envelope, else `dense`+iree at `pop ≥ 64` (a compiled graph cannot amortize below that), and `specialized`+numpy everywhere else (always specialized on a CPU box and on every fallback); `auto` never selects `batch`.
  That device path is gated by a MEMORY ENVELOPE, not a row ceiling: dense's largest intermediate is `pop_size * tree_len * rows * 4` bytes, so `auto` declines a `per_row=False` call whose product exceeds `EVOGP_DENSE_AUTO_BUDGET_MB` (8192), and `EVOGP_DENSE_AUTO_MAX_ROWS` (`0` = unpinned) can only tighten that allowance.
  `auto` also raises the dense trace cap for an over-cap population instead of declining it: the effective cap is `min(EVOGP_DENSE_AUTO_MAX_TREE_LEN (256), next_power_of_two(max(base 64, longest tree)))`, with the envelope re-checked at the rounded value, a refused raise staying on the device backend (`iree`, never numpy), and a generation that crosses a power of two costing one recompile.
  Measured on the large-scale column: `p256-L64-i32-N4096` 5.85 ms/call against 50.47 ms on the fallback (8.6×), `p256-L64-i32-N16384` 78.38 against 110.21 ms (1.41×), and `p2048-L128-i32-N1024-d7` (123-node trees) 105.81 ms/call and 127.05 ms `gp_step` at `L=128` against 857.22 / 10 014.83 ms — every other large-scale cell is unchanged.
  Per-structure compilation is memoized in one in-memory `evoxc.CompileCache` (`EVOGP_EVOXC_CACHE_SIZE`, default 4096; nothing persists across processes); on the specialized route a fresh population is a cold miss per distinct tree structure, duplicates/elites hit.
  The `batch` route has its own knobs (`EVOGP_BATCH_BAND_SIZE` 16, `EVOGP_BATCH_BANDS` — an explicit `K`, one of the flat spellings, or `auto`, `EVOGP_BATCH_CHUNK_BANDS` off, `EVOGP_BATCH_SWITCH_OPS`, `EVOGP_BATCH_ALIGNMENT`, `EVOGP_BATCH_CACHE_SIZE` 8, `EVOGP_BATCH_MIN_POP` 64, `EVOGP_BATCH_COMPILE_WORKERS` 4 — split the merge into contiguous chunks compiled concurrently, `0`/`1` = the single-executable path, `EVOGP_BATCH_DISPATCH_FORMATION` — where `auto` turns IREE's `--iree-dispatch-creation-enable-aggressive-fusion` on for rocm/cuda merged plans, `aggressive` forces it and `default`/`off` restores the plain build, feature-detected so an evoxc whose iree adapter does not declare the option degrades to `default` silently), a device binding-cap band policy (`K ≤ 15` bands with ≥ 8 merged functions per band on rocm/cuda), its own tables (`batch_cache_stats()` + `batch_content_stats()` + `batch_artifact_stats()`), the per-stage timers `batch_stage_stats()`/`batch_stage_reset()` and a content-addressed plan key; design of record `src/evogp/tree/BATCH_EVAL.md`.
  Aggressive fusion is worth −4.9 % / −4.8 % / −14.6 % warm on the three largest merges, ≈0 to +1.9 % elsewhere, and never worse cold (up to −36.5 %), so the shipped `auto` needs an evoxc checkout whose iree adapter declares the option — otherwise it silently serves the plain build.
  Its executable tier is persistent and shares `EVOGP_EVOXC_ARTIFACT_DIR` with the dense tier — entries under a `batch/` subdirectory keyed by the merged plan content digest + chunk index + compile options, counters `batch_artifact_stats()`; a full hit skips every compile (p2048 cold 44.27 s → 4.10 s, p1000 `N=4096` 16.98 s → 2.21 s, digests identical).
  IREE knobs: `EVOGP_EVOXC_BACKEND=iree`, `EVOGP_EVOXC_DEVICE`, `EVOGP_EVOXC_OPT_LEVEL` (only O0/O1); the compile target follows the evoxc `Device` kind (`cuda` on CUDA boxes, `rocm` on ROCm boxes).
  `EVOXC_DISABLE_LOCATIONS=1` speeds tracing up ~4x and is recommended for real runs (not part of the cache key).
  The `fused` route (knobs `EVOGP_FUSED_MIN_POP` 16, `EVOGP_FUSED_BLOCK_ROWS` 256, `EVOGP_FUSED_NUM_WARPS` 1, `EVOGP_FUSED_MAX_SCRATCH_MB` 8192, `EVOGP_FUSED_HOST_MEMO` 16; `auto`'s first choice on a device box, and `EVOGP_EVAL_MODE=fused` to force it; design + report of record `src/evogp/tree/FUSED.md`, campaign `test/benchmark/evoxc/results/t1a1_fused/`, gates `src/evogp/tests/test_fused_route.py` and `python -m evogp.tree.fused_check --stage all`) serves `output_len` 1..`MAX_OUT_LEN` (8), keeps the value buffer and the `(pop, n_rb)` loss chart device-resident, and pays no per-generation compile or re-prep (5/5 transforms hit, 0 compiles, 0 declines over five warm generations).
  Measured warm on the reference box: `Forest.batch_forward` 0.0995 ms at p256-L32-i8 / 0.1016 at p256-L64 / 0.1095 at N=4096 / 0.1053 at p1000 / 0.1460 at p4096 / 0.1673 on the 123-node `p2048-L128-d7` cell — 41×–157× the harness's `torch-batched` arm (0.10–0.17 ms against 4.0–26.5 ms; 32×–131× on `SR_fitness`) and 8.6×–663× the `dense` default; a whole GP generation is 2.64–2.90 ms with only 0.23–0.26 ms (8.7–9.1 %) in evaluation, so the operator layer is now the bottleneck.
  Its cold start is a one-time Triton JIT of ~1.6 s for the value kernel (0.94–0.99 s loss, 0.32 s per-row from an empty cache; ~2 ms from a warm disk cache, where the specialization key is `(per_row, reduce, use_mse, block_rows, num_warps)`), with NO per-shape compile, and `TRITON_CACHE_DIR` must point at a writable directory or the first launch dies on a read-only `$HOME`.
  Its residual limits: the single-output path folds the reduction in registers while `output_len ≥ 2` materializes the `(pop, rows, out_len)` prediction buffer; the tree walk repeats once per row block and per-program work scales with pop (0.1016 → 0.1460 ms from pop 256 to 4 096, while 4× the rows costs 0.1016 → 0.1095 ms); host glue is 22–49 % of a warm call where the kernel is 51–78 %; there is no per-stage timer surface; and `EVOGP_FUSED_MIN_POP` 16 keeps single-tree calls on the specialized engine.
  `auto` never selects `batch`: the opt-in merged-graph route stays opt-in, while the fused route IS the default on a device box.
- The evoxc↔torch device interop is an `evoxc` API: `evoxc.core.Tensor.__dlpack__` / `__dlpack_device__` export a DEVICE payload zero-copy, `evoxc.from_dlpack` imports one back, and `evoxc.register_external_kernel(..., device_resident=True)` lets a compiled graph call a device kernel (the fused Triton route is such a kernel) on device-resident inputs/outputs.
  `evogp.gp` still reaches that capability through its local `_device_interop.py` shim, which is explicitly transitional and is being replaced separately; the `tree/` value paths keep their host readback.
- `MAX_STACK` / `MAX_FULL_DEPTH` / `NType` / `Func` are single-sourced in `src/evogp/tree/utils.py` (the old Python/C++ duplication is gone).
- Optional heavy dependencies (torch, triton, jax/brax, mujoco_playground, genesis, scikit-learn, pygraphviz) are imported lazily inside constructors or declared as extras (`torch`, `fused`, `brax`, `iree`, `visualize`, `dev`); the hard requirements are `evoxc`, `evox`, numpy, scikit-learn, networkx and sympy.
- Legacy numeric parity: the engine reproduces the deleted CUDA kernels' semantics (semantics of record: `src/evogp/tree/ENGINE_SPEC.md`) and is cross-validated against frozen goldens; generation RNG is distribution-equivalent to the legacy taus88 stream, not bit-identical.
## Known Issues
Cross-cutting problems only; the owning node documents the details.
- No CI. Two pytest suites, neither part of a CI job: the torch stack at `src/evogp/tests/` (1 262 cases — 1 252 passed / 7 skipped / 3 failed in ~125 s on the device reference box) and the torch-free functional stack at `src/evogp/gp/tests/` (318 passed, ~66 s on a device box where its three device-gated modules run instead of skipping); `pytest test src/evogp/tests -q` is the historical full gate (it adds the harness's torch-free `test/benchmark/evoxc/` tests — 33 passed), and the rest of the repo-root `test/` directory remains scratch tooling.
- The 3 red cases are ONE stale assertion in the fused-route net: `src/evogp/tests/test_fused_route.py::test_auto_never_selects_fused` (parametrized over pop 16 / 64 / 256) asserts `resolve_route(pop, backend=None).engine != "fused"`, i.e. the pre-policy claim that `auto` never picks the fused route, so it fails on any device box with Triton where `auto` now resolves to `fused` from `EVOGP_FUSED_MIN_POP` up; the assertion has to be inverted (fused at/above the floor, `specialized` below it), not the policy.
- An explicit `EVOGP_EVAL_MODE=dense` never gets `auto`'s cap raise or envelope: on a large-population cell whose trees exceed `EVOGP_DENSE_MAX_TREE_LEN` it declines into per-structure `specialized`+iree with unbounded artifact growth (measured cgroup OOM kill at pop 2 048 / 123-node trees), so use `auto` or the `batch` route there (details in `src/evogp/tree/CONTEXT.md`).
- Performance against the plain-PyTorch baselines (warm medians, one process per config, MI300X; report of record `test/benchmark/evoxc/FINAL.md`): the default `auto` route is 4.9–75× faster than a per-tree torch eval loop at pop ≥ 64 on `Forest.SR_fitness` and 2.1–3.9× faster than the batched whole-population torch implementation, with one honest loss — at pop 1000 × tree length 64 `torch-batched` wins by 1.16× (the engine reads 0.86–0.88×).
- At pop 16 the shipped `auto` default is 1.22–1.37× slower than plain torch-per-tree because a compiled graph cannot amortize there; forcing `EVOGP_EVAL_MODE=dense` wins both baselines in that cell (1.26–2.08× / 2.17–3.03×) at the price of a compile, and the `fused` route wins it outright (its kernel is flat in `pop_size`), which is what `EVOGP_FUSED_MIN_POP` 16 is calibrated on.
- A full GP generation (`gp_step`) is at parity at pop 16–64 and 2.9–7.9× faster than torch-per-tree / 1.4–7.8× faster than torch-batched from pop 256; the operator layer alone costs 2.2–2.7 ms per generation and is 21–53% of it.
- The opt-in `batch` route (design of record `src/evogp/tree/BATCH_EVAL.md`, closing section `test/benchmark/evoxc/BATCH.md` §15, round-3 evidence `test/benchmark/evoxc/results/batch_opt_round3/`, round 2 in `…/batch_opt_round2/`, round 1 in `…/batch_opt_round1/`, earlier grid `…/results/batch/`) loses any generation loop and wins a fixed large population: at pop 256 the shipped default shape (band size 16, 4 compile chunks) is 3.38× (L32) / 1.84× (L64) slower warm than dense, an 8-generation `gp_step` loop is 64.9× / 71.5× / 17.8× slower (eval-only 868× / 680× / 229×) because a fresh generation is a new structure multiset (7 of 8 generations recompile) and a real `gp_step` loop on the large-scale column still loses by 68–178×. On the static axis it now leads dense on 7 of 8 large-scale cells (`test/benchmark/evoxc/LARGE_SCALE_ROUND2.md`): 6.34× on the row axis at `p256-L64-i32-N16384`, 5.11× against a raised-cap dense at `p2048-L128-i32-N1024-d7`, 1.61–1.71× at pop 4 096, losing only at `p2048-L64-i32-N1024` (dense 1.11× faster).
- `torch-batched` still beats every *evoxc* route on the single-call axis — up to 7.58× over dense on the large-scale cells, where the batch merge wins that axis only on the `d7` cell (1.27×) — and the batch artifact tier does not close the loop side: a hit still rebuilds decode+trace+merge (86 % of the 4.1 s pop-2 048 hit call) and the key includes the chunk partition, so a pool-4 directory does not serve a pool-1 run. The `fused` route reverses that axis: it beats `torch-batched` on every measured cell (41×–157× `batch_forward`, 32×–131× `SR_fitness`).
- The batch band policy is settled by measurement: `EVOGP_BATCH_BAND_SIZE` defaults to 16 (the minimax setting, never >6% off any measured warm column) and the first-order decision is flat vs banded (flat is 8–53% slower by workload); `EVOGP_BATCH_BANDS=auto` stays opt-in because evoxc's static cost model overshoots the device binding cap ~14× (213 bands against 15) and won 0/9 warm columns.
Pinning the band COUNT at the device cap (`EVOGP_BATCH_BANDS=15`) is a same-merge control at pop 256 — identical `band_sizes` and `emitted_ops` to band size 16, because the size model is already clamped to K = 15 there — and the `p64` K = 7 pin does change the plan (`[9]×7` vs `[16,16,16,15]`) but stays inside the ±5% box noise, so 16 stands and no pin beat it anywhere.
- One exported dispatch per band and 16 bindings per ROCm-HIP dispatch cap a banded merge at `K ≤ 15` bands with ≥ 8 merged functions per band (llvm-cpu `K ≤ 31`, numpy uncapped): the band-size model and `auto` are clamped to that set and record `band_clamped`/`band_note`, while an explicit illegal `EVOGP_BATCH_BANDS=K` raises `ValueError` naming the cap and the remedy.
- Chunked parallel compile (`EVOGP_BATCH_COMPILE_WORKERS`, default 4) cuts the pop-256 cold compile from 10.73 / 11.96 s to 4.06 / 4.07 s (band size 16; the compile pool is 89–96% of the cold call and `lower` only 0.8–11.6% of it) but costs 1.69–1.87× the warm call because each chunk uploads, runs and reads back separately, so break-even is 3 849 / 5 103 warm calls of one population (18 702 at 111-node trees, where the trade is 4.58× cold for 1.46× warm) and `=1` is the warm-oriented setting; chunking is inert (one chunk) below 32 deduped functions — including the `p64` fixed-population niche, whose value plans compile as `chunk_sizes [63]` — and refused for an explicit `EVOGP_BATCH_BANDS` spelling (flat included) or `switch_ops=True` — `EVOGP_BATCH_CHUNK_BANDS=1` (default off) is the only way to combine banding with chunking, and it is 2.6–2.9× faster cold / 1.69–1.87× slower warm than the single-body banded build, so it stays a fixed-population lever.
  Its fixed-population niche is narrow: a FIXED population of ~64 trees over few data rows (round-1 p64-L64-i32-N64: batch warm 1.127 ms vs dense 1.385 ms, cold 2.24 s vs 6.44 s), and because dense's cost tracks the `max_tree_len` trace cap while the merge tracks actual node count it also leads a raised-cap dense once the longest tree passes `EVOGP_DENSE_MAX_TREE_LEN` (see the large-scale bullet); a turnover loop loses at every size.
- `EVOGP_DENSE_MAX_TREE_LEN` is a cost knob as well as a safety valve: on identical 31-node trees, raising the cap 64 → 128 → 256 costs 2.0 → 5.3 → 19.5 ms per call; past it `auto` raises the cap by power of two under `EVOGP_DENSE_AUTO_MAX_TREE_LEN` while an explicit `dense` declines into the specialized fallback — so raise or pin it only to the depth actually generated, and a loop that knows its depth should pin it because a power-of-two cap crossing costs one recompile.
- Where a warm dense call's time goes now (`test/benchmark/evoxc/results/final/decompose/`): `evoxc.run` is 84.7% of a 2.40 ms call at pop 256 / L=64 / N=1024 and host glue is the remaining 15.3% — the two blocks have swapped roles since `test/benchmark/r5/RCA.md` measured host glue at 75–77%.
- The dispatch bound is gone on the fused route: it replaces dense's ~310 chained device ops with ONE kernel launch and wins 8.6×–663× on the measured cells, so the r6 Triton prototype under `test/benchmark/r6/` is now historical (superseded by `src/evogp/tree/fused_kernels.py`). `dense` itself keeps that bound, and its warm time is 84.7 % `evoxc.run` / 15.3 % host glue (`test/benchmark/evoxc/results/final/decompose/`).
- Cold start: the `dense` route compiles in ~3.1–3.4 s (L=32) / ~6.1 s (L=64) per shape × used-function-set, so a cold 50-generation run at pop 256 is 7.8× slower end to end than the plain-torch loop and break-even is ≈1250 generations; the opt-in artifact cache (`EVOGP_EVOXC_ARTIFACT_DIR`, default off) reloads an artifact in ~0.16 s and flips that run to 1.14× faster than torch. The fused route replaces that with a one-time Triton JIT of ~1.6 s for the value kernel (~2.9 s for the three surfaces from an empty cache), and `python -m evogp.sr_test` — whose default pop 200 rides `auto` onto that route on a device box — records −0.2259 in ~11 s there.
- Benchmarking keeps two measurement types: type-1 end-to-end and type-2 pure graph-forward (`test/benchmark/pure_forward.py`); the R1–R6 rounds and `test/benchmark/REPORT.md` are historical records.
- Numeric parity by route is measured in `test/benchmark/evoxc/VALIDATION.md`: value paths are bitwise exact for the arithmetic and ternary function sets and ~1e-6 relative elsewhere, but the transcendental (`rich`) set deviates up to 4.4e-01 absolute from the plain-torch oracle at large output magnitudes on the dense/iree route, and no pytest covers `rich`-set parity per route — treat the iree transcendental lowering as approximate. The `fused` route is the exception and is exact there (`batch_forward`/`forward` `max_abs = 0.0` on all three function sets), with losses ≤3.8e-7 relative.
- `specialized` + iree is a bit-level outlier (11/64 trees, abs ≤1.6e-2) but sits off the default path, since `auto` routes pop ≥ 64 to dense+iree; its cause is now identified — iree contracts `mul` into a following `add`/`sub` (FMA), leaving ≤1 ulp per op but up to 2.2e-3 / 6.1e-3 relative after deep-tree cancellation at generation depth 7/8, so it is also what the shipped cap-64 dense degrades to on deep trees (repro in `test/benchmark/evoxc/BATCH.md` §11.5).
- The `batch` route's loss path matches the oracle to ~1e-7 relative but its `batch_forward` is non-bitwise on the arithmetic and ternary sets (≤1.1e-3 relative, ~1e-8 of the value scale) where dense is exact, so its records form their own digest group; dense differs from numpy only in the NaN payload bit on `sub`, and the `fused` route differs only in NaN payload bits too (finite-space `max_abs = 0.0`) — both are value-neutral and digest-splitting.
- The merged-graph compile grows superlinearly in the population's TOTAL node count: pop 1000 × (L=128, generation depth 7) and pop 1000 × L=256 exceeded a 20-minute compile and were recorded as dropped, while pop 1000 at depth 5 costs 178.5 s on the single-body path; on the shipped chunked default `p1000-L32-i8-N1024` (817 functions) compiles in 15 517.88 ms and its warm `sr_fitness` is 6.9384 ms.
The measured law is quadratic in the plan's EMITTED OPS and nearly rows-insensitive (5 497 ops → 4.2 s, 21 339 → 19.6 s, 41 376 → 48.3 s, 78 189 → 191 s, 93 751 → 250 s cold; `48.9 s × (ops/41 376)²` fits within ~10 %), with 86–97 % of the cold call in the compile pool, so a static large population now compiles in 42 s at pop 2 048, 153 s at pop 4 096 and 800 s at pop 8 192 — feasible at 89 % of a 900 s cap, but a fresh generation replans and pays it again (`LARGE_SCALE_ROUND2.md`, `src/evogp/tree/CONTEXT.md`).
- Robotics problems cannot be verified on the validation box (third-party environment boundary, not library defects): dm_control-suite MuJoCo envs need `mujoco-warp` and jax's CUDA backend hits the CuDNN 9.1-vs-9.8 mismatch; `GenesisProblem.evaluate` is a stub returning `None`; only the lazy-import binding of `MujocoProblem` is covered by tests.
- Multi-output `CombinedForest` path: the engine and the single/batched `forward`/`batch_forward` contract are implemented and tested, but the containers still lack `SR_fitness`/`to_sympy_expr`, `CombinedForest.__next__` never advances, and `SymbolicRegression.evaluate` rejects a `CombinedForest` — the supported route is `evogp.problem.CustomLoss` (`example/combined_sr.py` runs end to end).
- No dimension validation exists between `GenerateDescriptor.input_len/output_len` and `problem.problem_dim/solution_dim` (the pipeline's asserts are commented out), so mismatches fail inside the tree layer/engine instead of at wiring time.
- `test/goldens/*.npz` are frozen outputs of the deleted CUDA engine (bitwise-reproducible captures, no longer re-capturable) — treat as read-only fixtures; comparisons use 1e-4 rtol/atol because the old kernels used fast-math.
- The `fused` route's own gaps (all reported in `src/evogp/tree/FUSED.md` §7): the multi-output path materializes the prediction buffer, `output_len` above `MAX_OUT_LEN` (8) declines cleanly but nothing wider is measured, the route has no per-stage timer surface and no zero-copy device export (a `(pop, rows, 1)` value tensor stays allocated and is never read back), `EVOGP_EVOXC_BACKEND=numpy` still reports `engine="fused"` while every call declines (prove a served call with `fused_kernel_launches`, not with the engine name), `clear_fused_cache()` does not reset `fused_kernels._KERNELS["specializations"]`, and `rows ≤ 64` at 8–32-node trees (pops 1–8) is an unmeasured corner where the kernel's ~0.09 ms launch floor is the whole call.
- The `evogp.gp` stack is single-output only (`init_population` raises `NotImplementedError` for `output_len > 1`, with `CustomLoss` the escape hatch), its device-native fused objective is fed through the local transitional `_device_interop.py` DLPack shim (`evoxc.core.Tensor.__dlpack__` + `register_external_kernel(device_resident=True)` are the supported replacement once the gp call sites move), no committed test compares its fitness numbers against the torch stack on a shared problem, channel validation is a ~50 ms Python loop per 256 × 300-node population (`validate=False` is the only mitigation), and the in-graph problem layer owns a second `CompileCache`.
- Packaging: `evox` 2.0.0a1 is a PyPI **pre-release** (a plain `pip install evox` still resolves the 1.x line, so the 2.0 line needs `--pre` and its own venv) and it is GPL-3.0-or-later while EvoGP is Apache-2.0; no `evogp` module imports `evox`, so the dependency is an alignment/interop pin, and `evoxc` is a pure-Python, numpy-only distribution (`evoxc[iree]` for the compiled backends).
## Test Strategy
Supported sequence on the validation box (repo root as CWD, `PYTHONPATH=src:<evoxc checkout>`, the project venv's `bin/python` — never the `python` on PATH, which lacks torch; `EVOXC_DISABLE_LOCATIONS=1` recommended; a fused run also needs `TRITON_CACHE_DIR` pointing at a writable directory):
1. Import check (no build needed): `PYTHONPATH=src <venv>/bin/python -c "import evogp.tree"` and `PYTHONPATH=src <venv>/bin/python -c "import evogp.gp"` (the second must also work without `evoxc`).
2. Convergence smokes: `PYTHONPATH=src <venv>/bin/python -m evogp.sr_test` (torch stack, synthetic SR; its default pop 200 runs on `auto` = the fused route, −0.2259 in ~11 s on the reference box) and `PYTHONPATH=src:<evoxc checkout> <venv>/bin/python -m evogp.gp.smoke` (functional stack, CPU, ~3.7 s, −0.27225 → −0.10690).
3. Pytest: `<venv>/bin/python -m pytest test src/evogp/tests -q` is the historical full gate (the two suites together: 1 570 passed / 7 skipped / 3 failed in ~172 s; without `PYTHONPATH` the `test/` half fails collection with `ModuleNotFoundError: evogp`, which is an environment error, not a test failure), `-m pytest src/evogp/gp/tests -q` is the torch-free functional-stack suite (318 passed, ~66 s on a device box), `--ignore=src/evogp/tests/test_equivalence.py` for the fast subset, `-k golden` for the legacy-golden cross-checks, `-k batch` for the batch route, `-k fused` for the fused-route net; the 3 red cases are the one stale `auto`-policy assertion in `test_fused_route.py` (see Known Issues).
4. Run the relevant `example/*.py` from the repository root (relative asset paths such as `imgs/` are CWD-dependent); `test/fix_bug.py` is a script (`python test/fix_bug.py`), not pytest.
5. Performance work: the current harness is `test/benchmark/evoxc/` (reproduce commands in its `README.md`, verdicts in `FINAL.md` for the shipped routes and `BATCH.md` for the opt-in `batch` route, gate `python test/benchmark/evoxc/check.py` per side with `--allow-missing --allow-digest-mismatch`, one process per config, warm medians, idle-GPU guard; `--cells large` is the large-scale column (ten cells, pop 2 048–8 192 / `N` 4 096–16 384 / 123–201-node trees / input_len 64; report of record `test/benchmark/evoxc/LARGE_SCALE_ROUND2.md`, evidence `results/largescale2/`, previous round in `LARGE_SCALE.md` over `results/largescale/` + `results/largascale/`); the record gate for that round is `python test/benchmark/evoxc/check.py --results test/benchmark/evoxc/results/largescale2/main --allow-snapshot --allow-missing --allow-digest-mismatch`; `--tree-root` times any checkout, e.g. the pre-optimization snapshot at commit `530518e`; `batch_economics.py` measures per-generation compile economics and `--cells long`/`--arms batch` scope the long-tree rounds; `band_sweep.py` runs the batch band-size/auto grid (including the `k15`/`k7` band-COUNT pins, gated by the device cap) and `--cold-only` re-prices the cold column in ~1.5 min per cell; `BATCH.md` §15 is the round-3 closing section (per-cell warm/cold/loop table, compile-pool break-even, band-size policy, what would have to change) with its numbers in `results/batch_opt_round3/SUMMARY.md`). The R1–R6 rounds under `test/benchmark/{r2,r4,r5,r6}/` plus `REPORT.md` are historical records with their own still-valid gates, and the r6 Triton prototype keeps `SUMMARY.md` + `check_r6.py` as its analysis of record. The `fused` route's campaign of record is `test/benchmark/evoxc/results/t1a1_fused/`, driven by the tooling committed there (`fused_campaign.py` registers the `evoxc-fused-iree` / `evoxc-fused` arms on top of the harness, `fused_probe.py` is the per-cell route/served-call/numerics/stage-split/GP-loop probe, `fused_gate.py` feeds its records to the harness gate with `--allow-missing --allow-digest-mismatch`, `fused_envelope.py` covers multi-output parity, the memory envelope, the min-pop column and the geometry sweep) and its gate is `python test/benchmark/evoxc/check.py --results test/benchmark/evoxc/results/t1a1_fused --allow-snapshot --allow-missing --allow-digest-mismatch` (the pre-fused baseline is `results/t1a1_baseline/`); `python -m evogp.tree.fused_check --stage all` is the in-library battery (route wiring, parity, goldens, declines, the six-cell timing and the tuning grid) and `src/evogp/tests/test_fused_route.py` is the pytest net.
Known coverage gaps: dense/iree parity on the transcendental (`rich`) set, `specialized`-iree parity bounds, robotics rollouts, `CustomLoss` end to end, multi-output `CombinedForest` training route, cold-compile economics (no test covers it), and bitwise `batch_forward` parity on the arithmetic set (measured non-bitwise, deliberately tolerated at ~1e-3 relative). Also uncovered: a parity test of the functional stack against the torch stack's fitness numbers, and the fused route's `rows ≤ 64` × 8–32-node-tree corner.
## Notes for Agents
- Read `src/evogp/CONTEXT.md` first; it is the entry point to the library (API surface, dependency DAG, engine constraints).
- Never reintroduce a compiled extension or hand-written kernels; legacy op semantics are preserved as documentation only (`src/evogp/tree/ENGINE_SPEC.md` appendices, `test/goldens/README.md`).
- The functional stack `src/evogp/gp/` is torch-free by contract: `tests/test_gp_stack_purity.py` greps every module of it for `import torch` / `from torch` / `import evox` / `from evox`, and `import evogp.gp` must keep working with `PYTHONPATH=src` alone (no `evoxc` at module scope).
- The fused route's kernels live in `src/evogp/tree/fused_kernels.py` and are JIT-compiled by Triton at the first call: never add a build step or a compiled extension, and keep `import triton` inside `fused_kernels.kernels()` so `import evogp.tree` stays GPU- and triton-free.
- The most valuable single place to look for a numeric bug is the boundary between `tree/` (tensor schema, host-side decode) and the evoxc engine (`tree/evoxc_engine.py`); the independent plain-torch oracle `src/evogp/tests/reference_eval.py` is the reference to diff against.
- `python`/`python3` on PATH lack torch — always use the project venv; that venv has no `pip` and no jupyter/nbconvert (notebook re-execution uses the stdlib-json runner recipe in `tutorial/CONTEXT.md`).
- Determinism comes from torch's global RNG: `torch.manual_seed(0)` makes generation reproducible (distribution-equivalent to the legacy stream, not bit-identical). The functional stack is key-based instead (`run(..., key=0)`, an `evoxc` splitmix64 key carried in the state), so it reproduces the same run from one integer with no global seed and no torch.
