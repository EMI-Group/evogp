# tutorial/

## Intent
Hands-on Jupyter notebooks that teach the user-facing EvoGP API: `GenerateDescriptor`, `Forest`/`Tree`, the `GeneticProgramming` operator set, `SymbolicRegression`/`Classification`, `StandardPipeline`, and `CombinedForest`.
This is a leaf directory: 3 notebooks plus one binary output asset, no subdirectories and no build step.
The notebooks are the closest thing to a narrative walkthrough, but they are **not** automated and **not** linked from the top-level README (the README's Basic API Usage section points at `../example/basic.py`), so the directory is currently undiscoverable from the docs.

## Environment Requirements
- All three notebooks `import evogp`, so the compiled extension `evogp.evogp_cuda` must exist (`pip install -e .` or `python setup.py build_ext --inplace`) and a CUDA-capable GPU must be present.
- There is no CPU path: `device="cuda"` is hard-coded in the notebooks (intro cells 7/9, combined cell 10), in `GenerateDescriptor` (const samples / depth probabilities / roulette vectors are built on `cuda:0`), and in `Forest.random_generate` (`torch.randint(..., device="cuda")`). Merely constructing a `GenerateDescriptor` requires a GPU.
- `combined_gp.ipynb` cell 10's comment "(running on CUDA for speed, but CPU is fine)" is wrong — the tensors are created with `device="cuda"` and the whole construction path is CUDA-only.
- `Classification` builds its `onehot_labels` on `device="cuda"` and `SymbolicRegression.generate_data` builds `inputs` on `device="cuda"`, so the notebooks' device strings match the library's hard-coded assumption rather than the other way round.
- `evogp_intro.ipynb` additionally needs `scikit_learn` (imported at cell 1 with `Classification`, used in cell 9) and `sympy` (`to_sympy_expr`), plus `networkx` + `pygraphviz` for the final `to_png` cell (`pygraphviz` is the optional `visualize` extra and is commented out in `../requirements.txt`).
- `combined_gp.ipynb` needs `sympy` for the sympy-formula discussion (the current cell 17 output carries sympy's rich `text/latex` repr next to `text/plain`).
- `forest_intro.ipynb` needs only `torch` + evogp.
- Recorded kernelspecs are the authors' local environments (`evogp312` for `evogp_intro`, `torch_env` for the other two) on Python 3.12; only `language: python3` matters.
- No notebook sets `torch.manual_seed`, `numpy.random.seed` or any other seed, so all stored outputs (trees, expressions, fitness traces, `best_tree.png`) are non-reproducible samples, not golden values.

## Constraints
- The notebooks must follow `../src/evogp`, never the reverse: treat `src/evogp` signatures as the source of truth when editing tutorial code.
- Do not modify source code to make a stale notebook run; fix the notebook or file a Known Issue.
- `evogp_intro.ipynb` is the only notebook currently consistent with the HEAD API; use it as the style/API reference when repairing the other two.
- Executing a notebook rewrites the committed JSON (including the multi-KB fitness-log outputs) and `best_tree.png`; prefer targeted edits over blindly re-running, or expect large diffs.
- Cell outputs are stored, so a reader can study results without a GPU, but only `evogp_intro.ipynb` has a self-consistent executed state (execution counters 1..12, outputs on every code cell except cell 1).
- Public surface the notebooks depend on (must keep working through the pure-torch, kernel-free rewrite): `evogp.tree.{Forest, Tree, GenerateDescriptor, CombinedForest, CombinedTree}`, `evogp.problem.{SymbolicRegression, Classification}`, the star-exported `evogp.algorithm` operators used above, `evogp.pipeline.StandardPipeline`, and the `from evogp.algorithm import *` star import itself.
- Behavioral contracts the notebooks (and their stored outputs) rely on: `Forest.random_generate(pop_size, descriptor)` positional order; `GenerateDescriptor(...)` keyword names and `update(**kwargs)` returning a new descriptor; `Tree.forward(x)`, `Tree.to_sympy_expr(symbol_names=None)`, `Tree.to_png(fname)`; `problem.datapoints` / `problem_dim` / `solution_dim`; `SymbolicRegression(..., execute_mode=...)` accepting `"torch"` and `"auto"`; `StandardPipeline(algorithm, problem, generation_limit=...).run()` returning the best `Tree` and printing the `Generation: N, Cost time: ...ms` / `fitness: valid cnt: ...` log captured in the stored outputs.

## Known Issues
1. **`forest_intro.ipynb` cell 0 uses the pre-`GenerateDescriptor` API (stale).** It calls `Forest.random_generate(pop_size=10, gp_len=128, input_len=3, output_len=1, max_layer_cnt=5, **{"const_prob":..., "out_prob":..., "func_prob":..., "layer_leaf_prob":..., "const_range":..., "sample_cnt":...})`. HEAD's signature is `Forest.random_generate(pop_size: int, descriptor: GenerateDescriptor)` — `gp_len` is now `GenerateDescriptor.max_tree_len`, `func_prob` is now `using_funcs` (dict or list), `const_range`/`sample_cnt` are now `const_samples`, and `input_len`/`output_len`/`max_layer_cnt`/`layer_leaf_prob`/`const_prob`/`out_prob` moved onto the descriptor. The cell raises `TypeError: Forest.random_generate() got an unexpected keyword argument 'gp_len'` before anything else runs.
2. **`forest_intro.ipynb` is in a half-executed state.** Cell 0 has `execution_count: null` and no outputs, while cells 1–8 still carry outputs from an older run (execution counters 3..10), i.e. it was edited but never re-run after the API change; cell 9 is an empty code cell with `execution_count: null`. Cells 1–8 themselves (`str`, `__getitem__`, `__setitem__`, `__add__`, empty-slice behavior) still match HEAD.
3. **`combined_gp.ipynb` is stale at its head and tail (markdown cells 0–3/5/7, code cells 11, 14, 17).** The markdown teaches the removed top-level `formula` concept (cell 1 item 4: `share_input` "MUST be True"; cell 2: formula callable; cell 7: `combined_tree.to_sympy_expr(SYMPY_FORMULA)`), and cell 11 makes the removed call `CombinedForest.random_generate(pop_size=5000, formula=lambda A, B, C: A + B * C, descriptors=descriptor, share_input=True)`. HEAD's signature is `CombinedForest.random_generate(pop_size: int, data_info: dict, descriptors: Union[List, GenerateDescriptor])`, where `data_info` maps each output name to the list of input names feeding it; it asserts `len(descriptors) == len(data_info)`, `descriptors[i].input_len == len(data_info[key])` and `descriptors[i].output_len == 1`. A current-API repair therefore needs e.g. `data_info={"A": [<3 input names>], "B": [...], "C": [...]}` (the same input names become the keys of the dict passed to `CombinedForest.forward`/`batch_forward`); the top-level formula left the tree classes entirely (see `../src/evogp/problem/custom_loss.py` for the current composition pattern). Cells 10, 12, 13 use current-API signatures but run only on top of the stale population.
4. **`combined_gp.ipynb` cells 14 and 17 call methods that do not exist / cannot work.** Cell 17 `best.to_sympy_expr(lambda A, B, C: A + B * C)` — `CombinedTree` has no `to_sympy_expr` (it exposes only `random_generate`, `forward`, `to_combined_forest` plus per-output attribute aliases); the direct replacement is to apply the formula to the sub-expressions, e.g. `formula = lambda A, B, C: A + B * C; formula(best.A.to_sympy_expr(), best.B.to_sympy_expr(), best.C.to_sympy_expr())`. Cell 14 `best.forward(XOR_INPUTS)` passes a raw tensor, but `CombinedTree.forward(x: dict[str, torch.Tensor])` starts with `list(x.values())[0].dim()` → `AttributeError` for a tensor, and even with the correct named dict it ends with `return pop_res[0]` on a dict keyed by output names → `KeyError` (the underlying `CombinedForest.forward`/`batch_forward` are dict-in/dict-out). Cells 15/16 (`best.A/B/C.to_sympy_expr()`) work only because `CombinedTree.__init__` `setattr`s every `data_info` key onto the instance, so they depend on the output names being literally `A`/`B`/`C`.
5. **A repaired `combined_gp.ipynb` still cannot run end-to-end at HEAD.** `SymbolicRegression.evaluate` reads `forest.share_input` when the forest is a `CombinedForest`, but `CombinedForest` no longer defines `share_input` (nothing in `src/` sets it) → `AttributeError`; even past that, `evaluate` would hand the plain `datapoints` tensor to `CombinedForest.batch_forward`, which expects a dict. Cell 10's `SymbolicRegression(..., execute_mode="torch")` on a `CombinedForest` therefore fails regardless of notebook edits. The fix belongs in `../src/evogp/problem/symbolic_regression.py`, outside this node.
6. **Minor consistency smell in `evogp_intro.ipynb`:** the iris `Classification` cell (cell 9) builds a 4-input, 3-output problem while the tutorial's descriptor is `input_len=2, output_len=1`, and the cell's `problem` is immediately overwritten by the custom-function `SymbolicRegression` in cell 11, so it is illustrative only and never validated by a pipeline run.
7. **Same stale pattern in sibling directories:** `../example/combined_sr.py` (lines 48/51/75) and `../test/combined_test.ipynb` (the `formula=`/`share_input=` + `best.to_sympy_expr(lambda ...)` cells) carry the identical removed calls, so do not use them as the reference for repairing `combined_gp.ipynb`.

## Test Strategy
There is no automated coverage of this directory: `../test/` only contains `test_bind_success.py`, `test_torch_env.py`, a few ad-hoc scripts and other notebooks, and no CI job executes the tutorials.
Verification is manual on a CUDA machine, e.g. `jupyter nbconvert --to notebook --execute --inplace <notebook>` (or running the cells by hand) and comparing semantics — API calls succeed and the expression/plots have the expected shape — never the literal values, which are random.
Cheap smoke check before touching a notebook: `python -m pytest ../test/test_bind_success.py` confirms the CUDA extension is importable, which is the usual first failure mode (`ModuleNotFoundError: No module named 'evogp.evogp_cuda'`).
When repairing a notebook, keep the existing markdown structure and correct the code cells + re-execute, so the stored outputs stay consistent with the narrative.
