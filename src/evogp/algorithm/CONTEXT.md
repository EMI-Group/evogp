# src/evogp/algorithm — GP operator layer

## Intent
The genetic-programming evolution engine of EvoGP: the population-level loop (`GeneticProgramming`) plus the three interchangeable operator families it composes — selection, crossover, mutation.
Everything here works on populations held in `evogp.tree` containers (`Forest`, and for multi-output problems `CombinedForest`) and is expressed as plain callable Python classes — no `nn.Module`, no autograd, no registered parameters.
Operators are duck-typed strategies: the loop only calls `__call__`, so any object honouring the documented contract can be plugged in.
This is the layer directly above `evogp.tree`: it consumes the tree layer (pure Python/torch + evoxc engine, no compiled extension) and is consumed by `evogp.pipeline` (and directly by `example/` scripts).

## API Surface
`algorithm/__init__.py` is 4 lines: `from .crossover import *`, `from .mutation import *`, `from .selection import *`, `from .genetic_programming import GeneticProgramming`.
None of the subpackages defines `__all__`, so every public name they bind is re-exported flat at `evogp.algorithm.<Name>`; that shallow namespace is the de-facto public API (README, `tutorial/` and every `example/*.py` import from `evogp.algorithm` only).
- Loop: `GeneticProgramming(initial_forest, crossover, mutation, selection, enable_pareto_front=False)` — `.forest` is the live population, `.step(fitness)` advances one generation.
- Pareto: `ParetoFront` lives in `genetic_programming.py` and is deliberately NOT re-exported (reachable only as `evogp.algorithm.genetic_programming.ParetoFront`); `algorithm.pareto_front` exists only when `enable_pareto_front=True`.
- Crossover (5 names): `BaseCrossover`, `DefaultCrossover`, `DiversityCrossover`, `LeafBiasedCrossover`, `CombinedDefaultCrossover`.
- Mutation (11 names): `BaseMutation`, `DefaultMutation`, `HoistMutation`, `DeleteMutation`, `InsertMutation`, `SinglePointMutation`, `SingleConstMutation`, `MultiPointMutation`, `MultiConstMutation`, `CombinedMutation`, `CombinedDefaultMutation`.
- Selection (11 names): population-level `BaseSelection`, `DefaultSelection`, `RankSelection`, `RouletteSelection`, `TournamentSelection`, `TruncationSelection` + crossover-facing `BaseSelector`, `RankSelector`, `RouletteSelector`, `TournamentSelector`, `TruncationSelector`.
- Documented/supported wiring (README quickstart, `example/basic.py`, `tutorial/evogp_intro.ipynb`): `GeneticProgramming(initial_forest=Forest.random_generate(pop_size=..., descriptor=descriptor), crossover=DefaultCrossover(), mutation=DefaultMutation(mutation_rate=0.2, descriptor=descriptor.update(max_layer_cnt=3)), selection=DefaultSelection(survival_rate=0.3, elite_rate=0.01), enable_pareto_front=True)`.
- Multi-output wiring (`example/combined_sr.py`): `CombinedForest.random_generate(...)` + `CombinedDefaultCrossover()` + `CombinedDefaultMutation(mutation_rate=..., descriptors=...)` + the same `DefaultSelection`.
- Exact constructor signatures (keyword names are part of the API; the mutation pair deliberately differs singular/plural): `DefaultMutation(mutation_rate, descriptor)` — singular `descriptor`, both required, no defaults (`mutation/default.py:19-30`); `CombinedDefaultMutation(mutation_rate, descriptors)` — plural `descriptors`, accepts one `GenerateDescriptor` (lazily wrapped in a list) or a list whose length must equal the sub-forest count (`mutation/combined_default.py:10-19,34-47`); `DefaultCrossover()` and `CombinedDefaultCrossover()` take no constructor args (`crossover/default.py:13-14`; `CombinedDefaultCrossover` defines no `__init__`); `DefaultSelection(survival_rate=0.3, elite_cnt=None, elite_rate=None)`, with `elite_cnt`/`elite_rate` mutually exclusive (`selection/default.py:15-35`); `GeneticProgramming(initial_forest, crossover, mutation, selection, enable_pareto_front=False)` (`genetic_programming.py:29-36`).
- No class in this node executes or imports the evaluation engine (grep-verified: no `evoxc_engine` / `evoxc` / `torch.ops` reference anywhere here); the tree operations are reached only through `Forest` methods (all pure torch now): `Forest.random_generate` → `tree/generation.py` (`../tree/forest.py:42`), `Forest.mutate` → `tree/splicing.py` (`../tree/forest.py:136`), `Forest.crossover` → `tree/splicing.py` (`../tree/forest.py:191`). `DefaultSelection` and the loop's own bookkeeping (`forest[elite_indices] + next_forest`) touch neither.

## The generation step (data flow)
`GeneticProgramming.step(fitness)` is the entire evolution loop; fitness is produced OUTSIDE by the problem — `pipeline/standard.py` calls `problem.evaluate(algorithm.forest)`, maps NaN to `-inf`, then calls `algorithm.step(fitnesses)`.
1. Asserts `fitness.shape == (forest.pop_size,)`.
2. If enabled, folds the population into the Pareto front per tree size.
3. `elite_indices, survivor_indices = self.selection(self.forest, fitness)`.
4. `next_forest = self.crossover(forest=self.forest, survivor_indices=survivor_indices, target_cnt=self.pop_size - elite_indices.shape[0], fitness=fitness)` — crossover returns exactly the offspring and must never include the elites (all four args are passed by keyword).
5. `next_forest = self.mutation(next_forest)` — mutation only ever sees the offspring.
6. `self.forest = self.forest[elite_indices] + next_forest` — elites are COPIED (fancy indexing) and prepended, offspring appended; this new forest is both stored and returned.
Invariants this creates: each generation is `elite_cnt` verbatim elites + `(pop_size - elite_cnt)` offspring, so `pop_size` never changes; elitism is applied AFTER mutation, hence elites are never mutated; the operators never need to know elites exist.
`survival_rate` only sizes the parent pool that crossover may draw from — it does not change `pop_size`.
Selection pressure is carried by the MULTIPLICITY of entries in `survivor_indices` (crossover resamples uniformly by position), not by their order.
With `DefaultSelection` both index tensors are the top individuals sorted by descending fitness, so the new population's leading rows are the fittest individuals in ranked order.
`GeneticProgramming` keeps no best-so-far individual of its own (only the optional Pareto front); tracking the best tree is the pipeline's job.

## Fitness tensor contract (`fitness` argument of `step`)
Read-only inside `algorithm/`: `step`, every `*Selection` class and every crossover class only reads it (`torch.sort`/`argsort` are out-of-place; `argmax`, indexing and `fitness / torch.sum(fitness)` allocate), mutation never receives it, and no reference outlives the `step` call — so a caller may recycle the buffer (the only in-place write in the shipped path is the caller's own NaN→`-inf` repair at `../pipeline/standard.py:43`), though returning a fresh writable tensor stays the safe convention.
No file in this node performs a device→host sync on fitness (grep-verified: no `.item()`/`.cpu()`/`.numpy()`/`.tolist()`, no `print`, no host `if` on a fitness-derived 0-dim tensor); every consumer is a device op (`torch.sort`/`argsort`/`argmax`/`multinomial`, gathers, `.to(dtype=...)`) whose results stay on the fitness device, and the operators' hardcoded `.cuda()` calls are no-ops for an already-CUDA fitness.
Elitism is sync-free as well: `elite_indices` is a `torch.sort(fitness, descending=True)` + slice inside the selection operator (never an `argmax(...).item()`), and the loop touches it only via the metadata `elite_indices.shape[0]` (`genetic_programming.py:114`) and device-side fancy indexing (`genetic_programming.py:118`).
The only unconditional per-generation readback of the fitness tensor in the shipped path is the caller's `cpu_fitness = fitnesses.cpu()` (`../pipeline/standard.py:46`; the pipeline's `int(torch.argmax(cpu_fitness))` and best-fitness comparison then act on that CPU copy, so `algorithm.step` itself is handed the original CUDA tensor).
`step` asserts ONLY the 1-D shape `fitness.shape == (self.forest.pop_size,)` (`genetic_programming.py:103-105`); dtype and device are never checked.
No device→host materialization happens anywhere in this node: no `.cpu()`/`.item()`/`.numpy()`/`.tolist()` touches `fitness`, every `int(...)` cast in selection/crossover is Python arithmetic on metadata (`forest.pop_size`, `fitness.size(0)`, `target_cnt`, `elite_indices.shape[0]` — e.g. `selection/default.py:55,62`, `crossover/diversity.py:58`), and the selection/crossover index tensors stay device tensors straight into `forest[elite_indices]` / `forest[survivor_indices]` / `forest.crossover(...)`.
The only host touch-points on fitness-derived data are `ParetoFront.__str__`, which formats `self.fitness[idx]` element by element on print (`genetic_programming.py:17-20`), and the dead `for_update_pareto_front`'s `if masked_fitness[best_idx] > ...` Python-bool test (`genetic_programming.py:61`; nothing calls the method).
The D2H readback in the shipped loop lives in the pipeline, not here: `../pipeline/standard.py:46-47` does `cpu_fitness = fitnesses.cpu()` and `int(torch.argmax(cpu_fitness))` before calling `step` (and `standard.py:43` is the in-place NaN→`-inf` repair).
`step` imposes no same-device coupling between fitness and the population beyond the ops it calls: with `enable_pareto_front=True` the size axis is a hardcoded `torch.arange(max_tree_len, device="cuda")` (`genetic_programming.py:73`), and `self.forest[elite_indices]` needs the selection output on the forest's device (per-operator device behavior is in the child contexts).
Direction: every selection path assumes HIGHER fitness = better — `torch.sort(..., descending=True)` at `selection/default.py:65`, `rank.py:80`, `roulette.py:75`, `truncation.py:67`, `tournament.py:130`, `selection_utils.py:25/123`, `torch.argmax`/`torch.argsort(..., descending=True)` at `tournament.py:83/90/91`, and Pareto `torch.max`/`>` at `genetic_programming.py:77/80` — so a problem that returns an un-negated error is optimized in the wrong direction.
Requirements beyond shape: the Roulette family needs float, finite, non-negative, positive-sum weights (they go straight into `torch.multinomial` at `roulette.py:64`, `rank.py:83`, `truncation.py:71`, `selection_utils.py:28/46/78/125`); device requirements live in the operators (`enable_pareto_front=True` builds `torch.arange(max_tree_len, device="cuda")` at `genetic_programming.py:73`).
The same tensor object is passed positionally to `selection` (`genetic_programming.py:110`) and by keyword to `crossover` (lines 111-115): `DefaultCrossover`/`CombinedDefaultCrossover` ignore it, `DiversityCrossover`/`LeafBiasedCrossover` forward it to their `*Selector`s.
`GeneticProgramming` stores no `self.fitness` and has no `run` method — `step` is the only fitness consumer and the loop is `StandardPipeline.run` (`../pipeline/standard.py:56-86`); the only fitness attribute in this package is `ParetoFront.fitness`, a separate device-resident `(max_tree_len,)` archive that outlives generations — `vmap_update_pareto_front` REBINDS it to a fresh `torch.where(...)` result each generation (`genetic_programming.py:81-85`) and never stores the input fitness tensor itself.

## Pareto front (`enable_pareto_front=True`)
`ParetoFront(max_tree_len, (max_tree_len, input_len, output_len))` allocates `fitness` of shape `(max_tree_len,)` filled with `-inf` plus `solution = Forest.zero_generate(...)`, i.e. ONE best solution per possible tree size (`pop_size` of that internal forest == `max_tree_len`).
`step` calls `vmap_update_pareto_front(fitness, solution)` (the name is misleading — it is a broadcasting implementation, no `torch.vmap`): it buckets individuals by `batch_subtree_size[:, 0]`, takes the per-size max, and writes back the winners' `batch_node_value`/`batch_node_type`/`batch_subtree_size` wherever the new best beats the stored one.
Fitness is assumed non-decreasing-in-quality (higher is better) and the front is a pure by-product: it never feeds back into selection in these strategies, it is only reported (`example/basic.py`, `example/classifier.py` print it).
`vmap_update_pareto_front` adds no host sync (broadcast/`torch.where`/`torch.max`/gathers are all device ops); `ParetoFront.__str__` formats `self.fitness[idx]`/`self.solution[idx]` elementwise in a Python loop, so PRINTING a front syncs once per tree size — the shipped examples print it once after `run()` (`example/basic.py:91`, `example/classifier.py:86`) — and the dead `for_update_pareto_front` would sync per tree size via its host `if masked_fitness[best_idx] > ...` if it were ever called.

## Constraints
- Dependency direction is one-way: `algorithm/` may import `evogp.tree`; `tree/` and `problem/` must NEVER import `algorithm/`, and the only package consumers are `pipeline/` (`from ..algorithm import GeneticProgramming`) plus the stray runnable script `src/evogp/sr_test.py`.
- Intra-package edge to respect: `crossover/leaf_biased.py` and `crossover/diversity.py` do `from ..selection import BaseSelector`, so `selection/` must never import from `crossover/` (cycle).
- Import ORDER inside `__init__.py` is load-bearing: `genetic_programming.py` does `from . import BaseMutation, BaseCrossover, BaseSelection`, which only resolves because the three star imports run first; hoisting the `genetic_programming` import above them raises `ImportError: cannot import name ... from partially initialized module` (verified).
- The loop is container-agnostic: `initial_forest` must expose `pop_size`, `max_tree_len`, `input_len`, `output_len`, support `forest[index_tensor]`, `forest_a + forest_b` and (for Pareto) `batch_subtree_size[:, 0]` — both `Forest.random_generate(...)` and `CombinedForest.random_generate(...)` satisfy this, but the container must MATCH the operators (plain operators for `Forest`, combined operators for `CombinedForest`); nothing validates this.
- CUDA-bound by device string, not by build: tensors are created with hardcoded `device="cuda"` (or `.cuda()`) throughout crossover/mutation/selection and in `ParetoFront`; only `DefaultSelection` is device-agnostic. Importing this package needs no compiled extension (`evogp.tree` is pure Python/torch + evoxc), but executing any operator creates CUDA tensors, so a real run still needs a CUDA-visible device (the same `"cuda"` string also selects AMD GPUs under ROCm).
- Operators are stateful-by-construction strategy objects: implement `__call__` with the exact keyword names (`forest`, `survivor_indices`, `target_cnt`, `fitness` for crossover; `forest` for mutation/selection) and preserve `pop_size`; fitness index tensors are `int32` by convention (the tree-side splices accept any integer dtype and validate out-of-range left parent indices).
- Do not add hyperparameter validation asymmetrically: `BaseSelection`/`DefaultSelection` assert, the crossover strategies do not.

## Design Decisions
- Strategy objects instead of subclasses with hooks: selection/crossover/mutation are injected into `GeneticProgramming.__init__`, so composing or replacing an operator is a constructor call, not a code change — this is why every example reads as configuration.
- The loop is deliberately dumb (select → crossover → mutate → concat): all policy lives in the operator objects, which keeps `step` 20 lines and lets the combined (multi-output) variants reuse the identical loop.
- Elites are concatenated by the loop rather than handled by the operators, so no operator has to reason about elitism and the elite block cannot be mutated or recombined away.
- The multi-output (`Combined*`) operators are separate modules because a `CombinedForest` holds one independent `Forest` per output and the plain (single-output) operators take single forests; the same parent pairing is reused across sub-forests to keep an individual's outputs aligned.
- The Pareto front exists as an optional side channel (archive of best-per-size) rather than a selection strategy: it gives a size/accuracy trade-off report (`batch_subtree_size[:, 0]` is the complexity measure) without perturbing the standard loop.
- Star re-exports are used so that `from evogp.algorithm import <anything>` works for users; the cost is the flat-namespace traps listed under Known Issues.
- Plain Python classes (no `nn.Module`) because GP here has no learnable parameters — random draws and plain torch tensor ops do the work.

## Hot path (operator cost & host-sync inventory)
One `GeneticProgramming.step` is selection → crossover → mutation → elite concat, and at pop 16-1000 the layer is *dispatch-bound*, not compute-bound: every cell of the operator path is a tiny kernel on a `[pop, max_tree_len]` tensor, so the per-generation cost tracks the number of torch calls (~9 us each on the validation box), not the number of individuals.
Measured (harness `gp_step`, default dense+iree route, pop64-L32-i8-N1024): ops 5.79 ms before the operator-layer round, 2.39 ms after; the largest single item was `Forest.random_generate` inside `DefaultMutation` (501 -> 66 kernel launches, 6.9 -> 0.9 ms CPU) after `tree/generation.py` grew a padded complete-tree hot path.
Host round trips per generation (the complete inventory; anything per individual would be `pop_size * 3`): `DefaultMutation` does exactly one `nonzero()` (it both tests the empty selection and yields the row ids reused by the gather/scatter), `tree/splicing.py` does one `all()` for the `left_indices` range check, `tree/generation.py` does one `max()` for the overflow guard, and `StandardPipeline.step` does one `.cpu()` for the fitness readback.
`algorithm/mutation/default.py` indexes with the integer row ids instead of the boolean mask (a boolean mask runs one extra `nonzero` per tree tensor) and treats the empty selection with `numel()`, so no `mask.sum() == 0` sync remains.
`DefaultSelection`/`DefaultCrossover` stay as they were apart from what `tree/splicing.py` now saves: the crossover range check is a single reduction (was two `bool(...)` calls) and `splicing` reuses a cached column-index row instead of allocating one per call.
Never put `repr`/`str`/`to_sympy_expr` on this path: `repr(Forest)` renders a sympy expression per individual.

## Known Issues
- Star-import submodule shadowing: `evogp.algorithm.base` and `evogp.algorithm.default` are bound by ALL THREE subpackages, so the LAST star import (selection) wins and they resolve to `evogp.algorithm.selection.{base,default}`; `from evogp.algorithm.base import BaseCrossover` therefore fails with a confusing `ImportError`, and `import evogp.algorithm.base` raises `ModuleNotFoundError` (it was never a real module path). Always import strategies from their owning subpackage (`evogp.algorithm.crossover.*`, ...). Verified by experiment.
- No class-name COLLISION between the three subpackages (all 27 strategy names are distinct), but two near-identical families coexist at `evogp.algorithm`: `RankSelection`/`RouletteSelection`/`TournamentSelection`/`TruncationSelection` vs `RankSelector`/`RouletteSelector`/`TournamentSelector`/`TruncationSelector`, with the same math duplicated (see `selection/CONTEXT.md`).
- `pareto_front` is a conditional attribute: with `enable_pareto_front=False` (the default) `algorithm.pareto_front` raises `AttributeError` — `example/regressor.py` does exactly this after passing `False`.
- `for_update_pareto_front` in `genetic_programming.py` is dead legacy code (nothing calls it), superseded by `vmap_update_pareto_front`; it also indexes `self.forest.max_tree_len` rather than the passed solution.
- Misspelled module filename `crossover/combined_dafault.py` (class `CombinedDefaultCrossover`); the sibling `mutation/combined_default.py` is spelled correctly. The misspelled path is importable surface — see `crossover/CONTEXT.md`.
- `CombinedMutation` is a NAME TRAP: it chains a list of mutation operators over a plain `Forest` (used this way in `example/regressor.py`); only `CombinedDefaultMutation` handles `CombinedForest`.
- Crossover↔selection signature drift: `BaseCrossover.__call__(forest, survivor_indices, target_cnt, fitness)` vs `DiversityCrossover`/`LeafBiasedCrossover` declaring `(forest, fitness, survivor_indices, target_cnt)` — only keyword calling keeps it working. Details in the child contexts.
- `BaseSelection.__call__(self, forest)` in `selection/base.py` is stale (no `fitness`), while every concrete class and `GeneticProgramming.step` use `(forest, fitness)`; no runtime effect, but misleading for new operator authors.
- Mutation operators mutate their input forest IN PLACE and return the same object, and crossover strategies pass the full population rather than a pre-sliced survivor set — see the child contexts for the per-operator consequences.
- There is no device/shape/dtype validation between stages: a descriptor whose `max_tree_len`/`input_len`/`output_len` does not match the forest trips asserts inside `evogp.tree` (hence the `descriptor.update(max_layer_cnt=3)` idiom) or raises a host-side decode error from the engine, and `crossover_rate`/`survival_rate` ranges are mostly unvalidated.

## Notes for Agents
- Read `genetic_programming.py` (121 lines) first — it is the whole contract; then open only the operator module you need (each is 50–140 lines and self-contained).
- Engine contact-point inventory: no file in this node imports `evogp.tree.evoxc_engine` / `evogp.tree.dense_engine`, the `evoxc` package or a torch custom op; the evaluation engine is reached only from the problem layer via `Forest.SR_fitness` / `Forest.forward`. The tree-side calls this layer makes are pure torch: `Forest.random_generate` → `tree/generation.py`, `Forest.mutate`/`Forest.crossover` → `tree/splicing.py`, and the Pareto-front path is engine-free too — `ParetoFront.__init__` calls `Forest.zero_generate` (pure `torch.zeros`, `../tree/forest.py:67`) and `vmap_update_pareto_front` is pure torch (`broadcast_to`/`where`/`max`/indexing). All of them still hardcode `device="cuda"`.
- To add an operator: new module in the right subpackage, subclass the `Base*` class, implement `__call__`, add the import line to that subpackage's `__init__.py`; the star import at `evogp.algorithm` makes it public automatically (no `__all__` to update).
- Never reorder `algorithm/__init__.py`; keep the three star imports above the `genetic_programming` import.
- `DefaultSelection` + `DefaultCrossover` + `DefaultMutation` is the only combination documented end-to-end in README/examples, and is the only selection that works on CPU — use it as the reference when reasoning about semantics.
- A CUDA-visible device is required to execute anything here (every operator builds its tensors on `"cuda"`); no compiled extension is involved, and reasoning about behavior is done by reading the code plus `evogp/tree/` (the engine that evaluates the populations produced here lives there).
- Do not "fix" the flat-namespace/star-import design casually: `evogp.algorithm.<Name>` is the API that README, `tutorial/` and `example/` rely on.

## Test Strategy
- Automated coverage: the pytest suite under `../tests/` — `test_convergence_smoke.py` drives this layer end to end (builds `GeneticProgramming` + `StandardPipeline` around `SymbolicRegression` and asserts the best fitness improves), and `test_operators.py` covers the tree-side splices these strategies call (`Forest.mutate`/`Forest.crossover`); the non-default selection/crossover strategies have no automated assertions (see the child contexts).
- There is no CI workflow (`.github/workflows` is absent) and no test file inside this directory.
- Real coverage of the wiring is still end-to-end — `example/basic.py`, `example/regressor.py`, `example/classifier.py`, `example/transformer.py`, `example/combined_sr.py`, `example/custom_sr.py`, `example/uci_sr.py`, `example/uci_classifier.py`, `example/brax_task.py`, `example/mjx_task.py`, plus `tutorial/evogp_intro.ipynb` and `tutorial/combined_gp.ipynb`.
- Everything that instantiates a `Forest`/operator still needs a CUDA-visible device (the operator tensors are hardcoded to `"cuda"`), so any new test here is de-facto an integration test; cheap unit-level checks (build a small `Forest.random_generate` and assert `pop_size`/`forest.pop_size` invariants) are possible on GPU.
- Coverage gaps: `DiversityCrossover`/`LeafBiasedCrossover` with explicit `*Selector`s, and the four non-default `*Selection` strategies (see the child contexts).

## Routing Table
- `genetic_programming.py` → `GeneticProgramming` loop (`step`, elite concat, Pareto front) — the only file in this node with cross-cutting logic.
- `crossover/` → parent-selection + subtree-swap strategies (`BaseCrossover`, `Default`, `Diversity`, `LeafBiased`, `CombinedDefault`); owns the `crossover/combined_dafault.py` typo and the crypto of `target_cnt` handling.
- `mutation/` → subtree/node perturbation strategies (`Default`, `Hoist`, `Delete`, `Insert`, `Single/MultiPoint`, `Single/MultiConst`, `Combined`, `CombinedDefault` + internal `mutation_utils.py`).

- `__init__.py` → star re-exports + `GeneticProgramming`; import order is load-bearing.
Sibling paths (READ-ONLY from this node — escalate writes to the parent):
- `../tree/` → `Forest`/`CombinedForest` containers, `GenerateDescriptor`, `NType`, `randint`, `MAX_STACK`, and the pure-torch generation/splicing modules + evoxc engines this layer calls.

- `../../example/`, `../../tutorial/`, `../../test/` → executable usage and the de-facto test suite; `../../README.md` documents the supported operator set and signatures.
