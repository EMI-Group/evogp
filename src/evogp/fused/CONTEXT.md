# `src/evogp/fused/` — the fused (Triton) evaluation route
## Intent
This package is the ONE survivor of the legacy engine layer: a device-native evaluator that evaluates a whole tree population with ONE JIT-compiled Triton kernel launch per (tree, row-block) pair, off the legacy population tensors themselves — no evoxc graph, no per-node dispatch, no per-tree readback.
It takes a population the way the GP stack already holds it: three prefix-order tensors (`batch_node_value` float32, `batch_node_type` int16, `batch_subtree_size` int16, all `(pop_size, max_tree_len)`).
Its callers are `evogp.gp.fused_eval.FusedDeviceEvaluator` (the torch-free stack's device objective, which exports its `evoxc` channels over DLPack and hands the kernel its own `out=` fitness buffer) and the in-library battery `evogp.fused.check`.
There is no route policy here: nothing selects this package, no `Forest`/`Tree` dispatch and no `EVOGP_EVAL_MODE` exist any more — a declined call raises `FusedUnsupported` and the CALLER owns the fallback.
There is NO build step and no compiled extension: `triton` is imported lazily inside `kernels.kernels()` and the first call JIT-compiles the specialization (~1.6 s for the value kernel from an empty writable `TRITON_CACHE_DIR`, ~2 ms from a warm one, nothing per call or per generation afterwards).
`torch` and `triton` are the optional `fused` extra (`pip install evogp[fused]`); `import evogp` and `import evogp.gp` never import this package, and this package imports no `evoxc`.
## API Surface
`evogp.fused` re-exports `FusedUnsupported`, `MAX_OUT_LEN` (8), `clear_fused_cache`, `envelope_decline`, `evaluate_fused`, `fused_available`, `fused_cache_stats`, `resolve_block_rows`, `resolve_dispatch`, `resolve_max_scratch_mb`, `resolve_num_warps`, `sr_fitness_fused` and the `kernels` submodule.
`evaluate_fused(batch_node_value, batch_node_type, batch_subtree_size, input_len, output_len, x, *, per_row, out=None, out_device=None, backend=None, block_rows=None, num_warps=None, max_scratch_mb=None)` is the value path and returns `(pop_size, output_len)` at `per_row=True` or `(pop_size, N, output_len)` at `per_row=False`, float32 on the computation device (or on `out_device`, or written in place into `out=`).
`sr_fitness_fused(batch_node_value, batch_node_type, batch_subtree_size, input_len, output_len, inputs, labels, use_MSE=True, *, out=None, out_device=None, backend=None, block_rows=None, num_warps=None, max_scratch_mb=None)` is the SR loss path and returns the `(pop_size,)` float32 POSITIVE loss (the reduction happens in the kernel), also honouring `out=`.
`envelope_decline(pop, tree_len, rows, *, out_len=1, holds_values=True, block_rows=None, num_warps=None, max_scratch_mb=None)` is the non-raising memory-envelope verdict (a decline message or `None`); `evaluate_fused` / `sr_fitness_fused` raise `FusedUnsupported` with the same words.
`fused_available()` answers `triton importable AND a torch CUDA/HIP device`.
`clear_fused_cache()` is the route's ONE reset entry; `fused_cache_stats()` reports its counters, all prefixed `fused_`: the attempt family (`fused_calls`, `fused_declines`), the kernel family (`fused_kernel_launches`, `fused_kernel_compiles`), the launch-path family (`fused_bound_launches`, `fused_dispatch_declines`), the scratch table (`fused_scratch_allocs`, `fused_scratch_reuses`, `fused_scratch_evictions`, `fused_scratch_entries`, `fused_scratch_bytes`), the transposed-input table (`fused_xt_hits`, `fused_xt_misses`, `fused_xt_entries`, `fused_xt_maxsize`), the tag-scan table (`fused_tag_*`), the prepared-call table (`fused_plan_hits`, `fused_plan_misses`, `fused_plan_entries`, `fused_plan_maxsize`) and the reported geometry (`fused_block_rows`, `fused_num_warps`, `-1` when the ambient knob is unusable — a stats call never raises).
`kernels` carries the device half: `kernels()`, `plan(rows, *, per_row, block_rows, num_warps)`, `launch_value` / `launch_loss`, `dispatch_stats()`, `scratch_stats()`, `emitted_function_ids()`, `clear_caches()`, `DEFAULT_BLOCK_ROWS` (256), `DEFAULT_NUM_WARPS` (1), `DISPATCH_ENV`.
Knobs (the only five): `EVOGP_FUSED_BLOCK_ROWS` (256), `EVOGP_FUSED_NUM_WARPS` (1), `EVOGP_FUSED_MAX_SCRATCH_MB` (8192), `EVOGP_FUSED_DISPATCH` (`bound`, with `jit` restoring `JITFunction.run`), `EVOGP_FUSED_HOST_MEMO` (16, the prepared-call table). A bad spelling raises `ValueError` naming the variable.
`cases.py` is the shared case library of the battery (population builders, tolerances, `time_call`); it is dev tooling inside the package, imported by `check.py` / `contract.py` / `timing.py` and by `tests/` (the triple builders there start from its `random_population` / `chain`).
## Constraints
`import torch` at module scope is fine HERE and nowhere else in the library: `engine.py` / `kernels.py` require torch, so `import evogp.fused` needs the `fused` extra.
`import triton` must stay inside `kernels.kernels()` — module scope stays triton-free so a triton-less box imports the package and gets a clean `FusedUnsupported` (`FusedUnavailable` from `kernels()`).
Never add a build step, a compiled extension or a cached binary: the kernels are JIT-compiled at the first call and `TRITON_CACHE_DIR` must be writable on a box with a read-only `$HOME`.
`EVOGP_FUSED_DISPATCH=bound` (the default) is a per-call correctness contract, not an optimisation: it must stay bitwise identical to `jit`, and it must DECLINE (onto the historical dispatch) whenever Triton's launch hooks are active or the bound handle is unusable.
The memory envelope is charged on the bytes one launch REALLY allocates — `scratch pop * n_rb * tree_len * block_rows * 4` (always) plus `values pop * rows * out_len * 4` (value paths and the multi-output loss path) plus `partials pop * n_rb * 4` (the loss chart) — never on a `pop * tree_len * rows * 4` approximation.
Declines are `FusedUnsupported` with a message naming the reason and the knob; the caller owns the fallback, so this package never imports a route and never silently changes what it serves.
Multi-output trees (`OUT_NODE`) are served up to `MAX_OUT_LEN` (8); a WIDER request declines and a single-output request over a tagged population raises `MultiOutputError` from `evogp/_multi_output.py` BEFORE any launch (the kernel's type dispatch would otherwise fold a tagged type into the ternary branch and return a plausible wrong number).
The node ids come from the torch-free `evogp/_tables.py` (`Func`, `FUNCS`, `FUNC_ARITY`, `FUNC_TYPE`, `NType`, `OUT_NODE`, `MAX_OUT_LEN`); `kernels.emitted_function_ids()` must always be exactly `FUNCS` split by arity, and both `check.py --stage declines` and the import-time check fail if a branch goes missing.
`engine.py` (1.9 k lines) is one deliberately single compilation unit — the pre-flight, the envelope, the transpose prep, the scratch table and the counters are checked together against the geometry `kernels.plan` returns; split it only with failing-test evidence. `kernels.py` (1.7 k lines) is one unit for the same reason: the compiled kernel resolves its callees through the module globals, so the helper names must BE the jitted objects.
`check.py` / `contract.py` / `timing.py` are a `__main__`-guarded dev battery (`python -m evogp.fused.check`) that nothing in the package imports; `cases.py` is the one module of the four the pytest net imports too (builders and tolerances only).
## Routing Table
- `./engine.py` → the call surface: pre-flight and decline reasons, the memory envelope, the transposed-operand prep, the prepared-call memo (`PLAN_MEMO`, the single-slot `_LAST` fast path, `_GEOMETRY_MEMO`), the launch, `out=` / `out_device`, and the counter/reset surface.
- `./kernels.py` → the Triton kernels (value, per-row, loss, multi-output), the float64 transcendental ladder, the launch geometry (`plan`), the byte-budgeted scratch table and the bound/jit dispatch.
- `./memo.py` → `Memo` (bounded LRU with `lookup` / `store` / `note_hit` / `reset` / `stats`), the identity key `token()` and its ABA guard `pin()`.
- `./cases.py` → the battery's case library: `PARITY_SETS` (arithmetic / ternary / loose / rich / compare_unary with their measured `value_tol`), `adversarial_cases()` (9), `multi_adversarial_cases()` (12), the node-spec DSL (`build_row`, `pack_rows`, `random_population`, `workload`), `compare()` and `time_call()`.
- `./check.py` → the CLI and the numeric legs (`--stage parity` / `multi` / `goldens`), the oracle-by-path bootstrap, the reporting helpers and `main()`.
- `./contract.py` → the decline matrix, the knob checks and the hardened contracts (`CONTRACT_CHECKS`: B1 clamp, B2 non-contiguous, B3 decline contract, S1 scratch budget, S2 envelope bytes, S3/S7 knobs, S5 operator table, S8 empty-stack pop, `out_device`) as `--stage declines`.
- `./timing.py` → the cell table and the two drivers with their single-process children: `--stage timing` / `time-one` and `--stage tuning` / `tune-one` (absolute milliseconds only).
- `./tests/` → the pytest net (29 functions / 45 cases) plus `conftest.py` (device/triton/cache guards, the oracle by path) and `support.py` (the shared triple builders and comparison helpers). See `./tests/CONTEXT.md` for the kept/rewritten/dropped table.
- `../_tables.py` → the torch-free single source of truth for node types, function ids, arities and `OUT_NODE`; this package reads it and redefines nothing.
- `../_multi_output.py` → the ONE `OUT_NODE` rule (`MultiOutputError`) a single-output call refuses with, mirrored by the gp stack.
- `../../../test/oracle/` → DEV tooling, read-only from here: `reference_eval.py` (the independent plain-torch oracle the numeric legs compare against) and `goldens/*.npz` (7 frozen cases, 1e-4 rtol/atol). It is not on `PYTHONPATH`; `check.py` and `tests/conftest.py` append it to `sys.path`.
## Test Strategy
Two layers, both requiring a CUDA/HIP device and a writable `TRITON_CACHE_DIR`:
1. The pytest net — `TRITON_CACHE_DIR=… PYTHONPATH=src:/root/evoxc:/root/evox/src EVOXC_DISABLE_LOCATIONS=1 pytest src/evogp/fused/tests -q` → 45 passed / 0 skipped / 0 failed in ~1.4 s. It compares both value paths and both loss paths against the oracle over five function sets and the handmade adversarial rows, pins the multi-output protocol at `output_len` 2 and 3 (width 8 is the battery's `--stage multi`), both `OUT_NODE` refusals, the result contracts, the non-contiguous and clamp cases, the `bound`/`jit` equivalence, the two in-place-mutation fast-path misses, the launch-hook declines and the reset entry. Device-gated: it SKIPS (never fails) when `torch` is missing, no CUDA/HIP device is visible, or `triton` is not importable.
2. The battery — `PYTHONPATH=src:/root/evoxc:/root/evox/src EVOXC_DISABLE_LOCATIONS=1 python -m evogp.fused.check --stage <leg>`:
   `parity` 56/56 comparisons (5 random op-set populations + 9 adversarial cases × batch_forward / per-row / MSE / MAE), `multi` 65/65, `goldens` 10/10 (the oracle fixtures plus the legacy `test/goldens` captures when present), `declines` 58/58, `timing` six cells in ~55 s (one subprocess each, absolute milliseconds), `tuning` 4 × 3 configs × six cells (12 legs, ~12 min, not run in CI).
   `all` runs the six stages in that order (parity, multi, goldens, declines, timing, tuning); `time-one` / `tune-one` are the single-process child legs and are not meant to be run by hand.
What needs a device: everything except importing the package (a plain-torch box imports it and gets `FusedUnsupported` / `FusedUnavailable` from `kernels()`), and `check.py --stage goldens` still needs one because the fixtures are compared on the device.
## Known Issues
The multi-output VALUE path is bitwise against the oracle on every case measured here (`output_len` 2 / 3 / 8, both value paths, `max_abs = 0.0`), but the multi-output LOSS path is not: it accumulates in float32 per row block where the oracle sums once, measured `<= 1.2e-07` relative (`<= 4.8e-07` absolute) — inside the `1e-5` gate, and non-bitwise by construction.
The single-output loss path is non-bitwise for the same reason (`<= 3.1e-05` absolute on the deepest adversarial rows, `<= 1.2e-07` relative); the single-output VALUE path is bitwise everywhere measured, with the NaN payload bit the only difference on a `mixed_deep` / `mixed_bag` population.
`rows <= 64` at 8-32-node trees (pops 1-8, input_len small) is still unmeasured: the timing cells start at `rows = 1024` and the pytest net uses `rows >= 8` with `pop <= 64`, so the corner where the kernel's ~0.09 ms launch floor is the whole call has no record.
A warm call is cheaper than ONE independently timed launch (`launch_value` pays its own binding/prepare per call: 0.090 ms alone against 0.035 ms for the whole `evaluate_fused` call), so `--stage timing`'s stage split does not decompose a call any more — it reports the kernel column as information and `n/a` for the host share, and only the TOTALS are quotable.
There is NO per-stage timer surface (no `stage_stats()` / `stage_reset()` anywhere in the library): the only timers are `cases.time_call()` in the battery.
`clear_fused_cache()` zeroes every counter and drops the memo tables and the scratch cache, but it deliberately keeps `kernels._KERNELS` (the jitted handles AND the set of specialization keys this process already compiled), so `fused_kernel_compiles` counts JITs that really happened after the reset instead of re-wrapping an already-compiled kernel — verified, and pinned by `test_clear_fused_cache_resets_every_table_and_counter`.
`fused_kernel_compiles` is the only cold-start signal in the counters; there is no per-shape compile counter and no way to ask whether a specialization came from the disk cache or a JIT (`--stage timing` measures the cold first call instead).
The envelope is a budget, not a guarantee: it charges the bytes a launch allocates and the measured peak-allocated tracks the scratch term within 3.5 %, so a box whose allocator fragments more than that can still OOM a call that passes the check.
`output_len > MAX_OUT_LEN` (8) declines cleanly and nothing wider has ever been measured; the `(pop, rows, out_len)` prediction buffer is materialised for every multi-output value call, so the widest shapes are the envelope's worst case.
`EVOGP_FUSED_DISPATCH` has no effect under a Triton that ships no `knobs.HookChain`: `bound` then stays the only path and the hook-decline case skips rather than fails.
The route is single-device by construction (`cuda:0`-style ambient device, no device argument), and `x` must be a device torch tensor — a numpy array declines, because the route never stages host memory.
