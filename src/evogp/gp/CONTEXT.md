# `src/evogp/gp/` — the evoxc-based functional GP stack (torch-free)
## Intent
This subtree is the new Evox-2.0-style EvoGP: a functional genetic-programming stack built on `evoxc` (EvoX Compiler) tensors with numpy host glue and exactly ONE deliberate, lazily resolved torch boundary (`fused_eval.py`, plus the measurement harness `measure_generation.py`).
It exists to replace the Torch-based stack in `../tree/`, `../algorithm/`, `../problem/` and `../pipeline/` once parity is established; the old stack stays in place, unchanged, as the reference implementation and the migration source.
The stack is complete along the canonical flow — encoding → operator layer → problem layer → driver (`init_gp` / `step` / `run`) — and it converges on `sr_test.py`'s workload on a CPU box in seconds (`python -m evogp.gp.smoke`).
It also runs a whole loop DEVICE-RESIDENT (`backend="iree"`, `evoxc.Device("rocm", 0)` on this box): a generation is two `evoxc.run` calls — the evaluation graph, then the variation graph, which does selection, crossover, mutation AND the elite splice — with zero host syncs, zero readbacks and zero transfers between them.
The economics, convergence and losses of that loop are the report of record `DEVICE_LOOP.md` (harness `measure_generation.py`, raw numbers `evidence/device_loop.json`).
Design idiom is copied from Evox 2.0 (`/root/evox/src/evox/DESIGN.md`): frozen config dataclasses holding static leaves only, state as a dataclass whose leaves are `evoxc` tensors, and plain module-level functions in the `init(config, key) -> state` / `step(config, state, evaluate) -> state` step protocol.
`evox` 2.0 has no tree/GP/symbolic-regression component (verified), so this is EvoGP's contribution to the Evox family rather than a port of something existing.
## API Surface
- `_constants.py` — `MAX_STACK`, `MAX_FULL_DEPTH`, `NType`, `Func`, `FUNCS_NAMES` plus the derived `FUNC_ARITY` / `FUNC_TYPE` / `FUNC_IDS`.
  It does NOT import `../tree/utils.py` (that module does `import torch`, and importing it would drag in all of `evogp.tree`): it reads the ids out of that same file with `ast`, so the tree layer stays the single source of truth and nothing is re-typed.
  `tests/test_gp_stack_purity.py` pins every mirrored value against the real `evogp.tree.utils` and against `evogp.tree.generation._func_tables`, so an upstream change cannot drift silently.
- `config.py` — `GPTreeConfig(max_nodes, input_len, using_funcs, output_len=1, max_layer_cnt=4, layer_leaf_prob=0.2, const_prob=0.5, out_prob=0.5, const_samples=None, const_range=None, sample_cnt=None, const_seed=0)` and `GPConfig(pop_size, elite_count=1, tournament_size=2, crossover_prob=0.9, mutation_prob=0.1, selection="tournament", selection_pressure=0.5, mutation_kind="subtree")`; both frozen, both `replace(**changes)`-able, both hashable (so a config is also the graph memo key).
  Derived (computed once in `__post_init__`, `init=False` fields): `roulette_funcs` (the cdf, length `Func.END`), `func_arity`, `func_type`, `depth2leaf_probs` (length `MAX_FULL_DEPTH`), `max_arity`, `levels`, and `const_samples` normalized to a tuple; helpers `max_tree_len`, `padded_widths()`, `padded_total()`, `depth2leaf_prob_at(depth)`.
  Validation is `GenerateDescriptor`'s rule set, raising `ValueError` (not `assert`): `max_nodes <= MAX_STACK`, a complete `max_arity`-ary tree of `max_layer_cnt` levels must fit `max_nodes`, `const_prob`/`out_prob`/`layer_leaf_prob` in `[0, 1]`, `1 <= max_layer_cnt <= MAX_FULL_DEPTH + 1`, and a non-empty function set with finite non-negative weights summing above 0.
  `using_funcs` accepts the names-only and the `(name, weight)` spellings and a dict; duplicates are rejected instead of merged.
  `const_samples=None` draws `sample_cnt` values from `const_range` with `np.random.default_rng(const_seed)`, so a config is a pure function of its fields (and two runs of the same config share one constant table).
  `SELECTION_MODES` (`tournament`, `rank`, `roulette`) and `MUTATION_KINDS` (`point`, `subtree`, `hoist`) live here too, so a config validates itself without importing an operator.
- `state.py` — `GPState(opcode, payload, size, fitness, key)` (frozen) plus `channels(state)`, `replace(state, **changes)`, `population_size(state)`, `max_nodes(state)`, `CHANNEL_NAMES`, `UNEVALUATED` (`-inf`).
  Every leaf shape is constant for a whole run: `opcode` int32 / `payload` float32 / `size` int32 are `[pop_size, max_nodes]`, `fitness` is float32 `[pop_size]`, `key` is a rank-0 int64 `splitmix64` key.
  `key` is the key of the *next* generation throughout: whatever produced the state advanced the RNG.
- `encoding.py` — the whole encoding concern:
  `init_population(config, key, pop_size=None, backend="numpy", device="cpu", validate=True) -> GPState`, where `config` is a `GPTreeConfig` (then `pop_size` is required) or a `(GPTreeConfig, GPConfig)` pair (then `pop_size` comes from the `GPConfig`), and `key` is an int seed or a concrete `evoxc` key tensor; the returned state's `key` is the NEXT generation's key (the graph returns it), and `fitness` is all `-inf` (unevaluated).
  `live_mask(channels)`, `row_length(channels)`, `is_leaf(size)` — host-side numpy helpers, all derived (nothing is stored).
  `validate_channels(channels, input_len=None)` — the host-side decode validation; raises `ValueError` naming the row and node.
  `to_legacy_triple(channels)` / `from_legacy_triple(value, type, size)` — numpy in / numpy out, float32 / int16 / int16, the exact `Forest` layout of `../tree/`.
  `_channel_arrays(channels)` is the ONE channel parser and accepts the three forms everywhere: a `GPState`, the three `[pop_size, max_nodes]` channels, or the three 1-D channel rows of ONE individual, which are promoted to a one-row population `[1, max_nodes]`.
  `validate_channels`, `to_legacy_triple`, `row_length`, `live_mask` and the evaluator/problem layers all read channels through it, so the accepted forms cannot diverge.
  A rank-3 channel or three 1-D rows of unequal length still raises the informative `ValueError`.
  `cache_stats()`, `clear_cache()`, `CACHE_SIZE_ENV` (`EVOGP_GP_COMPILE_CACHE_SIZE`, default 64).
- `selection.py` — one traced `(fitness, key) -> int32 [pop_size] indices` graph per static knob tuple: `select(fitness, key, *, pop_size=None, mode="tournament", tournament_size=2, selection_pressure=0.5, backend, device)`, its trace-time counterpart `select_indices(evoxc_module, fitness, key, pop_size, mode, tournament_size, selection_pressure)`, `rank_probabilities(pop_size, selection_pressure)` and `SELECTION_MODES`.
  `tournament` is `argmax` over `tournament_size` `randint` contenders (linear, the default), `rank` and `roulette` sample an inverse-CDF (quadratic in the population, opt-in).
- `crossover.py` — the splice (ENGINE_SPEC §7) on channels: `splice(evoxc_module, left, donor, pos, donor_pos, gate)` / `_splice_traced`, `draw_positions` / `_draw_positions`, and the host entry point `crossover(config, state, key=0, ...)`, re-exported at package level as `apply_crossover`.
- `mutation.py` — `apply_mutation(evoxc_module, tree_config, channels, key, probability, kind)` (the trace-time operator), `swap_table(tree_config)` (the same-arity opcode swap table `point` mutation uses) and the host entry points `mutate`, `point_mutation`, `subtree_mutation`, `hoist_mutation`; `MUTATION_KINDS` is the operator list.
- `variation.py` — `variation(config, state, fitness, key=0, *, elite_count=0, elite_index=None, backend="numpy", device="cpu")`: ONE traced graph for a whole generation — inputs `(opcode, payload, size, fitness, key[, elite_index])`, outputs `(opcode, payload, size, next_fitness, next_key)` — doing two parent draws by the configured selection mode, crossover gated by `crossover_prob`, mutation gated by `mutation_prob`, and the elite splice; re-exported at package level as `apply_variation`.
  The elite order is `argsort(multiply(fitness, -1.0), descending=False, stable=True)`, i.e. exactly `np.argsort(-fitness, kind="stable")`: a tie keeps the LOWER row index, and `descending=True` must not be used because it flips that order; `elite_index=` supplies the parent rows directly instead (and fixes `elite_count` to its length, a contradictory pair raising `ValueError`).
  Fitness is sanitized in-graph (`NaN → -inf`) before it can win a tournament or an elite slot, elite rows are gathered bit-identically out of the parent channels, and `next_fitness` is the elite values followed by `UNEVALUATED` (`-inf`) for every offspring — with `elite_count=0` (the default) the whole vector is `-inf` and the result is offspring-only.
  It runs DEVICE-RESIDENT: when `state` already holds `evoxc` tensors on a device (what `init_population(..., backend="iree", device="rocm")` returns), the channels and fitness go straight into `evoxc.run`, the shape/dtype checks read `.shape`/`.dtype` instead of `np.asarray`, and the returned channels, fitness vector and next key stay on the device — at most one upload per call (the key when it is a Python int), no readback. A numpy triple plus a device `device=` is uploaded once; `"cpu"` passes numpy arrays through unchanged, so the two routes produce the same offspring for the same seed.
- `_runtime.py` — the internal plumbing the four operator modules share (lazy `evoxc`, key resolution, the per-module executable memo in front of the one shared `CompileCache`, `resolve_configs`, the host-side channel/index glue, the typed `i32`/`f32` constants and the flattened-gather primitives); it is not part of the public surface.
  It also owns the device plumbing the `iree` route needs — `resolve_device` (`"rocm"` / `"rocm:0"` / an `evoxc.Device` / `None`→cpu), `is_tensor`, `device_text`, `to_device` (upload only when the tensor is not already there), `unevaluated(pop_size, device=None)` for a device-resident `-inf` fitness vector — and `cumsum_axis`, the cumsum decomposition (below).
- `evaluator.py` — `predict(channels, x, input_len=None, validate=True, backend="numpy", device="cpu", budget_mb=None)` (plus `ROW_BUDGET_ENV`): the numpy tree evaluator, `[pop_size, n_rows]` float32 predictions of a whole population, row-chunked under a memory budget; it is the CPU path and the parity oracle, and it is what the problem layer evaluates through.
- `problem.py` — `BaseProblem` (the duck-typed `evaluate`/`predict`/`problem_dim`/`solution_dim` contract), `SymbolicRegression(x, y, use_mse=True)` and `CustomLoss(x, loss, targets=None)`; each exposes `predict` / `loss` / `evaluate` (MAXIMIZED, non-finite → `-inf`, fresh float32) and `__call__`, so a problem instance IS an `evaluate` callable.
  The in-graph variant lives here too: `predict_graph` / `sr_fitness_graph` (one traced `evoxc` graph per `(pop_size, max_nodes, n_rows, input_len, used function ids)`; the fitness variant reduces the SR loss in-graph) plus `graph_cache_stats()` / `clear_graph_cache()` and `GRAPH_CACHE_SIZE_ENV`.
  Both are HOST-in/host-out: `_graph_inputs` pre-passes the channels in numpy and uploads seven structure arrays, so their executable rejects a device backend at the run boundary (use `graph_eval.py` there).
- `graph_eval.py` — the DEVICE-RESIDENT in-graph evaluator: `sr_fitness_channels(channels, x, y, *, use_mse=True, input_len=None, used_ids=None, sanitize=True, backend="numpy", device="cpu") -> evoxc.Tensor` (device fitness, NO readback), `sr_fitness_channels_numpy(...)` (the same call plus the one explicit D2H), `readback_fitness(tensor, pop_size=None)`, `resolve_used_ids` / `ALL_FUNC_IDS`, the `GraphEvaluator(x, y, *, use_mse=True, input_len=None, used_ids=None, sanitize=True, backend="numpy", device="cpu")` class (`.evaluate(channels) -> evoxc device tensor`, `.evaluate_numpy`, `.host_fitness`, `.warm(shape=...)`, `.problem_dim`, `.solution_dim`, `__call__`) — the object a device loop plugs in as `evaluate=` — and `device_graph_stats()` / `clear_device_graph_cache()`.
  The structure prelude (`kind`, `func_id`, `const_value`, `var_index`, `c1`, `c2`, `c3`) is traced INSIDE the graph from the channels — reproducing `problem._graph_inputs` op for op, in the `[pop, width]` layout then transposed to the `[width, pop]` one `problem._graph_body` slices, with the row-wise child lookups through `_runtime.take_per_row` — and then calls `problem._graph_sr_fitness`, so the two in-graph routes share their numerics by construction and the host pre-pass (0.15 / 0.29 / 1.12 ms at pop 64 / 256 / 1000) plus its seven-array upload is gone.
  `x`/`y` are uploaded once at construction; `used_ids` (a config, the `using_funcs` names, ids, or `None` = every id of `Func`) is the static dispatch chain; a row carrying an id outside it is marked `-inf` in-graph (`_uncovered_rows`) instead of being silently evaluated with the chain's `0.0`, and the mask is not traced at all for the all-ids default.
  Non-finite fitness -> `-inf` is applied in-graph (`sanitize`), `device` accepts `"cpu"` / `"rocm"` / `"rocm:0"` / `evoxc.Device`, and the graph is memoized per `(width, pop, n_rows, input_len, used_ids, use_mse, sanitize, backend, device)` in its own `_DEVICE_MEMO` in front of the shared `CompileCache`.
  Parity: bitwise exact against `SymbolicRegression.evaluate` on the numpy backend, 1.0e-07 relative on iree/rocm (iree contracts the odd multiply-add) — the device test asserts ≤1e-5.
  Structure validation is deliberately absent (it needs a readback): well-formedness is the operator layer's contract, and a single individual's 1-D channel rows are rejected (promotion needs `evoxc.reshape`, i.e. a trace).
- `workflow.py` — the driver: `init_gp(config, key, *, pop_size=None, backend, device, validate=True)`, `step(config, state, evaluate, *, key=None, backend, device) -> GPState`, `run(config, evaluate, generations=100, *, key=0, pop_size=None, backend, device, callback=None, validate=True) -> GPResult`, the frozen `GPResult(best_fitness, best_fitness_history, median_fitness_history, best_channels, best_generation, generations, state)` and its own `cache_stats()` / `clear_cache()`.
  The driver traces NOTHING: the elite splice lives in the variation graph, so `workflow.cache_stats()["graphs"]` is always `0` and the empty memo only keeps the aggregate cache surface's `workflow` entry.
  A device `step` is sync-free — the objective's device fitness tensor goes straight into the variation graph and the next fitness vector is an in-graph output — while `run` keeps ONE fitness readback per evaluated generation (the history and the best-tree report are built from the numbers) and downloads `best_channels` once at the end; `validate=True` is forwarded to `init_gp`, so `run(..., validate=False)` drops the generation-0 channel validation download too.
  `GPResult.best_channels` is a tuple of the three 1-D channel rows of the winning tree (`opcode` int32, `payload` float32, `size` int32), each of length `max_nodes`, i.e. ONE individual rather than a population.
  That single-individual form is accepted as-is by `predict` / `evaluate` / `validate_channels` / `to_legacy_triple`, each reading it as a population of one.
- `smoke.py` — the `main()`-guarded CPU smoke run (`EVOXC_DISABLE_LOCATIONS=1 PYTHONPATH=src:/root/evoxc /tmp/rocvenv/bin/python -m evogp.gp.smoke`): `target_function`, `make_data`, `make_configs`, `run_smoke`, `main` and the `--pop/--generations/--data/--seed/--max-nodes/--tournament-size/--quiet` flags; it does nothing at import time.
  Every print (the per-generation line and the summary) is behind `verbose`, so `--quiet` is silent and only the returned `GPResult` carries the numbers.
- `fused_eval.py` — the OPTIONAL fused (Triton) evaluation backend, and the ONE deliberate torch boundary of this subtree: `fused_available()`, `sr_fitness_fused_channels(channels, x, y, *, use_mse, input_len, device, validate)`, `FusedEvaluator(x, y, use_mse, *, device, validate)` (with `.evaluate` / `.available` / `.problem_dim` / `.solution_dim`, so it plugs in as `evaluate=`), `ensure_triton_cache_dir()` and `FusedUnavailable`.
  It resolves torch, triton and `evogp.tree.fused_engine` through `importlib.import_module` INSIDE the functions (a literal import statement fails `tests/test_gp_stack_purity.py` and the clean-subprocess test), then calls the sibling `fused_engine.sr_fitness_fused` on the `encoding.to_legacy_triple` layout, negates the positive kernel loss, maps non-finite to `-inf` and returns a fresh `(pop_size,)` float32 numpy array — the `problem.SymbolicRegression.evaluate` contract.
  `ensure_triton_cache_dir()` defaults `TRITON_CACHE_DIR` to `$TMPDIR/evogp-triton-cache` only when the caller has not set it, because this box's `$HOME` is read-only and triton's default cache path dies with `OSError: [Errno 30]`.
  Nothing in the stack selects this route: it is an opt-in `evaluate=` callable, not a driver path.
  Measured verdict (`DEVICE_LOOP.md` §6, transfers included): from HOST channels it is 2.12× / 1.89× / 2.10× / 4.61× faster than the in-graph route at pop 64 / 256 / 1000 / 256×4096 rows; from DEVICE channels it recovers a 0.27–0.42 ms transfer toll first, so it wins only where the in-graph `pop × rows` gather chain outgrows it (1.22× at pop 1000, 1.79× on the wide-row cell) and at pop ≤ 256 the in-graph route is the faster one (fused 1.25–1.26× slower).
- `measure_generation.py` — the committed measurement harness behind `DEVICE_LOOP.md` (`main()`-guarded, `python -m evogp.gp.measure_generation`): one cell is a `(pop, rows)` pair, `--cells`/`--side`/`--pop`/`--rows` plus the `--sides`/`--warmup`/`--reps`/`--no-guard`/`--guard-wait`/`--json` flags, five sides (`gp` = device-resident driver + `GraphEvaluator` + `workflow.step`, `numpy` = the host evaluator, `torch` = the torch stack's `StandardPipeline.step`, `torch-fused` = the same on `EVOGP_EVAL_MODE=fused`, `fused` = the `fused_eval` head-to-head).
  One process per (side, cell) — the parent re-executes itself and merges the children's JSON into `evidence/device_loop.json` — warm medians of `--reps` with a device sync around every timed repetition and an idle-device guard; torch is resolved through `importlib` inside the functions, like `fused_eval.py`.
- `measure_fused.py` — the committed measurement harness of the fused route against the in-graph route (`main()`-guarded, `python -m evogp.gp.measure_fused`): fused first-call / warm, numpy→torch upload, host decode, the evoxc-device→host transfer (quiet and after a device run), the end-to-end evaluator, the device-resident in-graph `evoxc` comparison and the host numpy evaluator, plus the parity delta and both verdicts (`--pops/--rows/--seed/--iters/--max-nodes/--no-graph/--numpy-graph/--json/--check`).
- `__init__.py` — the consolidated public surface (42 names): the config types and mode tuples, `GPState` and its helpers, the encoding helpers, the operator entry points, `predict`/`predict_graph`/`sr_fitness_graph` and the two problems, `GraphEvaluator`/`sr_fitness_channels`/`readback_fitness`, `FusedEvaluator`/`fused_available`, `init_gp`/`step`/`run`/`GPResult`, and the aggregate `cache_stats()` / `clear_cache()`.
  Two names are spelled differently at package level because the bare names are the submodules: `apply_variation` (`variation.variation`) and `apply_crossover` (`crossover.crossover`).
  `cache_stats()` returns `{"graphs", "compile_cache_size", "compile_cache_maxsize", "layers", "device_layers", "device_graphs"}`: `layers` is the per-layer dict over `encoding`, `selection`, `crossover`, `mutation`, `variation`, `workflow` and `problem` (the last one owns a separate `CompileCache`), `device_layers` holds `graph_eval` alone (it only memoizes on the device route, so a host run reads it empty) and `device_graphs` sums it; `clear_cache()` resets every layer and drops the compile cache.
## Constraints
- **The torch boundary is ONE module and ONE mechanism**: `fused_eval.py` (and the `measure_generation.py` harness, which benchmarks the torch stack) resolve torch and triton through `importlib.import_module` at CALL time, and a literal `import torch` / `from torch` / `import evox` / `from evox` statement stays forbidden in every module of this subtree (pinned by `tests/test_gp_stack_purity.py`'s source grep, docstrings included, and by the clean-subprocess test that `import evogp.gp` pulls no torch/evox/evoxc into `sys.modules`).
  Every other module is numpy + `evoxc` on the host side, and torch otherwise appears only in `tests/` as an oracle.
- **A device run is a transport contract, not a second code path**: a device executable's `evoxc.run` rejects host/numpy inputs (`DeviceError`, no implicit transfer), a device tensor's `.numpy()` raises so a download must go `.to(evoxc.Device("cpu", 0))` first (`encoding._as_numpy` is the one place that does it), and an `evoxc` string device is a bare KIND — pass an `evoxc.Device("rocm", 0)` (or `"rocm:0"`) rather than trusting `"rocm"` everywhere.
  IREE leaks buffers per live executable (nanobind leak warnings on interpreter exit), so keep device sessions short rather than opening many; the fused route additionally needs a writable `TRITON_CACHE_DIR` (`ensure_triton_cache_dir`).
- **No `evoxc` import at module scope either**: every entry point resolves it through `encoding._evoxc()` / `_runtime.evoxc()`, so `import evogp.gp` works with only `src` on `PYTHONPATH` (pinned by a clean-subprocess test); the graphs themselves need `evoxc` at call time and raise a `RuntimeError` naming the fix when it is missing.
- Tree encoding is static-shape: `[pop_size, max_nodes]` channels in prefix (pre-order) order, node 0 = root, padding past the row's live node count; variation lives in VALUES only, never in shapes.
- A **leaf is exactly a node with `size == 1`** (a function node always has a child), which is what disambiguates `opcode == 0` (`NType.VAR`) from `Func.IF` and `opcode == 1` (`NType.CONST`) from `Func.ADD`; the payload of a function node is always 0.0.
- EvoX Compiler has no eager mode: every `evoxc` op must run inside a trace (`evoxc.build`/`build_cached`/`run` of a built function), and `evoxc.zeros`/`ones`/`full` build CONCRETE tensors — inside a trace they must be wrapped in `evoxc.constant(...)`.
- evoxc gaps the encoding is built around: no `searchsorted` (the cdf lookup is a sum of `cdf[i] <= r` comparisons), no newaxis indexing (every axis insertion is an explicit `evoxc.reshape`), and `evoxc.scatter` takes the INDICES' shape as the middle axes (no per-row broadcast against a 2-D base), so the generation scatters a flattened 1-D buffer with per-row offsets.
- **The `iree` (stablehlo) backend narrows three of those further** — the operator layer is written so the SAME traced program serves numpy and iree, never a `backend == "iree"` branch in the math:
  `cumsum` has no stablehlo emitter ("op 'cumsum' is not supported in v1"), so every scan goes through `_runtime.cumsum_axis` (slices + typed-zero pad + `add`), which is bit-identical to `evoxc.cumsum` for the integer channels; it is used by `encoding.generate` (`axis=2`, `L = max_arity`) and by `selection._sample_cdf` (`axis=0`, rank/roulette only).
  dtype leakage from a bare Python literal is fatal there (`stablehlo.concatenate` refuses `i32` vs `i64`), so every literal in value arithmetic goes through `i32`/`f32` and operator outputs are cast back to the channel dtypes.
  Only ONE rank-1 `scatter` per program survives `iree-compile` (two of them fail "failed to legalize unresolved materialization"), so `encoding.generate` scatters a single inverse-permutation map and then `gather`s all three channels through it.
- Traced-code gotchas that cost real debugging time here (all verified against this evoxc checkout): `evoxc.gather` is numpy `take`, not `take_along_axis` — a row-wise 2-D lookup needs the flattened `gather(reshape(x, (pop*width,)), row*width + column)` idiom (`_runtime.take_per_row`).
  A Python `int`/`float` scalar is NOT weakly typed: evoxc promotes it to `int64`/`float64`, so every literal that takes part in value arithmetic must go through `_runtime.i32` / `_runtime.f32` (a typed rank-0 constant) and operators cast their outputs back to the channel dtypes.
  `reshape` and `broadcast` reject size mismatches instead of raising a backend error later, so a shape bug surfaces at trace time.
  `argmax` returns `int64` with the reduced axis dropped (`[pop, 1]` for a `[pop, k]` input), not an int32 vector — the selection operator reshapes and casts before using it as an index.
  `random.randint` accepts a symbolic `high` (the encoding's variable-index draw uses one).
  `argsort(descending=True)` breaks ties in reverse index order, so "the best row" on a flat fitness vector is the LAST index unless the caller imposes its own tie rule — the variation graph therefore sorts `-fitness` ASCENDING with `stable=True`, which is the host rule `np.argsort(-fitness, kind="stable")`.
  Operators leave stale values past the row's new live length (only `[0, size[:, 0])` is meaningful), exactly like `../tree/splicing.py`, so nothing may assume zeroed padding after a crossover/mutation.
- Randomness is stateless and key-based (`evoxc.random.key/split/split_n`); the key lives in `GPState` and is advanced there, and every draw takes its own split child. There is no global seed.
- `evoxc.random`'s `uniform`/`normal`/`randint`/`permutation`/`key_mix` all have StableHLO emitters, so they run on the `iree` backend as well as numpy (verified: an identical draw on both backends); only `random_multinomial` is deferred (`evoxc/backends/stablehlo/ops.py`), so nothing in this subtree may depend on `multinomial`.
- Numerics must match the semantics of record in `../tree/ENGINE_SPEC.md` (protected `DIV`, the `LOOSE_*` variants, `IF` short-circuit, ±1 comparison clamps).
- Fitness contract: `(pop_size,)` float32, MAXIMIZED (losses negated); callers may not mutate it in place, and a non-finite value means "unevaluable" (`-inf`).
- **Driver contract**: `evaluate` is any callable `channels -> (pop_size,) float32` and is called exactly once per generation on a concrete `GPState`, never traced.
  It may return a numpy array (the host path) or an `evoxc` tensor: a DEVICE tensor needs no declaration — the driver reads the state's device off the channel metadata and hands that tensor straight to the variation graph, so a device generation costs no readback at all, while `run` reads the numbers back once per evaluated generation because its history and best-tree report are built from them.
- **Elitism lives in the variation graph**: `variation(..., elite_count=GPConfig.elite_count)` puts the top rows of the evaluated parent state, bit-identically, in front of `pop_size - elite_count` offspring rows (an in-graph `argsort` of `-fitness` + `gather`, one `concatenate`) — the same wiring as `GeneticProgramming.step`'s `forest[elite_indices] + next_forest`, and the reason a `step` needs no readback.
  The offspring rows kept are the operator layer's first `pop_size - elite_count` rows (they are exchangeable draws); the rest are dropped.
  The next state's fitness vector therefore carries the elite's real fitness and `UNEVALUATED` (`-inf`) for every offspring, and `elite_count=0` (the operator-layer default) is offspring-only with an all-`-inf` vector.
- Elitism is what makes `GPResult.best_fitness_history` monotone non-decreasing, and `run` reports the best of each evaluated generation (not a re-evaluated copy), so the trajectory is a free consequence of the wiring rather than a separate repair step.
## Design Decisions
- **One traced graph per `(config, pop_size, backend, device, key shape/dtype)`**, memoized in a module dict plus one `evoxc.CompileCache`; the closure that holds the config is kept alive in the same dict because `evoxc.build_cached` keys on the callable's identity.
  The same layering is repeated per operator module (its own memo dict, the same shared compile cache); the driver adds NO graph of its own, because the elite splice is part of the variation graph.
- **The elite splice lives in the variation graph, not in a second executable**: ranking the elites and concatenating them is two more ops of a graph the generation needs anyway, while a separate splice graph cost a third `evoxc.run` plus two H2D uploads and one readback per generation (the measured before-and-after is in `DEVICE_LOOP.md` §3). The in-graph ranking is also what lets a device `step` be readback-free.
- **The structure prelude is traced, not pre-passed on the host**: `graph_eval` derives the seven structure arrays from the channels inside the graph, so a device loop never stages a population host-side; the semantics are shared with `problem._graph_inputs` by calling the same `_graph_sr_fitness` body, so the two in-graph routes cannot drift numerically.
- **Generation reproduces `../tree/generation.py`'s decision structure exactly** because that structure is what defines the distribution: a node at depth `d` is a function iff `r >= depth2leaf_probs[d]`, its id is the number of cdf entries `<= r` (clamped to `Func.END - 1`), its arity follows from the id; a leaf is a constant with probability `const_prob` (value drawn uniformly from the constant table) and a variable index `% input_len` otherwise.
  The growth layout is the padded complete tree (level `d` has `A ** d` slots, `A` = the largest arity of the function set), so parent/child links are static — a Python loop over levels and child ranks only, never over individuals or nodes — and the whole population is scattered into pre-order in one `evoxc.scatter` into a flat `pop_size * (max_nodes + 1)` buffer whose extra scratch column absorbs the dropped slots.
  Layout size is bounded by construction: a complete `A`-ary tree of `levels` levels must fit `max_nodes` (validated in the config), so the padded grid never exceeds `max_nodes` slots per row.
- The cdf lookup is a 29-step accumulation of `cast(cdf[i] <= r)` rather than one 3-D reduce, so the temporary is one `[pop, slots]` tensor instead of `[pop, slots, Func.END]`.
- The next generation's key is an OUTPUT of the same graph (`init_population`'s 6th `split_n` child, `variation`'s 5th), so a run advances its RNG in-graph and the host never has to know the key algorithm.
- Validation is host-side and Python-level (pop × nodes): it is the counterpart of the tree layer's decode validation and is not a hot path, but it is a real cost at large populations, hence the `validate=False` escape hatch on `init_population`.
- The multi-output protocol (`output_len > 1`, `out_prob`, `NType.OUT_NODE` tagging and the `(index << 16) | fid` float pack) is deliberately not implemented: `output_len == 1` only, with `init_population` raising `NotImplementedError` and the bridge raising for `OUT_NODE`-tagged inputs. `CustomLoss` is the multi-output escape hatch for now.
- **Selection has no truncation mode**: the torch stack's `DefaultSelection(survival_rate, elite_rate)` truncates to the top `survival_rate`, which this layer expresses as `tournament` (pressure = `tournament_size`), `rank` (`selection_pressure`) or `roulette`; a run that needs truncation-like pressure raises `tournament_size`.
- **Driver is a plain loop, not `evox.StdWorkflow`.** `StdWorkflow` requires `evaluate` to be traced in-graph, but EvoGP evaluation is per-generation engine work behind a plug-in callable (the numpy evaluator, the torch engine adapter, or the shape-static in-graph/dense/fused graph), so `run()` alternates one built operator graph per generation with one `evaluate` call; the objective is never traced, and on a device run the two calls are the whole generation.
- `GPResult` also carries `median_fitness_history` (median over the finite values of each generation) because a GP fitness vector is heavy-tailed: a few exploding trees move a mean by tens of orders of magnitude, so the mean says nothing about the population while the median tracks it.
  The best individual is materialized only once, at the end, from the state in which it was evaluated (one row readback), so tracking it costs no extra sync inside the loop.
- **Sibling subtree, not an in-place rewrite**: the torch stack keeps working (it is the oracle and the benchmark baseline) while this stack reaches parity; `tree/ENGINE_SPEC.md` + `tree/CONTEXT.md` are the shared semantics.
- **Evaluation is pluggable**: the operator layer owns population evolution, the engine owns evaluation; any backend implementing `evaluate(population) -> fitness` can drive `run`, and the adapter that turns channels into a `../tree/Forest` lives on the caller side (the tests own that glue).
## Known Issues
- **The fused (Triton) route measured against the in-graph route** (`python -m evogp.gp.measure_fused` and `DEVICE_LOOP.md` §6, MI300X/ROCm, pop 64 / 256 / 1000 / 256×4096 rows, `max_nodes=32`, `input_len=8`, `+ - * /`, `max_layer_cnt=4`, `N` 1024 or 4096, medians of 15, transfers included): the fused lane is FLAT in population and rows — 0.218–0.239 ms inside the torch-fused pipeline, 0.114 / 0.112 / 0.113 ms for the bare kernel — while the in-graph evaluation grows with `pop × rows` (0.673 / 0.816 / 1.681 / 1.782 ms).
  From HOST channels — what the numpy-backed operator layer hands an evaluator — the fused route is 2.12× / 1.89× / 2.10× / 4.61× faster (the `measure_fused` decomposition: kernel 0.11 ms, host decode 0.05 / 0.11 / 0.36, numpy→torch upload 0.052 / 0.067 / 0.087, end-to-end `FusedEvaluator` 0.264 / 0.376 / 0.730 against the in-graph 0.707 / 0.855 / 1.738 and the host numpy evaluator 2.79 / 9.76 / 38.71).
  From DEVICE channels it must first recover a 0.270–0.423 ms transfer toll (0.314–0.553 ms behind a device run, i.e. 18–41 % of the in-graph call), so it wins only where the gather chain outgrows that toll — 1.22× faster at pop 1000 and 1.79× on the 4096-row cell — and loses in the regime a GP loop lives in (pop 64 a coin-flip, pop 256 1.26× slower).
  Parity: max relative delta 1.2e-07 / 1.7e-07 / 3.4e-07 / 2.2e-07 with zero finiteness mismatches; `--check` re-verifies it on a fresh population, after three driver steps and over a short `gp.run` trajectory driven by each evaluator.
  Verdict: it stays an opt-in `evaluate=` callable and the device loop's shipped `evaluate=` stays `graph_eval.GraphEvaluator`, which also does not yet charge the fused lane for uploading the fitness vector back into the variation graph.
- `problem.sr_fitness_graph(backend="iree")` is not reachable from host channels: it stages its graph inputs as host numpy arrays and `evoxc.run` refuses a host tensor for a device executable (`DeviceError: no implicit device-to-... transfer happens at the run boundary`), so a device-resident in-graph run has to build the same executable directly (`problem._build_graph` + inputs already on the device — the idiom `measure_fused._in_graph_runner` uses); the public entry point is the numpy backend only.
- **Convergence evidence** (CPU box, numpy backend, `EVOXC_DISABLE_LOCATIONS=1`, `python -m evogp.gp.smoke`, pop 200 × 100 generations over 1 000 data rows, 64-slot trees, tournament 4 / crossover 0.9 / mutation 0.2 / 2 elites): generation-0 best `-0.27225` → `-0.10690` at generation 99, ~4.5 s wall (~45 ms per generation), monotone with checkpoints `-0.2722 / -0.2356 / -0.2344 / -0.2006 / -0.1240 / -0.1069` at generations 0 / 10 / 25 / 50 / 75 / 99.
  The same run at `tournament_size=2` (lower pressure) plateaus at `-0.23434`, which is the fitness of the best constant predictor (`-var(y)` for this target), and other seeds reach `-0.1305` / `-0.2343` at the same budget — GP-style premature convergence, not a driver defect.
  `../sr_test.py` records `-0.226` (README/suite note) and `-0.2511 → -0.1720` (its own docstring) on the same target with the torch stack, so this stack lands in the same range and can beat it with the higher-pressure wiring above; the two runs differ in RNG stream (torch vs `splitmix64`), in data draw and in the selection operator (truncation vs tournament), so they are never expected to agree bit-for-bit.
- **The operator layer runs on two routes**: numpy (host channels, the correctness backend, the whole host test suite) and device-resident `iree` (`init_population(..., backend="iree", device="rocm")` → `variation(...)` with device tensors, one `evoxc.run` per generation, no channel readback), both pinned by the device-gated test modules.
  The two are bitwise identical for the same seed — measured on the acceptance config (`max_nodes=32, input_len=8, +-*/ , max_layer_cnt=4`) at pop 64/256/1000 (opcode/payload/size all exact, three chained generations included) — and the variation lane of a whole `step` is 0.517 / 0.669 / 1.268 ms on iree/rocm at pop 64 / 256 / 1000 against 4.08 / 4.71 / 7.38 ms for a standalone numpy `variation` (`DEVICE_LOOP.md` §1; each lane carries its own sync bracket).
  What the device path still transfers per generation is at most the key (a Python int) upload and, when the caller has no device fitness vector, a `-inf` vector; `unevaluated(pop_size, device=...)` and passing the previous state's `fitness` keep even those off the wire.
  `mutation.mutate` / `crossover.crossover` / `select` remain host entry points (they accept a device state by downloading it through `encoding._as_numpy`, which is correct but not hot-path safe).
- **Device coverage is conditional**: the device route is pinned by two DEVICE-GATED test modules (20 cases), which skip on a box without `iree` or without a visible `rocm`/`cuda` device, so on such a box nothing in the suite exercises `variation`'s in-graph elite path, `GraphEvaluator` or a device `step`/`run`; the measurements in `DEVICE_LOOP.md` are likewise reproducible only on that hardware.
- Multi-output (`output_len > 1`) is rejected at `init_population` (see Design Decisions); `out_prob` is stored but unused.
- `validate_channels` is a Python loop over rows and nodes (~50 ms per 256 × 300-node population); the `validate=False` flag is the only mitigation, no vectorized version exists, and the driver does not re-validate its offspring (well-formedness is the operator layer's contract, pinned by `tests/test_gp_stack_operators_*.py`).
- **Device-loop economics of record** (`DEVICE_LOOP.md` §1–§3; warm medians of 15, one process per cell, device synced around every repetition, MI300X/ROCm, `max_nodes=32`, `input_len=8`, `+ - * /`, `max_layer_cnt=4`, tournament 4 / crossover 0.9 / mutation 0.2): a whole `step` is 1.209 / 1.480 / 2.951 ms at pop 64 / 256 / 1000 and 2.475 ms at pop 256 × 4 096 rows, of which evaluation is 0.673 / 0.816 / 1.681 / 1.782 and variation 0.517 / 0.669 / 1.268 / 0.699.
  That is 4.09× / 3.67× / 2.54× / 2.52× faster per generation than the torch stack's `StandardPipeline.step` (4.949 / 5.425 / 7.499 / 6.242 ms, its operator layer alone ~2.5 ms) and 8.35× / 24.37× / 23.59× / 30.76× faster than the same stack on numpy (10.099 / 36.059 / 69.600 / 76.123 ms).
  The honest losses are pop 1000 (0.91×) and the wide-row cell (1.03×) against the torch stack's FUSED route (2.621 / 2.647 / 2.698 / 2.538 ms): there the in-graph evaluation pays a `pop × rows` gather chain while the kernel is flat, so the ~1.2–1.3 ms operator-layer advantage is not enough.
  Cold start is the price: 6.3–7.0 s for the device path (two IREE compiles), against 3.5 s (torch dense), 0.61 s (Triton JIT) and 0.08–0.15 s (numpy), which pays back in 1–5 generations against every side except `torch-fused` (5–90 generations, and never at pop 1000).
  Convergence is checked against the numpy route rather than assumed: the device path follows its best-fitness trajectory to ≤1.0e-06 at every checkpoint of a 20-generation run (`DEVICE_LOOP.md` §4).
- The generation / variation / evaluation graphs are one compile per config: on numpy that is milliseconds, on `iree` a cold `variation` graph costs ~2.1 s (measured at pop 64 and pop 256, `max_nodes=32`) plus the evaluation graph, paid once per `(config, pop_size, backend, device)` and then 1.209–2.951 ms per warm generation (1.480 ms at the acceptance pop 256) — which is why a device run is warmed by `GraphEvaluator.warm(shape=...)` / one throwaway step, and why the short-run smoke stays on numpy.
- `docs`-level gap: the generation distribution was compared against the torch reference once per config (pop 2 000 and pop 20 000, no committed test pins those numbers against torch, only the config-derived expectations) — 3-ary mixed set / `max_layer_cnt` 4: mean length 9.21 vs 9.23, function fraction 0.447 vs 0.444, const-among-leaves 0.395 vs 0.398, per-depth function fraction 0.803/0.798/0.796 vs 0.791/0.799/0.795; weighted 6-function set / `max_layer_cnt` 5 / `layer_leaf_prob` 0.35: at pop 20 000 depth-0 function fraction 0.648/0.655/0.650 vs 0.654/0.653/0.658 and mean length 6.355/6.390/6.406 vs 6.392/6.493/6.470 (one standard error apart, the tree-length tail dominates the spread).
- No committed test compares this stack's fitness numbers against the TORCH stack on a shared problem: the two only share the target function and the fitness formula, and `sr_test.py` (the torch-side reference) cannot be imported without torch and CUDA-scale data.
  The comparison lives in the measurement harness instead (`measure_generation.py`'s `torch` / `torch-fused` sides, table in `DEVICE_LOOP.md` §4), where the two trajectories differ by construction — RNG stream (torch vs `splitmix64`), selection (truncation `survival_rate=0.3, elite_rate=0.01` vs tournament-4) and mutation wiring — so only the endpoints are comparable.
