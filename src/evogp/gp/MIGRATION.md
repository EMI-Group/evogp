# Migrating EvoGP off torch — current state, blockers, ordered plan
Scope: replacing the torch sites in `src/evogp/{tree,algorithm,problem,pipeline}` with the torch-free `evogp.gp` stack (`evoxc` + numpy) and the fused Triton route.
This is the plan of record for "prepare to replace all torch code"; the torch stack stays untouched and keeps its role as the numerics oracle and benchmark baseline until each step's gate passes.
Status vocabulary: **covered** (gp already has a working equivalent), **partial** (exists but with a stated gap), **missing** (no gp equivalent yet), **never** (must stay torch by nature).
## (a) What the new stack already covers
- Tree encoding and validation: the `[pop, max_nodes]` prefix-order `opcode`/`payload`/`size` channel triple with host validation and `to_legacy_triple` bridge (`gp/encoding.py`).
- Random generation of a whole population in one traced graph, key-based (`gp/encoding.py::init_population`), seedless and torch-free.
- Selection: tournament, rank and roulette on a fitness vector (`gp/selection.py::select`, `selection_pressure` knob).
- Crossover: splice crossover with per-individual probabilities (`gp/crossover.py::crossover`).
- Mutation: point, subtree and hoist (`gp/config.py:60` `MUTATION_KINDS = ("point", "subtree", "hoist")`).
- Whole-generation variation in ONE graph, elitism included (`gp/variation.py::apply_variation`), which is why a device generation needs no readback.
- Single-output symbolic-regression evaluation, host (`gp/evaluator.py::predict`) and in-graph (`gp/graph_eval.py`, `gp/problem.py::sr_fitness_graph`), plus `CustomLoss` (`gp/problem.py:225`).
- The driver contract `init_gp` / `step` / `run` / `GPResult` (`gp/workflow.py`), device-resident when `backend="iree"`, with key-based determinism (`run(..., key=0)`).
- The device objective over the fused Triton kernel (`gp/fused_eval.py`), gated by `interop_available()` — see the blocker in (b).
- All of the above is enforced torch-free by `gp/tests/test_gp_stack_purity.py`, and `import evogp.gp` works with `PYTHONPATH=src` alone (no evoxc at module scope).
## (b) What still depends on torch, and why
- `tree/` representation and operators: `utils.py:4`, `descriptor.py:3`, `generation.py:102`, `splicing.py:78`, `tree.py:1`, `forest.py:2`, `combined_tree.py:2`, `combined_forest.py:4` — torch tensors ARE the container format (`batch_node_value` float32 CUDA, `batch_node_type` int16, `batch_subtree_size` int16), and the operators are vectorized torch.
- `tree/` engines: `evoxc_engine.py:272`, `dense_engine.py:495`, `fused_engine.py:254`, `fused_kernels.py:202`, `batch_engine.py:142`, `batch_programs.py:46`, `batch_run.py:50`, `dense_memo.py:48` — the engines accept and return torch tensors because `Forest`/`Tree` are torch containers; the fused route additionally NEEDS torch for the Triton launch.
- `algorithm/` (24 of 29 modules import torch) — every operator is written against `Forest`/`CombinedForest` torch tensors and the `torch.manual_seed` global RNG.
- `problem/`: `symbolic_regression.py:61` and `custom_loss.py:13-20` (user callables are `torch.vmap`-ed over `Forest.forward`), `classification.py`, `transformation.py`; the robotics problems are jax/brax/genesis and are not a torch migration question.
- `pipeline/standard.py:3` — the loop, its `NaN -> -inf` in-place mutation of the fitness tensor, `is_show_details` printing and `best_tree` tracking.
- Determinism: the torch stack's contract is `torch.manual_seed(0)` on the global RNG (`generation.py:66-69`); gp is key-based instead, so the two are distribution-equivalent at best, never bit-identical.
- The device hand-off: `gp/fused_eval.py` reaches torch at call time through DLPack, and the native device export is an `evoxc` contribution STILL AWAITING MERGE (commit `474bf72`, reachable as the task's evoxc worktree checkout `/root/evoxc/.genesis/foreign_repos/evoxc`); on the current main-line checkout (`/root/evoxc` sha `9f66fec`) `Tensor.__dlpack__` raises `DeviceError` for a device payload, so `interop_available()` is `False` against it and the whole `gp-fused` lane is skipped (36 skipped cases in `gp/tests/test_gp_stack_device_fused.py`).
- `evogp.gp` has NO equivalent for: truncation selection and `best_probability`-weighted tournament, 7 of the torch stack's mutation kinds (insert, delete, single/multi-const, multi-point, combined), the Diversity / LeafBiased / Combined crossovers, multi-output (`init_population` raises `NotImplementedError` for `output_len > 1`), the `Forest`/`CombinedForest` container protocol (slicing, `__add__`, iteration), the Classification / Transformation / robotics problems, `fitness_target` / `time_limit` / `is_show_details` / `best_tree`, and the sympy / infix / png export.
## (c) Ordered migration steps, each with its parity gate
0. Freeze the oracle: no step may change `src/evogp/tests/reference_eval.py` or the torch stack's numbers. Gate: `pytest src/evogp/tests -q` stays green (base shape 1 308 passed / 7 skipped / 0 failed).
1. A numpy-native evaluation boundary for the existing torch `Forest`: add a `Forest -> gp channels` adapter (`gp/encoding.py::to_legacy_triple` already runs the other way) so one population can be evaluated by BOTH stacks. Gate: `gp.tests.test_gp_stack_parity_*`-style case on a shared problem, `max_rel <= 1e-6` value parity over 64 random trees on the arithmetic set — this is the currently-uncovered "no committed test compares the two stacks' fitness numbers" gap.
2. Port the operator primitives the torch stack has and gp lacks: truncation selection, `best_probability` tournament, the remaining 7 mutation kinds, and the 3 crossover kinds. Gate: for each operator, a distributional test — same config, same fitness vector, N=10 000 draws, `chi²`-level agreement of the selected-index histogram against the torch operator (not bitwise: the RNGs differ by design).
3. Generation: a gp generator that reproduces the `GenerateDescriptor` contract exactly, including `const_samples`, `out_prob`, `layer_leaf_prob` and the multi-output `OUT_NODE` tag. Gate: descriptor-equivalence test (same descriptor, same arity histogram and layer distribution within ±2 % at 10 000 trees) plus the depth/`MAX_FULL_DEPTH` invariant.
4. Container protocol: a gp-side `Forest`-compatible view (slicing, `__add__`, iteration, `SR_fitness`, `to_sympy_expr`) so `algorithm/` operators can be re-pointed without a rewrite. Gate: `tests/test_api_compat.py` re-run against the new container, plus the `__getitem__` view-vs-copy contract.
5. Algorithm loop: re-implement `GeneticProgramming.step` on the gp primitives, with elitism moved out of the operators (already the case in both stacks). Gate: same-seed trajectory comparison against the torch stack over 20 generations on one SR problem — best-fitness and median-fitness within the documented distribution-equivalence band, and the 4-host-round-trip budget of `tests/test_hot_path_contracts.py` kept.
6. Problems: `SymbolicRegression` (single-output first), then `Classification`/`Transformation`, then `CustomLoss` as the multi-output escape hatch. Gate: per-problem fitness parity against the torch path on identical data and identical populations (target `1e-6` relative for value paths, NaN/Inf placement identical).
7. Pipeline: `StandardPipeline` semantics (fitness sign convention, `NaN -> -inf`, `fitness_target`, `time_limit`, `is_show_details`, `best_tree`). Gate: an end-to-end `example/basic.py` equivalent on the gp stack reaching the same best fitness band, plus `sr_test` parity.
8. Multi-output: `OUT_NODE` in the gp encoder, the multi-output loss, and the `CombinedForest` container. Gate: the fused route's multi-output parity (`fused_check.py --stage multi`, bitwise on values) plus `tests/test_combined_forward.py` re-expressed for the gp path.
9. Display/export: sympy, infix and png. Gate: textual equality against the torch stack's `to_sympy_expr` on a fixture set (display only, no numerics).
10. Delete the torch stack only when steps 1–9 are green on a device box AND a CPU box. Until then both stacks ship, and the README's two-stack section is the accurate description.
## (d) What must never be torch-free (with evidence)
- The fused Triton route's kernels and launcher: `tree/fused_kernels.py` and `tree/fused_engine.py` are Triton on a torch device by construction — the route IS the torch device (`fused_kernels.py:196` imports torch, and the kernel is Triton). It is the fastest route, so this is the performance floor to keep, not a debt.
- The reference oracle: `src/evogp/tests/reference_eval.py:76` (`import torch`) is an INDEPENDENT plain-torch reimplementation of the engine; making it torch-free would destroy its value as an independent check.
- The benchmark baseline: `test/benchmark/evoxc/arms.py`'s `torch-per-tree` / `torch-batched` arms are the comparison of record for every speed claim in `FUSED.md` / `FINAL.md`. A torch-free baseline would silently redefine every published speedup.
- jax/brax/MuJoCo/Genesis robotics problems: `problem/brax_problem.py:8-23`, `problem/mujoco_playground.py:8-24`, `problem/genesis_problem.py:8-9`, `problem/go2_env.py:3-4` depend on third-party jax-based simulator stacks. There is nothing to migrate them to; they are not torch code in the first place, only torch-adjacent wrappers.
- torch-fed user callables: `problem/symbolic_regression.py:61` and `problem/custom_loss.py:13-20` accept a callable that operates on torch tensors and `torch.vmap` them. `CustomLoss` is the documented multi-output escape hatch, so a torch-free replacement is a user-facing API break, not an internal refactor.
- `torch.manual_seed(0)` replay: the shipped determinism contract of the torch stack (`generation.py:66-69`). Reproducing a run bitwise requires torch; the gp stack's answer is a different contract (`run(..., key=0)`), so any user script pinned on the seed cannot be migrated without an explicit behaviour change.
- Sympy / networkx / sklearn exports are already torch-free (`tree/tree.py`'s and `tree/utils.py`'s sympy mapping, `problem/symbolic_regression.py`'s sklearn loaders) and therefore need no migration at all — listed here so nobody "migrates" them into evoxc.
