# `src/evogp/` — EvoGP 2.0.0a2: tree-based genetic programming on EvoX Compiler (`evoxc`)

## Intent
EvoGP is a Tree-based Genetic Programming (TGP) framework for symbolic regression, the GP layer of the EvoX family and the subject of the paper at https://arxiv.org/abs/2501.17168.
The `2.0.0a2` line is one stack: every module of the package is torch-free except the one optional device route, and there is nothing left to migrate.
Three subpackages carry the library, one concern each: `evogp.gp` is the framework (a functional, `evoxc`-based GP stack in the EvoX 2.0 idiom), `evogp.fused` is the optional device-native Triton evaluator, and `evogp.evox_ext` presents the stack as `evox.core.StdWorkflow` components.
Two shared modules sit beside them: `_tables.py` (the torch-free single source of truth for node types, function ids, arities and `OUT_NODE`) and `_multi_output.py` (the one single-output `OUT_NODE` refusal rule, numpy only).
`evogp.gp` runs on a CPU box with numpy alone; `evogp.fused` is the one route that needs a CUDA/HIP device and the `fused` extra; `evogp.evox_ext` is the only subtree that imports `evox`.
There is NO build step and no compiled extension: `import evogp.gp` works from a plain checkout, `evoxc` is the one runtime engine dependency, and the only JIT outside `evoxc` is Triton's, at the fused route's first call.
No CUDA/HIP kernel belongs to EvoGP itself: the fused route's kernels are Triton source JIT-compiled on the fly, and every other route emits graphs through `evoxc`.
Evaluation is three routes over one population encoding: the HOST numpy evaluator (CPU, no device) → the IN-GRAPH `iree` route (device-resident, one compiled graph per shape) → the FUSED Triton route (one kernel launch per (tree, row block), the device loop's objective).
EvoGP is the sister project of EvoX; this directory is the library, and the experiment scripts, notebooks and dev tooling live outside it in the repo's `example/`, `tutorial/` and `test/`.

## Public API Surface
`src/evogp/__init__.py` is EMPTY by design: `import evogp` succeeds, has no side effects and exposes nothing, and every import in the repo goes through a submodule.
- `from evogp.gp import ...` is the whole framework: configs `GPTreeConfig`, `GPConfig`, `SELECTION_MODES`, `MUTATION_KINDS`; state `GPState`, `channels`, `replace`, `population_size`, `max_nodes`, `CHANNEL_NAMES`, `UNEVALUATED`; encoding `init_population`, `live_mask`, `row_length`, `is_leaf`, `validate_channels`, `to_legacy_triple`, `from_legacy_triple`; operators `select`, `apply_crossover`, `mutate`, `point_mutation`, `subtree_mutation`, `hoist_mutation`, `apply_variation`; problem layer `BaseProblem`, `SymbolicRegression`, `CustomLoss`, `predict`, `predict_graph`, `sr_fitness_graph`; evaluation `GraphEvaluator`, `sr_fitness_channels`, `readback_fitness`, `FusedEvaluator`, `FusedDeviceEvaluator`, `fused_available`, `interop_available`; driver `init_gp`, `step`, `run`, `GPResult`; cache surface `cache_stats`, `clear_cache`.
- `from evogp.fused import ...` is the device route: `evaluate_fused`, `sr_fitness_fused`, `envelope_decline`, `fused_available`, `fused_cache_stats`, `clear_fused_cache`, `FusedUnsupported`, `MAX_OUT_LEN` (8), the four knob resolvers `resolve_block_rows` / `resolve_num_warps` / `resolve_max_scratch_mb` / `resolve_dispatch`, and the `kernels` submodule.
- `from evogp.evox_ext import ...` is the EvoX 2.0 adapter: `GPAlgorithmConfig` / `GPAlgorithm` / `make_gp_algorithm`, `SRProblemConfig` / `SRProblem` / `SRProblemState` / `make_sr_problem`, `make_stdworkflow`, `accepts_cache_dir`, `OPT_DIRECTION`, and the readbacks `generation_fitness`, `best_so_far`, `best_row`, `host_channels`.
- Canonical flow through the driver (`key` is the whole seed, there is no global one):
```python
from evogp.gp import GPConfig, GPTreeConfig, SymbolicRegression, run
tree = GPTreeConfig(max_nodes=64, input_len=2, using_funcs=("+", "-", "*", "/"))
config = (tree, GPConfig(pop_size=200))
result = run(config, SymbolicRegression(x, y), generations=100, key=0)
result.best_fitness, result.best_fitness_history, result.best_channels
```
- The objective is the only plug-in point: any callable `channels -> (pop_size,) float32` MAXIMIZED, and a `SymbolicRegression` / `CustomLoss` instance is one twice over (the object is callable, and it also exposes `.evaluate`, `.predict` and `.evaluate_graph`); a `GraphEvaluator` or `FusedDeviceEvaluator` returns a DEVICE fitness tensor instead, which keeps the loop device-resident.
- The result is `GPResult(best_fitness, best_fitness_history, median_fitness_history, best_channels, best_generation, generations, state)`, and the winning tree is `best_channels` — the `opcode` / `payload` / `size` rows of ONE individual, a population of one for `predict`, `evaluate`, `validate_channels` and `to_legacy_triple`.
- The population is three prefix-order `[pop_size, max_nodes]` channels — `opcode` int32 (a `Func` id on a function node, an `NType` marker on a leaf), `payload` float32 (the constant value or the variable index) and `size` int32 (the node's subtree size) — and every entry point accepts them in the three documented forms: a `GPState`, the three channels, or the three 1-D rows of one individual (promoted to a population of one).
- `evogp.gp.cache_stats()` reports the whole stack's memoized graphs per layer plus the shared `evoxc` compile cache, with the device-evaluation layers in their own bucket, and `clear_cache()` drops all of them; `evogp.fused.clear_fused_cache()` is the separate reset of the kernel route's counters and tables.
- `evogp.fused` is importable only with the `fused` extra (it needs torch at module scope); `evogp.gp` and `evogp.evox_ext` import on a plain numpy box, and `import evogp.gp` needs neither `evoxc`, `evox` nor torch.
- `from evogp.evox_ext import make_stdworkflow` builds the `StdWorkflow(GPAlgorithm, SRProblem, opt_direction="max")` wiring (any other orientation is refused), forwards `backend` / `device` / `compile_options` / `generations` and, when the installed `evox` declares the keyword, the opt-in step-artifact `cache_dir=`; the trajectory is read back with `generation_fitness` / `best_so_far` / `best_row` / `host_channels`.

## Dependency Direction
The DAG is small and strict; preserve it when adding modules.
- `gp/ → _tables.py, _multi_output.py` (and numpy, plus `evoxc` at call time only): the stack owns the encoding, the operators, the evaluator, the problem layer and the driver.
- `fused/ → _tables.py, _multi_output.py` (plus torch at module scope, triton lazily): it reads the same node/function ids and the same `OUT_NODE` rule, and it imports nothing from `gp/`.
- `gp/` reaches `fused/` only through `gp/fused_eval.py`, which resolves `evogp.fused` (and torch and triton) with `importlib` INSIDE its functions — so `gp/fused_eval.py` is the one torch boundary of the stack, and a literal `import torch` there is a test failure.
- `evox_ext/ → gp/` (config, state, encoding, variation, graph_eval) and `evox` at call time only; nothing imports `evox_ext/`.
- Nothing imports `evogp.fused` at import time: not `evogp/__init__.py` (empty), not `evogp.gp`, not `evogp.evox_ext`.
- `_tables.py` imports nothing at all (no torch, numpy, evox, evoxc, not even stdlib); `_multi_output.py` imports numpy and `_tables` only, which is why both stacks may share the one `OUT_NODE` rule.

## Constraints
- **`gp/` is torch-free by contract**: `gp/tests/test_gp_stack_purity.py` greps every `*.py` of the subtree (parametrized by file, so a new module adds a case) for `import torch` / `from torch` / `import evox` / `from evox`, and clean-subprocess cases pin that `import evogp.gp` works with `PYTHONPATH=src` alone (no `evoxc` at module scope either).
- **`import triton` stays inside `fused.kernels.kernels()`**: a triton-less box imports `evogp.fused` and gets a clean `FusedUnsupported` / `FusedUnavailable` from `kernels()`, never an ImportError.
- **No build step, no compiled extension, no cached binary**: the fused kernels are JIT-compiled at the first call (~1.6 s for the value kernel from an empty cache, ~2 ms from a warm one, nothing per call afterwards), and `TRITON_CACHE_DIR` must point at a writable directory on a box whose `$HOME` is read-only.
- **Determinism is key-based**: `GPState.key` is an `evoxc` splitmix64 key carried through the state (the key of the NEXT generation throughout), so `run(config, evaluate, generations=…, key=0)` reproduces a run bit-identically from one integer — there is no global seed and no torch RNG.
- **Fitness contract, repo-wide**: `evaluate(channels)` returns a fresh, writable `(pop_size,)` float32 vector that is MAXIMIZED (losses negated) and whose every non-finite value is mapped to `-inf`; the in-graph operator layer applies the same rule before ranking, so a `+inf` can never win a tournament or an elite slot.
- **The elite and selection tie rule is the lower row index**: the elite order is the stable ascending order of `-fitness` (repeated `argmax` over a running mask below 50 elites, a stable `argsort` above it), and rank selection uses the same stable order, so a flip in that tie order is a behaviour change and is pinned by the suite.
- **Device policy**: `evogp.gp` defaults to the numpy/CPU backend and takes an `evoxc.Device` kind spelling (`"cpu"`, `"rocm"`, `"cuda"`, `"rocm:0"`, or a concrete `evoxc.Device`); the fused route takes torch tensors on a CUDA/HIP device, and torch's `"cuda"` spelling selects AMD GPUs under ROCm as well — nothing detects a device for you.
- **Surviving environment knobs** (each read by the module named here; a bad spelling raises `ValueError` naming the variable): `EVOGP_GP_COMPILE_CACHE_SIZE` (64, the shared compiled-graph cache of `gp/encoding.py`), `EVOGP_GP_GRAPH_CACHE_SIZE` (32, the in-graph problem layer's own cache), `EVOGP_GP_EVAL_BUDGET_MB` (256, the numpy evaluator's row-chunking budget), `EVOGP_FUSED_BLOCK_ROWS` (256), `EVOGP_FUSED_NUM_WARPS` (1), `EVOGP_FUSED_MAX_SCRATCH_MB` (8192, the launch memory envelope), `EVOGP_FUSED_DISPATCH` (`bound`, with `jit` restoring Triton's `JITFunction.run`), `EVOGP_FUSED_HOST_MEMO` (16, the prepared-call table, read once at import).
- `EVOXC_DISABLE_LOCATIONS=1` speeds `evoxc` tracing up substantially and is recommended for real runs (it is an `evoxc` knob and not part of any cache key); the runtime backend/device of the in-graph route are explicit arguments, not environment variables.
- **Host-in/host-out versus device-in/device-out**: `evaluator.predict`, `predict_graph` and `sr_fitness_graph` take host channels and return numpy (one readback per call), while `graph_eval.sr_fitness_channels` and `FusedDeviceEvaluator` take device channels and return an `evoxc` device tensor — a device loop passes the latter pair as `evaluate=`.
- **There is no route-selection environment variable**: the evaluation route is whatever the caller passes as `evaluate=` (plus the `backend=`/`device=` of the in-graph layers), so nothing in the library switches routes behind a call.
- **Optional extras**: `fused` (torch + triton) for `evogp.fused`, `iree` (iree-base-compiler / iree-base-runtime) for the device backend of the in-graph route, `torch` for the dev oracle and the harnesses' baselines, `dev` (pytest); `evox` is required only by `evogp.evox_ext`, and `evoxc` + numpy carry the rest.
- Multi-output (`OUT_NODE`) is refused, not evaluated, on every single-output door: `init_population` raises `NotImplementedError` for `output_len > 1`, and `_multi_output.MultiOutputError` (both a `ValueError` and a `NotImplementedError`) is what an `OUT_NODE`-tagged population meets at `encoding`, `evaluator`, `graph_eval` and `fused_eval`; only `evogp.fused` serves tagged trees, up to `MAX_OUT_LEN` (8), on the legacy triple.
- Keep `src/evogp/__init__.py` empty: adding imports there would make `import evogp` pull submodules and would break the documented import style.

## Known Issues
Cross-cutting problems only; the per-directory detail lives in the child CONTEXT files.
- **No CI**: the three suites and the fused battery are run by hand, quoted per path, never as a sum.
- **Symbolic regression is the whole problem layer**: `SymbolicRegression` and `CustomLoss` are the shipped problems, and there are no classification, transformation or robotics problems in this release.
- **No population container and no export**: there is no object protocol over a population (slicing, `__add__`, iteration, a per-tree `SR_fitness`) and no sympy / infix / png rendering — the population IS the three channel rows, and the winner is reported as `GPResult.best_channels`, so a caller inspects or prints a tree itself.
- **Multi-output is unimplemented in the stack**: `init_population` raises `NotImplementedError` for `output_len > 1` (the fused route does serve `output_len` 2..8 on the legacy triple), and `CustomLoss` is the escape hatch for any objective that is not the plain SR loss.
- **The device routes are the fast ones and the host numpy evaluator is the reference**: at large `n_rows` the in-graph body materializes `[pop_size, n_rows]` intermediates per tree column and costs far more than the host evaluator's one vectorized pass (the adapter's own measurement in `evox_ext/CONTEXT.md` quantifies it at 16× on `N=1000` / pop 200 / `max_nodes=64`), so the numpy backend is the correctness and CPU path.
- **Channel validation is host-side**: `encoding.validate_channels` is a Python pass over a numpy view, so no device route runs it (a traced function cannot download) and `validate=False` is the only switch; the operator layer's own well-formedness contract carries those runs.
- **The fused route's residual limits** (`fused/CONTEXT.md`): the multi-output LOSS path accumulates in float32 per row block (≤1.2e-07 relative, non-bitwise by construction) where the value path is bitwise; `rows ≤ 64` at 8–32-node trees is unmeasured; `output_len > 8` declines and nothing wider has been measured; the memory envelope is a budget, not a guarantee; and there is no per-stage timer surface.
- **The device hand-off is `evoxc`'s native DLPack export**: on an `evoxc` without `Tensor.__dlpack__` for a device payload the probe `interop_available()` answers `False` and `FusedDeviceEvaluator` falls back to the host hand-off — correct, but one upload and one readback per call.
- **`evogp.evox_ext` inherits the in-graph route's cost and its compile shape**: one graph per state signature, compiled inside `init()` (so the folded-in `evoxc.build` is paid there, removable only with `StdWorkflow(cache_dir=...)`), no route selection, and no monitor (a `GPState` is not an `(n, dim)` matrix).
- **The fused route is single-device by construction**: there is no device argument (the ambient `cuda:0`-style device is used), `x` must be a device torch tensor (a numpy array declines, because the route never stages host memory), and `EVOGP_FUSED_DISPATCH` has no effect under a Triton that ships no `knobs.HookChain` (`bound` then stays the only path).
- **The measurement harnesses are committed evidence, not gates**: `measure_generation.py` / `measure_popscale.py` / `measure_fused.py` produce the numbers in `DEVICE_LOOP.md` and `POPSCALE.md`, and nothing re-checks them.
- **No dimension validation between a config and a problem's data**: `GPTreeConfig.input_len` and a problem's `x.shape[1]` are not cross-checked, so a mismatch fails inside the tree layer / evaluator instead of at wiring time.

## Test Strategy
The gate is three pytest paths plus one CLI battery, quoted PER PATH and never as a sum; run them from the repo root with the torch-carrying venv and a writable Triton cache:
```bash
export TRITON_CACHE_DIR=/tmp/triton_cache_evogp && mkdir -p "$TRITON_CACHE_DIR"
export PYTHONPATH=src:/root/evoxc:/root/evox/src EVOXC_DISABLE_LOCATIONS=1
/tmp/rocvenv/bin/python -m pytest src/evogp/gp/tests -q          # 349 passed / 0 skipped
/tmp/rocvenv/bin/python -m pytest src/evogp/fused/tests -q       #  45 passed / 0 skipped
/tmp/rocvenv/bin/python -m pytest src/evogp/evox_ext/tests -q    #  13 passed
```
- `src/evogp/gp/tests` — 349 passed / 0 skipped on the device reference box, in ~63 s; the three `test_gp_stack_device_*` modules (the fused and in-graph device lanes) SKIP rather than fail where `iree`, a visible device, torch/triton or `evoxc`'s DLPack export is missing.
- `src/evogp/fused/tests` — 45 passed / 0 skipped in ~1.4 s from a warm Triton disk cache; device-gated, so a CPU-only or triton-less box (or one with no writable cache) skips the module.
- `src/evogp/evox_ext/tests` — 13 passed in ~6 s; the module skips as a whole without `evox` on the path.
- The fused battery is the in-library numeric/contract/measurement gate: `/tmp/rocvenv/bin/python -m evogp.fused.check --stage parity|multi|goldens|declines|timing|tuning|all` (56 / 65 / 10 / 58 comparisons, then six timing cells and the 4 × 3 geometry grid; every leg needs a device and a writable cache).
- The convergence smokes are `python -m evogp.gp.smoke` (CPU, numpy, nothing at import time, `--quiet` for the summary line) and `python -m evogp.evox_ext.demo_stdworkflow` (the `StdWorkflow` run, `--backend iree --device rocm:0` on a device box).
- The independent numeric oracle is DEV tooling at `../../test/oracle/`: `reference_eval.py` (a plain-torch evaluator) plus 7 frozen `goldens/*.npz` fixtures at 1e-4 rtol/atol. It is not on `PYTHONPATH` and no library module imports it; `evogp.fused.check` and `fused/tests/conftest.py` append it to `sys.path` themselves.
- Performance work is the harnesses in `gp/` (`measure_generation.py`, `measure_popscale.py`, `measure_fused.py`, with `_torch_baseline.py` supplying the plain-torch columns); their reports of record are `gp/DEVICE_LOOP.md` and `gp/POPSCALE.md`, and their raw numbers are the committed JSON under `gp/evidence/`.
- Known coverage gaps: the fused route's `rows ≤ 64` corner, `output_len` above `MAX_OUT_LEN`, cold-compile economics, and the elite `argsort` fallback above 50 elites have no test.

## Notes for Agents
- Environment: repo root as CWD, `PYTHONPATH=src:/root/evoxc:/root/evox/src`, `/tmp/rocvenv/bin/python` (the `python` on PATH has no torch), `EVOXC_DISABLE_LOCATIONS=1`, and a writable `TRITON_CACHE_DIR` for anything that launches the fused route.
- Read the owning child CONTEXT before editing: `gp/CONTEXT.md` for the encoding/operator/driver contracts, `fused/CONTEXT.md` for the kernel route's envelopes and decline rules, `evox_ext/CONTEXT.md` for the `StdWorkflow` component contract.
- `import evogp.gp` works with `PYTHONPATH=src` alone, but building or running a graph needs `evoxc` importable at call time (`/root/evoxc` on the path); `evogp.evox_ext` additionally needs `evox` on the path when `make_stdworkflow` is called.
- Never reintroduce torch into `gp/`: the purity test is a source grep, so even an unused `import torch` fails, and `gp/fused_eval.py` must keep resolving torch through `importlib` inside functions.
- Never add a build step, a compiled extension or a vendored binary: the kernels are JIT-compiled from source at the first call, and `fused/kernels.py` must keep its helpers as module-level jitted objects (the compiled kernel resolves its callees through module globals).
- Change GP behaviour in `gp/`, never in `evox_ext/`: the adapter is thin by contract and reaches the stack's private traced builders (`encoding._generator_fn`, `variation._variation_fn`, `graph_eval._device_sr_fitness`) because there is no public "traced function only" accessor.
- `evogp.fused` never chooses itself: a call it cannot serve raises `FusedUnsupported` and the caller owns the fallback, so a new consumer must handle that exception rather than expect a route switch.
- Numeric changes belong against the oracle at `../../test/oracle/`, not against hand-copied constants; the fused battery's `parity` / `multi` / `goldens` legs are the gate, and value paths are bitwise there while loss paths are within 1e-5 relative.
- Determinism questions are answered by the key, not by a seed: pass the same `key=` to reproduce a run, and remember `GPState.key` is the key of the NEXT generation.
- `MAX_STACK`, `MAX_FULL_DEPTH`, `NType`, `Func` and friends live only in `_tables.py`; nothing else may redefine them, and they must stay import-free so the tables survive any dependency change.
