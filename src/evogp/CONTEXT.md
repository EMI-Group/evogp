# `src/evogp/` — EvoGP: Tree-based Genetic Programming on PyTorch + `evoxc`

## Intent
EvoGP is a Tree-based Genetic Programming (TGP) framework for symbolic regression, classification, feature transformation and robotics-control benchmarks (Brax / MuJoCo-Playground / Genesis), with multi-output trees for classification and policy optimization.
Evaluation is a **"true jit"**: `tree/evoxc_engine.py` walks a population host-side into frozen per-tree static programs and specializes each structure into a fresh evoxc graph through `evoxc.build_cached` (memoized in one shared `evoxc.CompileCache`); `tree/dense_engine.py` is the alternative dense all-ops route (it also owns the route policy and `EVOGP_EVAL_MODE`); `tree/fused_engine.py` + `tree/fused_kernels.py` are the device-native fused Triton route — ONE JIT-compiled kernel launch for the whole population off the population tensors themselves, and the `auto` default on a device box; `tree/batch_engine.py` is the opt-in merged-graph route (`EVOGP_EVAL_MODE=batch`) that merges one traced graph per DISTINCT tree program into ONE executable with `evoxc.batch_functions` (static function axis, banded merge under the device binding-cap policy of `tree/batch_bands.py`); random generation, mutation and crossover are plain vectorized torch (`tree/generation.py`, `tree/splicing.py`).
There is **no custom CUDA/HIP kernel and no compiled extension**: nothing has to be built, `import evogp.<submodule>` works from a plain checkout, and the external **`evoxc`** package (EvoX Compiler, the EvoX-family tensor library/compiler that provides the graph API) is the evaluation-engine dependency.
This directory is the install root of the `evogp` package (version 2.0.0a1): `setup.py` lives at the repo root and uses `find_packages(where="src")` + `package_dir={"": "src"}` (repo-root packaging/dependency edits are a separate task).
EvoGP is the sister project of EvoX; experiment scripts live outside the package in the repo's `example/`, `tutorial/` and `test/` directories.
`tree/ENGINE_SPEC.md` (semantics of record), `tree/CONTEXT.md` (representation, engine, API details) and `tests/CONTEXT.md` (the pytest suite) are the authoritative companions to this file.

## Public API surface (what users import)
`src/evogp/__init__.py` is an EMPTY (0-byte) file — `import evogp` succeeds, has no side effects and exposes nothing; there is no version/model re-export anywhere.
Every import in the README, `example/`, `tutorial/` and `sr_test.py` goes through a submodule:
- `from evogp.tree import Forest, CombinedForest, Tree, CombinedTree, GenerateDescriptor` (also `MAX_STACK`, `randint`, `NType`).
- `from evogp.algorithm import GeneticProgramming, DefaultSelection, DefaultMutation, DefaultCrossover` (plus all `*Crossover` / `*Mutation` / `*Selection` / `*Selector` classes, via star imports).
- `from evogp.pipeline import StandardPipeline` (and `BasePipeline`).
- `from evogp.problem import SymbolicRegression, Classification, Transformation, BraxProblem, GenesisProblem, MujocoProblem, CustomLoss` (plus `BaseProblem`).
Canonical end-to-end flow (see `example/basic.py`, `sr_test.py`): `problem = <Problem>(...)` → `descriptor = GenerateDescriptor(...)` → `algorithm = GeneticProgramming(initial_forest=Forest.random_generate(pop_size=…, descriptor=…), crossover=…, mutation=…, selection=…)` → `best_tree = StandardPipeline(algorithm, problem, generation_limit=…).run()`.

## Dependency direction (the key architectural constraint)
The package is a strict four-layer DAG; preserve it when adding modules:
- `tree/` — foundation layer: representation (`tree.py` / `forest.py` / `combined_tree.py` / `combined_forest.py`), the generation blueprint (`descriptor.py`), the pure-torch operators (`generation.py`, `splicing.py`) and the evoxc evaluation engines (`evoxc_engine.py` for the specialized per-structure route, `dense_engine.py` for the dense all-ops route, `fused_engine.py` + `fused_kernels.py` for the fused Triton route, `batch_engine.py` plus its seven siblings for the opt-in batch route). It imports only torch/numpy/sympy/networkx, `evoxc` and stdlib; it must NEVER import from `algorithm/`, `problem/` or `pipeline/`.
- `algorithm/` — depends on `tree/` (Forest/CombinedForest + MAX_STACK/randint/NType). Note the intra-directory edge `crossover/ → selection/` (`BaseSelector`); no reverse edge exists.
- `problem/` — depends on `tree/` only.
- `pipeline/` — the top of the DAG: depends on `algorithm/` + `problem/`, and nothing may import it back (verified: zero references to `pipeline` below this layer).
The engine is reached ONLY through the `Forest`/`Tree` wrappers (`forward` / `batch_forward` / `SR_fitness`): no module outside `tree/` imports `evoxc_engine` / `dense_engine` / `batch_engine` or the `evoxc` package.

## Constraints
- **No build step, no compiled extension**: a built shared library is no longer a prerequisite for importing the library; the only engine requirement is that `evoxc` is importable (top-level `import evoxc` + `from evoxc.build_cache import CompileCache, build_cached` in `tree/evoxc_engine.py`, top-level `import evoxc` in `tree/dense_engine.py`). `evoxc` is declared in `setup.py`'s `install_requires` and, in this dev venv, resolved from the sibling checkout `/root/evoxc` on `PYTHONPATH`; without it `import evogp.tree` fails at import.
- Standard invocation for every script/test: repo root as CWD, `PYTHONPATH=src:/root/evoxc`, and a task venv carrying torch (`python`/`python3` on PATH have no torch); the reference environment is torch 2.13.0+rocm7.1 on an AMD MI300X with `evoxc` from the `/root/evoxc` checkout and `iree-base-compiler`/`iree-base-runtime` 3.11 installed (concrete interpreter path recorded in `../tests/CONTEXT.md`).
- Engine knobs (each documented in the owning module docstring; `tree/CONTEXT.md` has the consolidated table, with dense detail in `tree/DENSE_EVAL.md` and batch detail in `tree/BATCH_EVAL.md`): `EVOGP_EVOXC_BACKEND` (`numpy` default, `iree` opt-in), `EVOGP_EVOXC_DEVICE`, `EVOGP_EVOXC_OPT_LEVEL` (`"O0"`/`"O1"` only — measured verdict: O2/O3 compile no faster and run ~40 % slower warm), `EVOGP_EVOXC_CACHE_SIZE` (compile cache entries), `EVOGP_EVOXC_ARTIFACT_DIR` (opt-in on-disk artifact cache, off by default).
  `evoxc_engine._resolve_backend` defaults the backend to `"numpy"` (CPU reference interpreter, no GPU needed), while the ROUTE POLICY answers the default device-box call with the fused (Triton) route from `EVOGP_FUSED_MIN_POP` up and picks `iree` for dense at `pop_size >= 64` when fused is unavailable.
  `EVOXC_DISABLE_LOCATIONS=1` speeds tracing up ~4× and is recommended for real runs (it is NOT part of the cache key).
  `EVOGP_EVAL_MODE` (`auto` default, else `dense` / `dynamic` / `specialized` / `batch` / `fused`) and the `EVOGP_DENSE_*` family (`AUTO_MIN_POP`, `AUTO_MAX_ROWS`, `AUTO_BUDGET_MB`, `AUTO_MAX_TREE_LEN`, `MAX_TREE_LEN`, `BUDGET_MB`, `UPDATE_MODE`, `ALLOW_UNSAFE_SCATTER`, `PRUNE`, `HOST_MEMO`) select/tune the dense route; the `EVOGP_BATCH_*` family (`BAND_SIZE` 16, `BANDS` explicit/`auto`/flat, `CHUNK_BANDS` off, `SWITCH_OPS`, `CACHE_SIZE` 8, `MIN_POP` 64, `ALIGNMENT`, `COMPILE_WORKERS` 4) tunes the batch route, which only an explicit `EVOGP_EVAL_MODE=batch` selects — `auto` never picks it; the `EVOGP_FUSED_*` family (`MIN_POP` 16, `BLOCK_ROWS` 256, `NUM_WARPS` 1, `MAX_SCRATCH_MB` 8192, `HOST_MEMO` 16, `DISPATCH` `bound` with `jit` restoring Triton's `JITFunction.run`) tunes the fused route, which `EVOGP_EVAL_MODE=fused` forces and `auto` picks first on a device box.
- **Batch band legality**: a banded merge emits one exported dispatch per band and a ROCm/HIP dispatch binds at most 16 tensors, so `tree/batch_bands.py` caps band counts at `K <= 15` with `>= 8` merged functions per band (`K <= 31` on llvm-cpu, uncapped on numpy); the band-SIZE model and `EVOGP_BATCH_BANDS=auto` are CLAMPED to that cap (recorded as `band_clamped` plus a `band_note`), while an explicit `EVOGP_BATCH_BANDS=K` above it raises `ValueError` naming the cap and the remedy.
- Device policy: the engine (`evoxc_engine.evaluate` / `sr_fitness`) is device-agnostic — it accepts tensors on any torch device and returns results on the input device unless `out_device` is given. Everything ABOVE it is still hard-coded to the `"cuda"` device string (`check_tensor` relocates to `"cuda"`, descriptor tensors, `zero_generate`, `randint`, the algorithm operators, the problem data), the same string also selects AMD GPUs under ROCm, and there is no device-plumbing argument anywhere. A full training run therefore still needs a CUDA-visible device; only the engine itself can be exercised on CPU.
- IREE device kind and options: the GPU kind is resolved from the installed torch (`"rocm"` when `torch.version.hip` is set, else `"cuda"`), so the iree route works on this AMD box; compile options carry `opt_level` only (no `target_backends`) and the target is inferred from the device, so an ambient `EVOXC_TARGET_BACKENDS` can still enter the resolved options and must be paired with `clear_cache()` after changing it.
- Constants are single-sourced in Python: `MAX_STACK = 1024`, `MAX_FULL_DEPTH = 10`, `NType`, `Func` live only in `tree/utils.py` (there is no C++/header mirror to keep in sync any more).
- Fitness convention: every problem returns a `(pop_size,)` float32 tensor that the pipeline MAXIMIZES (losses are negated) and mutates in place (`NaN → -inf`) — so `evaluate` must return a fresh writable tensor.
- Keep `src/evogp/__init__.py` empty: adding imports there would make `import evogp` pull submodules and would not match the documented import style (`tests/test_api_compat.py` asserts the empty-`__init__` semantics).
- `setup.py` deps (repo root): `evoxc>=0.1.0`, `evox>=2.0.0a1`, numpy, scikit_learn, networkx, sympy; extras `torch`, `fused` (torch + triton), `iree` (iree-base-compiler/runtime), `visualize` (pygraphviz), `brax` (jax + brax) and `dev` (pytest). There is NO extra for `mujoco_playground` or `genesis` even though `problem/` needs them.
- The shared evoxc cache (`evoxc_engine.CACHE`, sized by `CACHE_SIZE_ENV` = `EVOGP_EVOXC_CACHE_SIZE`, default 4096 entries) is in-memory only — `cache_stats()` / `clear_cache()` inspect/reset it, and `_EXECUTABLE_MEMO` plus the three dense front tables are reset in lockstep.
- **Opt-in on-disk artifacts** (`tree/artifact_cache.py`, `EVOGP_EVOXC_ARTIFACT_DIR`, DEFAULT OFF): the one thing that survives a process. With the knob set, each executable `evoxc.build_cached` produces is saved under a stable content key (`<name>-<sha256>.evoxcart`) and a later process loads it instead of compiling (measured, dense+iree `Forest.SR_fitness`: 3.28 s compile → 160 ms first call at p256-L32-i8-N1024, 6.23 s → 174 ms at p64-L64-i32-N1024, artifacts 1.0/2.6 MiB).
  Unset/empty = exactly the in-memory behaviour (no key, no directory, no file touched); any load exception or signature mismatch drops the file and rebuilds; a save is best effort (`False`, never an exception).
  The disk layer has its own `artifact_cache_stats()` / `clear_artifacts()`; `clear_cache()` never touches the disk.
- `evoxc` call/transfer contract: it has no `jit` / `JitFunction` / `BoundJit`, so `_EXECUTABLE_MEMO` is the only pre-binding layer in front of `evoxc.build_cached` and raw `evoxc.run` is the cheapest supported per-call path; `evoxc.from_numpy` is a zero-copy HOST wrap rather than an upload site (the host→device upload is `Tensor.to(device)`), `evoxc.run` accepts only `evoxc.Tensor` / numpy arrays and never raw torch tensors, and the device↔host interop it DOES support is the DLPack one: `evoxc.core.Tensor.__dlpack__` / `__dlpack_device__` export a device payload zero-copy, `evoxc.from_dlpack` imports one back, and `register_external_kernel(..., device_resident=True)` registers a device kernel a compiled graph can call (`evogp.gp`'s `FusedDeviceEvaluator` uses the export direction and hands the kernel its own exported `evoxc` buffer through `fused_engine`'s `out=` destination, so it needs no local interop module).

## Design Decisions
- Descriptor-driven representation: `GenerateDescriptor(max_tree_len, input_len, output_len, using_funcs, max_layer_cnt, layer_leaf_prob, const_prob, out_prob, const_samples, const_range, sample_cnt)` fully parameterizes random tree generation; it is consumed by the pure-torch generator (`generation.py`) and by the algorithm-layer mutation operators (via its materialized `depth2leaf_probs` / roulette cdf tensors).
- Host-side decode + per-structure evoxc graph: the population tensors are read back to the CPU, validated and turned into flat int-only programs (constant subtrees folded), then specialized per *tree structure* so re-evaluating elites/duplicates is a cache hit; statics are re-passed by value at `evoxc.run`, so the cache key fully determines the executable. Validation replaces the legacy kernels' undefined behavior (a malformed tree raises `ValueError` naming row and node).
- Pure-torch operators replace the kernels: portable, toolchain-free and fast enough at these sizes, while keeping the legacy splice semantics including the silent copy-on-invalid-position behavior.
- **Batch route is a compilation strategy, not a semantics**: `tree/batch_engine.py` is the public facade (host program handling in `batch_programs.py`, the band/binding policy in `batch_bands.py`) and traces one graph per DISTINCT decoded program (the program is captured in a Python closure — a traced static argument makes `evoxc.batch_functions` reject the merge), merges them with `evoxc.batch_functions` (bands, `switch_ops` off, `out_axes=0`) built via `evoxc.lower` → `evoxc.compile` → `evoxc.load` (the `build_cached` path rejects a `Graph`), and reduces the SR loss in-graph so the readback is `(pop_size,)`.
  Per-tree programs come from `evoxc_engine.decode_population` / `_walk_tokens`, so parity is structural; host decode + trace + merge are memoized in the three front tables of `batch_keys.py` (identity-keyed plan and executable tables plus a content-addressed plan table that serves a rebuilt-but-equal population from a `blake2b` digest after verifying `plan.programs`), reached through `batch_engine.plan_batch` / `build_batch` / `describe_plan` and counted by `batch_cache_stats()`, and `evoxc_engine.clear_cache()` resets them too.
- **Batch bands**: the shipped default is the band-SIZE model (`EVOGP_BATCH_BAND_SIZE` 16, `K = ceil(n_functions / size)`) and `EVOGP_BATCH_BANDS` overrides it with an explicit `K`, the `auto` spelling (evoxc's static cost model) or a flat spelling (`none`/`flat`/`0` = `K = 1`); `batch_bands.py` clamps the model and `auto` to the device's loadable band count (the binding-cap constraint above) and refuses an explicit illegal `K`.
- The route's economics are per-CALL, not per generation: a warm batch `sr_fitness` is 7.6-18x faster than specialized+numpy from pop 64 up, but it is 1.8-3.4x dearer than dense at pop 256 (1.29x faster at the `p64` niche), a fresh generation changes the program multiset, and 7 of 8 generations recompile — so an 8-generation `StandardPipeline.step` loop is 64.9x / 71.5x / 17.8x dense's wall at `p256-L32` / `p256-L64` / `p64` (eval-only 868x / 680x / 229x) and the route is deliberately opt-in (`auto` never selects it).
  Cold, the shipped default costs 4 064.48 / 4 071.43 / 2 274.46 ms on those three cells and 15 517.88 ms at `p1000-L32-i8-N1024` (817 deduped functions, warm 6.9384 ms there); the compile pool is 89-96 % of every cold call and `lower` only 0.8-11.6 %, so the cost is the device-code compile, not MLIR construction.
  `EVOGP_BATCH_COMPILE_WORKERS` stays 4: the pool buys 2.64x / 2.94x / 4.58x on the cold call for a 1.87x / 1.69x / 1.46x dearer warm one, i.e. break-even is 3 849 / 5 103 / 18 702 warm calls of ONE population (`p256-L32` / `p256-L64` / `p256-L128-d7`), which a GP loop never reaches; it is inert below the 32-function chunk threshold and at the `p64` niche, and `=1` is the fixed-multiset escape hatch.
  `EVOGP_BATCH_BAND_SIZE` stays 16: pinning the band count at the rocm binding cap is the same merge at pop 256 (identical `band_sizes` and `emitted_ops`, since the size model is already clamped to `K = 15`) and a plan-changing but noise-level `K = 7` pin at `p64`, with an identical oracle deviation in every config — the partition is scheduling, never numerics (`test/benchmark/evoxc/BATCH.md` §15, `results/batch_opt_round3/SUMMARY.md`).
- The merge is compiled in `EVOGP_BATCH_COMPILE_WORKERS` (default 4) contiguous chunks of the deduped function list, one `BatchChunk`/graph/executable per chunk with global `row_index`; only `evoxc.lower`/`compile`/`load` run in a thread pool, the `W = 1` case is the old single-body path verbatim, and the chunked path must stay bitwise identical on numpy.
  An explicit band request (an explicit `K`, `auto` or a flat spelling) forces that single body; `EVOGP_BATCH_CHUNK_BANDS` (default off) composes banding with chunking instead — 2.6–2.8× faster cold, 1.6–2.5× slower warm — so it stays a fixed-population lever rather than a default.
- The same call reports itself through `batch_stages.py` (`batch_stage_stats()`/`batch_stage_reset()`, ten stages plus the compile wall/jobs), and `describe_plan` carries the band/merge surface (`bands`, `band_sizes`, `band_strategy`, `cost_estimate`, `flat_cost_estimate`, `band_requested`, `band_requested_bands`, `band_clamped`, `band_note`, `band_policy`, `chunk_bands`, `chunk_band_strategies`).
- numpy backend default, IREE opt-in: per-structure IREE compilation (~0.4–0.6 s) dominates while numpy builds in ms and runs in ~1 ms; IREE stays first-class for callers who need device execution and accept the compile economics.
- Population = batched fixed-width tensors: three parallel `[pop_size, max_tree_len]` matrices (`batch_node_value` float32, `batch_node_type` int16, `batch_subtree_size` int16) in prefix (pre-order) encoding with node 0 = root; only the first `subtree_size[0]` entries of each row are meaningful.
- Operationally parallel by container: `Forest` (single output) and `CombinedForest` (multi-output, dict-driven via `data_info`) are interchangeable at the `GeneticProgramming`/`StandardPipeline` level, so new operators should accept the container rather than assume tensors.
- Elitism is the algorithm's job, not the operators': operators return offspring only, and `GeneticProgramming.step` prepends elite copies.
- `execute_mode` is kept for API compatibility only: the legacy `kernel_type` dispatch is gone and all five accepted strings (`"torch"`, `"hybrid parallel"`, `"data parallel"`, `"tree parallel"`, `"auto"`) map to the same engine path.
- Multi-output trees pack an output index into the node value with the `OUT_NODE` (bit 7) flag rather than composing trees; the engine implements the multi-output protocol directly and is oracle-verified for `output_len` 2/3, while single-output populations containing an OUT_NODE tag are refused by every route through the single-sourced rule module `tree/multi_output.py` (`evoxc_engine`, `dense_engine` as its `DenseUnsupported` decline, `fused_engine._prepare` before any launch, and the gp stack's mirror in `graph_eval`).
- Optional heavy dependencies are always imported lazily inside constructors (`import_jax_based_package`, `import_genesis_based_package`), never at module import time, except `go2_env.py` (which is deliberately not imported by `problem/__init__.py`).

## Known Issues
Cross-cutting problems only; per-directory detail lives in the child CONTEXT.md files.
- **Specialized route economics** (numpy backend — the sub-64-population / CPU-box / fallback route): warm `Forest.SR_fitness` is 2.4 ms at p16, 9.3 ms at p64 and 36 ms at p256 (`L=32`, `i8`, `N=1024`).
  A warm call is one `evoxc.run` per non-constant tree (~129 µs per tree at `N=1024`), and the host decode is only 7-11 % of it (11 % at p16, 9 % at p64, 7 % at p256).
  Constant trees never compile, duplicate structures and elites hit the cache, and a changed batch size or tree shape re-compiles, so keep shapes stable in hot loops.
  Specialized+iree stays compile-bound (~0.27 s per tree structure in the campaign), which is why `auto` now sends device-box populations to the fused route first and to the dense route second.
- **Dense route economics**: one dense graph compiles in 3.1-3.4 s at `L=32` and 6.1 s at `L=64` (opt level O1 is the optimum — O2/O3 are ~40 % slower warm and save no compile time), and it is one compile per (shape, used-function-id set) reused by every population of that shape.
  A warm dense call is now graph-bound: `evoxc.run` is 67-80 % of it and the host glue ≈20 %, with one sync readback and one small upload left.
  `Forest.forward` at p256-L32-i32 went 2.50 → 0.68 ms and `batch_forward` 3.61 → 1.95 ms (host front tables + resident input staging, `EVOGP_DENSE_HOST_MEMO` = 16 entries, inspectable via `dense_cache_stats()`).
  A warm dense call's cost also tracks the data-row and population axes at scale — 2.06 ms at p1000-L64-i32-N1024 against 117.2 ms at `N=16384` and 76.2 ms at pop 8 192 — and that large-row / large-pop shape is where a whole-population torch-batched implementation beats dense by 3.5-4.3×, i.e. the context in which the opt-in `batch` route's row amortization appears.
  One full GP generation at `L=32`/`i8`/`N=1024` (the campaign's `gp_step` workload: `StandardPipeline.step`, i.e. evaluation + select/crossover/mutate) is 4.66 / 5.45 / 7.57 ms at p64 / p256 / p1000, of which the operator part is 2.20-2.64 ms (it used to be 5.7-6.6 ms flat across population sizes).
  The opt-in disk artifact cache (`EVOGP_EVOXC_ARTIFACT_DIR`, default off) turns a 3.28 / 6.23 s compile into a 160 / 174 ms load in a second process, while `clear_cache()` stays memory-only and `clear_artifacts()` owns the disk.
- **Still unaddressed**: the dense graph is dispatch-bound (~310 ops for a whole population, and no hand-written kernels by design); the dense/fused value paths still assemble their prediction host-side (evoxc now exports a device payload over DLPack, so this is a wiring gap in the engines, not an evoxc one); the specialized route is per-tree-run-bound; IREE numeric parity is not verified per shape; and `tests/test_convergence_smoke.py` runs 120 generations because the rewritten generator's RNG stream lands differently at seed 0 (its assertion is unchanged).
- **Measured negative results** (do not re-litigate without new evidence): reusing the dense decoder / deduping structurally identical programs on the specialized route was dropped (the decode is only 7-11 % of a warm call, and a fresh population is 16/16, 63/64 and 225/256 distinct at p16 / p64 / p256, so the dedupe ceiling is ≤1-12 % before the 1-2 elite copies); `non_blocking=True` on the dense output upload is worth ~8 µs (0.7 %); opt levels O2/O3 (above); a finer `_splice` rewrite moved ±5-10 dispatch ops out of ~45; and `EVOGP_BATCH_BANDS=auto` (evoxc's static cost model overshoots the ROCm/HIP binding cap ~14× and is then clamped, and it lost 9/9 warm columns to the numeric band-size model, which stays the default).
- **Default route policy**: with NO explicit backend, `auto` resolves in this order: (1) the FUSED (Triton) route from `EVOGP_FUSED_MIN_POP` (16) up, when `triton` is importable AND a CUDA/HIP device is usable from torch AND the population fits the fused memory envelope (`EVOGP_FUSED_MAX_SCRATCH_MB`, 8192 MiB — that term applies only when the caller passes `rows` and `tree_len`, and `dense_engine.auto_fused_decline` is the one decider) → `Route(engine="fused", backend="iree", fallback_backend="numpy")`; (2) else dense+iree from `EVOGP_DENSE_AUTO_MIN_POP` (64) up, exactly as before, rows envelope and trace-cap raise included; (3) else specialized+numpy (also the CPU-box, no-triton and `DenseUnsupported` answer).
  An explicit `EVOGP_EVAL_MODE` (`dense` / `dynamic` / `specialized` / `batch` / `fused`) and an explicit backend (`EVOGP_EVOXC_BACKEND` / `backend=`) keep their exact previous meaning, and the explicit-backend arm of `auto` keeps the historical dense/specialized rule and never reaches fused; a `FusedUnsupported` at call time keeps the existing fallback chain (the fused route's `numpy` fallback is the specialized engine), so a declined launch does not change the route.
  The resolver is `dense_engine.resolve_route` (`Route.engine` ∈ `specialized` / `dense` / `batch` / `fused`, `use_dense == (engine == "dense")`), `EVOGP_DENSE_AUTO_MIN_POP` (64) is the dense call-count break-even knob (≈460/95/23 calls at P=64/256/1000), and the two availability probes are the memoized module globals `dense_engine._DEVICE_AVAILABLE` / `_FUSED_AVAILABLE`, so a CPU box or a triton-less box imports no triton and resolves exactly as before.
  The pytest suite pins `EVOGP_EVOXC_BACKEND=numpy` via `tests/conftest.py` so it stays hermetic (an explicit backend is never fused, so the suite is unaffected), `EVOGP_EVAL_MODE=batch` is the only way to reach the batch engine (`auto` never selects it), and `EVOGP_EVAL_MODE=fused` only forces the fused route — it still declines to specialized+numpy without a device or below `EVOGP_FUSED_MIN_POP`.
- **The `auto` trace-cap raise** (dense `auto`, unpinned cap only): `dense_engine.evaluate_dense` / `sr_fitness_dense` lift the effective cap to `min(EVOGP_DENSE_AUTO_MAX_TREE_LEN (256), next_power_of_two(max(base, longest)))` — rounded UP to a power of two — with the allowance `floor(EVOGP_DENSE_AUTO_BUDGET_MB·2²⁰ / (pop_size·rows·4))` re-checked AT THAT ROUNDED VALUE (`auto_trace_cap` / `auto_tree_len_allowance` / `trace_cap_pinned`, `longest` from one memoized `batch_subtree_size[:, 0]` read) instead of degrading to specialized+numpy, so `p2048-L128-i32-N1024-d7` is traced at `L=128` on iree (~105.6 ms) instead of served by numpy (857.22 ms).
  The rounding is graph-key stability, not numerics: dense's key includes `max_tree_len`/`L`, so a cap that tracks the realized longest tree recompiled once per generation (`gp_step` 10 014.83 ms against 124.46 ms at a pinned 128 and 125.25 ms torch-per-tree; eval column 11 877.6 / 10 011.6 / 6 371.1 ms), while the rounded cap makes one graph serve a whole band (65..128, 129..256) for ~2 % more trace work per call (103.34 → ~105.6 ms at 123 nodes).
  Residual limit: a generation whose longest tree crosses a power of two (128 → 129) still recompiles once, and a shape that passes at the raw `longest` but not at the rounded value (100 nodes against a 110-node ceiling) now declines instead.
  A refused raise is the one `DenseUnsupported(device_fallback=True)` and continues on the route's device backend (`decline_backend(route, exc)`), not numpy; an explicit `EVOGP_EVAL_MODE=dense` and an explicit `EVOGP_DENSE_MAX_TREE_LEN` / `max_tree_len=` pin keep the base cap, the unflagged decline and add no host read.
  Residual limit: the refused-raise branch still lands on per-structure specialized+iree, which is compile-bound and unbounded in artifacts at large populations — the answer there is the opt-in batch route or a raised envelope, not a policy fix.
  Under that policy the warm `Forest.SR_fitness` at `L=32`/`i8`/`N=1024` is p16 3.06 ms (specialized numpy), p64 0.99 ms, p256 1.14 ms and p1000 1.93 ms (dense+iree), against the baseline campaign's `auto` column 3.01 / 9.50 / 36.8 / 147.0 ms.
- **Multi-output status**: the engine supports it (`output_len` 2/3 oracle-verified; `CombinedForest`/`CombinedTree` are the `data_info` dict-driven containers, and the single/batched `forward`/`batch_forward` input contract is covered by `tests/test_combined_forward.py`). The remaining combined-path gaps are outside the engine: `CombinedForest.__add__(CombinedTree)` reads `other.tree[i]` (AttributeError), `CombinedForest.__next__` never advances `iter_index` (endless iteration), neither combined container defines `SR_fitness` or `to_sympy_expr`, and `SymbolicRegression.evaluate` rejects a `CombinedForest` with `NotImplementedError`, so the combined route runs through `evogp.problem.CustomLoss` (the route taken by `example/combined_sr.py`, which runs end to end, and by `tutorial/combined_gp.ipynb`).
- No dimension validation exists between `GenerateDescriptor.input_len/output_len` and `problem.problem_dim/solution_dim` (the pipeline's asserts are commented out), so mismatches fail inside the tree layer / engine instead of at wiring time.
- Some shipped problems are broken or stubs: `GenesisProblem.evaluate` returns `None` (stub); the robotics problems additionally need lazily-imported `jax`/`brax`/`mujoco_playground`/`genesis` (only `brax` has a setup.py extra).
- Robotics env construction cannot be verified in the current validation venv (a third-party environment boundary, not a library defect): dm_control-suite MuJoCo envs default to `impl="warp"` and `mujoco-warp` is not installed, so `registry.load` fails with `AttributeError: type object 'int' has no attribute 'WARP'` inside `mujoco/mjx`; behind it sits the CuDNN 9.1-vs-9.8 `JaxRuntimeError ... dnn_support != nullptr` wall that also hits `example/brax_task.py`. `MujocoProblem`'s lazy-import binding itself is covered by `tests/test_mujoco_problem.py`, but no robotics rollout is verified here.
- `algorithm/__init__.py` uses star imports with no `__all__`, so `evogp.algorithm.base` / `evogp.algorithm.default` resolve to the SELECTION submodules (last star import wins) — import the concrete subpackage (`evogp.algorithm.crossover.base`) instead.
- `GenerateDescriptor.update(**kwargs)` returns a new descriptor but also mutates the receiver's captured params (kwargs are sticky) and re-draws `const_samples`; `MAX_STACK` overflow / malformed indices are now caught by the host-side decode (`ValueError`) rather than silently corrupting a kernel run.
- Sympy rendering is a display artifact with documented edge gaps (e.g. `LOOSE_POW(0,0)` renders `1` while the engine computes `0`, `LOG(0)` renders `zoo` while the engine returns `-inf`); see `tree/CONTEXT.md`.

## `sr_test.py` (top of this node)
Standalone install-validation smoke script documented in README §5 as `python -m evogp.sr_test`; it is NOT a unit test and is not pytest-collected.
It trains `SymbolicRegression` on a synthetic 2-input function (`func`/`num_inputs`/`num_data` constructor path) under fixed manual seeds and reports progress through `StandardPipeline`; its defaults are right-sized for the pure-Python/evoxc engine (a validation run, not a benchmark), it sets `EVOXC_DISABLE_LOCATIONS=1` by default, and it needs a CUDA-visible device like every other end-to-end entry point.
It has module-level side effects and NO `if __name__ == "__main__"` guard, so any `import evogp.sr_test` starts a full training run — never import it from tooling.

## Notes for Agents
- There is no build step: run everything from the repo root with `PYTHONPATH=src:/root/evoxc` and a torch-carrying task venv (`python` on PATH has none; the concrete interpreter used for this box's measurements is recorded in `tests/CONTEXT.md`), with `EVOXC_DISABLE_LOCATIONS=1` for speed. `evoxc` must be importable (`import evoxc` in `tree/evoxc_engine.py`, `tree/dense_engine.py` and the batch route's `batch_programs.py` / `batch_run.py` / `batch_chunks.py`, resolved only through the `/root/evoxc` path segment — there is no stub and no fallback).
- The pytest suite under `tests/` is the regression gate; `tests/goldens/*.npz` are the engine-vs-legacy-kernels golden fixtures and `tests/perf_probe.py` is a standalone build/run economics probe (not pytest).
- Import order inside `__init__.py` files is load-bearing in `tree/` (`utils` before `descriptor`) and in `problem/` (`.base` first, since siblings do `from . import BaseProblem`).
- `MAX_STACK` / `MAX_FULL_DEPTH` / `NType` / `Func` are defined only in `tree/utils.py`; function ids are positional across `Func`, `FUNCS_NAMES`, `FUNCS_DISPLAY`, `SYMPY_MAP`, so adding an operator means touching all four.
- Determinism comes from torch's global RNG: `generation.py` draws with `torch.rand`/`randint` and the splices use plain torch ops, so `torch.manual_seed(0)` makes generation reproducible (distribution-equivalent to the legacy taus88 stream, not bit-identical).
- `generation.py` / `splicing.py` now grow the population on the arity-padded complete-tree layout, with a compact fallback above `PADDED_SLOT_BUDGET` (1024 cells) — the two layouts must stay value-equivalent.
- The operator layer keeps at most 4 host round trips per generation (crossover's range check, the generation overflow guard, the mutation empty-selection test) and never one per individual; `tests/test_hot_path_contracts.py` pins that budget, so a new `.item()` / `bool()` in an operator fails the suite.
- The repo-root `CONTEXT.md` owns the repository-level view (structure, invariants, Known Issues, test strategy) and `../../README.md` the user-facing one; both are read-only from this node.
- Trees returned by `Forest.__getitem__` (int/slice) are views into the population tensors while `Tensor`/`ndarray` indexing returns copies — the algorithm rebinds `self.forest` each generation, so old buffers are never rewritten, but do not mutate a snapshot or write through a copy.
- Never reintroduce a compiled extension: the tree layer is deliberately extension-free and `tree/ENGINE_SPEC.md`'s Appendices are the only place where the legacy op schemas are kept, explicitly as historical reference.
- This node owns only these CONTEXT.md files; do not modify source code here (source changes belong to the specific child node's task).

## Test Strategy
The repo now HAS an automated pytest suite: `src/evogp/tests/` (see its CONTEXT.md for per-file detail) — an independent plain-torch reference evaluator (`reference_eval.py`), randomized/adversarial engine equivalence (`test_equivalence.py`), operator/splice invariants (`test_operators.py`), public-API compatibility (`test_api_compat.py`), the combined multi-output forward contract (`test_combined_forward.py`), the `MujocoProblem` lazy-import binding (`test_mujoco_problem.py`), the route policy and dense knobs (`test_route_policy.py`, `test_dense_policy.py`, `test_dense_prune.py`, `test_dense_sr_fitness.py`), the fused route's own net (`test_fused_route.py`, 53 cases that compile and launch the real Triton kernel, pin the `PLAN_MEMO` invalidation contract and lift the session backend pin per test), the batch route's engine/knobs/public wiring (`test_batch_engine.py`, `test_batch_knobs.py`, `test_batch_route.py`) plus its additions — chunked-compile equality and the worker knob (`test_batch_chunking.py`), the stage-timer surface and `describe_plan`'s chunk geometry (`test_batch_stages.py`), the content-addressed plan key (`test_batch_content_key.py`) and the band/binding policy (`test_batch_bands.py`, 37 numpy-only tests) — the dense front tables and the disk artifact layer (`test_dense_host_memo.py`, `test_artifact_cache.py`), the per-generation sync budget (`test_hot_path_contracts.py`), and a tiny SR convergence smoke (`test_convergence_smoke.py`), plus the in-repo golden fixtures `tests/goldens/*.npz` and the standalone `tests/perf_probe.py`; the route-local dev battery `tree/batch_band_check.py` (29 cases) remains a CLI gate, not pytest.
`tests/conftest.py` pins `EVOGP_EVOXC_BACKEND=numpy` for hermeticity, so the suite never compiles an iree graph on a GPU box (`EVOGP_TESTS_ALLOW_DEVICE=1` is the escape hatch that keeps the ambient backend).
Run it from the repo root: `EVOXC_DISABLE_LOCATIONS=1 PYTHONPATH=src:/root/evoxc <venv>/bin/python -m pytest src/evogp/tests -q` → 1 308 passed / 7 skipped / 0 failed in ~121 s (there are no red cases; `test_auto_never_selects_fused` no longer exists — the policy is pinned in both directions by `test_auto_selects_fused_above_the_floor` / `test_auto_keeps_the_pre_fused_policy_below_the_floor_or_without_triton`); add `-x` to stop at the first failure, or `--ignore=src/evogp/tests/test_equivalence.py` for the fast subset (~51 s) (the skips are pygraphviz+graphviz `dot` for `to_png`, two `execute_mode` attribute-export checks, and two `test_mujoco_problem.py` `importorskip('jax')` cases). Everything runs on CPU with the default numpy engine backend except the parts that build their tensors on `"cuda"` (they need a GPU; `test_batch_route.py` skips entirely on a CPU-only box and one batch+iree leg additionally needs the IREE Python packages).
The other de-facto validations are `python -m evogp.sr_test` (default pop 200, which `auto` now serves on the fused route: −0.2259 in ~11 s wall — the value shifted from ≈ -0.16 only because `generation.py` was rewritten to a distribution-equivalent RNG stream) and running the relevant `example/*.py` from the repository root (relative asset paths such as `imgs/` are CWD-dependent). The repo-root `test/` directory is not part of this suite (scratch scripts/notebooks; a separate task owns it).
Known coverage gaps: IREE numeric parity per shape, the robotics-control rollouts (jax/genesis/mujoco-warp required; only `MujocoProblem`'s lazy-import binding is tested), `CustomLoss` end to end, `Classification(multi_output=False)`, `Transformation.new_feature`, and the multi-output `CombinedForest` training route (its forward/batch_forward contract is covered by `tests/test_combined_forward.py`).
