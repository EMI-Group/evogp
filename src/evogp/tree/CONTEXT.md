# `src/evogp/tree/` — EvoGP tree representation, evoxc evaluation engine & pure-torch operators

## Intent
This is the **foundation layer** of EvoGP: the GP individual (`Tree`), the population (`Forest`), the multi-output variants (`CombinedTree` / `CombinedForest`), the generation blueprint (`GenerateDescriptor`), the pure-torch generation/splicing operators and the `evoxc`-backed evaluation engines — everything above it (fitness, selection, crossover, mutation, visualization) speaks the tensor representation defined here.
`evoxc` is the **EvoX Compiler**, the evaluation-engine dependency (a sibling checkout supplied on `PYTHONPATH`); the engine imports it as `evoxc` plus `from evoxc.build_cache import CompileCache, build_cached`.
This layer contains **no custom CUDA/HIP kernel source and no compiled extension**: nothing has to be built, and the one device-native route (`fused`) is a Triton JIT kernel written in Python.
Evaluation runs through ONE OF FOUR engines named by `EVOGP_EVAL_MODE`: the per-structure evoxc JIT engine (`evoxc_engine.py`), the **dense** all-ops whole-population evaluator (`dense_engine.py`), the opt-in **batch** merged-graph evaluator (`batch_engine.py`) and the opt-in **fused** Triton evaluator (`fused_engine.py` + `fused_kernels.py`); generation/mutation/crossover are vectorized plain torch (`generation.py`, `splicing.py`).
This package imports **nothing** from other `evogp` subpackages — it is the root of the package DAG (`algorithm/` and `problem/` are its consumers; `pipeline/` sits above both; no cycles).
Documents of record: `DENSE_EVAL.md`, `BATCH_EVAL.md`, `FUSED.md` (per route), `RUNNER_HOOKS.md`, `ENGINE_SPEC.md`; benchmark history: the reports (`test/benchmark/evoxc/FINAL.md`, `BATCH.md`, `LARGE_SCALE*.md`, `FUSED.md`).

## Representation (the schema every other module depends on)
An individual is three parallel tensors of length `max_tree_len`, batched as `[pop_size, max_tree_len]`, in **prefix (pre-order) encoding**: node 0 is the root, children follow depth-first left to right.
- `node_value` — `torch.float32` (`Forest.batch_node_value`); `node_type` — `torch.int16` (`batch_node_type`); `subtree_size` — `torch.int16` (`batch_subtree_size`), where `subtree_size[i]` = nodes in the subtree rooted at node `i`.
Only indices `[0, subtree_size[0])` are meaningful: `subtree_size[0]` is the real tree length and the rest of a row must never be read (the generator zeroes unused cells, an implementation detail). `batch_subtree_size[:, 0]` is the algorithm layer's "size of tree i".
`Tree` holds the same three tensors unbatched (1-D); `Forest[i]` / `Forest[a:b]` return `Tree` / `Forest` **views** sharing storage, while `Tensor`/`ndarray` indexing (incl. LongTensor / bool mask) goes through PyTorch advanced indexing and returns **copies**.

Node encoding:
- `node_type` base values: `0 VAR`, `1 CONST`, `2 UFUNC`, `3 BFUNC`, `4 TFUNC` (`NType`); `NType.OUT_NODE = 1<<7` is OR-ed in for multi-output nodes (`TYPE_MASK = 0x7F` extracts the base).
- `node_value`: `VAR` → variable index (float-encoded int); `CONST` → the constant; function node → function id (`Func.*`, i.e. the index in `FUNCS_NAMES`).
- Multi-output out-node packing: `node_value` is the float32 bit-reinterpretation of `struct OutNodeValue { int16_t function; int16_t outIndex; }` (`outIndex = int32_bits >> 16`, `function = int32_bits & 0xFF`).
- Function table: id 0 `IF` (ternary); ids 1–13 binary (`+ - * / loose_div pow loose_pow max min < > <= >=`); ids 14–28 unary (`sin cos tan sinh cosh tanh log loose_log exp inv loose_inv neg abs sqrt loose_sqrt`); operands are consumed leftmost-child-first.
- Exact per-operator edge cases (`DIV`/`LOG`/`SQRT`/loose variants, comparisons returning ±1, `IF` branch mapping) are `ENGINE_SPEC.md` §3.
- Multi-output semantics (`output_len > 1`): every out-node accumulates its own value into `out[outIndex]` and passes its right-most child up to the parent, tagged leaves behave like untagged ones, and outputs never tagged are `0.0`; `output_len == 1` is the single-output protocol, and a tree containing an OUT_NODE-tagged node is rejected at decode time with `ValueError`.

## Engine architecture (`evoxc_engine.py`)
Evaluation is a "true jit": `decode_population` walks a population **host-side** into frozen per-tree static programs (int-only, constant subtrees folded), then `evaluate` / `sr_fitness` specialize each program into a fresh evoxc graph via `evoxc.build_cached` and run it, with executables cached per *(tree structure, input shape, backend, device, options)*.
- `decode_population(node_value, node_type, subtree_size, input_len, output_len) -> Population` — pure host work (`.cpu()` readback), validating the structure and raising `ValueError` naming the row and node, `TypeError` for non-tensor / non-2-D input.
- `evaluate(population, x, *, per_row, out_device=None, backend=None, iree_device_index=None)` — `per_row=True`: `(pop, input_len) → (pop, output_len)`; `per_row=False`: `(N, input_len) → (pop, N, output_len)`; the result is fresh, contiguous, `requires_grad=False` float32 on `x`'s device unless `out_device` is given.
- `sr_fitness(population, inputs, labels, use_MSE=True, *, ...)` — `(pop,)` float32 POSITIVE loss `Σ_points Σ_outputs err / N` (err = diff² for MSE else |diff|, outputs summed but never divided by `output_len`, NaN/inf unsanitized); the caller negates for higher-is-better.
- One module-level `@evoxc.defn _eval_step` — it must stay module-level (its `id()` is part of the cache key; a closure would permanently miss); statics are codec-safe int-scalars/sequences re-passed by value at `evoxc.run`.
- Cache: one shared `evoxc.CompileCache` (`evoxc_engine.CACHE`), default maxsize 4096 (`EVOGP_EVOXC_CACHE_SIZE`, import time), in memory only, ~270–478 KiB per entry; `cache_stats()` reports `memo_hits` / `memo_misses` / `memo_entries` / `memo_maxsize`, `clear_cache()` resets both tables.
- Program→Executable memo (`_ExecutableMemo`, `_EXECUTABLE_MEMO`): an LRU sized to `CACHE.maxsize`, keyed by `(program, n_rows, input_len, backend, device, frozen options)` via `_executable_key`, consulted by `_executable` before any build.
- Node semantics are **correctly rounded float32** (transcendentals emitted as `cast_f32(op(cast_f64(v)))`, `sinh`/`cosh` composed from `exp` in f64; hardware-exact ops stay f32 and keep bit-exact ±1). The per-op rules and the deviation list are `ENGINE_SPEC.md` §3 + `evoxc_engine.py`'s module docstring.
- Backends: `numpy` (the evoxc reference interpreter, cpu, no GPU needed) by default; IREE is on the GPU HAL (CUDA or ROCm, the kind read from torch by `_gpu_device_kind()` and passed as `evoxc.core.Device(kind, idx)`) and its knobs are `EVOGP_EVOXC_BACKEND` / `EVOGP_EVOXC_DEVICE` / `EVOGP_EVOXC_OPT_LEVEL`.
- Device policy: the engine accepts population/input tensors from any torch device and returns results on the input device unless `out_device`; the `Tree`/`Forest` wrappers still pass everything through `check_tensor` (`.to("cuda")`), so the public API keeps its CUDA-bound behavior. Per-tree IREE is compile-bound (~0.27 s per tree structure), which is why the policy never sends the specialized route to IREE (`warm_path_findings.md` §11).

### On-disk artifacts (`artifact_cache.py`, `EVOGP_EVOXC_ARTIFACT_DIR`, DEFAULT OFF)
Unset/empty changes nothing (one env read, no key, no file); set, a front-table miss first tries `artifact_cache.load`, and an executable built or loaded is stored in the route's executable memo.
The key is a `"<slug>-<sha256 hex>"` digest (`evoxc.persist.cache.compute_key`) over the graph name, the build spec tuple (static content included), backend/device, frozen options and the evoxc/iree versions — so `ARTIFACT_NAME = "specialized"` gives one file per tree structure and the dense route one per shape + used-id set; `signature_matches` validates shapes/dtypes/statics, any mismatch or load exception deletes the file, and a save is atomic and best effort.
`clear_cache()` is the in-memory point and never deletes a file, `clear_artifacts()` owns the disk, `artifact_cache_stats()` reports the 7 `artifact_*` keys, and every route shares the directory (batch bodies under its `batch/` subdirectory). Neither the directory nor an ambient `EVOXC_*` compile knob is in the key — validation, not keying, is the safety net.
It buys a fresh process's first call and nothing else; contract, stat keys, recovery legs and economics: `DENSE_EVAL.md` §2.6/§6 + `## Measured detail`.

### Benchmark runner hooks (`build_specialized_runner` / `dense_engine.build_dense_runner`)
Build-once / run-many **benchmark-support** APIs: the build does the decode/prepare, the compiles and the staged payloads, and `.run()` executes ONLY the compiled forward pass (specialized: one `evoxc.run` per non-constant tree, raw per-tree results with `None` for constant trees; dense: ONE `evoxc.run` returning the raw result) with no readback, no re-key, no re-plan and no host assembly beyond what is baked in-graph.
`EVOGP_EVAL_MODE` is ignored and chunked dense plans are refused at build with `DenseUnsupported`; signatures, per-backend `.run()` semantics, the build-vs-run split and the evoxc call-boundary facts are in `RUNNER_HOOKS.md`, evidence battery `runner_check.py`.

## Dense one-graph evaluator (`dense_engine.py`) — the iree default route
`dense_engine.py` evaluates a WHOLE population with ONE compiled evoxc graph fed with the population's node tensors as runtime data (no per-tree Python loop, no per-tree readback): `prepare_dense` encodes the `(L, P)` `opcode`/`func_id`/`const_value`/`var_index`/`child1..3` columns, the trace-time unrolled graph computes each node value with the specialized engine's own private emitters (`evoxc_engine._emit_*` — parity by construction), the per-position candidate chain is emitted **only for the population's used function ids**, and the base trace cap is `L = min(EVOGP_DENSE_MAX_TREE_LEN (64), max_tree_len)`.
Single-output populations only (`output_len == 1`) within the effective trace cap; over-cap populations fall back with a deduped once-per-process `RuntimeWarning` on device backends. `DENSE_CACHE` IS `evoxc_engine.CACHE` (one miss per shape + used-id set), `dense_memo.py`'s three front tables sit in front of it, and the SR loss is computed in-graph — the cache key, prune, front-table and cap-raise mechanics are in `DENSE_EVAL.md` §2–§3 + `## Measured detail`.
Scheme, chunking and peak memory, the value-buffer write modes, the tolerance classes and the economics are owned by `DENSE_EVAL.md` (§2, §3, §5).

## Batch merged-graph evaluator (`batch_engine.py` facade + one-responsibility siblings) — opt-in, never selected by `auto`
`batch_engine.py` is the PUBLIC facade (the only name callers import): the route traces ONE graph per **deduped** tree program (program equality; constant trees keyed by `const_out`) and merges them into ONE executable with `evoxc.batch_functions` — one `evoxc.run` per compiled BODY, one readback per body, a host row expansion back to population order — built through the explicit `evoxc.lower` → `evoxc.compile` → `evoxc.load` sequence (`build_cached` / `evoxc.build` reject a `Graph`).
Route facts: reachable ONLY through `EVOGP_EVAL_MODE=batch`, catching exactly `BatchUnsupported` (the specialized engine owns the malformed-tree error contract); its economics are per CALL, not per generation, because the merged compile is population-specific. Bands come from the band-SIZE model (`EVOGP_BATCH_BAND_SIZE` 16) or an explicit `EVOGP_BATCH_BANDS` request, `batch_bands.py` clamps every count to the HAL binding cap (recording `band_clamped` + `band_note`) and refuses an explicit illegal `K`, `EVOGP_BATCH_COMPILE_WORKERS` chunks the `lower`/`compile`/`load` staging through a thread pool, and `describe_plan` reports the band seam plus the `band_*` keys of every `BatchChunk.report`.
Scheme, the `EVOGP_BATCH_*` knobs, the measured grid, the per-generation verdict, the band policy and its messages, the on-disk tier and its key, the `dispatch_formation` seam, `plan.chunks`'s two plan shapes, parity and the module contracts are owned by `BATCH_EVAL.md` (§5.1 scale envelope, §8 chunking/plan keys, §9.2 disk tier, §9.6 band policy, §9.7 dispatch formation); `test/benchmark/evoxc/BATCH.md` §15 + `results/batch_opt_round3/SUMMARY.md` + `LARGE_SCALE_ROUND2.md` carry the cold/warm/loop/pool/band/large-scale evidence.

## Fused (Triton) whole-population evaluator (`fused_engine.py` + `fused_kernels.py` + `fused_check.py`) — opt-in, never selected by `auto`
A fourth, device-native route: ONE Triton launch per (tree, row-block) pair evaluates the whole population from the population tensors themselves, with no host readback, no host decode and no per-node graph — the answer to "the dense graph is dispatch-bound (~310 chained ops)". The kernel walks each tree in REVERSE prefix order with a `prev` register plus an explicit shared-memory stack (the first child of node `j` is always `j+1`) and vectorizes the row axis (`BLOCK_R` lanes); numerics are the oracle's (correctly rounded float32, transcendentals widened to f64 via `triton.language.extra.libdevice`, arithmetic/ternary/comparison f32) with `enable_fp_fusion=False` mandatory.
Route facts: reachable ONLY through `EVOGP_EVAL_MODE=fused` (named by `EVAL_MODES` and `ENGINES`, reported by `Route.use_fused`, decided in `resolve_route`'s `fused` branch), with backend SPELLING `iree`; `EVOGP_EVOXC_BACKEND` can change the route's shape, so the engine name is never a served-call proof — prove a served call with `fused_cache_stats()` (`fused_kernel_launches` up, `fused_declines` unchanged).
The policy's own device answer falls back to specialized+`numpy`, but an explicit `backend=` / `EVOGP_EVOXC_BACKEND` spelling builds `Route(False, name, name, engine="fused")`, so a decline there lands on per-tree iree compiles; `Route.__post_init__` refuses `use_dense=True` with `engine="fused"`, `should_use_dense` is `False`, and all five call sites catch exactly `fused_engine.FusedUnsupported`.
Scope: `output_len` 1..`fused_engine.MAX_OUT_LEN` (8) over the `pop_size * max_tree_len * rows * 4` scratch envelope, including the `OUT_NODE` multi-output protocol (packed `function`/`outIndex`, the right-most operand passed up, untagged outputs `0.0`), with a BITWISE value path and `<= 1.2e-07` relative loss against `reference_eval.forward_tree(multi_output=True)`; a wider call declines naming `MAX_OUT_LEN` (`FUSED.md` §11–§12).
Evidence: `fused_check.py` (`--stage parity|multi|goldens|declines|wired|timing|tuning`; 56/56 oracle comparisons, 65/65 multi-output comparisons, 10/10 goldens, 24/24 decline/contract checks, 31/31 wiring checks) and the campaigns of record in `FUSED.md`, with their records under `fused_results/` (`ENVELOPE.md` is the envelope/min-pop/sweep table set).
The facade surface, the decline matrix, the per-call counter semantics (`fused_calls` counts ATTEMPTS), the `XT_MEMO` prep, the missing per-stage timers, the `TRITON_CACHE_DIR` requirement and the wiring facts are in `FUSED.md` §7 + `## Measured detail`.
Route-local known issues: the kernel never clamps `subtree_size[0]` to `max_tree_len` (`n` drives `range(0, n)` and every `row_base + j` load), so a row with an oversized `subtree_size` reads past its own row and burns up to 32 767 iterations — `fused_kernels.py`'s "malformed rows never read out of bounds" claim holds only for consistent `subtree_size`, and the route declines nothing on structure, so the specialized engine's malformed-tree `ValueError` is never reached on a served call.
`fused_engine._as_device_tensor` only casts device/dtype, never contiguity, so a non-contiguous `x` on the `per_row=True` path (`Forest.forward`, 1-D `Tree.forward`) is read with the wrong strides (the `per_row=False` and loss paths are safe through `_transposed`); the population tables are read with the same raw pointer arithmetic.
`fused_kernels._SCRATCH` holds up to `_SCRATCH_MAX_ENTRIES` (8, no documented measurement) scratch blocks with no byte bound, i.e. up to 8× `EVOGP_FUSED_MAX_SCRATCH_MB`, and the envelope formula omits the `(pop, rows, 1)` value buffer and the row-block rounding (`n_rb * BLOCK_R` can be ≈2× `rows`).
`EVOGP_FUSED_BLOCK_ROWS` accepts any value >= 1 but `plan()` does not round it to a power of two, so a non-power-of-two cap reaches `tl.arange(0, BLOCK_R)` and fails inside Triton instead of naming the knob.
`fused_available()` is exported and called by nothing (`_prepare` uses `_require_available`), and the parity battery's four `PARITY_SETS` never exercise `GT` / `LE` / `NEG` / `ABS` / `SINH` / `COSH`.

## Adding a further evaluation route (the dispatch seam)
- There is exactly ONE dispatcher, `dense_engine.resolve_route(pop_size, *, rows=None, backend=None, iree_device_index=None, eval_mode=None, auto_min_pop=None, auto_max_rows=None) -> Route(use_dense, backend, fallback_backend, reason="", engine="specialized")`, with `dense_engine.ENGINES = ("specialized", "dense", "batch", "fused")`; `engine` is `compare=False`, so a batch or fused route compares EQUAL to the old 3-field record — assert `route.engine`, never bare equality — and the invariant `use_dense == (engine == "dense")` holds (an old-style `Route(True, ...)` is promoted to `engine="dense"`, while `engine="batch"` or `"fused"` with `use_dense=True` raises `ValueError`). A further engine needs a name in `ENGINES` (and in `EVAL_MODES` if it gets its own spelling) plus an edit at each of the five call sites.
- The five call sites ask it per call and pass the resolved backend EXPLICITLY: `tree.py:83` (`Tree.forward`, 1-D `x` -> `per_row=True`), `tree.py:150` (`Tree.SR_fitness`), `forest.py:116` (`Forest.forward`, `per_row=True`), `forest.py:151` (`Forest.batch_forward`, `per_row=False`), `forest.py:344` (`Forest.SR_fitness`). Each wraps its `route.engine == "batch"` attempt in `except batch_engine.BatchUnsupported:`, its `"fused"` attempt in `except fused_engine.FusedUnsupported:` and its `"dense"` attempt in `except dense_engine.DenseUnsupported:`, then continues on `route.fallback_backend`.
- A new engine module mirrors one of the four existing fronts: the dense shape (population tensors + `input_len`/`output_len` + `x`, keyword-only `per_row`/`out_device`/`backend`/`iree_device_index`/`max_tree_len`/`budget_mb`/`update_mode`, plus a loss form `(..., inputs, labels, use_MSE=True, *, ...) -> (pop_size,)`), or the specialized shape fed by `decode_population`. `batch_engine.py` is the dense-shaped front plus a `BatchUnsupported`; `fused_engine.py` the same shape with a `FusedUnsupported` that runs on the torch device instead of an evoxc backend. Exact signatures: `RUNNER_HOOKS.md` §1.
- Per-tree programs already exist for reuse: `decode_population(...) -> Population(input_len, output_len, pop_size, trees)` of `DecodedTree(program, const_out, node_count, collapsed_nodes)`, where `program = (out_len, tokens)` holds int-only tokens (`(K_VAR, var_index)`, `(K_CONST, float32_bits)`, `(K_{U,B,T}FUNC, func_id, out_index)`; kinds 0..4, `_K_VAR` etc. at `evoxc_engine.py:536`) and `program is None` + `const_out` marks a fully constant tree; structural identity IS program equality (`len({t.program for t in pop.trees if t.program})` is the distinct-structure count; the batch route's `_dedup` is private).
- Two tables gate extension points: `evoxc_engine.SUPPORTED_BACKENDS = ("numpy", "iree")` must contain both `Route.backend` and `Route.fallback_backend` (`../tests/test_route_policy.py` asserts it), and `dense_engine.EVAL_MODES` / `EVAL_MODE_ALIASES` are pinned canonical (`../tests/test_dense_policy.py`).
- New counters go in a NEW `*_cache_stats()` function (`cache_stats()` is pinned at exactly 8 keys, `artifact_cache_stats()` keys must all start with `artifact_`, and `dense_cache_stats()` / `batch_cache_stats()` / `runner` counters stay separate), and `evoxc_engine.clear_cache()` stays the single in-memory invalidation point (`_register_cache_reset`).

## Environment knobs (read per call unless noted)
An unusable value raises `ValueError` naming the variable (except `EVOGP_DENSE_ALLOW_UNSAFE_SCATTER`, where anything but unset/`0` counts as set). Full semantics: the owning module docstring, `DENSE_EVAL.md` §3–§4, `BATCH_EVAL.md` §9, `FUSED.md`.
- `EVOGP_EVAL_MODE` (`auto`) — master route switch: `dense` (alias `dynamic`) / `specialized` / `batch` / `fused` / `auto`; `auto` = dense+iree from `EVOGP_DENSE_AUTO_MIN_POP` up, never `batch`/`fused`.
- `EVOGP_DENSE_AUTO_MIN_POP` (`64`) — `auto`'s dense population threshold (call-count break-even knob).
- `EVOGP_DENSE_AUTO_BUDGET_MB` (`8192`) — memory envelope of `auto`'s rows rule and of its trace-cap raise (`pop_size * tree_len * rows * 4` bytes; `rows` = data rows, one per tree on `per_row=True`).
- `EVOGP_DENSE_AUTO_MAX_ROWS` (`0`) — optional TIGHTENING row pin inside that envelope (`0`/unset = unpinned).
- `EVOGP_DENSE_AUTO_MAX_TREE_LEN` (`256`) — CEILING of the `auto`-only trace-cap raise; the raise itself is `next_power_of_two(max(base, longest))` under the envelope, re-checked at the rounded value, with no clamping (a refused raise falls back on the device backend).
- `EVOGP_DENSE_MAX_TREE_LEN` (`64`) — base trace cap `L = min(cap, row_len)`; an over-cap tree declines.
- `EVOGP_DENSE_BUDGET_MB` (`2048`) — chunking budget of `_chunk_shape`, bounding `(P_chunk, N_chunk)`.
- `EVOGP_DENSE_UPDATE_MODE` (`grow`) — `grow` / `concat` / `scatter` value-buffer strategy.
- `EVOGP_DENSE_ALLOW_UNSAFE_SCATTER` (unset) — opt into `scatter` on iree, where evoxc's scatter mutates its input.
- `EVOGP_DENSE_PRUNE` (on) — candidate chain for the used function ids only (`0`/`false`/`no`/`off` = full 28-id chain).
- `EVOGP_DENSE_HOST_MEMO` (`16`, import time) — entries of the dense plan/input front tables (`0` disables both).
- `EVOGP_BATCH_MIN_POP` (`64`) — batch route `pop_size` threshold (below it: `BatchUnsupported` → specialized); measured break-even, not a safety floor.
- `EVOGP_BATCH_BAND_SIZE` (`16`) — band SIZE (`K = ceil(n_functions / size)`, clamped to `1 <= K <= n` then to the binding cap); the measured minimax default, puts a pop-256 population on `K = 15–16`.
- `EVOGP_BATCH_BANDS` — overrides the size model: an explicit `K` (refused above the cap, never clamped), `auto` (evoxc's cost model, opt-in, 0/9 warm columns) or a flat spelling (`none`/`flat`/`0` = `K = 1`).
- `EVOGP_BATCH_CHUNK_BANDS` (off) — compose a band request with the chunked compile; off forces `W == 1` per band request (wins cold, loses warm).
- `EVOGP_BATCH_SWITCH_OPS` (off) — op-switching transform; forces the flat single-body merge, 4× slower on GP populations.
- `EVOGP_BATCH_ALIGNMENT` (`variant`) — pure evoxc performance heuristic.
- `EVOGP_BATCH_CACHE_SIZE` (`8`, import time) — entries of `BATCH_PLAN_MEMO` / `BATCH_EXEC_MEMO`.
- `EVOGP_BATCH_COMPILE_WORKERS` (`4`) — compile chunks per plan (`0`/`1` = single-executable path; forced to `1` below `MIN_CHUNK_FUNCTIONS` = 32, by `switch_ops` and — without `EVOGP_BATCH_CHUNK_BANDS` — by any band request); break-even 3 849 / 5 103 / 18 702 warm calls of ONE population.
- `EVOGP_BATCH_DISPATCH_FORMATION` (`auto`) — the merged compile's evoxc `dispatch_formation`: `auto` enables `aggressive` fusion only for `iree` on a GPU HAL when the evoxc adapter declares the option, `default` (alias `off`) derives no flag, a missing option degrades to `default` silently, an unusable spelling raises `ValueError`; reported by `describe_plan()` and part of both plan keys and of the disk key.
- `EVOGP_FUSED_MIN_POP` (`16`) — fused route `pop_size` threshold; its ONE parser is `fused_engine.resolve_min_pop`, which `dense_engine.resolve_fused_min_pop` delegates to (local import). Measured: the kernel is flat in `pop_size` (0.088–0.103 ms from pop 1 to 128) while `specialized` scales with the tree count, and 16 keeps a single `Tree` on the specialized route (`FUSED.md` §13).
- `EVOGP_FUSED_BLOCK_ROWS` (`256`) — kernel row-block lanes.
- `EVOGP_FUSED_NUM_WARPS` (1) — warps per launch.
- `EVOGP_FUSED_MAX_SCRATCH_MB` (`8192`) — the `pop_size * max_tree_len * rows * 4` memory envelope.
- `EVOGP_FUSED_HOST_MEMO` (`16`, import time) — transpose-table size.
- `EVOGP_EVOXC_CACHE_SIZE` (`4096`, import time) — `maxsize` of the shared `evoxc.CompileCache` and of the two executable front tables.
- `EVOGP_EVOXC_BACKEND` (`numpy` inside the engine; the route policy passes `iree`) — `numpy` / `iree`.
- `EVOGP_EVOXC_DEVICE` (`0`) — visible GPU index.
- `EVOGP_EVOXC_OPT_LEVEL` (`O1`) — iree opt level, `O0`/`O1` only, `O1` the measured optimum (`O2`/`O3` compile no faster, run ~40 % slower warm).
- `EVOGP_EVOXC_ARTIFACT_DIR` (unset = off) — on-disk executable artifacts, all routes (batch bodies under its `batch/` subdirectory; see `### On-disk artifacts`).
- External, not ours: `EVOXC_DISABLE_LOCATIONS=1` speeds evoxc tracing up ~4× (recommended, not part of any cache key); an ambient `EVOXC_TARGET_BACKENDS` / `EVOXC_OPT_LEVEL` / `EVOXC_IREE_*` can enter `build_cached`'s resolved options (ours carry only `opt_level` + `device=`), so pair a change with `clear_cache()` and `clear_artifacts()`.

## API Surface
`evogp.tree` exports: `GenerateDescriptor`, `Tree`, `Forest`, `CombinedForest`, `CombinedTree`, `MAX_STACK`, `randint`, `NType`.

### `tree.py` — `Tree(input_len, output_len, node_value, node_type, subtree_size)`
- `Tree.random_generate(descriptor)` delegates to `Forest.random_generate(pop_size=1)[0]`; `to_forest()` wraps a single tree as a `Forest`.
- `forward(x)` — 1-D `(input_len,)` → `(output_len,)`; 2-D `(batch, input_len)` → `(batch, output_len)`; route-resolved (batch / fused / dense / specialized), specialized fallback.
- `SR_fitness(inputs, labels, use_MSE=True, execute_mode="auto")` → `(1,)` positive loss (route-resolved, specialized fallback).
- `to_sympy_expr(symbol_names=None)` — sympy expr for `output_len == 1`, a list otherwise; comparisons render as the engine's ±1 (`Piecewise((1, cond), (-1, True))`), loose ops follow the zero-clamp conventions, a constant-only tree returns a sympy `Float`. Also `to_infix()` (single-output; warns for multi-output), `to_png(fname)`, `__repr__` (== sympy repr).
- `__python_forward` — name-mangled, debug-only, full-semantics pure-Python reference evaluator (single-output), the in-repo cross-check oracle; `__assert_valid` is likewise debug-only.

### `forest.py` — `Forest(input_len, output_len, batch_node_value, batch_node_type, batch_subtree_size)`
- Public attributes: `input_len`, `output_len`, `pop_size`, `max_tree_len`, `batch_node_value`, `batch_node_type`, `batch_subtree_size`; no `.device` and no `.trees`; the three tensors must be exactly `(pop_size, max_tree_len)`.
- `Forest.random_generate(pop_size, descriptor)` (static) → pure-torch vectorized generation on the descriptor tensors' device (cuda in practice); `zero_generate(pop_size, max_tree_len, input_len, output_len)` (static) → degenerate all-`CONST`-0 trees on cuda.
- `forward(x)` — `(pop_size, input_len)` → `(pop_size, output_len)` (asserts `x.shape[0] == pop_size`); `batch_forward(x)` — `(N, input_len)` → `(pop_size, N, output_len)`; both route-resolve (`batch` / `fused` / `dense` / specialized) and fall back on that route's `*Unsupported`.
- `mutate(replace_pos, new_sub_forest)` / `crossover(left_indices, right_indices, left_pos, right_pos)` → new `Forest` (the latter of size `len(left_indices)`); pure-torch splices with the legacy semantics (`splicing.py`).
- `SR_fitness(inputs, labels, use_MSE=True, execute_mode="auto")` → fresh `(pop_size,)` float32 positive loss (writable, the pipeline mutates it in place); route-resolved, specialized fallback.
- Dunders: `__getitem__` / `__setitem__` (branch rules below), `__iter__`/`__next__` (not reentrant: stores `iter_index` on the instance), `__len__`, `__add__`/`__radd__` (concat along dim 0, matching `input_len`/`output_len`), `__str__`/`__repr__` (sympy per individual — slow), `__getstate__`/`__setstate__` (pickle via CPU numpy; restores to cuda).
- `__getitem__` (`forest.py:372-394`) branches on exactly `isinstance(index, int) or index.shape == ()`: an `int` / 0-dim `Tensor` / 0-dim numpy scalar returns a `Tree` **view** (all three tensors alias the row), a `slice` returns a `Forest` **view**, and ANY other `Tensor`/`ndarray` (a 1-element 1-D index included) goes through advanced indexing and returns a **copied** `Forest` of pop 1, NOT a `Tree`; python lists raise `Exception`, non-integral tensor dtypes raise `IndexError`. A 0-dim **CUDA** index views but is not free (blocking internal D2H); a 1-element 1-D CUDA index does not sync but returns a copy.
- `__setitem__` (`forest.py:396-417`) matches only `isinstance(index, int)` for the `Tree` path, so `forest[0-dim tensor] = tree` takes the `Forest` branch and raises `AssertionError`; `forest[tensor_index] = forest_of_same_pop` writes in place through advanced-index assignment (the mutation operators rely on the copy-in/copy-out pattern `forest_to_mutate = forest[idx]` → mutate → `forest[idx] = ...`).

### `descriptor.py` — `GenerateDescriptor(max_tree_len, input_len, output_len, const_prob=0.5, out_prob=0.5, depth2leaf_probs=None, roulette_funcs=None, const_samples=None, using_funcs=None, max_layer_cnt=None, layer_leaf_prob=0.2, const_range=None, sample_cnt=None)`
- Validates its inputs, derives `depth2leaf_probs` from `using_funcs`/`max_layer_cnt` when omitted (`check_tree_length` asserts `max_tree_len` fits the worst-case complete tree), and materializes the cuda tensors shared with the engine and the algorithm layer (`depth2leaf_probs`, the `roulette_*` cdfs, `const_samples`).
- `update(**kwargs)` returns a new descriptor (two gotchas in Known Issues).

### `generation.py` — `generate_population(pop_size, descriptor, device=None)`
Two layouts share one entry point, selected by `PADDED_SLOT_BUDGET` (1024 cells). The *padded* hot path grows the population as a complete `max_arity`-ary tree of `levels` depth levels (arity = the max arity the descriptor can actually draw — a binary-only descriptor needs 7 slots instead of 2731), decides every padded slot in one batched draw, derives the level-arity masks from static `parent = j // arity` / `rank = j % arity` maps of a cached `_PaddedLayout`, and scatters the slots into the prefix rows; the *compact* fallback is the level-by-level breadth-first walk, for descriptors whose padded layout would exceed the budget.
The padded path needs one host sync (`sizes_all.max()` against `max_tree_len`, raising the documented `RuntimeError` on overflow) and 66 kernel launches for a 13-row batch (compact: 501); it is distribution-equivalent to the compact path while the RNG stream differs.
`_descriptor_plan` memoizes `(max_arity, levels)` on the descriptor (`_evogp_generation_plan`, keyed by the data_ptr/_version of `roulette_funcs` and `depth2leaf_probs`), `_LAYOUT_CACHE`/`_FUNC_TABLE_CACHE` cache layouts and arity tables per device, and generation draws from torch's global RNG (`torch.manual_seed` reproduces a population; not bit-identical to the legacy taus88 stream); it returns `(batch_node_value float32, batch_node_type int16, batch_subtree_size int16)`.

### `splicing.py` — `mutate(...)` / `crossover(...)`
Both splices are dispatch-bound (~45 tiny kernels over a `[rows, max_tree_len]` window), so the module caches the `[1, max_tree_len]` column-index row per (length, device) in `_cols` and keeps validation to one host round trip (`((0 <= left_idx) & (left_idx < pop_size)).all()` instead of two `bool(...)` calls).
Pure-torch scalar-free splices: `_splice` updates ancestor `subtree_size` cells with the closed form `(j < pos) & (j + size[j] > pos)`, copies the donor subtree verbatim and shifts the tail (an invalid position or overflow copies the row UNCHANGED — silent, matching the legacy op); index tensors may be int8/16/32/64; out-of-range `left_indices` and `pop_size_new == 0` raise `ValueError`. `crossover` also enforces the donor-side `rpos` bounds and the out-of-range `right_indices` rule.

### `combined_forest.py` / `combined_tree.py` — the `data_info`-driven multi-output model
`CombinedForest(forests, data_info)` with `data_info = {out_name: [input_name, ...]}`; `CombinedForest.random_generate(pop_size, data_info, descriptors)` takes one descriptor per sub-forest (each with `output_len == 1`).
The input-dict contract is single-sourced in `combined_forest.normalize_inputs` (its docstring is the contract of record): every required name holds a scalar/0-D number, a 1-D `(K,)` tensor or a 2-D `(K, 1)` tensor, all names agree on `K`, values are never broadcast, extra `x` keys are ignored completely (so `CustomLoss` can pass its `existing_data` incl. `"target"`), wrong shapes/keys raise `ValueError` naming the key, its shape and the sub-forest, and Python lists / `ndim >= 1` numpy arrays are rejected.
`forward(dict) → {out_name: (pop_size, out_len_sub)}` is single-point only (a `K > 1` value raises and points to `batch_forward(dict) → {out_name: (pop_size, K, out_len_sub)}`). `CombinedTree(trees, data_info)` exposes sub-trees by output name (`best.A.to_sympy_expr()`) and its `forward` routes on `K`: `{out_name: (out_len_sub,)}` for `K == 1`, `{out_name: (K, out_len_sub)}` for `K > 1`. Neither defines `SR_fitness`/`to_sympy_expr` and neither has a `share_input` attribute; the dict input protocol is the only accepted form.

### `execute_mode` mapping
`Tree.SR_fitness`, `Forest.SR_fitness` and the problem layer accept `"torch"`, `"hybrid parallel"`, `"data parallel"`, `"tree parallel"`, `"auto"`; the legacy `kernel_type` dispatch is gone and **all five map to the same evoxc engine path** (API compatibility only).

## Constraints
- Free of custom kernels and of any compiled-extension import; the legacy extension name must not reappear here (the old ops survive only as historical schemas in `ENGINE_SPEC.md` Appendix A).
- `MAX_STACK = 1024`, `MAX_FULL_DEPTH = 10`, `NType`, `Func` live only in `utils.py`; function ids are positional across `Func`, `FUNCS_NAMES`, `FUNCS_DISPLAY`, `SYMPY_MAP`, so adding/renaming an operator means touching all four.
- `max_tree_len <= MAX_STACK` (asserted in `GenerateDescriptor`); `check_tree_length` asserts it fits the worst-case tree of `using_funcs`/`max_layer_cnt`; `using_funcs` entries must be exact `FUNCS_NAMES` strings.
- Import-cycle rule: module-level imports go one way only (`utils` → `descriptor` → `forest` → `combined_forest` → `combined_tree`); `tree.py` imports `forest` inside its methods and `combined_tree.py` imports `combined_forest` inside its methods. `tree.py`/`forest.py` use `from .utils import *`, so every public `utils.py` name leaks into their namespaces.
- Fitness contract: the engine returns fresh writable tensors; repo-wide the pipeline MAXIMIZES a `(pop_size,)` float32 and mutates it in place (NaN → -inf).
- Several helpers hard-code `"cuda"` (descriptor tensors, `zero_generate`, `check_tensor`, `randint`, `Forest.__setstate__`; the same string selects AMD GPUs under ROCm); `Forest`/`Tree` themselves are device-agnostic (tensors stored by reference, no `check_tensor`/`.to()`/`.cpu()`/`.item()` in the dunders), and only the x/label/index arguments of `forward`/`batch_forward`/`SR_fitness`/`mutate`/`crossover` are forced to cuda. `check_tensor` raises `TypeError` for non-tensors and otherwise returns a `"cuda"` `requires_grad=False` tensor, returning an already-cuda autograd-free tensor as-is (deliberate: `../problem/brax_problem.py` relies on it, and the operators call it several times per generation).
- `randint` defaults to `device="cuda"`, `dtype=torch.int32`, sampling `low + torch.rand(...) * (high - low)` truncated toward zero.
- Frozen, oracle-validated modules: `generation.py`, `splicing.py`, `evoxc_engine.py` and `dense_engine.py` — code changes need failing-test evidence and a separate commit; docstring/comment edits are free.
- The artifact layer must stay a pure accelerator: with `EVOGP_EVOXC_ARTIFACT_DIR` unset both build sites behave exactly as before, `load`/`save` never raise, an underivable key returns `None`, and any change to the key derivation requires bumping `artifact_cache.KEY_FORMAT` (a stale file costs a rebuild; a colliding key would serve a wrong executable).
- `ENGINE_SPEC.md` §1–7 are the semantics of record, §12 the validation evidence, §13 the dense path as an implementation route only; the deviations from the legacy kernels (validation instead of UB, no fast-math, torch-RNG generation, composed `sinh`/`cosh` and `copysign`, constant trees never compiled, host-side numpy fitness reduction, int tolerance rules) are listed in `evoxc_engine.py`'s module docstring.
- The dense evaluator is an evaluation *route*, not a second semantics: it uses the specialized engine's private emitters (`evoxc_engine._emit_*`) and must never grow its own op table — any element-wise divergence is a bug (`../../tests/reference_eval.py` is the oracle, `DENSE_EVAL.md` §5 lists the known iree-compile classes).
- The runner builders are benchmark-support APIs: no route behavior change, `EVOGP_EVAL_MODE` ignored, chunked dense plans refused at build.

## Design Decisions
- **Host decode + per-structure evoxc graph** (instead of one generic interpreter graph): specialization makes re-evaluation of a structure a cache hit and keeps the graph free of dynamic dispatch; statics are re-passed by value so the cache key fully determines the executable, and the program→Executable memo removes the remaining per-call re-key cost.
- **Plain-torch operators** replace the kernels: portable, toolchain-free, fast enough at these sizes, and they keep the legacy splice semantics including the silent no-op on invalid input.
- Descriptors are the shared source of randomness: `generation.py` reproduces the kernel's decision structure distribution-equivalently, while the algorithm-layer mutation operators keep consuming the descriptor's roulette cdfs.

## Known Issues / Notes for Agents
- **One pytest test is stale by design after the fused wiring**: `../tests/test_dense_policy.py::test_eval_mode_tables_stay_canonical` hard-codes `EVAL_MODES == ("dense", "specialized", "batch", "auto")` and `ENGINES == ("specialized", "dense", "batch")`, the single expected failure of an otherwise green suite; it must become `("dense", "specialized", "batch", "fused", "auto")` / `("specialized", "dense", "batch", "fused")` with `auto` still last.
- **A 0-dim CUDA index synchronizes**: `forest[cuda_0dim_index]` returns the same `Tree` view as an `int`, but PyTorch's select does an implicit `.item()` D2H readback (41.4 µs vs 7.8 µs for a Python int, stalling behind queued stream work); a device 0-dim index (e.g. from `torch.argmax`) costs that sync, as does a `bool()`/`if` on a 0-dim CUDA bool.
- Per-call cost structure (specialized route): `evaluate` copies the population tensors to host at decode and `inputs`/`labels` once per call, then does one `_executable` memo lookup + one `evoxc.run` per non-constant tree with NO cross-tree batching (dedup lives inside `evoxc.CompileCache`), plus one upload of the assembled result; `sr_fitness` skips that upload and reduces the host rows in place with numpy (not torch — the interpreter must not starve on torch's thread pool), so only `(pop_size,)` reaches the device. Under IREE each tree run also reads back (one pop=N pass = N invocations + N synchronizations).
- Host→device input memo (`_run_tree`'s `prepared`, device backends only): `evoxc.from_numpy` is a zero-copy host wrap, so the upload is `Tensor.to(device)`, memoized per input block — `per_row=False` uploads the shared `(N, input_len)` `x` once per call, `per_row=True` each tree's own row; numpy never uploads (`dense_spike_check.py`'s `case_engine_per_row_iree_bug` pins it).
- **evoxc execution-model facts** (for a no-readback / no-rekey redesign): a `build_cached` hit returns the SAME `Executable` but still re-derives the key per call, so holding it and calling `evoxc.run` is the cheapest loop (~2.4 µs/tree against ~161–206 µs per fresh build). There is no `close()`/`release()`, no zero-copy device export (`__dlpack__` raises; `.to(cpu)` + `.numpy()` is the only readback), no GPU backend without per-graph AOT compilation, no multi-program execution and no `jit`/`JitFunction`/`BoundJit`; the runtime `Tensor` has no `__getitem__`, so a device-resident `(pop, input_len)` block cannot be split per tree (details: the `evoxc` repo CONTEXT).
- Dense-route and IREE-platform detail lives in `DENSE_EVAL.md`'s `## Measured detail`: steady-state host crossings (the value path still assembles the full `(P, N, 1)` host prediction, so `forward`/`batch_forward` stay readback-bound), the rows-envelope rationale with its numbers, the over-cap raise vs an explicit `dense` request (whose per-structure `specialized`+iree fallback is unbounded in artifacts and OOM-killed pop 2 048 at 123-node trees), the numpy never-dense verdict, the staged-iree teardown instability, the 12 GB sandbox `MemoryMax` limit and the IREE numerics classes (iree drops `pow(x, ±0) = 1` for a runtime exponent and computes f32 `sqrt` 1 ulp low; numpy is exact, dense and specialized agree bitwise; `DENSE_EVAL.md` §5).
- A passing route test does not prove the route ran: with `EVOGP_EVAL_MODE=dense` / `=batch` a population outside the subset silently falls back to the specialized engine — count `DenseUnsupported` / `BatchUnsupported` or use the `dense_*_check.py` batteries.
- `EVOGP_EVOXC_CACHE_SIZE`, `EVOGP_DENSE_HOST_MEMO` and `EVOGP_BATCH_CACHE_SIZE` are import-time (set them before the first import); the backend/device/opt-level and every `EVOGP_DENSE_*` / `EVOGP_BATCH_*` / `EVOGP_EVAL_MODE` policy knob are read per call.
- Sympy rendering has documented edge gaps: `LOOSE_POW(0,0)` renders `1` (engine `0`), `DIV`/`INV` at a literal zero render `zoo` (engine NaN), `LOG(0)` `zoo` vs −inf, `MAX`/`MIN` with a NaN literal raise, and a negative-zero divisor loses its sign in loose ops (sympy has no −0.0).
- `repr(Forest)` / `str(forest)` build a sympy expr per individual (CPU sync, slow); `__iter__` is not reentrant; view-vs-copy per `forest.py` — writes through copies are lost.
- `GenerateDescriptor.update(**kwargs)` returns a new descriptor but also mutates the receiver's captured params (kwargs are sticky) and re-draws `const_samples` from `const_range` when the original had `const_samples=None`.
- For raw timing use `test/benchmark/bench_gp.py` with the committed protocols (`test/benchmark/r4/run_e2e.sh` type-1 `problem.evaluate(forest)`, `run_pure.sh` type-2 pure forward); `../../tests/perf_probe.py` models evoxc build/run economics without importing `evogp`, and `test/benchmark/stage_probe.py` still targets the pre-evoxc module name, so its stage splits stay inert.
- Module granularity is deliberate: `evoxc_engine.py` (~2k lines, one frozen compilation unit) and `dense_engine.py` (~3k lines) stay single modules (no split without failing-test evidence); the batch route is the one split route, and `batch_engine.py` is 831 lines after the build path moved to `batch_build.py`, so keep extracting before it grows back past the threshold.
- **No pytest covers the round-2 band policy**: the caps, the clamp, the explicit-`K` refusal and the chunk-banded composition are pinned only by `batch_band_check.py` (29 assertions, numpy); the suite's batch tests still carry the pre-policy band-size expectations.
- **A chunked numpy plan must not be the process's first build** (the numpy kernel table is registered lazily and not thread-safely, so the first numpy build inside the compile pool fails with `BackendError: duplicate kernel registration`): warm a single-body build first; iree is unaffected (`BATCH_EVAL.md` `## Measured detail`).

This directory has **no child subdirectories** — the layer is the files listed here; do not look for sub-nodes to delegate to.
