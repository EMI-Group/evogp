# `src/evogp/tree/` — EvoGP tree representation, evoxc evaluation engine & pure-torch operators

## Intent
This is the **foundation layer** of EvoGP: the GP individual (`Tree`), the population (`Forest`), the multi-output variants (`CombinedTree` / `CombinedForest`), the random-generation blueprint (`GenerateDescriptor`), the pure-torch generation/splicing operators, and the `evoxc`-backed evaluation engines.
Everything the rest of the library manipulates (fitness, selection, crossover, mutation, visualization) is expressed in terms of the tensor representation defined here.
`evoxc` is the **EvoX Compiler**, the evaluation-engine dependency (checked out beside this repository, supplied on `PYTHONPATH`); the engine imports it as `evoxc` plus `from evoxc.build_cache import CompileCache, build_cached`.
This layer contains **no custom CUDA/HIP kernels and no compiled extension**: evaluation runs through one of THREE engines selected by `EVOGP_EVAL_MODE` (`dense` / `specialized` / `batch` / `auto`; alias `dynamic` = `dense`) — the per-structure evoxc JIT engine (`evoxc_engine.py`), the **dense** all-ops whole-population evaluator (`dense_engine.py`, one compiled graph per *(shape, used-function-id set)*) and the opt-in **batch** merged-graph evaluator (`batch_engine.py`, one compiled graph per deduped population) — while generation/mutation/crossover are vectorized plain torch (`generation.py`, `splicing.py`).
Under the default `auto` policy a device box at `pop_size >= EVOGP_DENSE_AUTO_MIN_POP` (64) runs dense on iree and every other case (below 64, a CPU box, a `DenseUnsupported` decline) stays on specialized+numpy; `batch` is never auto-selected (exact policy and break-even call counts: `DENSE_EVAL.md` §3).
This package imports **nothing** from other `evogp` subpackages — it is the root of the package DAG (`algorithm/` and `problem/` are its consumers; `pipeline/` sits above both; no cycles).
Documents of record in this directory: `DENSE_EVAL.md` (dense route), `BATCH_EVAL.md` (batch route), `RUNNER_HOOKS.md` (benchmark runners) and `ENGINE_SPEC.md`, the semantics spec whose Appendices keep the legacy op schemas as explicitly historical reference.

## Representation (the schema every other module depends on)
An individual is three parallel tensors of length `max_tree_len`, batched as `[pop_size, max_tree_len]`, encoded as a **prefix (pre-order) expression**: node 0 is the root and children follow depth-first, left to right.
- `node_value` — `torch.float32` (`Forest.batch_node_value`).
- `node_type` — `torch.int16` (`Forest.batch_node_type`).
- `subtree_size` — `torch.int16` (`Forest.batch_subtree_size`); `subtree_size[i]` = number of nodes in the subtree rooted at node `i`.
Only indices `[0, subtree_size[0])` are meaningful: `subtree_size[0]` is the real tree length, and the rest of a row must never be read (the generator zeroes unused cells, but that is an implementation detail).
`batch_subtree_size[:, 0]` is used throughout the algorithm layer as "the size of tree i".
`Tree` holds the same three tensors unbatched (1-D); `Forest[i]` / `Forest[a:b]` return `Tree` / `Forest` **views** sharing storage, while `Tensor`/`ndarray` indexing (incl. LongTensor / bool mask) goes through PyTorch advanced indexing and returns **copies**.

Node encoding:
- `node_type` base values: `0 VAR`, `1 CONST`, `2 UFUNC`, `3 BFUNC`, `4 TFUNC` (`NType`); `NType.OUT_NODE = 1<<7` is OR-ed in for multi-output nodes (`TYPE_MASK = 0x7F` extracts the base).
- `node_value`: `VAR` → variable index (float-encoded int); `CONST` → the constant; function node → function id (`Func.*`, i.e. the index in `FUNCS_NAMES`).
- Multi-output out-node packing: `node_value` is the float32 bit-reinterpretation of `struct OutNodeValue { int16_t function; int16_t outIndex; }` (`outIndex = int32_bits >> 16`, `function = int32_bits & 0xFF`).
- Function table: id 0 `IF` (ternary); ids 1–13 binary (`+ - * / loose_div pow loose_pow max min < > <= >=`); ids 14–28 unary (`sin cos tan sinh cosh tanh log loose_log exp inv loose_inv neg abs sqrt loose_sqrt`); operands are consumed leftmost-child-first.
- Exact per-operator edge cases (`DIV`/`LOG`/`SQRT`/loose variants, comparisons returning ±1, `IF` branch mapping) are in `ENGINE_SPEC.md` §3.
- Multi-output semantics (`output_len > 1`): every out-node accumulates its own value into `out[outIndex]` and passes its right-most child up to the parent, tagged leaves behave like untagged ones, and outputs never tagged are `0.0`; `output_len == 1` is the single-output protocol, and a tree containing an OUT_NODE-tagged node is rejected at decode time with `ValueError` (the legacy kernel had undefined behavior there).

## Engine architecture (`evoxc_engine.py`)
Evaluation is a "true jit": `decode_population` walks a population **host-side** into frozen per-tree static programs (int-only, constant subtrees folded), then `evaluate` / `sr_fitness` specialize each program into a fresh evoxc graph via `evoxc.build_cached` and run it, with the compiled executables cached per *(tree structure, input shape, backend, device, options)*.
- `decode_population(node_value, node_type, subtree_size, input_len, output_len) -> Population` — pure host work (tensors read back with `.cpu()`), validating the structure and raising `ValueError` naming the row and node (replacing the kernel's UB), `TypeError` for non-tensor / non-2-D input.
- `evaluate(population, x, *, per_row, out_device=None, backend=None, iree_device_index=None)` — `per_row=True`: `(pop, input_len) → (pop, output_len)`; `per_row=False`: `(N, input_len) → (pop, N, output_len)`; the result is fresh, contiguous, `requires_grad=False` float32 on `x`'s device unless `out_device` is given.
- `sr_fitness(population, inputs, labels, use_MSE=True, *, ...)` — `(pop,)` float32 POSITIVE loss `Σ_points Σ_outputs err / N` (err = diff² for MSE else |diff|, outputs summed but never divided by `output_len`, NaN/inf unsanitized); the caller negates for higher-is-better.
- One module-level `@evoxc.defn _eval_step` — it must stay a module-level function (its `id()` is part of the cache key; a closure would permanently miss); statics are codec-safe int-scalars/sequences re-passed by value at `evoxc.run`.
- Cache: one shared `evoxc.CompileCache` (`evoxc_engine.CACHE`), default maxsize 4096 (`EVOGP_EVOXC_CACHE_SIZE`, read at import time), in memory only, measured ~270–478 KiB per entry; `cache_stats()` reports `memo_hits` / `memo_misses` / `memo_entries` / `memo_maxsize`, `clear_cache()` resets both tables.
- Program→Executable memo (`_ExecutableMemo`, `_EXECUTABLE_MEMO`): an LRU sized to `CACHE.maxsize`, keyed by `(program, n_rows, input_len, backend, device, frozen options)` via `_executable_key` and consulted by `_executable` before any build, so the `build_cached` re-encode / key re-derivation is paid only on first sight of a shape.
- Node semantics are **correctly rounded float32**: the software transcendentals (`sin`/`cos`/`tan`/`sinh`/`cosh`/`tanh`/`log`/`loose_log`/`exp`/`pow`/`loose_pow`) are emitted as `cast_f32(op(cast_f64(v)))` (evoxc has no `sinh`/`cosh`: the `exp`/`-exp` composition in f64), while hardware-exact ops (`+ - * /`, `sqrt`, `abs`, `neg`, `copysign`, `min`/`max`, comparisons/select) stay f32 and keep bit-exact ±1 — the f32 kernels are 1 ulp off on 5–39% of inputs, and `sinh` keeps `x` below `|x| < 1e-4` so `loose_inv(sinh(-0.0)) = -1e9` holds on both paths.
- Backends: `numpy` (the evoxc reference interpreter, cpu, no GPU needed) by default; IREE is on the GPU HAL (CUDA or ROCm, the kind read from torch by `_gpu_device_kind()` and passed as `evoxc.core.Device(kind, idx)`) and its knobs are `EVOGP_EVOXC_BACKEND` / `EVOGP_EVOXC_DEVICE` / `EVOGP_EVOXC_OPT_LEVEL`.
- Device policy: the engine accepts population/input tensors from any torch device and returns results on the input device unless `out_device`; the `Tree`/`Forest` wrappers still pass everything through `check_tensor` (`.to("cuda")`), so the public API keeps its CUDA-bound behavior.
- Per-tree IREE is compile-bound (~0.27 s per tree structure, ~2.4–3.6 ms/run), which is why the policy never sends the specialized route to IREE (`warm_path_findings.md` §11).

### On-disk artifacts (`artifact_cache.py`, `EVOGP_EVOXC_ARTIFACT_DIR`, DEFAULT OFF)
- Unset/empty changes nothing (one environment read, no key, no directory, no file); set, a front-table miss first tries `artifact_cache.load`, and an executable built or loaded is stored in the route's executable memo.
- Key: `"<slug>-<sha256 hex>"` from `evoxc.persist.cache.compute_key` over `(KEY_FORMAT, graph name, the build's spec tuple incl. static content, backend name, "kind:index", frozen options, evoxc.__version__, iree-base-compiler version)`; the specialized graph name is `evoxc_engine.ARTIFACT_NAME = "specialized"` (program in the spec tuple), so a distinct tree structure is a distinct file, while the dense route writes one artifact per shape and used-id set (`DENSE_ARTIFACT_NAMES`: `dense:value` / `dense:loss`).
- `signature_matches` accepts a loaded artifact only on agreeing tensor shapes/dtypes and flattened static values; any load exception or mismatch deletes the file, and a successful build is `save`d atomically (temp file + `os.replace`, best effort — no usable backend `save` yields `False` and no file).
- Two lifetimes: `clear_cache()` is the in-memory point (compile cache + `_EXECUTABLE_MEMO` + the dense front tables) and never deletes a file, while `clear_artifacts()` deletes every `*.evoxcart` and resets the disk counters without touching memory; `artifact_cache_stats()` reports `artifact_enabled`, `artifact_files`, `artifact_hits`, `artifact_misses`, `artifact_load_failures`, `artifact_stores`, `artifact_save_failures` (disjoint from `cache_stats()`'s 8 keys and from `dense_cache_stats()`).
- Not in the key (the same blind spot `build_cached` has): the ambient `EVOXC_*` process-env compile knobs. The safety net is validation, not keying — evoxc's loader refuses an artifact whose compile targets do not fit the requested device kind (`BackendError`) and `signature_matches` refuses a mismatched call shape, so a stale file costs one rebuild, never a wrong number.
- It buys a fresh process's first call and nothing else; the specialized route writes one file per distinct tree structure (a random population fills the directory), so the dense route plus an occasional `clear_artifacts()` is the sensible pairing, and no pytest test covers the disk layer. Measured economics and recovery legs (a truncated file costs one rebuild; `python -m evogp.sr_test` 15.30 s cold vs 9.25 s warm-artifact): `artifact_cache.py`'s docstring, `DENSE_EVAL.md` §2.6/§6.

### Benchmark runner hooks (`build_specialized_runner` / `dense_engine.build_dense_runner`)
Build-once / run-many **benchmark-support** APIs: the build does the decode/prepare, the compiles and the staged payloads, and `.run()` executes ONLY the compiled forward pass (specialized: one `evoxc.run` per non-constant tree, raw per-tree results with `None` for constant trees; dense: ONE `evoxc.run` returning the raw result) with no readback, no re-key, no re-plan and no host assembly beyond what is baked in-graph.
`EVOGP_EVAL_MODE` is ignored and chunked dense plans are refused at build with `DenseUnsupported`; signatures, per-backend `.run()` semantics, the build-vs-run split and the evoxc call-boundary facts are in `RUNNER_HOOKS.md`, the evidence battery is `runner_check.py`.

## Dense one-graph evaluator (`dense_engine.py`) — the iree default route
`dense_engine.py` evaluates a WHOLE population with ONE compiled evoxc graph fed with the population's node tensors as runtime data (no per-tree Python loop, no per-tree readback): host preprocessing (`prepare_dense`) encodes the `(L, P)` `opcode`/`func_id`/`const_value`/`var_index`/`child1..3` columns, the trace-time unrolled graph computes each node value with the specialized engine's own private emitters (`evoxc_engine._emit_*` — parity by construction), the per-position candidate chain is emitted **only for the population's used function ids**, and `L = min(EVOGP_DENSE_MAX_TREE_LEN (64), max_tree_len)`.
- Wiring: the five call sites dispatch on `route.engine` and fall back ONLY on that engine's own `*Unsupported` (silent, except the over-cap decline; the specialized path owns the error contract for malformed trees, every other exception propagates), so the public API contracts are unchanged.
- Supported subset: single-output populations (`output_len == 1`) with every tree within the 64-node trace cap; an over-cap population emits a deduped once-per-process `RuntimeWarning` (device backends only) and falls back.
- Cache: `dense_engine.DENSE_CACHE` IS `evoxc_engine.CACHE`, keyed on the compiled body identity + `(L, P, N, input_len, per_row, update_mode, used_func_ids[, use_mse], backend, device, options)` — ONE miss per (shape, used-id set) against pop_size misses on the specialized path; `_dense_step` / `_dense_loss_step` must stay module-level (`id()` is part of the key).
- Pruning (`EVOGP_DENSE_PRUNE`, default ON; `=0` restores the full 28-id chain byte-for-byte): the used-id set (sorted unique ids 1..28, `DensePrep.used_func_ids`, empty when there is no function node) travels as a static `cfg[6]` entry, so it joins the cache key and a population whose set differs from the last compiled one recompiles (the set saturates quickly in a GP run); an empty set emits no candidate and every position keeps a defined value; the knob accepts on/off spellings case-insensitively, anything else raises `ValueError`.
- Front tables (`dense_memo.py`, `DenseMemo` LRUs whose `clear` is registered with `evoxc_engine._register_cache_reset` and whose keys are identity tokens of `data_ptr`/shape/dtype/device/`_version`, pinning held storages against address recycling): `DENSE_EXECUTABLE_MEMO` (`dense_exec_*`, sized like `DENSE_CACHE`) in front of `build_cached`, `DENSE_PLAN_MEMO` (`dense_plan_*`) holding the `DenseEntry` — `DensePlan`, executable and staged payloads — of an unchanged population, and `DENSE_INPUT_MEMO` (`dense_input_*`) holding the host copy of an unchanged `inputs`/`labels`; a non-torch `x`/`labels` or population is simply not memoized.
- `dense_cache_stats()` returns exactly those 12 keys and is deliberately not folded into `cache_stats()`; `evoxc_engine.clear_cache()` is the single invalidation point of all three tables.
- The dense SR loss is computed **in-graph** (`_dense_loss_step`; the static `use_mse` selector lives in `cfg[7]`), so the loss readback is `(p_chunk,)`-scale and only the `/ N` divide and the `(pop_size,)` assembly stay host-side, while the specialized `sr_fitness` reduces its host rows in place with numpy — same formula, differing only in float32 reduction order by ~1e-7 relative on the fixtures, and both routes return fresh, contiguous, `requires_grad=False` float32.
Scheme, chunking and peak memory, the value-buffer write modes, the tolerance classes, the measured economics (the ≈3.4–6.8k-row warm crossover, the prune A/B numbers, the front-table before/after timings) and the future work are owned by `DENSE_EVAL.md`.

## Batch merged-graph evaluator (`batch_engine.py`, `batch_programs.py`, `batch_knobs.py`) — opt-in, never selected by `auto`
`batch_engine.py` is the PUBLIC facade (the only name callers import): it traces ONE graph per **deduped** tree program (program equality; constant trees keyed by `const_out`) and merges them into ONE executable with `evoxc.batch_functions` — one `evoxc.run` per population, one readback, a host row expansion back to population order — built through the explicit `evoxc.lower` → `evoxc.compile` → `evoxc.load` sequence (`build_cached` / `evoxc.build` reject a `Graph`).
- Reachable ONLY through `EVOGP_EVAL_MODE=batch`; each of the five call sites catches exactly `BatchUnsupported` and continues on `Route.fallback_backend` (the specialized engine, which owns the malformed-tree error contract).
- Its economics are per CALL, not per generation: the merged compile is population-specific, so a GP loop recompiles every generation and the route only pays on repeated evaluation of a stable/duplicate-rich population.
Scheme (dedup → per-function trace → banded merge), the `EVOGP_BATCH_*` knobs, the measured grid and the per-generation verdict, parity, the known gaps (no disk artifacts, numpy debug-only) and the module contracts are owned by `BATCH_EVAL.md`.

## Adding a further evaluation route (the dispatch seam)
- There is exactly ONE dispatcher, `dense_engine.resolve_route(pop_size, *, rows=None, backend=None, iree_device_index=None, eval_mode=None, auto_min_pop=None, auto_max_rows=None) -> Route(use_dense, backend, fallback_backend, reason="", engine="specialized")`, with `dense_engine.ENGINES = ("specialized", "dense", "batch")`; `engine` is `compare=False`, so a batch route compares EQUAL to the old 3-field record — assert `route.engine`, never bare equality — and the class invariant `use_dense == (engine == "dense")` holds (an old-style `Route(True, ...)` is promoted to `engine="dense"`, `engine="batch"` with `use_dense=True` raises `ValueError`). A further engine needs a name in `ENGINES` plus an edit at each of the five call sites.
- The five call sites ask it per call and pass the resolved backend EXPLICITLY: `tree.py:83` (`Tree.forward`, 1-D `x` -> `per_row=True`), `tree.py:150` (`Tree.SR_fitness`), `forest.py:116` (`Forest.forward`, `per_row=True`), `forest.py:151` (`Forest.batch_forward`, `per_row=False`), `forest.py:344` (`Forest.SR_fitness`); each wraps its `route.engine == "batch"` attempt in `except batch_engine.BatchUnsupported:` and its `"dense"` attempt in `except dense_engine.DenseUnsupported:`, then continues on `route.fallback_backend`.
- A new engine module should mirror one of the three existing fronts (`batch_engine.py` is the dense-shaped front plus a `BatchUnsupported` decline type): either the dense form (population tensors + `input_len`/`output_len` + `x`, keyword-only `per_row`/`out_device`/`backend`/`iree_device_index`/`max_tree_len`/`budget_mb`/`update_mode`) plus the loss form `(..., inputs, labels, use_MSE=True, *, ...) -> (pop_size,)`, or the specialized form `evaluate(Population, x, ...)` / `sr_fitness(Population, inputs, labels, use_MSE, ...)` fed by `decode_population`. Exact signatures: `RUNNER_HOOKS.md` §1 and the two route sections above.
- Per-tree programs already exist for reuse: `decode_population(...) -> Population(input_len, output_len, pop_size, trees)` of `DecodedTree(program, const_out, node_count, collapsed_nodes)`, where `program = (out_len, tokens)` holds int-only tokens (`(K_VAR, var_index)`, `(K_CONST, float32_bits)`, `(K_{U,B,T}FUNC, func_id, out_index)`; kinds 0..4, `_K_VAR` etc. at `evoxc_engine.py:536`) and `program is None` + `const_out` (float32 bit patterns) marks a fully constant tree; structural identity IS program equality, so `len({t.program for t in pop.trees if t.program})` is the distinct-structure count and a per-row list comprehension over `pop.trees` is the row->structure mapping (there is no dedup helper in the library).
- Two tables gate extension points: `evoxc_engine.SUPPORTED_BACKENDS = ("numpy", "iree")` must contain both `Route.backend` and `Route.fallback_backend` (`../tests/test_route_policy.py` asserts it), and `dense_engine.EVAL_MODES` / `EVAL_MODE_ALIASES` are pinned canonical (`../tests/test_dense_policy.py`).
- New counters go in a NEW `*_cache_stats()` function (`cache_stats()` is pinned at exactly 8 keys, `artifact_cache_stats()` keys must all start with `artifact_`, and `dense_cache_stats()` / `batch_cache_stats()` / `runner` counters stay separate), and `evoxc_engine.clear_cache()` stays the single in-memory invalidation point via `_register_cache_reset`.

## Environment knobs (read per call unless noted)
Every knob below is read by `evoxc_engine.py`, `dense_engine.py`, `batch_engine.py` or `artifact_cache.py`; an unusable value raises `ValueError` naming the variable (except `EVOGP_DENSE_ALLOW_UNSAFE_SCATTER`, where anything but unset/`0` counts as set).
- `EVOGP_EVAL_MODE` (`auto`) — the master route switch: `dense` (alias `dynamic`) / `specialized` / `batch` / `auto`; `auto` picks dense+iree from `EVOGP_DENSE_AUTO_MIN_POP` up and never selects `batch`.
- `EVOGP_DENSE_AUTO_MIN_POP` (`64`) — `auto`'s population threshold for dense (the call-count break-even knob); `EVOGP_DENSE_AUTO_MAX_ROWS` (`2048`) — `auto`'s data-row ceiling for `per_row=False` calls, above which the attempt declines to the specialized engine.
- `EVOGP_DENSE_MAX_TREE_LEN` (`64`) — the trace cap `L = min(cap, row_len)`; a longer tree declines (once-per-process warning on device backends); `EVOGP_DENSE_BUDGET_MB` (`2048`) — the chunking memory budget of `_chunk_shape` bounding the `(P_chunk, N_chunk)` execution.
- `EVOGP_DENSE_UPDATE_MODE` (`grow`) — `grow` / `concat` / `scatter` value-buffer strategy; `EVOGP_DENSE_ALLOW_UNSAFE_SCATTER` (unset) is the opt-in for `scatter` on iree, where evoxc's scatter mutates its input.
- `EVOGP_DENSE_PRUNE` (on) — emit the candidate chain for the population's used function ids only; `0`/`false`/`no`/`off` restores the full 28-id chain; `EVOGP_DENSE_HOST_MEMO` (`16`, import time) — entries of the dense plan and input front tables, `0` disables both.
- `EVOGP_BATCH_MIN_POP` (`64`) — the batch route's `pop_size` threshold; below it the route declines (`BatchUnsupported`, fallback to specialized). Measured break-even, not a safety floor.
- `EVOGP_BATCH_BAND_SIZE` (`32`) — band SIZE of the merge: `K = ceil(n_functions / size)`, clamped to `1 <= K <= n`; `EVOGP_BATCH_BANDS` overrides it with an explicit `K` or a flat spelling (`none` / `flat` / `0`).
- `EVOGP_BATCH_SWITCH_OPS` (off) — op-switching transform; forces the flat merge, measured 4× slower on GP populations. `EVOGP_BATCH_ALIGNMENT` (`variant`) is a pure evoxc performance heuristic.
- `EVOGP_BATCH_CACHE_SIZE` (`8`, import time) — entries of `BATCH_PLAN_MEMO` / `BATCH_EXEC_MEMO` (reported by `batch_cache_stats()`, 8 keys).
- `EVOGP_EVOXC_CACHE_SIZE` (`4096`, import time) — `maxsize` of the shared `evoxc.CompileCache` and of the two executable front tables.
- `EVOGP_EVOXC_BACKEND` (`numpy` inside the engine; the route policy passes `iree`) — `numpy` / `iree`; `EVOGP_EVOXC_DEVICE` (`0`) — visible GPU index of the iree route; `EVOGP_EVOXC_OPT_LEVEL` (`O1`) — iree opt level, `O0`/`O1` only, and `O1` is the measured optimum (`O2`/`O3` compile no faster and run ~40 % slower warm).
- `EVOGP_EVOXC_ARTIFACT_DIR` (unset = off) — enables the on-disk executable artifacts (see `### On-disk artifacts`).
- External, not ours: `EVOXC_DISABLE_LOCATIONS=1` speeds evoxc tracing up ~4× (recommended for real runs, not part of any cache key), and an ambient `EVOXC_TARGET_BACKENDS` / `EVOXC_OPT_LEVEL` / `EVOXC_IREE_*` can enter `build_cached`'s resolved options (our compile options carry only `opt_level` + `device=`; passing `target_backends` makes evoxc mis-target), so pair a change with `clear_cache()` and `clear_artifacts()`.

## API Surface
`evogp.tree` exports: `GenerateDescriptor`, `Tree`, `Forest`, `CombinedForest`, `CombinedTree`, `MAX_STACK`, `randint`, `NType`.

### `tree.py` — `Tree(input_len, output_len, node_value, node_type, subtree_size)`
- `Tree.random_generate(descriptor)` delegates to `Forest.random_generate(pop_size=1)[0]`; `to_forest()` wraps a single tree as a `Forest`.
- `forward(x)` — 1-D `(input_len,)` → `(output_len,)`; 2-D `(batch, input_len)` → `(batch, output_len)`; route-resolved (batch / dense / specialized) through the evoxc engine, falling back to the specialized path on that route's own `*Unsupported`.
- `SR_fitness(inputs, labels, use_MSE=True, execute_mode="auto")` → `(1,)` positive loss (route-resolved, specialized fallback).
- `to_sympy_expr(symbol_names=None)` — sympy expr for `output_len == 1`, a list for `output_len > 1`; comparisons render as the engine's ±1 (`Piecewise((1, cond), (-1, True))`), loose ops follow the engine's zero-clamp conventions, and every leaf is sympified (a constant-only tree returns a sympy `Float`).
- `to_infix()` (single-output; warns and returns one string for multi-output), `to_png(fname)`, `__repr__` (== sympy repr).
- `__python_forward` — name-mangled, debug-only, full-semantics pure-Python reference evaluator (single-output) used as the in-repo cross-check oracle; `__assert_valid` is likewise debug-only.

### `forest.py` — `Forest(input_len, output_len, batch_node_value, batch_node_type, batch_subtree_size)`
- Public attributes: `input_len`, `output_len`, `pop_size`, `max_tree_len`, `batch_node_value`, `batch_node_type`, `batch_subtree_size`; no `.device` and no `.trees`; the three tensors must be exactly `(pop_size, max_tree_len)`.
- `Forest.random_generate(pop_size, descriptor)` (static) → pure-torch vectorized generation on the descriptor tensors' device (cuda in practice); `zero_generate(pop_size, max_tree_len, input_len, output_len)` (static) → degenerate all-`CONST`-0 trees on cuda.
- `forward(x)` — `(pop_size, input_len)` → `(pop_size, output_len)` (asserts `x.shape[0] == pop_size`); `batch_forward(x)` — `(N, input_len)` → `(pop_size, N, output_len)`; both route-resolve (`batch` / `dense` / specialized) and fall back to the specialized engine on that route's `*Unsupported`.
- `mutate(replace_pos, new_sub_forest)` → new `Forest`; `crossover(left_indices, right_indices, left_pos, right_pos)` → new `Forest` of size `len(left_indices)`; both pure-torch splices with the legacy semantics (see `splicing.py`).
- `SR_fitness(inputs, labels, use_MSE=True, execute_mode="auto")` → fresh `(pop_size,)` float32 positive loss (writable; the pipeline mutates it in place); route-resolved (batch / dense / specialized), specialized fallback.
- Dunders: `__getitem__` / `__setitem__` (branch rules below), `__iter__`/`__next__` (not reentrant: stores `iter_index` on the instance), `__len__`, `__add__`/`__radd__` (concat along dim 0, matching `input_len`/`output_len`), `__str__`/`__repr__` (sympy per individual — slow), `__getstate__`/`__setstate__` (pickle via CPU numpy; restores to cuda).
- `__getitem__` (`forest.py:372-394`) branch rule is exactly `isinstance(index, int) or index.shape == ()`: an `int` / 0-dim `Tensor` / 0-dim numpy scalar returns a `Tree` **view** (all three tensors alias the population row), a `slice` returns a `Forest` **view**, and ANY other `Tensor`/`ndarray` (a 1-element 1-D index included) goes through advanced indexing and returns a **copied** `Forest` — a 1-element index therefore yields a `Forest` of pop 1, NOT a `Tree`; python lists raise `Exception`, non-integral tensor dtypes raise `IndexError`. A 0-dim **CUDA** index views but is NOT free (blocking internal D2H, see Known Issues), a 0-dim **CPU** index views with no sync, and a 1-element 1-D CUDA index does not sync but returns a copy.
- `__setitem__` (`forest.py:396-417`) matches only `isinstance(index, int)` for the `Tree` path, so `forest[0-dim tensor] = tree` takes the `Forest` branch and raises `AssertionError`; `forest[tensor_index] = forest_of_same_pop` writes in place through advanced-index assignment (the mutation operators rely on the copy-in/copy-out pattern `forest_to_mutate = forest[idx]` → mutate → `forest[idx] = ...`).

### `descriptor.py` — `GenerateDescriptor(max_tree_len, input_len, output_len, const_prob=0.5, out_prob=0.5, depth2leaf_probs=None, roulette_funcs=None, const_samples=None, using_funcs=None, max_layer_cnt=None, layer_leaf_prob=0.2, const_range=None, sample_cnt=None)`
- Validates its inputs, derives `depth2leaf_probs` from `using_funcs`/`max_layer_cnt` when omitted (`check_tree_length` asserts `max_tree_len` fits the worst-case complete tree), and materializes the cuda tensors the engine and the algorithm-layer operators share (`depth2leaf_probs`, the `roulette_*` cdfs, `const_samples`).
- `update(**kwargs)` returns a new descriptor (see Known Issues for its two gotchas).

### `generation.py` — `generate_population(pop_size, descriptor, device=None)`
Two layouts share one entry point, selected by `PADDED_SLOT_BUDGET` (1024 cells): the *padded* hot path grows the population as a complete `max_arity`-ary tree of `levels` depth levels (arity = the max arity of the functions the descriptor can actually draw, so a binary-only descriptor needs 7 slots instead of 2731), decides every padded slot in one batched draw, computes the level-arity masks from static `parent = j // arity` / `rank = j % arity` maps of a cached `_PaddedLayout`, and scatters the slots into the prefix rows; the *compact* fallback is the level-by-level breadth-first walk, kept for descriptors whose padded layout would exceed the budget.
The padded path needs exactly one host sync (`sizes_all.max()` against `max_tree_len`, raising the documented `RuntimeError` on overflow) and 66 kernel launches for a 13-row batch (compact: 501), and it is distribution-equivalent to the compact path on tree sizes and composition while the RNG stream differs.
`_descriptor_plan` memoizes `(max_arity, levels)` on the descriptor object (`_evogp_generation_plan`, keyed by the data_ptr/_version of `roulette_funcs` and `depth2leaf_probs`), `_LAYOUT_CACHE`/`_FUNC_TABLE_CACHE` cache the static layouts and function/arity tables per device, and generation draws from torch's global RNG (`torch.manual_seed` reproduces a population; not bit-identical to the legacy taus88 stream); it returns `(batch_node_value float32, batch_node_type int16, batch_subtree_size int16)`.

### `splicing.py` — `mutate(...)` / `crossover(...)`
Both splices are dispatch-bound (~45 tiny kernels over a `[rows, max_tree_len]` window), so the module caches the `[1, max_tree_len]` column-index row per (length, device) in `_cols` and keeps validation to one host round trip (`((0 <= left_idx) & (left_idx < pop_size)).all()` instead of two `bool(...)` calls).
Pure-torch scalar-free splices: `_splice` updates ancestor `subtree_size` cells with the closed form `(j < pos) & (j + size[j] > pos)`, copies the donor subtree verbatim and shifts the tail; an invalid position or overflow copies the row UNCHANGED (silent, matching the legacy op); index tensors may be int8/16/32/64; out-of-range `left_indices` → `ValueError`; `pop_size_new == 0` → `ValueError`. `crossover` enforces the donor-side `rpos` bounds and the out-of-range `right_indices` rule (`_splice` already validates the target position against the left parent's real length).

### `combined_forest.py` / `combined_tree.py` — the `data_info`-driven multi-output model
`CombinedForest(forests, data_info)` with `data_info = {out_name: [input_name, ...]}`; `CombinedForest.random_generate(pop_size, data_info, descriptors)` (one descriptor per sub-forest, each with `output_len == 1`).
The input-dict contract is single-sourced in `combined_forest.normalize_inputs` (its docstring is the contract of record): every required name must hold a scalar/0-D number, a 1-D `(K,)` tensor or a 2-D `(K, 1)` tensor, all names must agree on `K`, values are never broadcast, extra `x` keys are ignored completely (so `CustomLoss` can pass its `existing_data` including `"target"`), wrong shapes/keys raise `ValueError` naming the offending key, its shape and the sub-forest, and Python lists / `ndim >= 1` numpy arrays are rejected.
`CombinedForest.forward(dict) → {out_name: (pop_size, out_len_sub)}` is single-point only (a `K > 1` value raises and points to `batch_forward`); `CombinedForest.batch_forward(dict) → {out_name: (pop_size, K, out_len_sub)}`.
`CombinedTree(trees, data_info)` exposes each sub-tree by output name (`best.A.to_sympy_expr()`); its `forward` routes on `K`: `{out_name: (out_len_sub,)}` for `K == 1` and `{out_name: (K, out_len_sub)}` for `K > 1` (the one-individual forest's pop dim is stripped).
Neither defines `SR_fitness`/`to_sympy_expr`, and neither has a `share_input` attribute; the dict input protocol is the only accepted form.

### `execute_mode` mapping
`Tree.SR_fitness`, `Forest.SR_fitness` and the problem layer accept `"torch"`, `"hybrid parallel"`, `"data parallel"`, `"tree parallel"`, `"auto"`; the legacy `kernel_type` dispatch is gone and **all five map to the same evoxc engine path** (kept for API compatibility only).

## Constraints
- This layer must stay free of custom kernels and of any compiled-extension import; the legacy extension name must not reappear anywhere in this directory (the old ops are kept only as historical schemas in `ENGINE_SPEC.md` Appendix A).
- `MAX_STACK = 1024`, `MAX_FULL_DEPTH = 10`, `NType`, `Func` are defined only in `utils.py` and are the single source of truth; function ids are positional across `Func`, `FUNCS_NAMES`, `FUNCS_DISPLAY`, `SYMPY_MAP`, so adding/renaming an operator means touching all four.
- `max_tree_len <= MAX_STACK` (asserted in `GenerateDescriptor`); `check_tree_length` asserts `max_tree_len` fits the worst-case tree of `using_funcs`/`max_layer_cnt`; `using_funcs` entries must be exact `FUNCS_NAMES` strings.
- Import-cycle rule: module-level imports go one way only (`utils` → `descriptor` → `forest` → `combined_forest` → `combined_tree`); `tree.py` imports `forest` inside its methods and `combined_tree.py` imports `combined_forest` inside its methods.
- `tree.py` / `forest.py` use `from .utils import *`, so every public name in `utils.py` leaks into their namespaces — avoid adding casual public names.
- Fitness contract: the engine returns fresh writable tensors; the repo-wide convention is `(pop_size,)` float32 MAXIMIZED and mutated in place by the pipeline (NaN → -inf).
- Several helpers still hard-code the `"cuda"` device string (descriptor tensors, `zero_generate`, `check_tensor`, `randint`, `Forest.__setstate__`; the same string selects AMD GPUs under ROCm); `Forest`/`Tree` themselves are device-agnostic — `__init__` stores the three tensors by reference and the dunders never call `check_tensor`/`.to()`/`.cpu()`/`.item()`, so a `Forest` lives on whatever device its tensors were built on, and only the x/label/index arguments of `forward`/`batch_forward`/`SR_fitness`/`mutate`/`crossover` are forced to cuda.
- `check_tensor` raises `TypeError` for non-tensors and otherwise returns a `"cuda"` `requires_grad=False` tensor (kept deliberately: `../problem/brax_problem.py` relies on it); a tensor already on cuda without an autograd graph is returned as-is (same object, no `to`/`detach`/`requires_grad_` dispatch), because the operators call it several times per generation.
- `randint` defaults to `device="cuda"`, `dtype=torch.int32` and samples via `low + torch.rand(...) * (high - low)` truncated toward zero; it costs ~2x `torch.randint` but runs once per crossover, so it is left alone (a stream-changing swap measured < 0.02 ms/generation).
- Frozen, oracle-validated modules: `generation.py`, `splicing.py`, `evoxc_engine.py` — code changes need failing-test evidence and a separate commit; docstring/comment edits are free.
- `dense_engine.py` is frozen like `evoxc_engine.py` for code changes (failing-test evidence + a separate commit); docstring/comment edits are free.
- The artifact layer must stay a pure accelerator: with `EVOGP_EVOXC_ARTIFACT_DIR` unset both build sites behave exactly as before, `load`/`save` never raise, and an underivable key returns `None` (the build proceeds); any change to the key derivation (a new component, a different graph-name spelling, a changed spec tuple) requires bumping `artifact_cache.KEY_FORMAT`, since a stale file only costs a rebuild but a colliding key would serve a wrong executable.
- `ENGINE_SPEC.md` sections 1–7 are the semantics of record, §12 carries the validation evidence and §13 records the dense path as an implementation route only; the deviations from the legacy kernels (validation instead of UB, no fast-math, torch-RNG generation, composed `sinh`/`cosh` and `copysign`, constant trees never compiled, host-side numpy fitness reduction, int tolerance rules) are listed in `evoxc_engine.py`'s module docstring.
- The dense evaluator is an evaluation *route*, not a second semantics: it computes node values through the same private emitters as the specialized engine (`evoxc_engine._emit_*`) and must never grow its own op table. Any element-wise divergence from the specialized path is a bug — `src/evogp/tests/reference_eval.py` is the oracle, `DENSE_EVAL.md` §5 lists the known (non-dense-specific) iree-compile classes.
- The runner builders are benchmark-support APIs: no route behavior change, `EVOGP_EVAL_MODE` ignored, chunked dense plans refused at build.

## Design Decisions
- **Host decode + per-structure evoxc graph** (instead of one generic interpreter graph): specialization makes re-evaluation of a structure a cache hit and keeps the graph free of dynamic dispatch; statics are re-passed by value so the cache key fully determines the executable, and an in-process program→Executable memo on top removes the remaining per-call re-key cost.
- **Plain-torch operators** replace the kernels because they are portable and fast enough at these sizes; they keep the legacy splice semantics, including the silent no-op on invalid input.
- Descriptors remain the shared source of randomness: `generation.py` reproduces the kernel's decision structure distribution-equivalently, while the algorithm-layer mutation operators keep consuming the descriptor's roulette cdfs.

## Known Issues / Notes for Agents
- **Indexing with a 0-dim CUDA tensor synchronizes**: `forest[cuda_0dim_index]` returns the same `Tree` view as an `int`, but PyTorch's select does an implicit `.item()` D2H readback (41.4 µs vs 7.8 µs for a Python int, torch 2.6.0+cu124 / RTX A6000; it also stalls behind queued stream work), so keeping a `torch.argmax` output as a device 0-dim index costs a blocking sync per access; a `bool()`/`if` on a 0-dim CUDA bool (e.g. `if best_fitness > self.best_fitness:`) is likewise one sync per evaluation.
- Per-call cost structure (specialized route): `evaluate` copies the population tensors to host at decode and `inputs`/`labels` once per call, then does one `_executable` memo lookup + one `evoxc.run` per non-constant tree with NO cross-tree batching (dedup lives inside `evoxc.CompileCache`), plus one upload of the assembled result; `sr_fitness` skips that upload and reduces the host rows in place with numpy (not torch — the interpreter must not starve on torch's thread pool), so only `(pop_size,)` reaches the device. Under IREE each tree run also reads back (one pop=N pass = N invocations + N synchronizations).
- Host→device input memo (`_run_tree`'s `prepared`, device backends only): `evoxc.from_numpy` is a zero-copy host wrap, so the upload is `Tensor.to(device)`, memoized per distinct input block keyed by the caller — `per_row=False` uploads the shared `(N, input_len)` `x` ONCE per `evaluate` call, `per_row=True` uploads each tree's own `(1, input_len)` row (tree `i` must see row `i`; numpy consumes the host array and never uploads). `case_engine_per_row_iree_bug` in `dense_spike_check.py` pins the numbers and upload counts.
- **evoxc execution-model facts** (for a no-readback / no-rekey redesign): a `build_cached` hit returns the SAME `Executable` but still re-derives the key per call, so holding it and calling `evoxc.run` (or `exe.backend_executable.run(flat)` to skip the wrapper's structure walk) is the cheapest loop — the value-keyed `_ExecutableMemo` (~2.4 µs/tree vs ~161–206 µs per fresh build). There is no `close()`/`release()`, no zero-copy device export (`__dlpack__` raises; `.to(cpu)` + `.numpy()` is the only readback), no GPU backend without per-graph AOT compilation, no multi-program execution and no function-entry caching (`jit`/`JitFunction`/`BoundJit` do not exist), so `_EXECUTABLE_MEMO` is the only pre-binding layer and `evoxc.run` re-validates statics every call; the runtime `Tensor` has no `__getitem__`, so a device-resident `(pop, input_len)` block cannot be split per tree at run time (details: the `evoxc` repo CONTEXT).
- Dense-route host crossings (steady state = same `Forest`, same dataset): a pre-conversion decline from `inputs.shape`, memoized host copies of `x`/`labels`, the three population tensors only on a `DENSE_PLAN_MEMO` miss, and ONE `(p_chunk,)` loss readback per chunk; the **value** path still assembles the full `(P, N, 1)` host prediction and uploads it once, so `forward`/`batch_forward` stay readback-bound on device backends (inventory + timings: `device_resident_findings.md` §2).
- `EVOGP_EVOXC_CACHE_SIZE`, `EVOGP_DENSE_HOST_MEMO` and `EVOGP_BATCH_CACHE_SIZE` are import-time and must be set before the first import; the backend/device/opt-level and every `EVOGP_DENSE_*` / `EVOGP_BATCH_*` / `EVOGP_EVAL_MODE` policy knob are read per call.
- **IREE device numerics (both paths, not dense-specific)**: iree-compile's own lowering drops the C99 `pow(x, ±0) = 1` case when the exponent is a runtime value (`pow(0,0)` / `pow(NaN,0)` → NaN) and computes the emitted f32 `sqrt` 1 ulp low for some inputs (e.g. `0.47954902f`); both classes vanish on numpy, are bit-identical between the dense and the specialized path whenever the specialized path emits the op, and are reported (not chased) by the batteries. Numeric tolerances (numpy dense bit-exact; iree only the engine's fold-vs-emit ≈1 ulp, `max_rel` ≤ 3.3e-7; `rtol=atol=1e-4` on finite values plus exact NaN/±inf masks and zero signs): `DENSE_EVAL.md` §5.
- Sympy rendering has documented edge gaps: `LOOSE_POW(0,0)` renders `1` (engine `0`), `DIV`/`INV` at a literal zero render `zoo` (engine NaN), `LOG(0)` `zoo` vs −inf, `MAX`/`MIN` with a NaN literal raise, and a negative-zero divisor loses its sign in loose ops (sympy has no −0.0).
- `repr(Forest)` / `str(forest)` build a sympy expr per individual (CPU sync, slow); `__iter__` is not reentrant; `Forest[int]`/`[slice]` views vs `Tensor`-indexing copies — writes through copies are lost.
- `GenerateDescriptor.update(**kwargs)` returns a new descriptor but also mutates the receiver's captured params (kwargs are sticky) and re-draws `const_samples` from `const_range` when the original had `const_samples=None`.
- For raw timing use `test/benchmark/bench_gp.py` with the committed protocols (`test/benchmark/r4/run_e2e.sh` type-1 `problem.evaluate(forest)`, `run_pure.sh` type-2 pure forward; R2's `run_all.sh` is retained); `src/evogp/tests/perf_probe.py` and the engine-side probe under `test/` model evoxc build/run economics without importing `evogp`, so they cover no decode/copy/assembly cost, and `test/benchmark/stage_probe.py` still targets the pre-evoxc module name, so its stage splits stay inert.
- Module granularity is deliberate: `evoxc_engine.py` (~2k lines — decode, op emission, the multi-output protocol, the memo and the cache policy are one frozen compilation unit) and `dense_engine.py` (~3k lines) stay single modules, so do not split without failing-test evidence; the batch route is the one split route (`batch_engine` + `batch_programs` + `batch_knobs`, one responsibility per file).
- The `dense_spike_check.py` name is historical (`dense_adversarial_check.py` imports its `TreeSpec`/`pack_trees` builders); it is the engine-level parity + measurement harness, `case_compile_reuse` pins compile reuse at used-id-set granularity, its IR introspection reads `evoxc.trace(...)`'s `Graph.module.main.entry_block.ops`, and the `who=` / `got_path` labels name the deviating path(s).
- With `EVOGP_EVAL_MODE=dense` (or `=batch`) a population outside that route's subset silently falls back to the specialized engine, so a passing test does not prove the route ran — count `DenseUnsupported` / `BatchUnsupported` (or use `dense_integration_check.py` / `dense_adversarial_check.py`); the last dense-forced full-suite run (32-node cap) had 18 declines of 510 attempts, all supported at the 64-node cap.
- On the numpy backend `auto` never selects dense (a full-chain verdict, 0.006–0.91× of the specialized warm throughput — slow *by design*, the interpreter pays per-op overhead); the pruned default cuts dense's op count ~7× on low-id populations, so this verdict is **not re-measured under the pruned chain** (`DENSE_EVAL.md` §9.1).
- **iree sessions are fragile**: the evoxc/iree binding leaks device buffers per live executable and the failure mode is a **teardown-only** crash, not a cap on compiled executables (P=64 with 55 builds wrote a correct JSON before the nanobind traceback; a single-family 338-row session SIGSEGVs) — run iree checks staged, one family per process, `clear_cache()` between stages (`DENSE_EVAL.md` §7).
- The 12 GB sandbox `MemoryMax` kills `dense_spike_check.py --backend numpy --full` with measurements on (the `(L, P, N)` numpy graphs are host-memory heavy) — use `--skip-measure` for parity; `dense_peak_bytes` is a design bound, not an RSS predictor.
