# `src/evogp/tree/` — EvoGP tree representation, evoxc evaluation engine & pure-torch operators

## Intent
This is the **foundation layer** of EvoGP: the GP individual (`Tree`), the population (`Forest`), the multi-output variants (`CombinedTree` / `CombinedForest`), the random-generation blueprint (`GenerateDescriptor`), the pure-torch generation/splicing operators, and the `evoxc`-backed evaluation engine.
`evoxc` is the **EvoX Compiler**, the evaluation-engine dependency (checked out beside this repository, supplied on `PYTHONPATH`); the engine imports it as `evoxc` plus `from evoxc.build_cache import CompileCache, build_cached`.
Everything the rest of the library manipulates (fitness, selection, crossover, mutation, visualization) is expressed in terms of the tensor representation defined here.
This layer contains **no custom CUDA/HIP kernels and no compiled extension**: evaluation and fitness run through a per-structure evoxc JIT engine (`evoxc_engine.py`) or, on a non-numpy backend, through the **dense** whole-population evaluator (`dense_engine.py`, one compiled graph per *(shape, used-function-id set)*; the per-call strategy is `EVOGP_EVAL_MODE` and `dynamic` is accepted as an alias for `dense`), generation/mutation/crossover are vectorized plain torch (`generation.py`, `splicing.py`), and `import evogp.tree` works without any built extension.
The dense path is the **default route** under the default `auto` policy whenever a device is usable from torch: no explicit `EVOGP_EVOXC_BACKEND`/`backend=` plus `pop_size >= EVOGP_DENSE_AUTO_MIN_POP` (64) selects dense on iree, and every other case — below 64, a CPU box, or a `DenseUnsupported` decline — stays on the specialized path with backend `numpy` (measured policy and break-even call counts: `DENSE_EVAL.md` §3). Design documentation of record: `DENSE_EVAL.md` (this directory).
This package imports **nothing** from other `evogp` subpackages — it is the root of the package DAG (`algorithm/` and `problem/` are its consumers; `pipeline/` sits above both; no cycles).
`ENGINE_SPEC.md` (this directory) is the authoritative semantics spec: prefix encoding, the full op table with edge cases, evaluation order, SR fitness, the multi-output protocol, and the generation/splicing algorithms, distilled from the legacy CUDA sources at snapshot `8a487f19`.
Its Appendices keep the legacy op schemas and the old call-site map as explicitly marked historical reference.

## Representation (the schema every other module depends on)
An individual is three parallel tensors of length `max_tree_len`, batched as `[pop_size, max_tree_len]`, encoded as a **prefix (pre-order) expression**: node 0 is the root and children follow depth-first, left to right.
- `node_value` — `torch.float32` (`Forest.batch_node_value`).
- `node_type` — `torch.int16` (`Forest.batch_node_type`).
- `subtree_size` — `torch.int16` (`Forest.batch_subtree_size`); `subtree_size[i]` = number of nodes in the subtree rooted at node `i`.
Only indices `[0, subtree_size[0])` are meaningful: `subtree_size[0]` is the real tree length, and the rest of a row must never be read (the generator zeroes unused cells, but that is an implementation detail).
`batch_subtree_size[:, 0]` is used throughout the algorithm layer as "the size of tree i".
`Tree` holds the same three tensors unbatched (1-D); `Forest[i]` / `Forest[a:b]` return `Tree` / `Forest` **views** sharing storage, while `Tensor`/`ndarray` indexing (incl. LongTensor / bool mask) goes through PyTorch advanced indexing and returns **copies**.

Node encoding:
- `node_type` base values: `0 VAR`, `1 CONST`, `2 UFUNC`, `3 BFUNC`, `4 TFUNC` (`NType`); `NType.OUT_NODE = 1<<7` is OR-ed in for multi-output nodes (`TYPE_MASK = 0x7F` extracts the base).
- `node_value`: `VAR` → variable index (float-encoded int); `CONST` → the constant; function node → function id (`Func.*`, i.e. the index in `FUNCS_NAMES`).
- Multi-output out-node packing: `node_value` is the float32 bit-reinterpretation of `struct OutNodeValue { int16_t function; int16_t outIndex; }` (`outIndex = int32_bits >> 16`, `function = int32_bits & 0xFF`).
- Function table: id 0 `IF` (ternary); ids 1–13 binary (`+ - * / loose_div pow loose_pow max min < > <= >=`); ids 14–28 unary (`sin cos tan sinh cosh tanh log loose_log exp inv loose_inv neg abs sqrt loose_sqrt`); operands are consumed leftmost-child-first.
- Exact per-operator edge cases (`DIV`/`LOG`/`SQRT`/loose variants, comparisons returning ±1, `IF` branch mapping) are in `ENGINE_SPEC.md` §3.
- Multi-output semantics (`output_len > 1`): every out-node accumulates its own value into `out[outIndex]` and passes its right-most child up to the parent; tagged leaves behave like untagged ones; outputs that were never tagged are `0.0`.
- `output_len == 1` is the single-output protocol; a tree containing an OUT_NODE-tagged node is rejected at decode time with `ValueError` (the legacy kernel had undefined behavior there).

## Engine architecture (`evoxc_engine.py`)
Evaluation is a "true jit": `decode_population` (`evoxc_engine.py`) walks a population **host-side** into frozen per-tree static programs (int-only, constant subtrees folded), then `evaluate` / `sr_fitness` specialize each program into a fresh evoxc graph via `evoxc.build_cached` and run it, with the compiled executables cached per *(tree structure, input shape, backend, device, options)*.
An in-process, bounded **program→Executable memo** (`_ExecutableMemo`, `_EXECUTABLE_MEMO` — an LRU sized to `CACHE.maxsize` and keyed by `(program, n_rows, input_len, backend, device, frozen options)` via `_executable_key`) serves repeats from memory: `_executable` consults it before building, so the `build_cached` re-encode / key re-derivation is paid only on first sight of a shape; `cache_stats()` reports `memo_hits` / `memo_misses` / `memo_entries` / `memo_maxsize` and `clear_cache()` resets both tables.
- `decode_population(batch_node_value, batch_node_type, batch_subtree_size, input_len, output_len) -> Population` — pure host work (tensors read back with `.cpu()`); validates the structure and raises `ValueError` naming the row and node (replacing the kernel's UB); `TypeError` for non-tensor / non-2-D input.
- `evaluate(population, x, *, per_row, out_device=None, backend=None, iree_device_index=None)` — `per_row=True`: `(pop, input_len) → (pop, output_len)`; `per_row=False`: `(N, input_len) → (pop, N, output_len)`; returns a fresh, contiguous, `requires_grad=False` float32 tensor on `x`'s device unless `out_device` is given.
- `sr_fitness(population, inputs, labels, use_MSE=True, *, ...)` — `(pop,)` float32 POSITIVE loss `Σ_points Σ_outputs err / N` (err = diff² for MSE else |diff|; outputs summed but never divided by `output_len`; NaN/inf propagate unsanitized); the caller applies the higher-is-better negation.
- `build_specialized_runner(population_or_forest, inputs, *, per_row=False, backend=None, iree_device_index=None) -> SpecializedRunner` (`SpecializedRunner`, builder `build_specialized_runner`) — the build-once / run-many **benchmark-support** runner: build = one `decode_population` + one `_executable` per non-constant tree + the staged input upload; `.run()` executes ONLY the compiled forward pass (one `evoxc.run` per non-constant tree — no readback, no host assembly, no re-key) and returns the raw per-tree results (`None` for constant trees); `EVOGP_EVAL_MODE` is ignored. Contract: `RUNNER_HOOKS.md`.
- One module-level `@evoxc.defn _eval_step` — it must stay a module-level function (its `id()` is part of the cache key; a closure would permanently miss); statics are codec-safe int-scalars/sequences re-passed by value at `evoxc.run`.
- Cache: one shared `evoxc.CompileCache` (`evoxc_engine.CACHE`), default maxsize 4096 (`EVOGP_EVOXC_CACHE_SIZE`, read at import time), in memory only; `cache_stats()` / `clear_cache()` inspect/reset it; measured ~270–478 KiB per entry.
- Opt-in on-disk artifacts (`artifact_cache.py`, `EVOGP_EVOXC_ARTIFACT_DIR`): unset/empty (the default) leaves the build path exactly as it is (one environment read, no key, no directory, no file); set, a front-table miss first tries `artifact_cache.load` of the file named by `artifact_key`.
- The artifact key is `"<slug>-<sha256 hex>"` from `evoxc.persist.cache.compute_key` over `(KEY_FORMAT, graph name, the build's spec tuple incl. static content, backend name, "kind:index", frozen options, evoxc.__version__, iree-base-compiler version)`; the graph name is `evoxc_engine.ARTIFACT_NAME = "specialized"` (the program travels in the spec tuple), so a distinct tree structure is a distinct file.
- A loaded artifact is accepted only when `signature_matches` agrees on the tensor shapes/dtypes and the flattened static values; on any load exception or mismatch the file is deleted and the code falls through to a real `evoxc.build_cached`, whose result is then `save`d atomically (temporary file in the same directory + `os.replace`, best effort — a backend executable without a usable `save` yields `False` and no file), and the loaded executable is also stored in `_EXECUTABLE_MEMO`.
- Invalidation keeps two lifetimes: `clear_cache()` is the in-memory point (compile cache + `_EXECUTABLE_MEMO` + the dense front tables) and never deletes a file, while `clear_artifacts()` deletes every `*.evoxcart` and resets the disk counters without touching memory; `artifact_cache_stats()` reports `artifact_enabled`, `artifact_files`, `artifact_hits`, `artifact_misses`, `artifact_load_failures`, `artifact_stores`, `artifact_save_failures` (disjoint from `cache_stats()`'s 8 keys and from `dense_cache_stats()`).
- Not in the artifact key (the same blind spot `build_cached` has): the ambient `EVOXC_*` process-env compile knobs (`EVOXC_TARGET_BACKENDS`, `EVOXC_OPT_LEVEL`, `EVOXC_IREE_*`); the safety net is validation, not keying — evoxc's loader refuses an artifact whose compile targets do not fit the requested device kind (a device/target mismatch is its `BackendError`) and `signature_matches` refuses a mismatched call shape, so a stale file costs one rebuild, never a wrong number.
- Why the disk layer: one dense compile is 3.1–3.4 s at `L=32` and 6.1 s at `L=64`, independent of `pop_size`, and the specialized route pays 271–284 ms per distinct tree structure — both re-paid by every fresh process.
- Measured artifact economics (this box: AMD MI300X VF, torch 2.13.0+rocm7.1, IREE 3.11, `EVOXC_DISABLE_LOCATIONS=1`, dense+iree `Forest.SR_fitness`; "first call" = cold `SR_fitness` in a fresh process including host plan prep): `p256`/`L=32`/`i8`/`N=1024` cache OFF 3276 ms vs cache ON 3307 ms (compile + save) with a 1 056 791 B artifact, a second process's first call 160 ms (20.5× faster, 48–53 ms of it pure `evoxc.Executable.load`) and warm calls 1.1–1.3 ms on every leg; `p64`/`L=64`/`i32`/`N=1024` OFF 6234 ms vs ON 6408 ms with a 2 747 325 B (2.62 MiB) artifact, second process 174 ms (35.8×), pure load 60–62 ms, warm 1.5–1.8 ms.
- Artifact numerics and recovery: every leg matches specialized+numpy at `rtol=atol=1e-4` with identical NaN placement (`max_rel` 2.2e-7 / 2.1e-7, the pre-existing fold-vs-emit ulp class); a truncated artifact gives `artifact_load_failures` 1, a 3229 ms rebuild, a rewritten 1 056 791 B file and unchanged loss numbers; `python -m evogp.sr_test` (pop 200, `max_tree_len=64`, 100 generations, default dense+iree route) runs 15.48 s cache OFF, 15.30 s cache ON cold and 9.25 s cache ON with a warm artifact with bit-identical final population statistics.
- When it pays: when a fresh process repeats a shape signature; the specialized route writes one artifact per distinct tree structure (a random population fills the directory), so the dense route plus an occasional `clear_artifacts()` is the sensible pairing, and no pytest test covers the disk layer yet.
- Backends: default `"numpy"` (the evoxc reference interpreter, cpu, no GPU needed); IREE is opt-in via `EVOGP_EVOXC_BACKEND=iree` + `EVOGP_EVOXC_DEVICE=<visible gpu index>` + `EVOGP_EVOXC_OPT_LEVEL` (`O0`/`O1` only, on the GPU HAL — CUDA or ROCm, the kind read from torch by `_gpu_device_kind()` and passed as `evoxc.core.Device(kind, idx)`) — experimental, ~0.4–0.6 s build per structure + ~2.4–3.6 ms/run, impractical at population scale.
- Compile options carry `{"opt_level": opt_level}` plus `device=` and no `target_backends` (evoxc mis-targets when it is passed and infers the target instead), so an ambient `EVOXC_TARGET_BACKENDS` can still reach `build_cached`'s resolved options on the iree route — a process-env compile knob, to be paired with `clear_cache()` (same discipline as `EVOGP_EVOXC_OPT_LEVEL`).
- Node semantics are **correctly rounded float32**: the software transcendentals (`sin`/`cos`/`tan`/`sinh`/`cosh`/`tanh`/`log`/`loose_log`/`exp`/`pow`/`loose_pow`) are emitted as `cast_f32(op(cast_f64(v)))` (evoxc has no `sinh`/`cosh`: they are the `exp`/`-exp` composition in f64, each node value stored back as f32), since the f32 kernels are not correctly rounded (numpy f32 `exp`/`sin`/`cos`/`tan` are 1 ulp off on 5–39% of inputs). Hardware-exact ops stay f32 (`+ - * /`, `sqrt`, `abs`, `neg`, `copysign`, `min`/`max`, comparisons/select, keeping their bit-exact ±1). `sinh` keeps `x` (sign of zero included) below `|x| < 1e-4`, where the correctly rounded f32 result *is* `x` — which makes `loose_inv(sinh(-0.0)) = -1e9` come out right on both the folded and the emitted path.
- Measured numpy economics (with `EVOXC_DISABLE_LOCATIONS=1`, current f64-emission code): 30–43-node trees 9.9 ms cold build / 0.46 ms warm run (N=100) and 9.8 ms / 0.49 ms (N=1000); the `_executable` memo turns a repeated lookup from ~161–206 µs/tree into ~2.4–2.8 µs/tree (fixture64 / fixture200 / N=10000 medians), cutting warm `Forest.SR_fitness` 21.1 → 10.3 ms (pop 64), 92.8 → 57.4 ms (pop 200) and 23.2 → 15.7 ms (pop 64, N=10000); ~102 distinct builds/s, so an all-distinct pop=1000 costs ~10 s cold and ~5.4 s at 50% duplicates, against a 0.5 s all-cached floor (full record: `warm_path_findings.md` §11).
- `EVOXC_DISABLE_LOCATIONS=1` speeds tracing up ~4× on this workload and is recommended for production runs; it is not part of the cache key.
- Device policy: the engine accepts population/input tensors from any torch device and returns results on the input device unless `out_device`; the `Tree`/`Forest` wrappers still pass everything through `check_tensor` (`.to("cuda")`), so the public API keeps its CUDA-bound behavior.

## Dense one-graph evaluator (`dense_engine.py`) — wired, the iree default route
`dense_engine.py` evaluates a WHOLE population with ONE compiled evoxc graph fed with the population's node tensors as runtime data (no per-tree Python loop, no per-tree readback): host preprocessing (`prepare_dense`) encodes the `(L, P)` `opcode`/`func_id`/`const_value`/`var_index`/`child1..3` columns, the trace-time unrolled graph computes each node value with the specialized engine's own private emitters (`evoxc_engine._emit_*` — parity by construction), the per-position candidate chain is emitted **only for the population's used function ids** (`EVOGP_DENSE_PRUNE`, default ON; `=0` restores the full 28-id chain byte-for-byte), and `L = min(EVOGP_DENSE_MAX_TREE_LEN (64), max_tree_len)`.
It is wired into five call sites — `Tree.forward` / `Tree.SR_fitness` and `Forest.forward` / `Forest.batch_forward` / `Forest.SR_fitness` — each trying the dense entry point first and falling back to the specialized path ONLY on `DenseUnsupported` (silent, except the over-cap decline below; the specialized path owns the error contract for malformed trees, every other exception propagates). The public API contracts are unchanged.
- Policy (`should_use_dense` + `auto_rows_decline`): `EVOGP_EVAL_MODE` = `dense` / `specialized` / `auto` (default; `dynamic` is folded to `dense` after case-fold/trim, any other value raises `ValueError`), resolved per call (an explicit `eval_mode=` argument wins); the policy is a single resolver (`resolve_route` -> frozen `Route(use_dense, backend, fallback_backend, reason)`; `should_use_dense` and `auto_rows_decline` delegate to it) which the five call sites use to pick route AND backend explicitly; `auto` selects dense+iree only for `pop_size >= EVOGP_DENSE_AUTO_MIN_POP` (64) on a device box with no explicit backend, and specialized+numpy everywhere else (below the threshold, no device, or the `DenseUnsupported` fallback), still gated on `per_row=False` calls to at most `EVOGP_DENSE_AUTO_MAX_ROWS` (2048) rows; an explicit backend/`EVOGP_EVAL_MODE` keeps the old precedence and `evoxc_engine._resolve_backend` keeps its numpy default.
- `per_row=True` and an explicit `EVOGP_EVAL_MODE=dense` are never gated, and a decline surfaces as a normal `DenseUnsupported` fallback — so a single `Tree` (pop 1) and `CombinedForest` sub-forests follow the pop rule, and large-`N` fitness passes stay specialized. Gate rationale and the measured crossover: `DENSE_EVAL.md`.
- Pruning (`resolve_prune`): `prepare_dense` derives the used-id set (`DensePrep.used_func_ids` — the sorted unique tuple of ids 1..28, empty when no function node exists) and the set travels as a static `cfg[6]` entry, so it joins the compiled-graph cache key and a population whose set differs from the last compiled one recompiles (the set saturates quickly in a GP run); an empty set emits no candidate and every position keeps a defined value. `EVOGP_DENSE_PRUNE` accepts on/off spellings case-insensitively; anything else raises `ValueError`.
- Measured economics (firm-up: `dense_bench_findings.md` §1–4, `dense_bench_results.json`; compact in `DENSE_EVAL.md` §6): dense is pop- and rows-linear while the specialized engine is pop-linear and rows-flat (1.24–1.94 ms/tree up to N=10000), so on iree dense wins the **cold** phase by orders of magnitude (ONE 13–17 s compile per shape signature against the 13–28 per-tree compiles of P=16–32) and the **warm** phase only modestly where both sides are direct — 1.49× / 1.30× at P=16 with 64 / 1024 rows, 1.18× *slower* at 10000 rows (same-process A/B), 3.09–3.16× at N=64 cross-process; P=64/N=64 is ≈5.0–6.2×, not ≥10×, and the measured warm crossover runs from ≈3.4–6.8k rows (P=16) to ~11k (P=64), which is what the 2048-row default encodes.
- The prune lever's own in-process A/B (`device_resident_findings.md` §10): 420 → 60 candidate ops on its 4-id fixture, compile ~1.24–1.36 s → ~0.25–0.37 s, warm SR loss P=64/N=1024 ~0.30–0.57 s → ~0.044–0.048 s, near-full 18/28-id sets up to ~1.55× (`DENSE_EVAL.md` §9.1). Grid provenance traps (stale `ratio_warm_spec_over_dense` cells, earlier-grid P≥64 cells, the anchored-law P=1000 specialized side) are catalogued in `dense_bench_findings.md` — check a cell's `status`/`source` before quoting it.
- Supported subset: single-output populations (`output_len == 1`) with every tree within the 64-node trace cap; an over-cap population emits a deduped once-per-process `RuntimeWarning` (device backends only) and falls back. Knobs: `EVOGP_DENSE_BUDGET_MB` (2048) bounds the chunked `(P_chunk, N_chunk)` execution, `EVOGP_DENSE_UPDATE_MODE` = `grow` (default) / `concat` / `scatter` (`scatter` is unsafe on iree unless `EVOGP_DENSE_ALLOW_UNSAFE_SCATTER=1`).
- Cache: `dense_engine.DENSE_CACHE` IS `evoxc_engine.CACHE`; the key covers the compiled body identity + `(L, P, N, input_len, per_row, update_mode, used_func_ids[, use_mse for the loss variant], backend, device, options)` — ONE miss per (shape, used-id set) against pop_size misses on the specialized path — and the module-level `_dense_step` / `_dense_loss_step` must stay module-level (`id()` is part of the key).
- Front tables (`dense_memo.py`, `DenseMemo` LRUs whose `dense_memo.clear` is registered with `evoxc_engine._register_cache_reset`): `DENSE_EXECUTABLE_MEMO` (`dense_exec_*`, sized like `DENSE_CACHE`) sits in front of `build_cached` so a repeated build is one dict lookup, `DENSE_PLAN_MEMO` (`dense_plan_*`) holds the `DenseEntry` — `DensePlan`, executable and staged payloads — of an unchanged population, and `DENSE_INPUT_MEMO` (`dense_input_*`) holds the host copy of an unchanged `inputs`/`labels`.
- `dense_cache_stats()` returns exactly those 12 keys and is deliberately not folded into `cache_stats()`; `evoxc_engine.clear_cache()` is the single invalidation point of all three tables.
- Front-table keys are identity tokens (`dense_memo.token` = `data_ptr`, shape, dtype, device and `_version`, so an in-place torch write is a miss by construction); a plan entry also keys on the RESOLVED plan parameters (cap, budget, update mode, prune, variant, `use_mse`, backend, device, options) and pins the population storages against address recycling (`dense_memo.pin`), a plan entry pins `x`/`labels` while its payloads are held (`payload_key`/`payload_pins`), and a non-torch `x`/`labels` or population is simply not memoized.
- `EVOGP_DENSE_HOST_MEMO` (default 16, `0` disables both tables, read at import time like `EVOGP_EVOXC_CACHE_SIZE`) sizes the plan and input tables; they are deliberately small because a plan entry holds a whole decoded population plus its device payloads and a training loop presents a new population every generation.
- Disk artifacts for this route: `build_dense` follows the same memo-miss → artifact load → `build_cached` → save chain, with graph names from `DENSE_ARTIFACT_NAMES` (`dense:value` / `dense:loss`) and the plan's whole spec tuple in the key — one artifact per shape and used-id set — and a loaded executable is stored in `DENSE_EXECUTABLE_MEMO`.
- The result contracts mirror the specialized engine (fresh, contiguous, `requires_grad=False` float32); the dense SR loss is computed **in-graph** (`_dense_loss_step`; the static `use_mse` selector lives in `cfg[7]`) so the loss readback is `(p_chunk,)`-scale — only the `/ N` divide and the `(pop_size,)` assembly stay host-side — while the specialized `sr_fitness` reduces its host rows in place with numpy; same formula, differing only in float32 reduction order by ~1e-7 relative on the fixtures.
- Internals: the readback-free chunk seam is `_iter_plan_chunks`, `run_plan` / `run_loss_plan` add the readback via `_to_host`, `device_resident=True` refuses the numpy backend and chunked plans with `DenseUnsupported`, and `plan_dense` (`variant=`, `use_mse=`, `prune=`) exposes `DensePlan`/`describe_plan` with `prune`, `used_func_ids` and `candidate_ops`.
- The benchmark-support counterpart is `build_dense_runner(population_or_forest, inputs, *, per_row=False, backend=None, iree_device_index=None, max_tree_len=None, budget_mb=None, update_mode=None) -> DenseRunner` (`DenseRunner`, builder `build_dense_runner`): one compile + the staged columns at build; `.run()` = ONE `evoxc.run` returning the raw result (device-resident on iree; the zero-copy host view on numpy); chunked plans are refused at build with `DenseUnsupported`.
Full detail (scheme, chunking model, knobs, tolerance classes, measured economics, evoxc/iree constraints, future work) is in `DENSE_EVAL.md` — keep it there, not here.

## Environment knobs (read per call unless noted)
Every knob below is read by `evoxc_engine.py`, `dense_engine.py` or `artifact_cache.py`; an unusable value raises `ValueError` naming the variable (the one exception is `EVOGP_DENSE_ALLOW_UNSAFE_SCATTER`, where anything other than unset/`0` counts as set).
- `EVOGP_EVAL_MODE` (`auto`) — the master route switch: `dense` (alias `dynamic`) / `specialized` / `auto`; `auto` picks dense+iree from `EVOGP_DENSE_AUTO_MIN_POP` up on a device box.
- `EVOGP_DENSE_AUTO_MIN_POP` (`64`) — `auto`'s population threshold for dense; the call-count break-even knob.
- `EVOGP_DENSE_AUTO_MAX_ROWS` (`2048`) — `auto`'s data-row ceiling for `per_row=False` calls; above it the attempt declines to the specialized engine.
- `EVOGP_DENSE_MAX_TREE_LEN` (`64`) — the trace cap `L = min(cap, row_len)`; a longer tree declines (with the once-per-process warning on device backends).
- `EVOGP_DENSE_BUDGET_MB` (`2048`) — the chunking memory budget of `_chunk_shape`.
- `EVOGP_DENSE_UPDATE_MODE` (`grow`) — `grow` / `concat` / `scatter` value-buffer strategy.
- `EVOGP_DENSE_ALLOW_UNSAFE_SCATTER` (unset) — opt-in for `scatter` on iree, where evoxc's scatter mutates its input.
- `EVOGP_DENSE_PRUNE` (on) — emit the candidate chain for the population's used function ids only; `0`/`false`/`no`/`off` restores the full 28-id chain.
- `EVOGP_DENSE_HOST_MEMO` (`16`, import time) — entries of the dense plan and input front tables; `0` disables both.
- `EVOGP_EVOXC_CACHE_SIZE` (`4096`, import time) — `maxsize` of the shared `evoxc.CompileCache` and of the two executable front tables.
- `EVOGP_EVOXC_BACKEND` (`numpy` inside the engine; the route policy passes `iree`) — `numpy` / `iree`.
- `EVOGP_EVOXC_DEVICE` (`0`) — visible GPU index of the iree route.
- `EVOGP_EVOXC_OPT_LEVEL` (`O1`) — iree opt level; only `O0` / `O1` are accepted, and `O1` is the measured optimum.
- `EVOGP_EVOXC_ARTIFACT_DIR` (unset = off) — enables the on-disk executable artifacts; see the artifact bullets above.
- External, not ours: `EVOXC_DISABLE_LOCATIONS=1` speeds evoxc tracing up ~4× (recommended for real runs, not part of any cache key), and an ambient `EVOXC_TARGET_BACKENDS` / `EVOXC_OPT_LEVEL` / `EVOXC_IREE_*` can enter `build_cached`'s resolved options, so pair a change with `clear_cache()` (and with `clear_artifacts()` for the disk layer).
## API Surface
`evogp.tree` exports: `GenerateDescriptor`, `Tree`, `Forest`, `CombinedForest`, `CombinedTree`, `MAX_STACK`, `randint`, `NType`.

### `tree.py` — `Tree(input_len, output_len, node_value, node_type, subtree_size)`
- `Tree.random_generate(descriptor)` delegates to `Forest.random_generate(pop_size=1)[0]`; `to_forest()` wraps a single tree as a `Forest`.
- `forward(x)` — 1-D `(input_len,)` → `(output_len,)`; 2-D `(batch, input_len)` → `(batch, output_len)`; evaluated through the evoxc engine (dense attempt first, `DenseUnsupported` → specialized path).
- `SR_fitness(inputs, labels, use_MSE=True, execute_mode="auto")` → `(1,)` positive loss.
- `to_sympy_expr(symbol_names=None)` — sympy expr for `output_len == 1`, a list of exprs for `output_len > 1`; comparisons render as the engine's ±1 (`Piecewise((1, cond), (-1, True))`), loose ops follow the engine's zero-clamp conventions, and every leaf is sympified (a constant-only tree returns a sympy `Float`).
- `to_infix()` (single-output; warns and returns one string for multi-output), `to_png(fname)`, `__repr__` (== sympy repr).
- `__python_forward` — name-mangled, debug-only, full-semantics pure-Python reference evaluator (single-output) used as the in-repo cross-check oracle; `__assert_valid` is likewise debug-only.

### `forest.py` — `Forest(input_len, output_len, batch_node_value, batch_node_type, batch_subtree_size)`
- Public attributes: `input_len`, `output_len`, `pop_size`, `max_tree_len`, `batch_node_value`, `batch_node_type`, `batch_subtree_size`; no `.device` and no `.trees`; the three tensors must be exactly `(pop_size, max_tree_len)`.
- `Forest.random_generate(pop_size, descriptor)` (static) → pure-torch vectorized generation on the descriptor tensors' device (cuda in practice); `zero_generate(pop_size, max_tree_len, input_len, output_len)` (static) → degenerate all-`CONST`-0 trees on cuda.
- `forward(x)` — `(pop_size, input_len)` → `(pop_size, output_len)` (asserts `x.shape[0] == pop_size`); `batch_forward(x)` — `(N, input_len)` → `(pop_size, N, output_len)`; both try the dense entry point first (`per_row=True` / `False`) and fall back to the specialized engine on `DenseUnsupported`.
- `mutate(replace_pos, new_sub_forest)` → new `Forest`; `crossover(left_indices, right_indices, left_pos, right_pos)` → new `Forest` of size `len(left_indices)`; both pure-torch splices with the legacy semantics (see `splicing.py`).
- `SR_fitness(inputs, labels, use_MSE=True, execute_mode="auto")` → fresh `(pop_size,)` float32 positive loss (writable; the pipeline mutates it in place); dense attempt first, specialized fallback.
- Dunders: `__getitem__` / `__setitem__` (branch rules below), `__iter__`/`__next__` (not reentrant: stores `iter_index` on the instance), `__len__`, `__add__`/`__radd__` (concat along dim 0; matching `input_len`/`output_len`), `__str__`/`__repr__` (renders every individual via sympy — slow), `__getstate__`/`__setstate__` (pickle via CPU numpy; restores to cuda).
- `__getitem__` (`forest.py:372-394`) branch rule is exactly `isinstance(index, int) or index.shape == ()`: an `int` / 0-dim `Tensor` / 0-dim numpy scalar returns a `Tree` **view** (all three tensors alias the population row), a `slice` returns a `Forest` **view**, and ANY other `Tensor`/`ndarray` (a 1-element 1-D index included) goes through advanced indexing and returns a **copied** `Forest` — a 1-element index therefore yields a `Forest` of pop 1, NOT a `Tree`; python lists raise `Exception`, non-integral tensor dtypes raise `IndexError`.
- A 0-dim **CUDA** tensor index is a view but NOT free (PyTorch's select does an internal `tensor.item<int64_t>()`, a blocking D2H: measured 41.4 µs vs 7.8 µs for a Python int — see Known Issues); a 0-dim **CPU** index has identical view semantics with no sync; a 1-element 1-D CUDA index does not sync but is a copy returning a `Forest`.
- `__setitem__` (`forest.py:396-417`) matches only `isinstance(index, int)` for the `Tree` path, so `forest[0-dim tensor] = tree` takes the `Forest` branch and raises `AssertionError`; `forest[tensor_index] = forest_of_same_pop` writes in place through advanced-index assignment (the mutation operators rely on the copy-in/copy-out pattern `forest_to_mutate = forest[idx]` → mutate → `forest[idx] = ...`).

### `descriptor.py` — `GenerateDescriptor(max_tree_len, input_len, output_len, const_prob=0.5, out_prob=0.5, depth2leaf_probs=None, roulette_funcs=None, const_samples=None, using_funcs=None, max_layer_cnt=None, layer_leaf_prob=0.2, const_range=None, sample_cnt=None)`
- Validates its inputs, derives `depth2leaf_probs` from `using_funcs`/`max_layer_cnt` when omitted (`check_tree_length` asserts `max_tree_len` fits the worst-case complete tree), and materializes the cuda tensors the engine and the algorithm-layer operators share (`depth2leaf_probs`, the `roulette_*` cdfs, `const_samples`).
- `update(**kwargs)` returns a new descriptor (see Known Issues for its two gotchas).

### `generation.py` — `generate_population(pop_size, descriptor, device=None)`

Two layouts share one entry point, selected by `PADDED_SLOT_BUDGET` (1024 cells): the *padded* hot path grows the population as a complete `max_arity`-ary tree of `levels` depth levels (arity is the max arity of the functions the descriptor can actually draw, so a binary-only descriptor needs 7 slots instead of 2731), decides every padded slot in one batched draw, computes the level-arity masks with static `parent = j // arity`, `rank = j % arity` maps from a cached `_PaddedLayout`, and scatters the slots into the prefix rows; the *compact* fallback is the previous level-by-level breadth-first walk (kept for descriptors whose padded layout would exceed the budget).
The padded path needs exactly one host sync (`sizes_all.max()` against `max_tree_len`, which raises the documented `RuntimeError` on overflow) and 66 kernel launches for a 13-row batch (the compact path needed 501); `torch.manual_seed` still reproduces a population exactly, and the tree-size/composition distributions match the compact path (measured on the smoke, uci-like and deep descriptors), so the RNG stream differs but its distribution does not.
`_descriptor_plan` memoizes `(max_arity, levels)` on the descriptor object (`_evogp_generation_plan`, keyed by the data_ptr/_version of `roulette_funcs` and `depth2leaf_probs`), and `_LAYOUT_CACHE`/`_FUNC_TABLE_CACHE` cache the static layouts and the function/arity tables per device.
Returns `(batch_node_value float32, batch_node_type int16, batch_subtree_size int16)`.
Vectorized level-wise torch that reproduces the descriptor-driven decision structure distribution-equivalently; draws from torch's global RNG, so `torch.manual_seed` / `torch.cuda.manual_seed` make generation reproducible (not bit-identical to the legacy taus88 stream); a length overflow raises `RuntimeError`.

### `splicing.py` — `mutate(...)` / `crossover(...)`

Both splices are dispatch-bound (~45 tiny kernels over a `[rows, max_tree_len]` window), so the module caches the `[1, max_tree_len]` column-index row per (length, device) in `_cols` and keeps the validation to one host round trip (`((0 <= left_idx) & (left_idx < pop_size)).all()` instead of two `bool(...)` calls); the donor-block/tail index maps and the ancestor size fix-up are unchanged.
The redundant `lpos` bounds checks in `crossover`'s `extra_valid` are gone because `_splice` already validates the target position against the left parent's real length; the donor-side `rpos` bounds and the out-of-range `right_indices` rule are still enforced here.
Pure-torch scalar-free splices: `_splice` updates ancestor `subtree_size` cells with the closed form `(j < pos) & (j + size[j] > pos)`, copies the donor subtree verbatim and shifts the tail; an invalid position or overflow copies the row UNCHANGED (silent, matching the legacy op); index tensors may be int8/16/32/64; out-of-range `left_indices` → `ValueError`; `pop_size_new == 0` → `ValueError`.

### `combined_forest.py` / `combined_tree.py` — the `data_info`-driven multi-output model
`CombinedForest(forests, data_info)` with `data_info = {out_name: [input_name, ...]}`; `CombinedForest.random_generate(pop_size, data_info, descriptors)` (one descriptor per sub-forest, each with `output_len == 1`).
The input-dict contract is single-sourced in `combined_forest.normalize_inputs` (its docstring is the contract of record): every required name must hold a scalar/0-D number, a 1-D `(K,)` tensor or a 2-D `(K, 1)` tensor; all names must agree on `K`; values are never broadcast; extra `x` keys are ignored completely (so e.g. `CustomLoss` can pass its `existing_data` including `"target"`); wrong shapes/keys raise `ValueError` naming the offending key, its shape and the sub-forest; Python lists and `ndim >= 1` numpy arrays are rejected.
`CombinedForest.forward(dict) → {out_name: (pop_size, out_len_sub)}` is single-point only (a `K > 1` value raises and points to `batch_forward`); `CombinedForest.batch_forward(dict) → {out_name: (pop_size, K, out_len_sub)}`.
`CombinedTree(trees, data_info)` exposes each sub-tree by output name (`best.A.to_sympy_expr()`); its `forward` routes on `K`: `{out_name: (out_len_sub,)}` for `K == 1` and `{out_name: (K, out_len_sub)}` for `K > 1` (the one-individual forest's pop dim is stripped).
Neither defines `SR_fitness`/`to_sympy_expr`, and neither has a `share_input` attribute; the dict input protocol is the only accepted form.

### Benchmark runner hooks (`dense_engine.build_dense_runner` / `evoxc_engine.build_specialized_runner`)
Benchmark-support APIs (no public route behavior change; `EVOGP_EVAL_MODE` ignored; chunked dense plans refused at build with `DenseUnsupported`): signatures in the two sections above; `.run()` executes only the compiled forward pass — dense returns the raw `(pop_size, n_rows)` result and specialized a `pop_size`-tuple of raw per-tree results (`None` for constant trees) — with no readback, no re-plan, no re-key and no host assembly beyond what is baked in-graph. Contract, what is timed, the build-vs-run split and per-backend semantics: `RUNNER_HOOKS.md`; evidence battery: `runner_check.py`.

### `execute_mode` mapping
`Tree.SR_fitness`, `Forest.SR_fitness` (and the problem layer) accept the five strings `"torch"`, `"hybrid parallel"`, `"data parallel"`, `"tree parallel"`, `"auto"`.
The legacy `kernel_type` dispatch is gone and **all five map to the same evoxc engine path** — the string no longer changes behavior (it is kept for API compatibility).

## Constraints
- This layer must stay free of custom kernels and of any compiled-extension import; the legacy extension name must not reappear anywhere in this directory (the old ops are kept only as historical schemas in `ENGINE_SPEC.md` Appendix A).
- `MAX_STACK = 1024`, `MAX_FULL_DEPTH = 10`, `NType`, `Func` are defined only in `utils.py` and are the single source of truth; function ids are positional across `Func`, `FUNCS_NAMES`, `FUNCS_DISPLAY`, `SYMPY_MAP`, so adding/renaming an operator means touching all four.
- `max_tree_len <= MAX_STACK` (asserted in `GenerateDescriptor`); `check_tree_length` asserts `max_tree_len` fits the worst-case tree of `using_funcs`/`max_layer_cnt`; `using_funcs` entries must be exact `FUNCS_NAMES` strings.
- Import-cycle rule: module-level imports go one way only (`utils` → `descriptor` → `forest` → `combined_forest` → `combined_tree`); `tree.py` imports `forest` inside its methods and `combined_tree.py` imports `combined_forest` inside its methods.
- `tree.py` / `forest.py` use `from .utils import *`, so every public name in `utils.py` leaks into their namespaces — avoid adding casual public names.
- Fitness contract: the engine returns fresh writable tensors; the repo-wide convention is `(pop_size,)` float32 MAXIMIZED and mutated in place by the pipeline (NaN → -inf).
- Several helpers still hard-code the `"cuda"` device string (descriptor tensors, `zero_generate`, `check_tensor`, `randint`, `Forest.__setstate__`); `Forest`/`Tree` themselves are device-agnostic — `__init__` stores the three tensors by reference and the dunders never call `check_tensor`/`.to()`/`.cpu()`/`.item()`, so a `Forest` lives on whatever device its tensors were built on (only the x/label/index arguments of `forward`/`batch_forward`/`SR_fitness`/`mutate`/`crossover` are forced to cuda); the same string also selects AMD GPUs under ROCm.
- `check_tensor` raises `TypeError` for non-tensors and otherwise returns a `"cuda"` tensor with `requires_grad=False` (kept deliberately: `../problem/brax_problem.py` relies on it); a tensor that already lives on cuda without an autograd graph is returned as-is (same object, no `to`/`detach`/`requires_grad_` dispatch), because the operators call it several times per generation.
- `randint` defaults to `device="cuda"`, `dtype=torch.int32` and samples via `low + torch.rand(...) * (high - low)` truncated toward zero; it costs ~2x `torch.randint` but is only called once per crossover, so it is left alone (a stream-changing swap was measured to be worth < 0.02 ms/generation).
- Frozen, oracle-validated modules: `generation.py`, `splicing.py`, `evoxc_engine.py` — code changes need failing-test evidence and a separate commit; docstring/comment edits are free.
- `dense_engine.py` is frozen like `evoxc_engine.py` for code changes (failing-test evidence + a separate commit); docstring/comment edits are free.
- The artifact layer must stay a pure accelerator: with `EVOGP_EVOXC_ARTIFACT_DIR` unset both build sites behave exactly as before, `load`/`save` never raise, and an underivable key returns `None` (the build proceeds) instead of failing the call.
- Any change to the artifact key derivation (a new component, a different graph-name spelling, a changed spec tuple) requires bumping `artifact_cache.KEY_FORMAT`, otherwise an old file can be mistaken for a new one; the layer is a cache, so a stale file costs one rebuild but a colliding key would serve a wrong executable.
- The disk layer and the in-memory tables never invalidate each other: `clear_artifacts()` leaves `CACHE` / `_EXECUTABLE_MEMO` / the dense front tables alone, and `clear_cache()` never deletes a file.
- `ENGINE_SPEC.md` sections 1–7 are the semantics of record; the documented deviations from the legacy kernels are listed in `evoxc_engine.py`'s module docstring ('Documented deviations from the old kernels': validation instead of UB, no fast-math, torch-RNG generation, composed `sinh`/`cosh` and `copysign`, constant trees never compiled, host-side numpy fitness reduction, int tolerance rules), while `ENGINE_SPEC.md` §12 'Validation notes' carries the validation evidence and §13 records the dense path as an implementation route only.
- The dense evaluator is an evaluation *route*, not a second semantics: it computes node values through the same private emitters as the specialized engine (`evoxc_engine._emit_*`) and must never grow its own op table. Any element-wise divergence from the specialized path is a bug — `src/evogp/tests/reference_eval.py` is the oracle, `DENSE_EVAL.md` §5 lists the known (non-dense-specific) iree-compile classes.
- The runner builders are benchmark-support APIs: no public route behavior change, `EVOGP_EVAL_MODE` ignored, chunked dense plans refused at build.

## Design Decisions
- **Host decode + per-structure evoxc graph** (instead of one generic interpreter graph): specialization makes re-evaluation of a structure a cache hit and keeps the graph free of dynamic dispatch; statics are re-passed by value so the cache key fully determines the executable. An in-process program→Executable memo on top removes the remaining per-call re-key cost without changing the cache.
- **numpy backend default, IREE opt-in**: the per-structure IREE compile (~0.4–0.6 s) dominates while numpy builds in ms and runs in ~1 ms; IREE stays first-class for callers who need GPU execution and accept the compile economics.
- **Plain-torch operators** replace the kernels because they are portable and fast enough at these sizes; they keep the legacy splice semantics, including the silent no-op on invalid input.
- **Multi-output implemented in the engine** (oracle-verified for `output_len` 2/3) instead of raising; single-output trees with OUT_NODE tags raise `ValueError` instead of the legacy UB.
- Descriptors remain the shared source of randomness: `generation.py` reproduces the kernel's decision structure distribution-equivalently, while the algorithm-layer mutation operators keep consuming the descriptor's roulette cdfs.

## Known Issues / Notes for Agents
- The cache is per *(structure, shape)*: a fresh random population is a miss per individual (pop=1000 ≈ 5.5 s cold), constant trees never compile, duplicate structures hit; changing batch size or tree shape re-compiles — keep shapes stable in hot loops.
- **Indexing with a 0-dim CUDA tensor synchronizes**: `forest[cuda_0dim_index]` returns the same `Tree` view as an `int`, but PyTorch's select does an implicit `.item()` D2H readback (41.4 µs vs 7.8 µs for a Python int, torch 2.6.0+cu124 / RTX A6000; it also stalls behind queued stream work), so a plan that keeps a `torch.argmax` output as a device 0-dim index pays a blocking sync per indexed access; a `bool()`/`if` on a 0-dim CUDA bool (e.g. `if best_fitness > self.best_fitness:`) is likewise one sync per evaluation.
- Per-call GPU cost structure (the optimization target, specialized route): `evaluate` copies the three population tensors to host once at decode (`_as_numpy`) and `inputs`/`labels` once per call (the specialized route has no input front table), then issues one `_executable` memo lookup (~2.4 µs) + one `evoxc.run` per non-constant tree (`_evaluate_rows`, `_run_tree`) with NO cross-tree batching (dedup happens only inside `evoxc.CompileCache`), and one device upload of the assembled result (`evaluate`); `sr_fitness` skips that upload and reduces the host rows in place with numpy (`np.subtract(..., out=rows)`, not torch, so the interpreter is not starved by torch's intra-op thread pool), so only the `(pop_size,)` loss reaches the input device. Under IREE every tree run also ends with a host readback, so one pop=N fitness pass costs N device invocations + N synchronizations.
- Host→device input memo (`_run_tree`'s `prepared`, device backends only): `evoxc.from_numpy` is a zero-copy host wrap, so the upload is `Tensor.to(device)`, and that upload is memoized per distinct input block, keyed by the caller — `per_row=False` uploads the shared `(N, input_len)` `x` ONCE per `evaluate` call, `per_row=True` keys by tree index and uploads each tree's own `(1, input_len)` row (tree `i` must see row `i`; the numpy backend consumes the host array directly and never uploads). `case_engine_per_row_iree_bug` in `dense_spike_check.py` pins both the numbers and the upload counts.
- evoxc per-call overheads on that path are small on both sides: `_executable` serves repeats from the in-process memo (~2.4–2.8 µs/tree vs ~161–206 µs for a fresh lookup), `CompileCache` carries a multi-slot content-fingerprint memo (a repeated program's key is a ~17–25 µs replay instead of a full codec+sha256 walk: ~32 µs per call in a steady-state K=50 cycle of 60-token programs against ~660 µs), and `evoxc.run` has a per-executable static-validation fast path (60-token program 303 → 67–71 µs, 170 tokens 758 → 87–96 µs) though it still re-passes and re-validates the statics every call. `evoxc` has no function-entry caching (no `jit` / `JitFunction` / `BoundJit`), so `_EXECUTABLE_MEMO` is the only pre-binding layer and `evoxc.run` is the cheapest supported call.
- **evoxc execution-model facts** (for a no-readback / no-rekey redesign): a `build_cached` hit returns the SAME `Executable`, yet it still re-derives the key per call, so holding the executable and calling `evoxc.run` directly — or `exe.backend_executable.run(flat_tensors)` to also skip the wrapper's structure walk — is the cheapest loop, and `_ExecutableMemo` is that value-keyed table (~2.4 µs/tree on the fixtures). There is no `Executable.close()/release()` and no zero-copy device export (`core.Tensor.__dlpack__` raises for payload-backed tensors; `.to(cpu)` + `.numpy()` is the only readback), so an evoxc device result cannot reach torch without a D2H. No GPU backend runs without per-graph AOT compilation (numpy = CPU interpreter, iree/xla compile per graph, tvm is CPU-only), there is no multi-program/"super graph" execution, and the runtime `Tensor` has no `__getitem__` (only graph-time `SymbolicTensor` slicing or the static-index `getitem` op, which would bake the index into the cache key), so a device-resident `(pop, input_len)` block cannot be split per tree at run time — `per_row=True` uploads one row per tree. Details: the `evoxc` repo CONTEXT.
- Dense-route host crossings per call (steady state = the same `Forest` and the same dataset, which is what a training loop and every benchmark repeat): the loss path declines from `inputs.shape` BEFORE any conversion, serves the `inputs`/`labels` host copies from `DENSE_INPUT_MEMO` (one D2H per distinct tensor, none afterwards), reads the three population tensors only on a `DENSE_PLAN_MEMO` miss (3 D2H), re-uses the staged payloads of the entry by reference while `x`/`labels` stay put, and reads back ONE `(p_chunk,)` loss per chunk, so there is NO full-prediction round trip on that path.
- A dense memo miss costs what the pre-front-table path paid on every call: 3 population D2H + the whole vectorized decode/validate pass, the `build_cached` key derivation, and the 7 `(L, p_chunk)` column payloads plus the `x`/`labels`/keep-mask payloads prepared and uploaded per `p0` / `n0`.
- The **value** path also serves `x` from `DENSE_INPUT_MEMO` and the plan from `DENSE_PLAN_MEMO`, but still assembles the full `(P, N, 1)` host prediction and uploads it once (blocked on evoxc-side zero-copy work; `evoxc.from_dlpack` is host-memory v1 only), so on device backends `Forest.forward`/`batch_forward` stay readback-bound.
- `sr_fitness_dense` never calls `decode_population` (its host prep is `prepare_dense`) and its compiled graph is a memo/cache hit through `DENSE_EXECUTABLE_MEMO`; the measured warm `Forest.SR_fitness` at `L=32`/`i8`/`N=1024` is p64 2616 → 988 µs, p256 3122 → 1137 µs and p1000 5655 → 1926 µs before → after the front tables, with `evoxc.run` now 67–80 % of the call.
- Same tables on the value path: `forward` at p256/`L=32`/`i32` 2502 → 675 µs and `batch_forward` 3611 → 1949 µs.
- Crossing inventory before the front tables (still the right accounting for a miss): `device_resident_findings.md` §2.
- `EVOGP_EVOXC_CACHE_SIZE` (module-level `CACHE = CompileCache(...)`) and `EVOGP_DENSE_HOST_MEMO` (the plan/input tables) are read at import time, while `EVOGP_EVOXC_BACKEND` / `EVOGP_EVOXC_DEVICE` / `EVOGP_EVOXC_OPT_LEVEL` and every `EVOGP_DENSE_*` / `EVOGP_EVAL_MODE` policy knob are read per call; set the import-time ones before the first import (full list: "Environment knobs").
- IREE is wired but experimental: not numerically verified for every shape; `O0`/`O1` are the only supported levels, on the GPU HAL (CUDA or ROCm — `_gpu_device_kind()` reads the kind from torch, and `Device("cuda", ...)` fails to load on a ROCm box).
- **IREE device numerics (both paths, not dense-specific)**: iree-compile's own lowering of the verbatim StableHLO drops the C99 `pow(x, ±0) = 1` case when the exponent is a runtime value (`pow(0,0)` / `pow(NaN,0)` → NaN) and computes the emitted f32 `sqrt` 1 ulp low for some inputs (e.g. `0.47954902f`); both classes vanish on numpy, are bit-identical between the dense and the specialized path whenever the specialized path emits the op, and are reported (not chased) by the batteries — full detail in `DENSE_EVAL.md` §5.
- Sympy rendering is a display artifact with documented edge gaps: `LOOSE_POW(0,0)` renders `1` (engine `0`), `DIV`/`INV` at a literal zero render sympy `zoo` while the engine computes NaN, `LOG(0)` renders `zoo` vs −inf, `MAX`/`MIN` with a NaN literal raise, and a negative-zero divisor loses its sign in loose ops (sympy has no −0.0).
- `repr(Forest)` / `str(forest)` build a sympy expr per individual (CPU sync, slow); `__iter__` is not reentrant; `Forest[int]`/`[slice]` views vs `Tensor`-indexing copies — writes through copies are lost.
- `GenerateDescriptor.update(**kwargs)` returns a new descriptor but also mutates the receiver's captured params (kwargs are sticky) and re-draws `const_samples` from `const_range` when the original had `const_samples=None`.
- `randint` truncates toward zero after `torch.rand` (biased for negative `low`); `dict2prob` is torch-only now and validates names against `FUNCS_NAMES`.
- `Tree.to_infix` warns and returns a single string when `output_len != 1`; `__python_forward` / `__assert_valid` are debug-only and not on any production path.
- The engine is correctness-first: the numpy backend does one `evoxc.run` per tree per call — profile before assuming throughput.
- For raw timing use the committed benchmark harness `test/benchmark/bench_gp.py` driven by the committed protocols (`test/benchmark/r4/run_e2e.sh` type-1 end-to-end `problem.evaluate(forest)`, `test/benchmark/r4/run_pure.sh` type-2 pure forward; the R2 protocol `run_all.sh` is retained). `src/evogp/tests/perf_probe.py` and the engine-side build/run economics probe under `test/` model evoxc build/run economics but never import `evogp`, so they cover no decode/input-copy/output-assembly cost. For the warm-path stage split of the specialized engine (decode, one `_run_tree`, the `_executable` lookup, whole-population `evaluate`, `sr_fitness`) use `warm_path_probe.py` (`warm_path_findings.md`), and for the **compiled forward pass itself** the runner APIs (`RUNNER_HOOKS.md`, evidence `runner_check.py`); `dense_crossover_probe.py` re-measures the `auto` pop/rows gates. Note for the benchmark node: `test/benchmark/stage_probe.py` wraps the engine's `build_cached`, so its build-hit column collapses toward 0 — its R2-protocol stage splits are NOT comparable to `warm_path_findings.md` §4 as-is, and it still targets the pre-evoxc engine module name, so its stages stay inert until that probe is retargeted (`warm_path_findings.md` §2).
- `evoxc_engine.py` (~2k lines) is intentionally a single module: decode, op emission, the multi-output protocol, the memo and the cache policy form one compilation unit and were frozen together after oracle validation — do not split without failing-test evidence.
- The dense-layer dev scripts are intentionally large single coherent tools and are NOT imported by the library (`dense_engine.py` ~2.2k lines, `dense_adversarial_check.py` ~1.9k, `dense_bench.py` ~1.9k, `dense_spike_check.py` ~1.3k, `device_resident_check.py` ~0.9k, `dense_integration_check.py` ~0.8k, plus the small check CLIs `runner_check.py` / `executable_memo_check.py` / `dense_crossover_probe.py`); don't split them for tidiness, a split needs a concrete maintenance reason (they are run as CLIs).
- The `dense_spike_check.py` name is historical (kept because `dense_adversarial_check.py` imports its `TreeSpec`/`pack_trees` builders): it is the **current** engine-level parity + measurement harness. Its `case_compile_reuse` pins the compile-reuse contract at used-id-set granularity (same values always reuse; a different population rebuilds iff its used set differs), and its IR introspection reads `evoxc.trace(...)`'s `Graph.module.main.entry_block.ops`; the `who=` / `got_path` labels on the adversarial battery's bit-diff lines name the deviating path(s) and where the printed value came from.
- With `EVOGP_EVAL_MODE=dense` a population outside the dense subset (multi-output `output_len > 1`, a tree longer than the 64-node trace cap, any structural doubt) silently falls back to the specialized engine, so a passing test does not by itself prove the dense path ran — count `DenseUnsupported` (or use `dense_integration_check.py` / `dense_adversarial_check.py`). The last recorded full-suite dense-forced run (32-node cap) had 18 declines of 510 attempts (15 multi-output populations + 3 over-cap trees — all now supported at the 64-node cap).
- On the numpy backend the default `auto` policy never selects dense (a full-chain verdict, 0.006–0.91× of the specialized warm throughput — slow *by design*, the interpreter pays per-op overhead); the pruned default cuts dense's own op count ~7× on low-id populations, so this verdict is **not re-measured under the pruned chain** (`DENSE_EVAL.md` §9.1).
- **Tolerance classes**: numpy dense is bit-exact against the specialized engine (0 non-bit-exact finite values, 192/192 adversarial checks; the prune lever adds prune-vs-full-chain bit-exactness on the value and both loss variants — `device_resident_check.py` 104/104 incl. its 25-check prune stage); on iree the only dense-vs-specialized difference is the *engine's* fold-vs-emit ≈1 ulp (`max_rel` up to 3.3e-7, constant subtrees folded host-side with numpy f64 vs emitted with iree f64). The batteries require exact NaN/±inf masks and zero signs and `rtol=atol=1e-4` on finite values; bit-exactness is reported, not required.
- **iree sessions are fragile**: the evoxc/iree binding leaks device buffers per live executable and the recorded failure mode is a **teardown-only** crash, not a cap on the number of compiled executables — P=64 with 55 builds wrote a correct JSON and only then hit the nanobind teardown traceback, P=200 with 170 builds completed cleanly, while a single-family 338-row `dense_adversarial_check` session SIGSEGVs. Run iree checks staged — one family per fresh process (`--only <family>`), `CUDA_VISIBLE_DEVICES` + `--gpu <visible index>`, `evoxc_engine.clear_cache()` between stages; `EVOGP_EVAL_MODE=auto` + iree is the only default configuration that exercises the dense path.
- The 12 GB sandbox `MemoryMax` kills `dense_spike_check.py --backend numpy --full` when measurements are on (the `(L, P, N)` numpy graphs are host-memory heavy) — use `--skip-measure` for the parity portion; the documented peak model (`dense_peak_bytes`) is a design bound, not an RSS predictor (~85× optimistic at the small-N numpy cells; `DENSE_EVAL.md` §2.4).
