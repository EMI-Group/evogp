# `src/evogp/tree/` — EvoGP tree representation, ETL evaluation engine & pure-torch operators

## Intent
This is the **foundation layer** of EvoGP: the GP individual (`Tree`), the population (`Forest`), the multi-output variants (`CombinedTree` / `CombinedForest`), the random-generation blueprint (`GenerateDescriptor`), the pure-torch generation/splicing operators, and the ETL-backed evaluation engine.
Everything the rest of the library manipulates (fitness, selection, crossover, mutation, visualization) is expressed in terms of the tensor representation defined here.
This layer contains **no custom CUDA/HIP kernels and no compiled extension**: evaluation and fitness run through a per-structure ETL JIT engine (`etl_engine.py`) or, on a non-numpy backend, through the **dense** whole-population evaluator (`dense_engine.py`, one compiled graph per shape signature; the per-call strategy is `EVOGP_EVAL_MODE`), generation/mutation/crossover are vectorized plain torch (`generation.py`, `splicing.py`), and `import evogp.tree` works without any built extension.
The dense path is the **default route for device-backed (iree) evaluation** under the default `auto` policy — for populations with `pop_size >= 16` and, on rows-per-tree (`per_row=False`) calls, at most `EVOGP_DENSE_AUTO_MAX_ROWS` (2048) data rows; the default numpy backend always stays on the specialized path. Design documentation of record: `DENSE_EVAL.md` (this directory).
This package imports **nothing** from other `evogp` subpackages — it is the root of the package DAG (`algorithm/` and `problem/` are its consumers; `pipeline/` sits above both; no cycles).
`ENGINE_SPEC.md` (this directory) is the authoritative semantics spec: prefix encoding, the full op table with edge cases, evaluation order, SR fitness, the multi-output protocol, and the generation/splicing algorithms, distilled from the legacy CUDA sources at snapshot `8a487f19`.
Its Appendices keep the legacy op schemas and the old call-site map as explicitly marked historical reference.

## Representation (the schema every other module depends on)
An individual is three parallel tensors of length `max_tree_len`, batched as `[pop_size, max_tree_len]`, encoded as a **prefix (pre-order) expression**: node 0 is the root and children follow depth-first, left to right.
- `node_value` — `torch.float32` (`Forest.batch_node_value`).
- `node_type` — `torch.int16` (`Forest.batch_node_type`).
- `subtree_size` — `torch.int16` (`Forest.batch_subtree_size`); `subtree_size[i]` = number of nodes in the subtree rooted at node `i`.
Only indices `[0, subtree_size[0])` are meaningful: `subtree_size[0]` is the real tree length, and the rest of a row must never be read (the generator zeroes unused cells, but that is an implementation detail).
`batch_subtree_size[:, 0]` is used throughout the algorithm layer as "the size of tree i".
`Tree` holds the same three tensors unbatched (1-D); `Forest[i]` / `Forest[a:b]` return `Tree` / `Forest` **views** sharing storage, while `Tensor`/`ndarray` indexing (incl. LongTensor / bool mask) goes through PyTorch advanced indexing and returns **copies**.

Node encoding:
- `node_type` base values: `0 VAR`, `1 CONST`, `2 UFUNC`, `3 BFUNC`, `4 TFUNC` (`NType`); `NType.OUT_NODE = 1<<7` is OR-ed in for multi-output nodes (`TYPE_MASK = 0x7F` extracts the base).
- `node_value`: `VAR` → variable index (float-encoded int); `CONST` → the constant; function node → function id (`Func.*`, i.e. the index in `FUNCS_NAMES`).
- Multi-output out-node packing: `node_value` is the float32 bit-reinterpretation of `struct OutNodeValue { int16_t function; int16_t outIndex; }` (`outIndex = int32_bits >> 16`, `function = int32_bits & 0xFF`).
- Function table: id 0 `IF` (ternary); ids 1–13 binary (`+ - * / loose_div pow loose_pow max min < > <= >=`); ids 14–28 unary (`sin cos tan sinh cosh tanh log loose_log exp inv loose_inv neg abs sqrt loose_sqrt`); operands are consumed leftmost-child-first.
- Exact per-operator edge cases (`DIV`/`LOG`/`SQRT`/loose variants, comparisons returning ±1, `IF` branch mapping) are in `ENGINE_SPEC.md` §3.
- Multi-output semantics (`output_len > 1`): every out-node accumulates its own value into `out[outIndex]` and passes its right-most child up to the parent; tagged leaves behave like untagged ones; outputs that were never tagged are `0.0`.
- `output_len == 1` is the single-output protocol; a tree containing an OUT_NODE-tagged node is rejected at decode time with `ValueError` (the legacy kernel had undefined behavior there).

## Engine architecture (`etl_engine.py`)
Evaluation is a "true jit": `decode_population` walks a population **host-side** into frozen per-tree static programs (int-only, constant subtrees folded), then `evaluate` / `sr_fitness` specialize each program into a fresh ETL graph via `etl.build_cached` and run it, with the compiled executables cached per *(tree structure, input shape, backend, device, options)*.
- `decode_population(batch_node_value, batch_node_type, batch_subtree_size, input_len, output_len) -> Population` — pure host work (tensors read back with `.cpu()`); validates the structure and raises `ValueError` naming the row and node (replacing the kernel's UB); `TypeError` for non-tensor / non-2-D input.
- `evaluate(population, x, *, per_row, out_device=None, backend=None, iree_device_index=None)` — `per_row=True`: `(pop, input_len) → (pop, output_len)`; `per_row=False`: `(N, input_len) → (pop, N, output_len)`; returns a fresh, contiguous, `requires_grad=False` float32 tensor on `x`'s device unless `out_device` is given.
- `sr_fitness(population, inputs, labels, use_MSE=True, *, ...)` — `(pop,)` float32 POSITIVE loss `Σ_points Σ_outputs err / N` (err = diff² for MSE else |diff|; outputs summed but never divided by `output_len`; NaN/inf propagate unsanitized); the caller applies the higher-is-better negation.
- One module-level `@etl.defn _eval_step` — it must stay a module-level function (its `id()` is part of the cache key; a closure would permanently miss); statics are codec-safe int-scalars/sequences re-passed by value at `etl.run`.
- Cache: one shared `etl.CompileCache` (`etl_engine.CACHE`), default maxsize 4096 (`EVOGP_ETL_CACHE_SIZE`), in-memory only (nothing persists across processes); `cache_stats()` / `clear_cache()` inspect/reset; measured ~270–478 KiB per entry.
- Backends: default `"numpy"` (ETL reference interpreter, cpu, no GPU needed); IREE is opt-in via `EVOGP_ETL_BACKEND=iree` + `EVOGP_ETL_IREE_DEVICE=<visible gpu index>` + `EVOGP_ETL_IREE_OPT_LEVEL` (`O0`/`O1` only on cuda) — experimental, ~0.4–0.6 s build per structure + ~2.4–3.6 ms/run, impractical at population scale.
- Node semantics are **correctly rounded float32**: the software transcendentals (`sin`/`cos`/`tan`/`sinh`/`cosh`/`tanh`/`log`/`loose_log`/`exp`/`pow`/`loose_pow`) are emitted as `cast_f32(op(cast_f64(v)))` (ETL has no `sinh`/`cosh`: they are the `exp`/`-exp` composition in f64) and every node value is stored back as f32 — the best possible f32 answer, since the f32 kernels are not correctly rounded (numpy f32 `exp`/`sin`/`cos`/`tan` are 1 ulp off on 5–39% of inputs). Hardware-exact ops stay f32 (`+ - * /`, `sqrt`, `abs`, `neg`, `copysign`, `min`/`max`, comparisons/select, which must keep their bit-exact ±1). `sinh` keeps `x` (sign of zero included) below `|x| < 1e-4`, where the correctly rounded f32 result *is* `x` — this is what makes `loose_inv(sinh(-0.0)) = -1e9` come out right on both the folded and the emitted path.
- Measured numpy economics (with `ETL_DISABLE_LOCATIONS=1`, current f64-emission code): 30–43-node trees 9.9 ms cold build / 0.46 ms warm run (N=100) and 9.8 ms / 0.49 ms (N=1000); `build_cached` cache hit 0.45 ms; ~102 distinct builds/s, so an all-distinct pop=1000 costs ~10 s cold and ~5.4 s at 50% duplicates, against a 0.5 s all-cached floor. The f64 casts add a handful of ops per software transcendental but do not change the order of magnitude (earlier revision, 30-node/60-node trees: 8.5/21.4 ms build, 0.87/1.47 ms run).
- `ETL_DISABLE_LOCATIONS=1` speeds tracing up ~4× on this workload and is recommended for production runs; it is not part of the cache key.
- Device policy: the engine accepts population/input tensors from any torch device and returns results on the input device unless `out_device`; the `Tree`/`Forest` wrappers still pass everything through `check_tensor` (`.to("cuda")`), so the public API keeps its CUDA-bound behavior.

## Dense one-graph evaluator (`dense_engine.py`) — wired, the iree default route
`dense_engine.py` evaluates a WHOLE population with ONE compiled ETL graph fed with the population's node tensors as runtime data (no per-tree Python loop, no per-tree readback): host preprocessing (`prepare_dense`) encodes the `(L, P)` `opcode`/`func_id`/`const_value`/`var_index`/`child1..3` columns, the trace-time unrolled graph computes each node value with the same private emitters the specialized engine uses (`etl_engine._emit_unary`/`_emit_binary`/`_emit_ternary` — parity by construction), and `L = min(EVOGP_DENSE_MAX_TREE_LEN (32), max_tree_len)`.
It is wired into five call sites — `Tree.forward` / `Tree.SR_fitness` and `Forest.forward` / `Forest.batch_forward` / `Forest.SR_fitness` — each trying the dense entry point first and falling back to the specialized path ONLY on `DenseUnsupported` (silent; the specialized path owns the error contract for malformed trees, every other exception propagates). The public API contracts are unchanged.
- Policy (`should_use_dense` + `auto_rows_decline`): `EVOGP_EVAL_MODE` = `dense` / `specialized` / `auto` (default), resolved per call (an explicit `eval_mode=` argument wins; an unknown value raises `ValueError`); `auto` never selects dense on numpy (measured slower there) and selects it on iree only for `pop_size >= EVOGP_DENSE_AUTO_MIN_POP` (16) **and** — on `per_row=False` calls, where the data-row count is known — at most `EVOGP_DENSE_AUTO_MAX_ROWS` (2048) rows. The rows half of the rule is enforced inside `evaluate_dense` (the wired call sites pass `pop_size` only; `sr_fitness_dense` routes through it), `per_row=True` and an explicit `EVOGP_EVAL_MODE=dense` are never gated, and a decline surfaces as a normal `DenseUnsupported` fallback. So a single `Tree` (pop 1) and `CombinedForest` sub-forests follow the pop rule, and large-`N` fitness passes stay specialized.
- Measured economics (firm-up: `dense_bench_findings.md` §1–4, `dense_bench_results.json`; compact in `DENSE_EVAL.md` §6): dense is pop- and rows-linear while the specialized engine is pop-linear and rows-flat (1.24–1.94 ms/tree up to N=10000), so on iree dense wins the **cold** phase by orders of magnitude (ONE 13–17 s compile per shape signature against the 13–28 per-tree compiles of P=16–32) and the **warm** phase only modestly where both sides are direct — 1.49× / 1.30× at P=16 with 64 / 1024 rows, 1.18× *slower* at 10000 rows (same-process A/B), 3.09–3.16× at N=64 cross-process. The old grid's "≥10× warm on iree-cuda" ratios came from a per-tree model inflated ~3× by per-call overhead and are NOT supported (P=64/N=64 is ≈5.0–6.2×); the measured warm crossover runs from ≈3.4–6.8k rows (P=16) to ~11k (P=64), which is what the 2048-row default encodes. Provenance traps: a cell's `ratio_warm_spec_over_dense` is stale wherever the specialized value was later corrected, the P≥64 dense cells are earlier-grid cells (partly unit-cost fitted), and P=1000's specialized side is an anchored-law extrapolation.
- Supported subset: single-output populations (`output_len == 1`) with every tree within the 32-node trace cap; `EVOGP_DENSE_BUDGET_MB` (2048) bounds the chunked `(P_chunk, N_chunk)` execution; `EVOGP_DENSE_UPDATE_MODE` = `grow` (default) / `concat` / `scatter` (`scatter` is unsafe on iree unless `EVOGP_DENSE_ALLOW_UNSAFE_SCATTER=1`).
- Cache: `dense_engine.DENSE_CACHE` IS `etl_engine.CACHE`; the key is the shape signature `(L, P, N, input_len, per_row, update_mode, backend, device, options)` — ONE miss per population/compile against `pop_size` misses on the specialized path — and the module-level `_dense_step` must stay module-level (`id()` is part of the key).
- The result contracts mirror the specialized engine (fresh, contiguous, `requires_grad=False` float32; the dense SR loss is a torch reduction over the assembled prediction, while the specialized `sr_fitness` reduces its host rows in place with numpy — same formula, differing only in float32 reduction order by ~1e-7 relative on the fixtures).
Full detail (scheme, chunking model, knobs, tolerance classes, measured economics, ETL/iree constraints, future work) is in `DENSE_EVAL.md` — keep it there, not here.

## API Surface
`evogp.tree` exports: `GenerateDescriptor`, `Tree`, `Forest`, `CombinedForest`, `CombinedTree`, `MAX_STACK`, `randint`, `NType`.

### `tree.py` — `Tree(input_len, output_len, node_value, node_type, subtree_size)`
- `Tree.random_generate(descriptor)` delegates to `Forest.random_generate(pop_size=1)[0]`; `to_forest()` wraps a single tree as a `Forest`.
- `forward(x)` — 1-D `(input_len,)` → `(output_len,)`; 2-D `(batch, input_len)` → `(batch, output_len)`; evaluated through the ETL engine (dense attempt first, `DenseUnsupported` → specialized path).
- `SR_fitness(inputs, labels, use_MSE=True, execute_mode="auto")` → `(1,)` positive loss.
- `to_sympy_expr(symbol_names=None)` — sympy expr for `output_len == 1`, a list of exprs for `output_len > 1`; comparisons render as the engine's ±1 (`Piecewise((1, cond), (-1, True))`), loose ops follow the engine's zero-clamp conventions, and every leaf is sympified (a constant-only tree returns a sympy `Float`, never a raw numpy scalar).
- `to_infix()` (single-output; warns and returns one string for multi-output), `to_png(fname)`, `__repr__` (== sympy repr).
- `__python_forward` — name-mangled, debug-only, full-semantics pure-Python reference evaluator (single-output) used as the in-repo cross-check oracle; `__assert_valid` is likewise debug-only.

### `forest.py` — `Forest(input_len, output_len, batch_node_value, batch_node_type, batch_subtree_size)`
- Public attributes: `input_len`, `output_len`, `pop_size`, `max_tree_len`, `batch_node_value`, `batch_node_type`, `batch_subtree_size`; no `.device` and no `.trees`; the three tensors must be exactly `(pop_size, max_tree_len)`.
- `Forest.random_generate(pop_size, descriptor)` (static) → pure-torch vectorized generation on the descriptor tensors' device (cuda in practice).
- `zero_generate(pop_size, max_tree_len, input_len, output_len)` (static) → degenerate all-`CONST`-0 trees on cuda.
- `forward(x)` — `(pop_size, input_len)` → `(pop_size, output_len)` (asserts `x.shape[0] == pop_size`); `batch_forward(x)` — `(N, input_len)` → `(pop_size, N, output_len)`; both try the dense entry point first (`per_row=True` / `False`) and fall back to the specialized engine on `DenseUnsupported`.
- `mutate(replace_pos, new_sub_forest)` → new `Forest`; `crossover(left_indices, right_indices, left_pos, right_pos)` → new `Forest` of size `len(left_indices)`; both pure-torch splices with the legacy semantics (see `splicing.py`).
- `SR_fitness(inputs, labels, use_MSE=True, execute_mode="auto")` → fresh `(pop_size,)` float32 positive loss (writable; the pipeline mutates it in place); dense attempt first, specialized fallback.
- Dunders: `__getitem__` / `__setitem__` (branch rules below), `__iter__`/`__next__` (not reentrant: stores `iter_index` on the instance), `__len__`, `__add__`/`__radd__` (concat along dim 0; matching `input_len`/`output_len`), `__str__`/`__repr__` (renders every individual via sympy — slow), `__getstate__`/`__setstate__` (pickle via CPU numpy; restores to cuda).
- `__getitem__` (`forest.py:363-385`) branch rule is exactly `isinstance(index, int) or index.shape == ()`: an `int` / 0-dim `Tensor` / 0-dim numpy scalar returns a `Tree` **view** (all three tensors alias the population row; `Tree.__init__` stores references untouched), a `slice` returns a `Forest` **view**, and ANY other `Tensor`/`ndarray` (a 1-element 1-D index included) goes through advanced indexing and returns a **copied** `Forest` — a 1-element index therefore yields a `Forest` of pop 1, NOT a `Tree`; python lists raise `Exception`, non-integral tensor dtypes raise `IndexError`.
- A 0-dim **CUDA** tensor index is a view but NOT free: PyTorch's select path does `tensor.item<int64_t>()` internally (shipped `ATen/TensorIndexing.h:479-489`; verified at the Python level), so `forest[cuda_0dim_index]` is a blocking D2H readback — measured torch 2.6.0+cu124 / RTX A6000: 41.4 µs vs 7.8 µs for a Python int, and it stalls behind queued stream work (even a cross-GPU index is accepted, which itself proves the host readback). A 0-dim **CPU** index has identical view semantics with no sync; a 1-element 1-D CUDA index does not sync but is a copy and returns a `Forest`.
- `__setitem__` (`forest.py:387-407`) matches only `isinstance(index, int)` for the `Tree` path, so `forest[0-dim tensor] = tree` takes the `Forest` branch and raises `AssertionError` (`value should be Forest when index is slice...`); `forest[tensor_index] = forest_of_same_pop` writes in place through advanced-index assignment into the population tensors (the mutation operators rely on the copy-in/copy-out pattern `forest_to_mutate = forest[idx]` → mutate → `forest[idx] = ...`).

### `descriptor.py` — `GenerateDescriptor(max_tree_len, input_len, output_len, const_prob=0.5, out_prob=0.5, depth2leaf_probs=None, roulette_funcs=None, const_samples=None, using_funcs=None, max_layer_cnt=None, layer_leaf_prob=0.2, const_range=None, sample_cnt=None)`
- Validates its inputs, derives `depth2leaf_probs` from `using_funcs`/`max_layer_cnt` when omitted (`check_tree_length` asserts `max_tree_len` fits the worst-case complete tree), and materializes the cuda tensors the engine and the algorithm-layer operators share: `depth2leaf_probs [MAX_FULL_DEPTH]`, `roulette_funcs [Func.END]` cdf, `roulette_ufuncs`/`roulette_bfuncs`/`roulette_tfuncs` (used only by the mutation operators), `const_samples [sample_cnt]`.
- `update(**kwargs)` returns a new descriptor (see Known Issues for its two gotchas).

### `generation.py` — `generate_population(pop_size, descriptor, device=None)`
Returns `(batch_node_value float32, batch_node_type int16, batch_subtree_size int16)`.
Vectorized level-wise torch that reproduces the descriptor-driven decision structure distribution-equivalently; draws from torch's global RNG, so `torch.manual_seed` / `torch.cuda.manual_seed` make generation reproducible (not bit-identical to the legacy taus88 stream); a length overflow raises `RuntimeError`.

### `splicing.py` — `mutate(...)` / `crossover(...)`
Pure-torch scalar-free splices: `_splice` updates ancestor `subtree_size` cells with the closed form `(j < pos) & (j + size[j] > pos)`, copies the donor subtree verbatim and shifts the tail; an invalid position or overflow copies the row UNCHANGED (silent, matching the legacy op); index tensors may be int8/16/32/64; out-of-range `left_indices` → `ValueError`; `pop_size_new == 0` → `ValueError`.

### `combined_forest.py` / `combined_tree.py` — the `data_info`-driven multi-output model
`CombinedForest(forests, data_info)` with `data_info = {out_name: [input_name, ...]}`; `CombinedForest.random_generate(pop_size, data_info, descriptors)` (one descriptor per sub-forest, each with `output_len == 1`).
The input-dict contract is single-sourced in `combined_forest.normalize_inputs` (its docstring is the contract of record, mirrored by all three forward docstrings): every required name must hold a scalar/0-D number, a 1-D `(K,)` tensor or a 2-D `(K, 1)` tensor; all names must agree on `K`; values are never broadcast; extra `x` keys are ignored completely (so e.g. `CustomLoss` can pass its `existing_data` including `"target"`); wrong shapes/keys raise `ValueError` naming the offending key, its shape and the sub-forest (no bare asserts); Python lists and `ndim >= 1` numpy arrays are rejected.
`CombinedForest.forward(dict) → {out_name: (pop_size, out_len_sub)}` is single-point only (a `K > 1` value raises and points to `batch_forward`); `CombinedForest.batch_forward(dict) → {out_name: (pop_size, K, out_len_sub)}`.
`CombinedTree(trees, data_info)` exposes each sub-tree by output name (`best.A.to_sympy_expr()`); its `forward` routes on `K`: `{out_name: (out_len_sub,)}` for `K == 1` (one point shared by the whole population) and `{out_name: (K, out_len_sub)}` for `K > 1` (the one-individual forest's pop dim is stripped).
Neither defines `SR_fitness`/`to_sympy_expr`, and neither has a `share_input` attribute; the dict input protocol is the only accepted form.

### `execute_mode` mapping
`Tree.SR_fitness`, `Forest.SR_fitness` (and the problem layer) accept the five strings `"torch"`, `"hybrid parallel"`, `"data parallel"`, `"tree parallel"`, `"auto"`.
The legacy `kernel_type` dispatch is gone and **all five map to the same ETL engine path** — the string no longer changes behavior (it is kept for API compatibility).

## Constraints
- This layer must stay free of custom kernels and of any compiled-extension import; the legacy extension name must not reappear anywhere in this directory (the old ops are kept only as historical schemas in `ENGINE_SPEC.md` Appendix A).
- `MAX_STACK = 1024`, `MAX_FULL_DEPTH = 10`, `NType`, `Func` are defined only in `utils.py` and are the single source of truth; function ids are positional across `Func`, `FUNCS_NAMES`, `FUNCS_DISPLAY`, `SYMPY_MAP`, so adding/renaming an operator means touching all four.
- `max_tree_len <= MAX_STACK` (asserted in `GenerateDescriptor`); `check_tree_length` asserts `max_tree_len` fits the worst-case tree of `using_funcs`/`max_layer_cnt`; `using_funcs` entries must be exact `FUNCS_NAMES` strings.
- Import-cycle rule: module-level imports go one way only (`utils` → `descriptor` → `forest` → `combined_forest` → `combined_tree`); `tree.py` imports `forest` inside its methods and `combined_tree.py` imports `combined_forest` inside its methods.
- `tree.py` / `forest.py` use `from .utils import *`, so every public name in `utils.py` leaks into their namespaces — avoid adding casual public names.
- Fitness contract: the engine returns fresh writable tensors; the repo-wide convention is `(pop_size,)` float32 MAXIMIZED and mutated in place by the pipeline (NaN → -inf).
- Several helpers still hard-code the `"cuda"` device string (descriptor tensors, `zero_generate`, `check_tensor`, `randint`, `Forest.__setstate__`); `Forest`/`Tree` themselves are device-agnostic — `__init__` stores the three tensors by reference and `__getitem__`/`__setitem__`/`__add__`/`__next__` never call `check_tensor`/`.to()`/`.cpu()`/`.item()`, so a `Forest` lives on whatever device its tensors were built on (only the x/label/index arguments of `forward`/`batch_forward`/`SR_fitness`/`mutate`/`crossover` are forced to cuda by `check_tensor`); consistent with the rest of the repo, the same string also selects AMD GPUs under ROCm.
- `check_tensor` raises `TypeError` for non-tensors and relocates to `"cuda"` with `.detach().requires_grad_(False)` (kept deliberately: `../problem/brax_problem.py` relies on it); `randint` defaults to `device="cuda"`, `dtype=torch.int32`.
- Frozen, oracle-validated modules: `generation.py`, `splicing.py`, `etl_engine.py` — code changes need failing-test evidence and a separate commit; docstring/comment edits are free.
- `ENGINE_SPEC.md` sections 1–7 are the semantics of record; the documented deviations from the legacy kernels are listed in `etl_engine.py`'s module docstring ('Documented deviations from the old kernels': validation instead of UB, no fast-math, torch-RNG generation, composed `sinh`/`cosh` and `copysign`, constant trees never compiled, host-side numpy fitness reduction, int tolerance rules), while `ENGINE_SPEC.md` §12 'Validation notes' carries the validation evidence (the `__python_forward` reference, the legacy-extension oracle runs, the self-consistency checks) and §13 records the dense path as an implementation route only.
- The dense evaluator is an evaluation *route*, not a second semantics: it computes node values through the same private emitters as the specialized engine (`etl_engine._emit_*`) and must never grow its own op table. Any element-wise divergence from the specialized path is a bug — `src/evogp/tests/reference_eval.py` is the oracle, `DENSE_EVAL.md` §5 lists the known (non-dense-specific) iree-compile classes.
- `dense_engine.py` is frozen like `etl_engine.py` for code changes (failing-test evidence + a separate commit); docstring/comment edits are free.

## Design Decisions
- **Host decode + per-structure ETL graph** (instead of one generic interpreter graph): specialization makes re-evaluation of a structure a cache hit and keeps the graph free of dynamic dispatch; statics are re-passed by value so the cache key fully determines the executable.
- **numpy backend default, IREE opt-in**: the per-structure IREE compile (~0.4–0.6 s) dominates while numpy builds in ms and runs in ~1 ms; IREE stays first-class for callers who need CUDA execution and accept the compile economics.
- **Plain-torch operators** replace the kernels because they are portable and fast enough at these sizes; they keep the legacy splice semantics, including the silent no-op on invalid input.
- **Multi-output implemented in the engine** (oracle-verified for `output_len` 2/3) instead of raising; single-output trees with OUT_NODE tags raise `ValueError` instead of the legacy UB.
- Descriptors remain the shared source of randomness: `generation.py` reproduces the kernel's decision structure distribution-equivalently, while the algorithm-layer mutation operators keep consuming the descriptor's roulette cdfs.

## Known Issues / Notes for Agents
- The cache is per *(structure, shape)*: a fresh random population is a miss per individual (pop=1000 ≈ 5.5 s cold), constant trees never compile, duplicate structures hit; changing batch size or tree shape re-compiles — keep shapes stable in hot loops.
- **Indexing with a 0-dim CUDA tensor synchronizes**: `forest[cuda_0dim_index]` returns the same `Tree` view as an `int`, but PyTorch's select does an implicit `.item()` D2H readback (see API Surface), so a plan that keeps a `torch.argmax` output as a device 0-dim index pays a blocking sync per indexed access (`torch.argmax` itself is async). No Python-level control flow on device scalars is readback-free either: a `bool()`/`if` on a 0-dim CUDA bool (e.g. `if best_fitness > self.best_fitness:`) is one sync per evaluation.
- Per-call GPU cost structure (the optimization target): `evaluate` copies the three population tensors to host once at decode (`_as_numpy:934-948` called from `decode_population:1258-1260`), copies `x` per call (`sr_fitness` converts `inputs`/`labels` once: `_input_to_numpy:951-963`, `_as_numpy:1482`), then loops over `pop_size` trees issuing one `build_cached` lookup + one `etl.run` per non-constant tree (`_evaluate_rows:1357-1375`, `_run_tree:1298-1326`, `_executable:904-926`) with NO cross-tree batching or grouping (dedup happens only inside `etl.CompileCache`: identical programs hit but are still run one by one), and finally moves the assembled `(pop, N, out_len)` result back to the caller's device once (`evaluate:1423-1427`) -- but only for `evaluate`: `sr_fitness` calls the same host-rows core `_evaluate_rows` (`1329`) directly and reduces those rows with numpy IN PLACE (`np.subtract(..., out=rows)` etc., numpy rather than torch so the single-threaded ETL interpreter is not starved by torch's intra-op thread pool), so no prediction is uploaded and only the `(pop_size,)` loss reaches the input device. Under the IREE backend every tree run additionally ends with a fresh host readback (`_run_tree:1326`), so one pop=N fitness pass costs N device invocations + N synchronizations.
- Host→device input memo (`_run_tree`'s `prepared`, device backends only): the `etl.from_numpy(xin)` conversion is memoized per distinct input block, keyed by the caller — `per_row=False` uploads the shared `(N, input_len)` `x` ONCE per `evaluate` call, `per_row=True` keys by tree index and uploads each tree's own `(1, input_len)` row (tree `i` must see row `i`; the numpy backend consumes the host array directly and never uploads). `case_engine_per_row_iree_bug` in `dense_spike_check.py` pins both the numbers and the upload counts.
- ETL per-call overheads on that path: `build_cached` re-encodes the static program and re-derives its sha256 cache key on every `_executable` call (hit or miss), and `etl.run` re-validates the statics by value in O(#tokens) per call; the program is a nested tuple of ints, so this is per-element Python work. ETL has no supported multi-program/“super graph” execution (only a hand-written interpreter graph with runtime `gather`/`select`/`while_loop`, or a device-resident `external_call` batched kernel), and no ETL GPU backend executes without per-graph AOT compilation (numpy = CPU interpreter, iree/xla compile per graph, tvm is CPU-only) — see the `etl` repo CONTEXT for details. The runtime `etl.Tensor` also has no `__getitem__` (only graph-time `SymbolicTensor` slicing / the static-index `getitem` op, which would bake the index into the per-structure cache key), so a device-resident `(pop, input_len)` block cannot be split per tree at run time — the `per_row=True` path uploads one row per tree instead.
- `EVOGP_ETL_CACHE_SIZE` is read at import time (module-level `CACHE = CompileCache(...)` at `etl_engine.py:256`), while `EVOGP_ETL_BACKEND` / `EVOGP_ETL_IREE_DEVICE` / `EVOGP_ETL_IREE_OPT_LEVEL` are read per `evaluate` call (`_resolve_backend:870-901`); set the cache size before the first import.
- IREE is wired but experimental: not numerically verified for every shape, and O2/O3 are buggy on cuda — use O0/O1 only.
- **IREE device numerics (both paths, not dense-specific)**: iree-compile's own lowering of the verbatim StableHLO drops the C99 `pow(x, ±0) = 1` case when the exponent is a runtime value (`pow(0,0)` / `pow(NaN,0)` → NaN) and computes the emitted f32 `sqrt` 1 ulp low for some inputs (e.g. `0.47954902f`); both classes vanish on numpy, are bit-identical between the dense and the specialized path whenever the specialized path emits the op, and are reported (not chased) by the batteries — full detail in `DENSE_EVAL.md` §5.
- Sympy rendering is a display artifact with documented edge gaps: `LOOSE_POW(0,0)` renders `1` (engine `0`), `DIV`/`INV` at a literal zero render sympy `zoo` while the engine computes NaN, `LOG(0)` renders `zoo` vs −inf, `MAX`/`MIN` with a NaN literal raise, and a negative-zero divisor loses its sign in loose ops (sympy has no −0.0).
- `repr(Forest)` / `str(forest)` build a sympy expr per individual (CPU sync, slow); `__iter__` is not reentrant; `Forest[int]`/`[slice]` views vs `Tensor`-indexing copies — writes through copies are lost.
- `GenerateDescriptor.update(**kwargs)` returns a new descriptor but also mutates the receiver's captured params (kwargs are sticky) and re-draws `const_samples` from `const_range` when the original had `const_samples=None`.
- `randint` truncates toward zero after `torch.rand` (biased for negative `low`); `dict2prob` is torch-only now and validates names against `FUNCS_NAMES`.
- `Tree.to_infix` warns and returns a single string when `output_len != 1`; `__python_forward` / `__assert_valid` are debug-only and not on any production path.
- The engine is correctness-first: the numpy backend does one `etl.run` per tree per call — profile before assuming throughput.
- For raw timing use the unmerged benchmark harness `test/benchmark/bench_gp.py` (retrievable from the refs listed in `test/CONTEXT.md`; it times `problem.evaluate(forest)` with `--task evalfresh` cold/warm and JSON output). `src/evogp/tests/perf_probe.py` and `test/etl_jit_probe.py` model ETL build/run economics but never import `evogp`, so they cover no decode/input-copy/output-assembly cost. For the warm-path stage split of the specialized engine (decode, one `_run_tree`, the `_executable` lookup, whole-population `evaluate`, `sr_fitness`) on any box, CPU/numpy included, use `warm_path_probe.py` (this directory; findings in `warm_path_findings.md`).
- `etl_engine.py` (~1.5k lines) is intentionally a single module: decode, op emission, the multi-output protocol and the cache policy form one compilation unit and were frozen together after oracle validation — do not split without failing-test evidence.
- The dense-layer dev scripts are intentionally large single coherent tools and are NOT imported by the library: `dense_engine.py` ~1.5k lines, `dense_adversarial_check.py` ~1.9k, `dense_bench.py` ~1.9k, `dense_spike_check.py` ~1.3k, `dense_integration_check.py` ~0.8k. Don't split them for tidiness; a split needs a concrete maintenance reason (they are run as CLIs, so their internal helper layout is free).
- The `dense_spike_check.py` name is historical (it comes from the round in which the evaluator was written; the name is kept because `dense_adversarial_check.py` imports its `TreeSpec`/`pack_trees` builders): it is the **current** engine-level parity + measurement harness for the integrated evaluator, not dead prototype code.
- The `who=` label of `dense_adversarial_check.py`'s bit-diff lines names the path(s) KNOWN to deviate from the oracle (`dense_only` / `specialized_only` / `both`, or the bare `dense` / `specialized` when that comparison measured only one side); each entry also carries `got_path`, the path the printed value came from.
- With `EVOGP_EVAL_MODE=dense` a population outside the dense subset (multi-output `output_len > 1`, a tree longer than the 32-node trace cap, any structural doubt) silently falls back to the specialized engine, so a passing test does not by itself prove the dense path ran — count `DenseUnsupported` (or use `dense_integration_check.py` / `dense_adversarial_check.py`) when that distinction matters. Expected fallbacks in the full suite: 18 of 510 dense attempts (15 multi-output populations, 3 over-cap trees).
- On the numpy backend the default `auto` policy never selects dense (it lost at every measured size, 0.006–0.91× of the specialized warm throughput — slow *by design*: the interpreter pays per-op overhead on the ≈264·L graph ops). Forcing `EVOGP_EVAL_MODE=dense` slows the pytest suite (~140 s vs ~102 s) and changes the warning summary, because the specialized op emitters' numpy `RuntimeWarning`s (invalid value in power/sqrt/log) do not fire for populations the dense path handles.
- **Tolerance classes**: numpy dense is bit-exact against the specialized engine (0 non-bit-exact finite values, 192/192 adversarial checks); on iree the only dense-vs-specialized difference is the *engine's* fold-vs-emit ≈1 ulp (`max_rel` up to 3.3e-7, constant subtrees folded host-side with numpy f64 vs emitted with iree f64). The batteries require exact NaN/±inf masks and zero signs and `rtol=atol=1e-4` on finite values; bit-exactness is reported, not required.
- **iree sessions are fragile**: the etl/iree binding leaks device buffers per live executable and the recorded failure mode is a **teardown-only** crash, not a cap on the number of compiled executables — P=64 with 55 builds wrote a correct JSON and only then hit the nanobind teardown traceback, P=200 with 170 builds completed cleanly, while a single-family 338-row `dense_adversarial_check` session SIGSEGVs outright. Run iree checks staged — one family per fresh process (`dense_adversarial_check.py --only <family>`), `CUDA_VISIBLE_DEVICES` + `--gpu <visible index>`, and `etl_engine.clear_cache()`/`cache_stats()` between stages. `EVOGP_EVAL_MODE=auto` + iree is the only configuration that exercises the dense path by default.
- The 12 GB sandbox `MemoryMax` kills `dense_spike_check.py --backend numpy --full` when measurements are on (the `(L, P, N)` numpy graphs are host-memory heavy) — use `--skip-measure` for the parity portion, and note the documented peak model (`dense_peak_bytes`) is a design bound, not an RSS predictor (~85× optimistic at the small-N numpy cells; see `DENSE_EVAL.md` §2.4).

## Test Strategy
- No pytest suite inside this node; the validation stack is: (a) `ENGINE_SPEC.md` §12 self-consistency (compare against `Tree.__python_forward`, arity walks, splice identities); (b) the pytest suite under `../../tests/` — the primary regression gate for BOTH evaluation routes (independent plain-torch oracle, randomized/adversarial equivalence, operator and API-compat tests, convergence smoke, plus the in-repo `goldens/` fixtures cross-validated against the legacy kernels before deletion).
- Run everything with the project venv (`/mnt/local-ssd/bchuang/evox/.venv/bin/python`), from the repo root, with `PYTHONPATH=src` and `ETL_DISABLE_LOCATIONS=1`. numpy needs no GPU; the iree legs need a CUDA-visible device.
- Route coverage: the default `auto` policy keeps the suite on the specialized path (numpy), so exercise the dense path explicitly.
  - Suite: `PYTHONPATH=src ETL_DISABLE_LOCATIONS=1 <venv>/bin/python -m pytest src/evogp/tests -q` → `308 passed, 4 skipped` (~2 min, zero dense attempts); prefix `EVOGP_EVAL_MODE=dense` to force the dense route (~140 s, same result; instrumented 510 dense attempts, 492 evaluated densely, only the expected fallbacks), or use a cheap dense subset: `-k "forward or fitness"` (31 passed / 2 skipped), `--ignore=src/evogp/tests/test_equivalence.py` (119 passed / 4 skipped), `test_equivalence.py` alone (189 passed).
- Engine-level dense batteries (dev CLIs with `__main__` guards, imported by nothing, NOT pytest-collected):
  - `src/evogp/tree/dense_spike_check.py --backend numpy --skip-measure` → 37/37 (`--full --skip-measure` → 57/57; measurements are only safe outside the 12 GB sandbox) — dense vs specialized parity + the economics numbers.
  - `src/evogp/tree/dense_integration_check.py --stage numpy,fallback` → 118/118 (wiring + silent-`DenseUnsupported`-fallback smoke); `--stage iree` → 7/7 (`auto`+iree selects dense at P=32 with ONE compile per population).
  - `src/evogp/tree/dense_adversarial_check.py --backend numpy` → 192/192 checks, 0 non-bit-exact finite values, against the independent oracle `src/evogp/tests/reference_eval.py`.
- **iree legs are staged** (executable leak / teardown instability, see Known Issues): one family per fresh process — `CUDA_VISIBLE_DEVICES=<physical> ... dense_adversarial_check.py --backend iree --gpu <visible index> --iree-max-pop 2 --only <family>`; at that budget all 19 families exit 0 with 189/189 checks and the only non-bit-exact finite value is `deep_chain`'s single `emitted` 1-ulp element. A single all-rows `binary_var` session (338 rows) SIGSEGVs; larger budgets (up to `--iree-max-pop 64` completes) expose the shared-path iree-compile classes that stride-2 sampling hides — `--iree-max-pop 32` → 6/10 checks, `nan_ok=False` on the `POW(0,0)` row for BOTH paths — recorded, not chased (`DENSE_EVAL.md` §5).
- The recorded acceptance numbers for this HEAD (suite, batteries, dense-forced counts, both backends) are in `DENSE_EVAL.md` §8; re-run the commands above rather than re-deriving them from this file.
- Coverage gaps: IREE numeric parity per shape for the WHOLE pytest equivalence file (the adversarial battery's iree leg is run manually, one family per process), non-default selection/crossover operators, robotics problems, and the multi-output training pipeline (the combined `forward`/`batch_forward` contract itself is covered by `../tests/test_combined_forward.py`).
