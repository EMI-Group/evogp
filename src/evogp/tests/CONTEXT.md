# `src/evogp/tests/` — pytest suite for the evoxc-based (CUDA-free) EvoGP engine
## Intent
Automated verification of EvoGP's rewritten evaluation engine: GP trees are evaluated through evoxc's "true jit" (host-side decode of the population tensors into a static structure → `evoxc.build_cached` specialization → shared `evoxc.CompileCache`), and generation/mutation/crossover are plain-torch tensor ops.
These tests are the regression gate: an independent plain-torch reference evaluator plus randomized/adversarial equivalence tests, operator-invariant tests, public-API compatibility tests, a small convergence smoke, the numeric cross-check against the frozen outputs of the deleted CUDA kernels, and a counter-based regression layer for the dense evaluator / engine memos / policy + trace cap / pruning / runner hooks (the dense engine-round files `test_dense_sr_fitness.py`, `test_engine_memos.py`, `test_dense_policy.py`, `test_dense_prune.py`, `test_runner_hooks.py`) together with the numeric, public-route, knob and cache surface of the opt-in merged-graph "batch" route (`test_batch_engine.py`, `test_batch_route.py`, `test_batch_knobs.py`, `test_batch_chunking.py`, `test_batch_stages.py`, `test_batch_content_key.py`).
## Contents
- `reference_eval.py` — independent plain-torch oracle (slow, obviously-correct) implementing the original `_process_node` semantics; must NOT import the engine it verifies.
  Public entries (`__all__`): `decode_row(row_value, row_type, row_size, out_len=1, check=True)` (`:261`), `flatten(node)` (`:339`), `forward_tree(tree, x, out_len=1, multi_output=None)` (`:478`), `forward_from_rows(node_value, node_type, subtree_size, inputs, out_len=1)` (`:560`), `batch_forward_from_rows(node_value, node_type, subtree_size, x, out_len=1)` (`:582`), `sr_fitness_from_rows(...)` (`:601`), plus `arity_of`/`is_function_kind`.
  Cost per tree: one Python-level torch op per node over the `(N,)` data vectors (reverse-prefix stack walk, correctly-rounded float32 via float64 intermediates) — O(nodes) Python work and O(nodes) transient `N`-wide tensors per row, O(pop × nodes × N) per population; CPU-oriented and slow, use it for correctness spot checks, never for timing.
- `test_equivalence.py` — randomized + adversarial engine-vs-reference equivalence through the public `Forest`/`Tree` API; also owns the golden-fixture discovery, schema dispatch and every golden comparison (see "Golden fixtures" below).
  Multi-output (`output_len > 1`, out-nodes) is part of the engine's contract and its two equivalence tests RUN against the engine; the `multi_output_supported()` probe before them skips ONLY on a design-level refusal (`NotImplementedError`) and turns a wrong shape / wrong value / any other exception into a test FAILURE (a broad `except Exception` there would hide engine bugs behind a skip; the guard's two branches are pinned by `test_multi_output_guard_skips_only_design_level_refusals`).
- `test_operators.py` — generation validity/reproducibility + mutate/crossover splice invariants and silent-copy edge cases (int32 index tensors).
- `test_api_compat.py` — import surface (incl. the `CustomLoss` re-export), indexing/pickle/concat/sympy (incl. constant-only tree repr/sympy), execute_mode string compatibility.
- `test_combined_forward.py` — input-dict shape-contract regression for `CombinedForest.forward`/`batch_forward` and `CombinedTree.forward`: hand-checked single-point/batch values, batch==per-row equivalence, column-form equivalence and the exact rejection messages (12 tests).
- `test_mujoco_problem.py` — `MujocoProblem` lazy-import binding (module globals `jax`/`jnp`/`registry`/`MjxEnv` after `import_jax_based_package`) plus a construction smoke, both guarded by `pytest.importorskip("jax")`/`("mujoco_playground")` (`:34`, `:57`) and then by the third-party `mujoco-warp`/CuDNN boundary — on a venv without jax (this box) BOTH tests skip.
- `test_artifact_cache.py` — the opt-in on-disk artifact layer (`../tree/artifact_cache.py`) and its wiring into both routes: off by default (no key derived, no file touched), stable/process-independent keys, the dense and specialized round trips (save → `clear_cache()` → load, numerics bit-identical to a fresh build), a truncated artifact falling back to exactly one rebuild, foreign/signature-mismatched files rejected, a backend without `save` (`numpy`'s `_NoSave`) yielding `False` and no file, atomic temp-file writes, and `clear_cache()` (memory only) vs `clear_artifacts()` (disk only) semantics; `tmp_path` + `monkeypatch` only, numpy backend, no iree.
- `test_convergence_smoke.py` — tiny end-to-end symbolic-regression run; asserts best fitness improves strictly.
  The target (`x0**2 + x1**2 + 0.5`) has no exact representation in the descriptor's constant set, so *which* generation finds the best reachable 9-node composition is chaotic in the RNG stream (measured between generation ~13 and ~95 across operator-stream variants); `EVOGP_SMOKE_GENS` therefore defaults to 120 for a deterministic pass, and the assertion itself is unchanged/strict.
- `test_hot_path_contracts.py` — performance contracts of the operator/training-loop hot path (9 tests, ~8 s): `check_tensor`'s device/grad short-circuit (same object on cuda without grad; `.to("cuda")`+detach otherwise), valid prefix encodings on BOTH `generation.py` layouts (padded hot path and the `PADDED_SLOT_BUDGET=0` compact fallback, incl. a multi-output descriptor) plus layout selection and exact reproducibility, `splicing._cols` caching, `DefaultMutation` rewriting exactly the `torch.rand(pop) < rate` rows in place (the mask is replayed from the seeded CPU generator), a counter-based assertion that one select+crossover+mutate+elite-concat pass makes at most 4 python-level host round trips (`item`/`tolist`/`cpu`/`int`/`float`/`bool`), and `StandardPipeline.step`'s NaN→`-inf` mapping (with `+inf`/`-inf` untouched and the CPU copy handed to the algorithm).
- `test_dense_sr_fitness.py` — dense SR-loss contract + host-traffic regression (25 tests): `sr_fitness_dense` MSE/MAE vs the independent oracle and the specialized engine (`rtol=atol=1e-4` + exact NaN/±inf masks), the `(pop_size,)` float32 / device / `out_device` / freshness contract, unread-row-tail bit-invariance, exact-`0.0` perfect fit, `ValueError` shapes, and counter-based `(p_chunk,)`-scale host-crossing checks ported from the battery (`hotpath`/`parity` stages: inputs+labels converted once, no `(P,N)` readback, no labels-shaped torch tensor, chunked == single-chunk at `1e-6`). Its env-pinning fixture `_pin_route_and_backend` (`:140`) is MODULE-scoped on purpose (the module-scoped plan fixtures read the env first, and it pins eval-mode/backend/update-mode/prune) — do not downgrade it.
- `test_dense_host_memo.py` — the dense route's three front tables (`D.DENSE_PLAN_MEMO` / `DENSE_INPUT_MEMO`, both bounded by `D.DEFAULT_HOST_MEMO` = 16, and `DENSE_EXECUTABLE_MEMO` bounded by `D.DENSE_CACHE.maxsize`): `dense_cache_stats()` reports `<table>_hits`/`_misses`/`_entries`/`_maxsize` per registered table (`dense_memo.DenseMemo.stats`), a repeated call hits all three, `clear_cache()` resets them in lockstep and re-pays the decode, a `DenseUnsupported` decline converts nothing and leaves the counters untouched, and the loss output is fresh/writable/never shared with a memo.
  Its autouse `_clean_tables` fixture (`:118`) brackets every test with `E.clear_cache()`, and every call passes `backend=` explicitly.
- `test_engine_memos.py` — the two engine memos (12 tests): payload memo (`_iter_plan_chunks` prepares AND uploads each distinct payload once per call — a synthetic device-backend upload counter (`_FakeDeviceTensor`/`_SeamCounters`) proves prep == upload; the injected `staged` dict refills nothing on a second iteration) and the executable memo (`cache_stats()`'s 8 keys, one `build_cached` per DISTINCT program, `clear_cache()` resets both tables, memo vs memo-free vs cold-rebuild bit-identical; the `Forest.SR_fitness` differential pins `EVOGP_EVAL_MODE=specialized` + numpy itself so it cannot go vacuous under a forced-dense run).
- `test_dense_policy.py` — dense policy surface (50 tests): `resolve_eval_mode` (`dynamic` alias == `dense`, case/trim, per-call env, `ValueError`, the canonical 4-mode table with `batch` as a first-class mode reached by its own spelling only), alias equivalence in `should_use_dense`/`auto_rows_decline` (a forced `batch` is never the dense half of the policy), `_iter_plan_chunks(device_resident=True)` refusals (numpy backend; chunked plan refused pre-flight — no iree involved), trace-cap resolution (`L = min(64, row_len)`, explicit/env overrides, `<=0` ValueError) and the once-per-process over-cap `RuntimeWarning` (silent on numpy; exactly one warning over 3 device-backend declines; other declines don't consume the flag).
- `test_dense_prune.py` — `EVOGP_DENSE_PRUNE` candidate-chain pruning (44 tests): `resolve_prune` spellings/`ValueError`/precedence, exact `used_func_ids` derivation, prune-vs-full bit-exact A/B (value + loss, `per_row` both ways, P+N-chunked, edge fixtures — raw `int32` views), API-side proof the full-chain cfg was actually compiled (cache bracket `_api_call_compiles_the_full_chain`, `:324`), and cache-key/emitted-op granularity.
- `test_runner_hooks.py` — runner hooks (20 tests): numpy-leg pytest port of `../tree/runner_check.py` for `build_dense_runner`/`build_specialized_runner` — build/run contract, zero cache/traffic deltas across repeated `.run()`, numerics vs `evaluate` (`per_row` both ways, exact masks), the constant-tree `None` slot, build-time refusals (`DenseUnsupported`/`ValueError`/`TypeError`), neither builder reads nor writes `EVOGP_EVAL_MODE`; import guards are narrowed to `ImportError`, so a real engine import regression FAILS this file instead of skipping it. No in-suite iree leg (documented).
- `test_batch_engine.py` — numeric + engine-API contract of `evogp.tree.batch_engine` (one MERGED evoxc graph for the whole population through `evoxc.batch_functions`; 47 tests → 47 passed, ~8 s): `plan_batch` (host-only: decode/dedup/trace/merge), `build_batch` (lower/compile/load, memoized), `evaluate_batch`/`sr_fitness_batch` (the keyword names of `dense_engine.evaluate_dense`/`sr_fitness_dense` plus `out_device`/`band_size`/`bands`/`switch_ops`/`alignment`), the `value` variant (`(pop, out_len)` at `per_row=True` / `(pop, N, out_len)` at `per_row=False`) and the `loss` variant (in-graph-reduced positive `(pop,)` MSE/MAE).
  Also pinned here: parity vs the specialized engine AND vs the independent plain-torch oracle (`rtol=atol=1e-4` with exact NaN/±inf masks, `torch.equal` only where it is the MEASURED numpy behaviour, never as a contract), multi-output `output_len` 2/3, duplicate-row expansion (16 rows / 4 programs → 4 functions, each row against its own program's oracle row, a constant tree included; at `per_row=True` each function is keyed on that row's own `x` bytes, so only the constant row collapses across distinct `x` rows), the band spellings `bands=1/2/4/"none"/"flat"` + `band_size=1` + `switch_ops=True` all bit-identical to the default merge, the output-tenancy contract (float32/contiguous/`requires_grad`/`out_device`/freshness, inputs and population never mutated), `describe_plan` field-by-field on a known duplicate fixture (its `device` field is the `evoxc.core.Device` repr string, so tests match a substring), the all-constant population escalation pop 4 → 64 → 256 in ONE process (the flagged stale-executable regression: each call must answer the RIGHT `(pop,)` / `(pop, N, 1)` shape), and `BatchUnsupported` (⊂ `RuntimeError`: empty population, `pop_size < EVOGP_BATCH_MIN_POP`, unknown backend, an `x`/`per_row` shape doubt) vs `ValueError` (malformed knob, unknown variant).
  Its single iree leg (`requires_device_iree`, `skipif` on `find_spec("iree.compiler")`/`find_spec("iree.runtime")` AND `torch.cuda.is_available()`, batch+iree vs dense+iree at ≤ 6 merged functions) RUNS on this box: it has the IREE Python packages and a CUDA-visible MI300X (device kind `rocm`), and on a venv without them it skips instead of erroring.
- `test_batch_route.py` — public-route wiring of the five batch-capable call sites (`Forest.forward`, `Forest.batch_forward`, `Forest.SR_fitness`, `Tree.forward`, `Tree.SR_fitness`) (27 tests, ~8 s): a recording monkeypatch on `batch_engine.evaluate_batch`/`sr_fitness_batch` proves the batch branch was ATTEMPTED (exactly one attempt, the site's own `per_row`, the route's backend) and that the numbers returned equal both the directly-called engine output and the `specialized`-mode reference of the SAME public call site; a forced `BatchUnsupported` and a threshold decline (`EVOGP_BATCH_MIN_POP` above the population) both fall back to the specialized numbers bit-for-bit while still recording the attempt (a silent fallback cannot pass); `Tree` (pop 1) declines at the default threshold and takes the branch once the threshold is lowered; plus MAE, NaN/±inf placement, multi-output `output_len=2`, and a one-line trip-wire that `batch == specialized == auto` never changes the numbers.
  The WHOLE module is `pytestmark = skipif(not torch.cuda.is_available())` (`requires_cuda`): every public entry point relocates its inputs to the hard-coded `"cuda"` string through `check_tensor`, so there is no route to observe without a CUDA-visible device and a CPU-only box reports 27 skips with zero errors.
- `test_batch_knobs.py` — knob / band-selection / cache-and-stats surface of the batch route (97 tests, ~7 s): `resolve_band_size`/`resolve_bands`/`resolve_switch_ops`/`resolve_alignment`/`resolve_min_pop` (defaults, explicit-argument-wins, per-call env read, case/trim folding, `ValueError` naming the env var for every invalid spelling, `bool` rejected for `bands`), `resolve_band_count` (the `ceil(n / size)` model, clamping to `[1, n]`, an explicit out-of-range `K` → `ValueError` naming `EVOGP_BATCH_BANDS`, `switch_ops` forcing `K = 1`, `n_functions < 1` → `ValueError`), the knobs reaching a real `plan_batch` (argument vs env produce an identical `describe_plan`), both front tables' identity semantics, the exact 8 stat keys and their disjointness from `cache_stats()`/`dense_cache_stats()`/`artifact_cache_stats()`, and the decline vs `ValueError` split.
  `resolve_bands` semantics pinned here: unset/empty answer `None` ("the band-size model decides"), every flat spelling (`none` / `flat` / `0`, case- and whitespace-folded) and the integer `0` answer `1` (an explicit SINGLE band), an integer `K` answers itself.
  The four-distinct-program plan fixture cannot see that distinction (its function count makes the size model answer `K == 1` too), so `test_a_flat_spelling_selects_the_flat_merge_over_the_band_size_model` re-plans a `WIDE_POP_SIZE = 40`-distinct-program population with each flat spelling and `bands=1` and asserts `band_count == 1`, `band_strategy == "flat"`, `band_sizes == [40]` and an `emitted_ops` count identical to the `bands=1` plan, while the same population's default plan really bands (`band_count == 3`, `band_strategy == "explicit"`, `band_sizes == [14, 13, 13]`, 28 vs 9 emitted ops at the shipped band size 16); the cache is cleared between plans because `bands=1` and `bands="flat"` resolve to the same memo key.
  Front-table semantics pinned here: a repeat call on the SAME tensor objects increments `batch_plan_hits` and no `batch_exec_misses` (a plan hit returns before `build_batch`), a fresh identical copy is a plan miss + an exec hit, `evoxc_engine.clear_cache()` resets both tables and re-pays the plan work, and an all-constant population at pop 4 → 64 → 256 is 3 plan misses / 1 exec miss / 2 exec hits.
  Two non-obvious pinned facts: an explicit `bands=1` (and every flat spelling, which resolves to `1`) reports `band_strategy == "flat"` (only `K >= 2` reads `"explicit"`, because `_plan_host` passes `bands=None` for a resolved count `<= 1`), and `EVOGP_BATCH_CACHE_SIZE` is read at IMPORT time (the tables report their import-time `maxsize`).
  `test_the_batch_tables_are_disjoint_from_every_other_stats_surface` compares the content surface against the three NON-content surfaces only (`dense_cache_stats()` / `cache_stats()` / `artifact_cache_stats()`) and matches `"no batch_ key leaked into another surface"` on that same union: `batch_content_stats()`'s own keys ARE `batch_content_*`, and comparing a set with itself (or treating its own keys as a leak) can never pass.
- `test_batch_stages.py` — the stage timer surface (`9 tests`): `batch_stage_stats()` is exactly the 32 documented keys (`STAGE_NAMES` × `calls`/`total_ms`/`max_ms` + `batch_compile_wall_ms` + `batch_compile_jobs`), a real plan/build/run moves the counters of ITS stages in order, a reused executable adds no compile job, `batch_stage_reset()` zeroes all 32 while `evoxc_engine.clear_cache()` keeps the measurement, the stage keys stay disjoint from the five other stats surfaces, and `describe_plan` reports the chunk geometry (`chunk_count`/`chunk_sizes`/`chunk_strategy`) together with `BatchPlan.stage_ms` and `BatchExecutable.build_stage_ms`.
  `len(plan.chunks) == describe_plan(plan)["chunk_count"]` is asserted for EVERY plan, single-chunk ones included (a single-chunk plan carries exactly one `BatchChunk` mirroring `merged`/`graphs`/`specs`/`report`).
- `test_batch_chunking.py` — the chunked parallel compile (`29 tests`): chunked `value`/`loss` are bitwise equal to the single executable, the partition is contiguous/balanced/complete and a different worker count never reuses a body, `EVOGP_BATCH_COMPILE_WORKERS` parsing (default 4, argument-wins, `ValueError` naming the variable), every "chunking killer" (`1`/`0` workers, explicit bands, flat bands, `switch_ops`, below `MIN_CHUNK_FUNCTIONS`) falling back to the SINGLE-body path with identical numbers, a chunk compile failure propagating as the original exception, and the declines staying unchanged under chunking.
- `test_batch_bands.py` — the band POLICY of `../tree/batch_bands.py` (`37 tests`, the pytest home of the `../tree/batch_band_check.py` dev battery): the HAL binding tables and `BandPolicy.cap` (15 on rocm/cuda, 31 on cpu, uncapped on numpy/vulkan, the `n // 8` band floor), the four request spellings and their precedence (`switch_ops` → `auto` → an explicit `K` → the band-size model), the `auto` passthrough onto `describe_plan` (`cost_estimate`/`flat_cost_estimate`/`band_requested`/`band_requested_bands`/`band_clamped`/`band_note`/`band_policy`/`chunk_bands`/`chunk_band_strategies`), the clamp reached through `merge_with_spec` (one re-merge, both estimates preserved, the note naming the 16-binding cap + remedy), an explicit unloadable `K` raising `ValueError` naming `K <= 15` / `K <= 31` and the remedy (accepted on the uncapped numpy/vulkan policies), the size model clamped at pop 1000 (`ceil(1000/16) == 63` → 15), the unchanged no-knob default (`requested == "size"`), `resolve_band_count`'s `ValueError` for `"auto"`, and `EVOGP_BATCH_CHUNK_BANDS` (off forces the single body, on repeats the request per chunk with bitwise-identical values, and the setting is in BOTH plan memo keys — a flip re-plans and misses the content level).
- `test_batch_content_key.py` — the two-level plan key of `BATCH_PLAN_MEMO` + `BATCH_CONTENT_MEMO` (`8 tests`): identity level unchanged (a repeat call on the same tensors never computes a digest), a rebuilt-equal population HITS the content level (no re-plan, no re-compile, identical numbers), an in-place mutation and a genuinely different population MISS both levels, a forced digest collision is REJECTED (population B gets B's numbers) and counted, and `evoxc_engine.clear_cache()` empties the table and re-pays the plan; `batch_content_stats()` is exactly five `batch_content_*` counters, absent from the other four surfaces.
  Its oracle is the repo's container-based one (`Forest` built from the rows under test + `te.reference_sr_fitness`) — `test_equivalence` has no rows-level `sr_fitness_from_rows` re-export.
- `perf_probe.py` — standalone evoxc build/run economics probe (numpy vs iree); NOT a pytest module (`__main__`-guarded, never collected).
  It imports `evoxc`/numpy/torch directly and re-implements the engine's meta-programming pattern locally (module-level `@evoxc.defn _step(x, tree)` at `:313-314` + nested-tuple static trees composed at trace time) — it never imports `evogp`, so it measures the evoxc pattern, not `evogp.tree.evoxc_engine` itself.
  Measures per tree (wall-clock ms): cold `build_cached` miss, warm `evoxc.run` (device-only and host-readback), cache-hit `build_cached`, trace/lower/compile/load breakdown, the `EVOXC_DISABLE_LOCATIONS=1` delta (one subprocess per setting), bounded process/thread-pool build throughput, and extrapolated pop=200/1000 per-generation cost (`extrapolate` at `:939`, model `pop × warm_run + #distinct × cold_build`).
  evoxc API surface it drives: `evoxc.CompileCache` (`:153`), `evoxc.core.Device("cpu", 0)` (`:155`) / `evoxc.core.Device(HOST_GPU_KIND, i)` (`:484`), `evoxc.TensorSpec((N, 2), evoxc.float32)` (`:541`), `evoxc.build_cached(_step, spec, tree, cache=..., backend=..., device=..., **{"opt_level": "O1"})` (`:557`), `evoxc.run(exe, x, tree)` (`:585`), `evoxc.trace`/`evoxc.lower`/`evoxc.compile`/`evoxc.load` (`:654`-`:663`), `evoxc.from_numpy(...).to(device)` (`:560`).
  Two evoxc-specific adaptations the probe must keep: (a) the device KIND is torch-derived (`HOST_GPU_KIND = "rocm" if torch.version.hip else "cuda"`, `:162`) because evoxc's IREE adapter loads the HAL driver matching the kind — never hard-code `"cuda"`; (b) compile options are `{"opt_level": "O1"}` only (`IREE_OPTIONS`, `:169`) — the target backend is inferred from the device by `build_cached`, and the manual stage-decomposition section re-adds it itself via `_stage_options`/`_INFERRED_TARGET_BACKENDS` (`:504`-`:526`, mirroring `evoxc.pipeline._resolve_backend_device`: cpu→llvm-cpu, cuda→cuda, rocm/hip→rocm, vulkan→vulkan-spirv; numpy passes `{}`) because it bypasses `build_cached` and an `evoxc.compile` call without a target backend emits an llvm-cpu artifact that `evoxc.load` refuses on a rocm device.
  CLI (`parse_args` at `:1163`): `--quick` (effective default) / `--full` (presets QUICK/FULL at `:173`/`:183`), `--backends numpy|iree` (default both), `--n` (default 100,1000; `--full` appends 10000), `--trees`, `--seed` (default 20240), `--device-index`, `--skip-parallel`, `--skip-locations`, `--json-out PATH`, plus hidden child-mode args `--child-locations`/`--reps`; always writes the JSON report under `$TMPDIR/evogp_evoxc_perf_probe_<ts>.json` (`:1387`) and prints it between `JSON-BEGIN`/`JSON-END` (human tables from `print_tables` at `:983`).
  Semantics: NO `assert`/PASS-FAIL/threshold checks anywhere — failed sections are recorded in the JSON `errors` dict and the exit code stays 0 (unlike repo-root `test/etl_jit_probe.py`, which exits 1 on FAIL); the parity block (`:1300`-`:1319`) reports max|diff| vs numpy but never asserts it.
  Coverage boundary: the stage breakdown is fixed at N=1000 on `trees[0]`, the locations child at N=1000 and the parallel section at N=1000 on `trees[:5]`, so `--n` only affects sections 1-3 + tables; it never measures `evogp.tree.evoxc_engine`'s `decode_population` cost, the per-call input cast/host→device copy or the output assembly/transfer — pop=200/1000 generation costs are model extrapolations (`extrapolate`, `:939`), not measurements.
  The frozen `RESULTS` table in its docstring is historical A6000/CUDA-era data, kept for comparison; live tables print this host's device kind.
- `goldens/` — data only: 7 committed `.npz` golden fixtures (`01_random_single_out` … `07_deep_skew`) in the **engine schema** plus `README.md` documenting each case and the format. Loaded by `test_equivalence.py`; not a Python package.
## How to run
From the repository root, with `PYTHONPATH=src:/root/evoxc` (`evoxc` is importable ONLY through that path segment), the torch-carrying interpreter of the task's own venv (`/tmp/rocvenv/bin/python` on this box, torch 2.13.0+rocm7.1 — the path is per-task; `/tmp/iree311/bin/python` exists but has NO torch, and `python`/`python3` on PATH have none either), and `EVOXC_DISABLE_LOCATIONS=1` (speeds tracing up ~4× and is what the counts below were measured with).
The box has torch 2.13.0+rocm7.1 and one shared AMD MI300X (gfx942, ROCm 7.1, jax NOT installed) visible through torch's `"cuda"` device string, so `DEVICE` defaults to `"cuda"` in the equivalence/smoke tests while the evoxc device KIND that implies is `"rocm"`.
- Whole suite: `EVOXC_DISABLE_LOCATIONS=1 PYTHONPATH=src:/root/evoxc /tmp/rocvenv/bin/python -m pytest src/evogp/tests -q -p no:cacheprovider` → **1074 passed, 5 skipped, 8 warnings in ~119-130 s** (1079 collected).
- The 5 skips are stable and none of them is a multi-output skip: `test_api_compat.py`'s pygraphviz/`to_png` guard (`:381`, needs pygraphviz + the graphviz `dot` binary), the two "`forward` exposes no `execute_mode`" guards (`:466`, `:489`), and `test_mujoco_problem.py`'s two tests (`:34`, `:57`, both `pytest.importorskip` → `could not import 'jax'`).
- On a venv WITH jax installed only the mujoco construction smoke skips; both mujoco tests skipping here is that documented third-party environment boundary, not a port regression.
- Fast subset (skips the heavy differential file): append `--ignore=src/evogp/tests/test_equivalence.py` → **885 passed, 5 skipped in ~61 s**; `test_equivalence.py` is ~189 tests (~71 s) and dominates the full run.
- Forced-mode runs are done on SUBSETS (append `-k "forward or fitness"`, or name single files): do NOT run the FULL suite forced-dense, the dense numpy graphs OOM at the 64-node cap.
  The three batch modules are mode-INDEPENDENT — each test sets the mode it needs, so they pass under `EVOGP_EVAL_MODE=dense`/`=batch` as well (measured: 543 passed / 0 skipped across `test_batch_engine.py` + `test_batch_route.py` + `test_batch_knobs.py` + `test_route_policy.py` + `test_dense_policy.py` under `EVOGP_EVAL_MODE=batch`).
- Golden cross-checks only: append `-k golden` (6 tests) → **6 passed, 2 warnings in ~9 s** (both warnings are the documented RNG-dependent legacy-capture skips: `forest_random.npz` regeneration and the training trajectory).
- Single file: replace the path (`-x` stops at the first failure).
- Write-free run (worktree stays clean): add `-p no:cacheprovider` and `PYTHONDONTWRITEBYTECODE=1`.

## Constraints
- No test may depend on a compiled extension (there is none any more) and the reference path must not require a GPU.
- `reference_eval.py` stays independent: no imports from `evogp.tree.evoxc_engine` (it is the oracle the engine is checked against).
- `evoxc.from_numpy` is a zero-copy HOST wrap, so the real host→device upload is `Tensor.to(device)`: upload counters count at `.to(device)` (`test_engine_memos.py`'s `_FakeDeviceTensor`/`_SeamCounters`, `test_runner_hooks.py`'s `(D.evoxc.core.Tensor, "upload", "to")` seam), while `test_dense_sr_fitness.py`'s `_HostCrossings` patches `evoxc.core.Tensor.numpy` plus `evoxc.run`.
- The evoxc device KIND is torch-derived (`"rocm"` when `torch.version.hip`, else `"cuda"`; `evoxc_engine._gpu_device_kind()`): tests must follow it and never hard-code `"cuda"` for the evoxc kind (torch device strings such as `x.to("cuda")` are unaffected).
- Compile options are `{"opt_level": ...}` only and the target backend is inferred from the device (no `target_backends` key anywhere on the engine path; only `perf_probe.py`'s manual stage-decomposition section re-adds it).
- `evoxc.run` rejects raw torch tensors and device inputs must already be on the device, so tests hand it `from_numpy`/`.to(device)` operands only.
- No test references a `jit`/`JitFunction`/`BoundJit` layer — evoxc has none; the engine's own `_ExecutableMemo` is the only pre-binding layer.
- RNG semantics intentionally differ from the old kernels (torch-RNG sampling, distribution-equivalent, not bit-exact) — tests must not assert exact sampled values; the legacy fixtures are therefore used as frozen *inputs* to the engine, never as RNG transcripts.
- Semantics authority: `../tree/ENGINE_SPEC.md` (durable spec extracted from the kernels) and `../tree/CONTEXT.md`; for the legacy capture also `<repo-root>/test/goldens/README.md`.
- The suite contains NO timing/performance assertions; the engine-round files use counters/monkeypatch instead.
- Exactly ONE in-suite iree leg exists (`test_batch_engine.py`'s `requires_device_iree`, `skipif`-guarded on both IREE packages AND `torch.cuda.is_available()`), so on a venv without `iree.compiler`/`iree.runtime` it SKIPS instead of erroring; device-backend numbers and traffic otherwise stay in `perf_probe.py`'s separate iree leg and in the `tree/` dev batteries, and `backend="iree"` appears elsewhere only where a path just resolves the backend name (e.g. the trace-cap warning checks in `test_dense_policy.py`).

  `perf_probe.py` keeps zero `assert` statements (its cache expectations at `:568` and `:809`; failures go to the JSON `errors` dict, exit code 0).
## Numeric contract pinned by these tests (engine implementations must preserve)
- Engine-vs-oracle comparisons use global `RTOL = ATOL = 1e-4` (`test_equivalence.py:176-177`); NaN/±inf placement is asserted first (`torch.equal` on the masks + inf signs, `:388-402`) and only the finite entries are then compared (`assert_close_with_placement`, `:377-409`).
- Stricter-than-1e-4 engine checks: comparison ops must be bit-exact (`test_comparison_operators_are_exact`, `:1013-1035`, `exact=True` → rtol=atol=0 at `:407`), a perfect SR fit must be exactly 0.0 (`:1138-1143`), and the unread row tail must be bit-invariant via `assert_same_bits` (`torch.equal` after NaN/±inf canonicalization, `:604-613`, `:1198-1219`; tail junk tested as CONST/BFUNC/TFUNC types).
- `test_api_compat.py` cross-call tolerances: forward modes rtol=1e-4/atol=1e-5 (`:482`, `:502`), SR_fitness modes and SR_fitness-vs-MSE magnitude rtol=1e-3/atol=1e-4 (`:415`, `:427`, `:441-443`), batch_forward vs forward rtol=1e-4/atol=1e-5 (`:516`).

- Batch engine-round pins: batch vs specialized vs the plain-torch oracle at rtol=atol=1e-4 with exact NaN/±inf masks (both variants, `per_row` both ways, multi-output 2/3); the numpy backend's bit identity against the specialized numpy engine is stated as MEASURED behaviour (max|diff| 0.0), never as a contract; every band spelling (`bands=1/2/4/"none"/"flat"`, `band_size=1`, `switch_ops=True`) is bit-identical to the default flat merge; the batch loss is a positive `sum_N sum_out err / N` with no `/output_len`; and the public batch route must equal the `specialized` and `auto` results on the same rows (a fallback or a route switch may never move a number).

## Route pinning (where the suite pins WHICH engine a call takes)
`conftest.py:18-23` — session-scoped autouse `hermetic_backend` does `os.environ.setdefault("EVOGP_EVOXC_BACKEND", "numpy")` (`EVOGP_TESTS_ALLOW_DEVICE=1` disables it); it pins the BACKEND only, so `EVOGP_EVAL_MODE` stays live in every test.

The decoded route object is `dense_engine.Route(use_dense, backend, fallback_backend, reason="", engine="specialized")` (frozen dataclass); a policy test never builds one to read a decision — it reads `.use_dense` / `.backend` / `.fallback_backend` / `.engine` / `.use_batch` and matches `.reason` by SUBSTRING only (`AUTO_MIN_POP_ENV`, `AUTO_MAX_ROWS_ENV`, `AUTO_BUDGET_MB_ENV`, `"device"`), and the batch half is asserted through `.engine` / `.use_batch`, never through bare route equality.
The `auto` rows half is a MEMORY ENVELOPE, not a row ceiling: `auto_row_allowance(pop_size, tree_len)` answers `min(pin, floor(budget_bytes / (pop_size * tree_len * 4)))` with `pin = resolve_auto_max_rows()` (`DEFAULT_AUTO_MAX_ROWS = 0` = unpinned) and `budget = resolve_auto_budget_mb()` (`DEFAULT_AUTO_BUDGET_MB = 8192` MiB), so a rows-only caller with no shape can only be declined by an explicit pin, and `resolve_route`/`should_use_dense` take the optional `tree_len=` + `auto_budget_mb=` for the envelope half.
The wired call sites pass `pop_size` only, so `evaluate_dense`/`sr_fitness_dense` enforce the envelope themselves through `_decline_rows(x)` / `_population_shape(batch_subtree_size)` (`.shape` reads only, before any host conversion) and raise `DenseUnsupported` with the envelope reason.
`engine` is declared `compare=False` (an old-style three-field `Route(True, ...)` is promoted to `engine="dense"`, so equality checks against the three-field record keep their meaning) and `__post_init__` enforces the invariant `use_dense == (engine == "dense")`: `engine="dense"` with `use_dense=False`, `engine="batch"` with `use_dense=True`, and an unknown engine name each raise `ValueError`.
Those field contracts are the only place the suite builds a `Route` itself — `test_route_policy.py::test_route_engine_and_use_dense_stay_consistent` and `::test_batch_route_equality_ignores_the_engine_field`.
`test_route_policy.py` owns the batch branches of the policy: `resolve_route(..., eval_mode="batch")` has NO pop/rows gate (device box → `iree` + `numpy` fallback, CPU box → `numpy`/`numpy`, an explicit backend from the argument or `EVOGP_EVOXC_BACKEND` sets BOTH fields to that name), and `auto` NEVER selects batch over the eval-mode × backend × device × pop × rows matrix (`::test_auto_never_selects_the_batch_route`); no graph is built there (`backend="iree"` is only a name, `dense._DEVICE_AVAILABLE` is pinned), and `should_use_dense` is `False` for every batch route.
The valid `EVOGP_EVAL_MODE` spellings are enumerated by exactly one assertion — `test_dense_policy.py::test_eval_mode_tables_stay_canonical` `assert tuple(dense.EVAL_MODES) == ("dense", "specialized", "batch", "auto")` — together with `tuple(dense.ENGINES) == ("specialized", "dense", "batch")`, `dict(dense.EVAL_MODE_ALIASES) == {"dynamic": "dense"}` (no batch alias, and no alias value may point at it) and `aliases.values() <= EVAL_MODES`, all in that one test; a new mode string must be added to `dense.EVAL_MODES`/`dense.ENGINES` and to those asserts, while the `parametrize` matrices adapt themselves (`test_route_policy.py`'s `resolve_route` <-> `should_use_dense` consistency matrix lists `batch` among its modes explicitly).
`test_route_policy.py`'s `test_resolve_route_and_should_use_dense_agree` and `test_auto_never_selects_the_batch_route` require every `Route.backend` AND `Route.fallback_backend` to be a member of `evoxc_engine.SUPPORTED_BACKENDS` (`("numpy", "iree")`), so a route naming a backend the engine cannot run fails there — both fields of the batch route included.
Stats-key contracts that must not be disturbed: `cache_stats()` is exactly the 8 keys (`test_engine_memos.py:644-653`), `batch_cache_stats()` is exactly `batch_exec_{hits,misses,entries,maxsize}` + `batch_plan_{hits,misses,entries,maxsize}` and stays ABSENT from `cache_stats()`/`dense_cache_stats()`/`artifact_cache_stats()`, `artifact_cache_stats()` is disjoint from `cache_stats()` and `dense_cache_stats()` (`test_artifact_cache.py:508-520`), and the dense tables are `<table>_{hits,misses,entries,maxsize}` (`test_dense_host_memo.py:200-221`).
